KVS 운영·보안·비용

학습 목표

  • 디바이스(MASTER)·운영자(VIEWER)·프로비저닝 백엔드에 각각 필요한 KVS IAM 액션만 골라 최소 권한 정책을 쓸 수 있다.
  • 디바이스 등록부터 폐기까지 채널·스트림·IoT 리소스의 수명을 태그로 관리하고, 고아 채널을 정리할 수 있다.
  • CloudWatch 메트릭이 보여 주는 것과 보여 주지 못하는 것을 구분하고, SDK 로그로 빈자리를 채울 수 있다.
  • 활성 채널·시그널링 메시지·TURN 분으로 월 비용을 추정하고, TURN 비중을 줄이는 방법을 안다.
  • 조정 불가 할당량에 맞춰 설계하고, 시계 오차·자격증명 만료·1시간 연결 한도 같은 흔한 장애를 진단할 수 있다.

1. IAM 최소 권한: 주체별로 나눈다

KVS WebRTC에 접근하는 주체는 성격이 전혀 다른 셋이다. 현장의 디바이스, 브라우저 앞의 운영자, 채널을 만들고 지우는 백엔드다. 하나의 넓은 정책을 셋이 같이 쓰면, 디바이스 하나가 탈취됐을 때 공격자가 다른 농기계 채널에 viewer로 붙거나 채널을 지울 수 있다. 원칙은 단순하다. 주체마다 역할을 나누고, 역할마다 필요한 액션과 리소스만 허용한다.

정책을 쓰기 전에 알아둘 IAM 사실

AWS Service Authorization Reference(Kinesis Video Streams 항목) 기준으로 정리하면 다음과 같다.

항목내용
채널 리소스 ARNarn:${Partition}:kinesisvideo:${Region}:${Account}:channel/${ChannelName}/${CreationTime}
스트림 리소스 ARNarn:${Partition}:kinesisvideo:${Region}:${Account}:stream/${StreamName}/${CreationTime}
채널 대상 액션ConnectAsMaster, ConnectAsViewer, GetSignalingChannelEndpoint, GetIceServerConfig, DescribeSignalingChannel, UpdateSignalingChannel, DeleteSignalingChannel, UpdateMediaStorageConfiguration, DescribeMediaStorageConfiguration, JoinStorageSession, JoinStorageSessionAsViewer 등. 모두 aws:ResourceTag/${TagKey} 조건을 지원한다
리소스 없는 액션ListSignalingChannels, ListStreams는 리소스 타입이 없어 "Resource": "*"로만 허용할 수 있다
생성 시 태그CreateSignalingChannel API는 kinesisvideo:CreateSignalingChannel과 함께 kinesisvideo:TagResource를 요구한다(태그를 붙일 때). CreateStream은 TagStream을 함께 요구한다. 생성 액션은 aws:RequestTag, aws:TagKeys 조건을 지원한다

ARN 끝에 생성 시각이 붙는다는 점이 중요하다. 같은 이름으로 채널을 지웠다 다시 만들면 ARN이 바뀐다. 그래서 정책에는 channel/tractor-001/*처럼 이름 뒤를 와일드카드로 둔다. ARN 전체를 정책에 박아 두면 채널을 재생성하는 순간 권한이 끊긴다.

디바이스용 MASTER 정책

디바이스는 19장에서 본 AWS IoT Credential Provider로 임시 자격증명을 받는다. 이 역할에 붙이는 권한 정책은 다음과 같다. IAM 정책 변수 ${credentials-iot:ThingName}으로 "자기 이름의 채널에만" 붙게 만든다.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SignalingAsMasterOnOwnChannel",
      "Effect": "Allow",
      "Action": [
        "kinesisvideo:DescribeSignalingChannel",
        "kinesisvideo:DescribeMediaStorageConfiguration",
        "kinesisvideo:GetSignalingChannelEndpoint",
        "kinesisvideo:GetIceServerConfig",
        "kinesisvideo:ConnectAsMaster"
      ],
      "Resource": "arn:aws:kinesisvideo:ap-northeast-2:123456789012:channel/${credentials-iot:ThingName}/*"
    },
    {
      "Sid": "StorageModeDevicesOnly",
      "Effect": "Allow",
      "Action": "kinesisvideo:JoinStorageSession",
      "Resource": "arn:aws:kinesisvideo:ap-northeast-2:123456789012:channel/${credentials-iot:ThingName}/*"
    },
    {
      "Sid": "ProducerSdkRecordingOnOwnStream",
      "Effect": "Allow",
      "Action": [
        "kinesisvideo:DescribeStream",
        "kinesisvideo:GetDataEndpoint",
        "kinesisvideo:PutMedia"
      ],
      "Resource": "arn:aws:kinesisvideo:ap-northeast-2:123456789012:stream/${credentials-iot:ThingName}-rec/*"
    }
  ]
}

이 정책에서 의도적으로 빼거나 넣은 것들이 있다.

  • CreateSignalingChannel을 뺐다. KVS C SDK README의 IoT 예시 정책에는 CreateSignalingChannel이 들어 있다. 샘플이 채널이 없으면 직접 만들기 때문이다. 운영에서는 채널을 백엔드가 미리 만들고 디바이스는 쓰기만 하게 하는 편이 낫다. 디바이스가 채널을 만들 수 있으면 인증서 하나로 채널 수 할당량을 소진하는 공격도 가능해진다.
  • DescribeMediaStorageConfiguration을 넣었다. C SDK 샘플의 기본 캐시 정책(SIGNALING_API_CALL_CACHE_TYPE_FILE_EXCEPT_DESCRIBE_MEDIA)은 연결할 때마다 이 API로 저장 모드 여부를 확인한다.
  • JoinStorageSession은 저장 모드(21장)를 쓰는 디바이스에만, PutMedia 묶음은 Producer SDK로 병행 녹화하는 디바이스에만 둔다. 쓰지 않는 문은 닫는다.

${credentials-iot:ThingName}에는 함정이 두 가지 있다. 이 변수는 IAM 정책에서만 동작하고 IoT Core 정책에서는 쓸 수 없다. 그리고 디바이스가 자격증명을 요청할 때 x-amzn-iot-thingname 헤더를 보내야만 값이 채워진다. 헤더의 thing 이름이 인증서에 붙은 thing과 다르면 403이 난다. 채널 이름을 thing 이름과 같게 하라는 권장("KVS recommendation is to use iot thing name as channel name")과 채널용 정책 예시는 awslabs C SDK README에 있고, KVS 개발자 가이드의 IoT 예시는 스트림(stream/${credentials-iot:ThingName}/*) 기준이다.

역할 쪽 설정도 짝을 맞춘다. 먼저 device-master 역할의 신뢰 정책이다. IoT credentials provider만 이 역할을 맡을 수 있게 한다.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Service": "credentials.iot.amazonaws.com" },
    "Action": "sts:AssumeRole"
  }]
}

디바이스 인증서에 붙이는 IoT Core 정책에는 role alias로 자격증명을 받을 권한만 준다.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "iot:AssumeRoleWithCertificate",
    "Resource": "arn:aws:iot:ap-northeast-2:123456789012:rolealias/kvs-device-master"
  }]
}

role alias의 credentialDurationSeconds는 900~43,200초(기본 3,600초)이고 역할의 최대 세션 시간 이하여야 한다. 길게 잡으면 탈취된 자격증명의 수명도 길어진다. 인증서·thing·정책 연결 방식은 AWS IoT Core 완전 정복 포스트에서 다뤘다.

운영자용 VIEWER 정책

운영자 브라우저에는 20장에서 설계한 대로 백엔드가 STS로 짧은 임시 자격증명을 발급한다. 역할 정책은 넓게(태그 조건), 발급 시 세션 정책으로 좁게(채널 하나) 두 겹으로 거른다. 유효 권한은 두 정책의 교집합이다. 아래 operator-viewer 역할 정책은 env=prod 태그가 붙은 채널에 대해서만 viewer 액션을 허용한다.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "ViewerOnProdChannels",
    "Effect": "Allow",
    "Action": [
      "kinesisvideo:DescribeSignalingChannel",
      "kinesisvideo:GetSignalingChannelEndpoint",
      "kinesisvideo:GetIceServerConfig",
      "kinesisvideo:ConnectAsViewer",
      "kinesisvideo:JoinStorageSessionAsViewer"
    ],
    "Resource": "arn:aws:kinesisvideo:ap-northeast-2:123456789012:channel/*",
    "Condition": { "StringEquals": { "aws:ResourceTag/env": "prod" } }
  }]
}

// 백엔드: 운영자가 권한을 가진 디바이스인지 확인한 뒤, 그 채널 하나로 좁혀 발급
import { STSClient, AssumeRoleCommand } from '@aws-sdk/client-sts';

const region = 'ap-northeast-2';
const accountId = process.env.AWS_ACCOUNT_ID;
const sts = new STSClient({ region });

export async function issueViewerCredentials(operatorId, channelName) {
  const sessionPolicy = {
    Version: '2012-10-17',
    Statement: [{
      Effect: 'Allow',
      Action: [
        'kinesisvideo:DescribeSignalingChannel',
        'kinesisvideo:GetSignalingChannelEndpoint',
        'kinesisvideo:GetIceServerConfig',
        'kinesisvideo:ConnectAsViewer',
      ],
      Resource: `arn:aws:kinesisvideo:${region}:${accountId}:channel/${channelName}/*`,
    }],
  };
  const { Credentials } = await sts.send(new AssumeRoleCommand({
    RoleArn: process.env.OPERATOR_VIEWER_ROLE_ARN,
    RoleSessionName: `op-${operatorId}`.slice(0, 64),   // CloudTrail에서 누가 붙었는지 추적
    Policy: JSON.stringify(sessionPolicy),
    DurationSeconds: 900,                               // AssumeRole 최소값
  }));
  return Credentials;
}

녹화 재생(HLS URL 발급, GetClip)은 브라우저에 권한을 주지 말고 백엔드가 대신 호출해 URL만 넘긴다(21장 1절). 스트림 권한까지 브라우저로 내보낼 이유가 없다.

프로비저닝 백엔드 정책

채널을 만들고 지우는 백엔드는 가장 강한 권한을 가지므로 태그 조건으로 자기 소유 리소스에만 손대게 한다.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "CreateOnlyWithManagedTags",
      "Effect": "Allow",
      "Action": ["kinesisvideo:CreateSignalingChannel", "kinesisvideo:TagResource"],
      "Resource": "arn:aws:kinesisvideo:ap-northeast-2:123456789012:channel/*",
      "Condition": {
        "StringEquals": { "aws:RequestTag/managed-by": "device-provisioner" },
        "ForAllValues:StringEquals": { "aws:TagKeys": ["managed-by", "fleet", "device-id", "env"] }
      }
    },
    {
      "Sid": "ManageOwnChannels",
      "Effect": "Allow",
      "Action": [
        "kinesisvideo:DescribeSignalingChannel",
        "kinesisvideo:UpdateSignalingChannel",
        "kinesisvideo:DeleteSignalingChannel",
        "kinesisvideo:ListTagsForResource",
        "kinesisvideo:UpdateMediaStorageConfiguration",
        "kinesisvideo:DescribeMediaStorageConfiguration"
      ],
      "Resource": "arn:aws:kinesisvideo:ap-northeast-2:123456789012:channel/*",
      "Condition": { "StringEquals": { "aws:ResourceTag/managed-by": "device-provisioner" } }
    },
    {
      "Sid": "ListHasNoResourceType",
      "Effect": "Allow",
      "Action": "kinesisvideo:ListSignalingChannels",
      "Resource": "*"
    },
    {
      "Sid": "RecordingStreams",
      "Effect": "Allow",
      "Action": [
        "kinesisvideo:CreateStream",
        "kinesisvideo:TagStream",
        "kinesisvideo:DescribeStream",
        "kinesisvideo:UpdateDataRetention",
        "kinesisvideo:DeleteStream"
      ],
      "Resource": "arn:aws:kinesisvideo:ap-northeast-2:123456789012:stream/*-rec/*"
    }
  ]
}
  • 첫 문장은 managed-by=device-provisioner 태그 없이는 채널을 못 만들게 하고, 허용된 태그 키 외에는 붙이지 못하게 한다.
  • UntagResource는 일부러 뺐다. 백엔드 버그로 managed-by 태그가 지워지면 이 정책의 둘째 문장이 그 채널을 관리하지 못하게 되기 때문이다. 태그 수정이 필요하면 별도 운영 역할로 한다.
  • 이 백엔드는 ECS 태스크 역할이나 Lambda 실행 역할로 돌려서 장기 액세스 키를 아예 만들지 않는다.

2. 채널 수명관리: 만들고, 표시하고, 지운다

채널은 디바이스와 수명을 같이해야 한다. 디바이스 등록 시점에 만들고, 폐기 시점에 지운다. 20장에서 등록 쪽을 다뤘으니 여기서는 태그 설계와 폐기·정리를 다룬다.

왜 지워야 하나

과금만 보면 채널을 지울 이유가 약해 보인다. 활성 채널 요금은 그 달에 디바이스나 앱이 한 번이라도 연결한 채널에만 붙기 때문이다. 연결이 없는 채널은 그 달 요금이 0이다. 그래도 지워야 하는 이유는 따로 있다.

  • 할당량: 계정·리전당 채널 수 한도가 있다. 문서끼리 숫자가 다르다(WebRTC 개발자 가이드는 us-east-1·us-west-2 10,000 / 그 외 5,000, General Reference는 20,000 / 10,000). 저장 설정 채널은 기본 100개다. 고아 채널이 쌓이면 신규 등록이 막힌다.
  • 보안: 폐기한 디바이스의 인증서가 살아 있고 채널도 남아 있으면, 그 인증서를 손에 넣은 누군가가 master로 붙어 "폐기된 트랙터" 행세를 할 수 있다. 채널 삭제와 인증서 폐기는 같이 간다.
  • 저장 비용: 채널에 연결된 스트림은 별개 리소스다. 채널을 지워도 스트림과 보존 중인 데이터는 남아 저장 요금이 계속 나간다.
  • 이름 재사용: 같은 thing 이름으로 디바이스를 다시 등록할 때 이전 채널이 남아 있으면 메시지 TTL·저장 설정 같은 이전 상태를 물려받는다.

태그 설계

채널에는 태그를 최대 50개 붙일 수 있다. 이 스터디의 예시는 네 개만 쓴다.

키예시 값쓰임
managed-bydevice-provisionerIAM 조건(1절), 정리 작업의 대상 판별
device-idtractor-001디바이스 레지스트리와 대조

fleet을 농장별 비용 집계에 쓰려면 Billing 콘솔에서 비용 배분 태그로 활성화해야 한다. KVS 채널 요금이 실제로 태그별로 나뉘어 잡히는지는 첫 달 청구 내역으로 확인한다.

폐기 순서

디바이스 한 대를 폐기할 때의 순서는 다음과 같다. 순서가 중요하다.

  1. IoT 인증서를 비활성화·폐기한다(aws iot update-certificate --new-status REVOKED). 새 자격증명 발급을 먼저 막아야 이후 단계 중에 디바이스가 다시 붙지 않는다.
  2. 저장 모드를 끈다(UpdateMediaStorageConfiguration, Status=DISABLED). DeleteSignalingChannel API의 오류 목록에는 저장 매핑과 관련된 ResourceInUseException이 있으므로, 매핑을 먼저 풀고 지우는 편이 안전하다.
  3. 채널을 삭제한다. DeleteSignalingChannel은 비동기 작업이라 잠시 DELETING 상태를 거친다. CurrentVersion을 넘기면 그 사이 누가 채널을 바꿨을 때 VersionMismatchException으로 막을 수 있다.
  4. 녹화 스트림을 처리한다. 사고 조사용으로 남겨야 할 구간이 있으면 GetClip으로 내려받아 S3 등에 옮긴 뒤 DeleteStream을 호출한다.
  5. IoT thing·정책 연결을 정리하고 디바이스 레지스트리 상태를 retired로 바꾼다.

고아 채널 정리 작업

레지스트리와 실제 채널은 언젠가 어긋난다. 등록 중 실패, 수동 테스트, 레지스트리 버그 때문이다. 주기적으로 대조해 정리하는 작업을 둔다.

// Node.js (AWS SDK v3) — 레지스트리에 없는 채널을 찾아 정리. 기본은 dry-run
import {
  KinesisVideoClient, ListSignalingChannelsCommand, ListTagsForResourceCommand,
  DescribeMediaStorageConfigurationCommand, UpdateMediaStorageConfigurationCommand,
  DeleteSignalingChannelCommand,
} from '@aws-sdk/client-kinesis-video';

const kv = new KinesisVideoClient({ region: 'ap-northeast-2' });
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

export async function sweepOrphanChannels(isRegisteredDevice, { dryRun = true } = {}) {
  let NextToken;
  do {
    const page = await kv.send(new ListSignalingChannelsCommand({
      ChannelNameCondition: { ComparisonOperator: 'BEGINS_WITH', ComparisonValue: 'tractor-' },
      MaxResults: 500,
      NextToken,
    }));
    for (const ch of page.ChannelInfoList ?? []) {
      const { Tags = {} } = await kv.send(new ListTagsForResourceCommand({ ResourceARN: ch.ChannelARN }));
      if (Tags['managed-by'] !== 'device-provisioner') continue;   // 다른 시스템의 채널은 건드리지 않는다
      if (await isRegisteredDevice(Tags['device-id'])) continue;
      console.log('orphan channel', ch.ChannelName, dryRun ? '(dry-run)' : '→ delete');
      if (!dryRun) await retireChannel(ch.ChannelARN, ch.Version);
      await sleep(250);   // Delete/Tag/ListTags 계열: 계정 50 TPS, 리소스당 5 TPS
    }
    NextToken = page.NextToken;
  } while (NextToken);
}

export async function retireChannel(channelArn, version) {
  const { MediaStorageConfiguration: msc } = await kv.send(
    new DescribeMediaStorageConfigurationCommand({ ChannelARN: channelArn }));
  if (msc?.Status === 'ENABLED') {
    await kv.send(new UpdateMediaStorageConfigurationCommand({
      ChannelARN: channelArn,
      MediaStorageConfiguration: { Status: 'DISABLED' },
    }));
  }
  await kv.send(new DeleteSignalingChannelCommand({ ChannelARN: channelArn, CurrentVersion: version }));
}

삭제는 되돌릴 수 없으므로 dry-run 결과를 사람이 확인한 뒤에만 실제 삭제를 돌린다. 반대 방향(레지스트리에는 있는데 채널이 없는 디바이스)도 같은 작업에서 찾아 재생성 큐에 넣으면 대조가 완성된다.

CloudWatch가 보여 주지 못하는 것

기본 모드에서 미디어는 피어끼리 직접 흐른다. AWS는 그 경로를 보지 못하므로 RTT·지터·손실·프레임 드롭 같은 품질 지표는 CloudWatch에 없다. 품질은 양 끝에서 모아야 한다.

  • 브라우저: getStats()로 candidate-pair·inbound-rtp 지표를 주기적으로 모아 백엔드로 보낸다. 무엇을 볼지는 15장에 정리했다.
  • 디바이스(C SDK): rtcPeerConnectionGetMetrics()로 같은 종류의 통계를 얻는다. 샘플 코드는 이 API로 선택된 로컬·원격 후보 타입(candidateType)을 로그로 찍는다. signalingClientGetMetrics()는 시그널링 단계별 소요 시간을 준다.
  • 세션 종료 시 "선택된 후보 쌍이 relay였는가"를 한 줄 이벤트로 남겨 두면, 5절의 TURN 비율을 디바이스·통신사·농장별로 쪼개 볼 수 있다.

수집한 지표를 메트릭·로그·트레이스로 다루는 방법은 관측성 스터디를 참고한다.

농기계 200대 추정 (서울 리전, 2026-09-30 가격)

가정은 다음과 같다. 숫자보다 가정이 바뀌면 결과가 어떻게 바뀌는지를 보는 것이 목적이다.

  • 디바이스 200대, 모두 매달 연결한다.
  • 운영자가 디바이스마다 하루 3번, 한 번에 20분 실시간으로 본다. 한 달 30일이면 디바이스당 90세션, 전체 18,000세션이다.
  • 세션당 시그널링 메시지는 offer 1 + answer 1 + ICE 후보 양쪽 합계 약 18건으로 20건이라고 둔다. 송·수신 집계 방식을 모르니 보수적으로 두 배(40건)로 잡는다.
  • 세션의 20%가 TURN을 쓰고, relay 세션은 보수적으로 양쪽 모두 allocation을 잡는다고 본다(allocation 2개 × 20분).
단계계산결과
① 활성 채널200 × $0.04$8.00
② 메시지 수18,000세션 × 40건720,000건
③ 메시지 요금0.72 × $2.75$1.98
④ relay 세션18,000 × 20%3,600세션
⑤ TURN 분3,600 × 20분 × allocation 2144,000분
⑥ TURN 요금144 × $0.15$21.60
월 합계(데이터 전송 제외)① + ③ + ⑥$31.58

같은 가정을 us-east-1 요금으로 계산하면 $6.00 + $1.62 + $17.28 = $24.90이다.

이 표에서 읽어야 할 것은 두 가지다.

  1. TURN이 지배한다. relay 비율이 20%만 돼도 TURN이 전체의 70% 가까이를 차지한다. relay 비율이 60%로 오르면(LTE CGNAT 환경에서 흔히 생길 수 있는 상황) TURN 분은 432,000분, 요금은 $64.80이 되고 합계는 $74.78로 두 배 이상이 된다.
  2. TURN 분 요금보다 데이터 전송량이 더 클 수 있다. relay된 데이터가 인터넷으로 나가면 표준 데이터 전송 요금이 별도로 붙는다(KVS 가격 페이지의 WebRTC 예시에 명시). 2 Mbps 영상 20분은 약 300 MB다(2 Mbps × 1,200초 = 2,400 Mb). 3,600세션이면 약 1,080 GB, 1 TB가 넘는다. GB당 요율이 센트 단위만 돼도 TB 단위 송신은 위 표의 TURN 분 요금(수십 달러)을 쉽게 넘는다. 요율은 리전별 데이터 전송 요금표에서 확인한다(서울 인터넷 송신 첫 10 TB $0.126/GB로 계산한 예는 25장 6절).

저장 모드를 켠 채널은 여기에 분당 녹화·viewer 요금이 더해진다. 상시 녹화라면 이 항목이 전체 비용을 압도할 수 있다는 계산은 21장 6절에서 했다.

5. TURN 비용 최적화: 직접 P2P 비율 높이기

TURN은 비용만의 문제가 아니다. TURN 세션은 대역폭이 5 Mbps로 고정(조정 불가)이고 채널당 동시 allocation은 50개다. relay를 거치면 지연도 늘어난다. 직접 P2P 비율을 높이는 것은 비용·품질·한도 모두에 이득이다.

먼저 잰다

최적화는 측정에서 시작한다.

  • 채널별 TURNConnectedMinutes로 "어느 디바이스가 relay를 많이 쓰는가"를 본다.
  • 세션마다 선택된 후보 쌍의 타입(브라우저 getStats()의 local/remote candidate candidateType, C SDK rtcPeerConnectionGetMetrics())을 기록해 relay 비율을 통신사·농장·운영자 네트워크별로 나눈다. relay가 "디바이스 쪽 NAT" 때문인지 "운영자 사무실 방화벽" 때문인지에 따라 처방이 다르다.

줄이는 방법

방법효과주의
iceTransportPolicy를 all(기본)로 둔다relay 강제를 피한다C SDK KVS_ICE_TRANSPORT_POLICY=relay나 브라우저 relay 설정이 테스트 후 그대로 남아 있지 않은지 점검한다
STUN을 항상 함께 넣는다srflx 후보로 홀펀칭 기회를 만든다KVS는 STUN을 GetIceServerConfig로 주지 않는다. stun:stun.kinesisvideo.{region}.amazonaws.com:443을 직접 넣어야 한다(18장)
운영자 네트워크에서 UDP 아웃바운드 허용사무실 방화벽이 UDP를 막으면 TURN TCP/TLS로 떨어진다IT 팀과 협의. 최소한 STUN의 UDP 443과 P2P용 UDP 아웃바운드
디바이스 회선 개선LTE CGNAT은 symmetric NAT 동작이 많아 직결이 어렵다(05장)통신사 APN·요금제에 따라 다르다. 고정 공인 IP나 NAT 동작이 완화된 회선을 검토한다
IPv6 dual-stack 검토양쪽 모두 IPv6면 NAT 없이 직결될 수 있다C SDK v1.20(KVS_DUALSTACK_ENDPOINTS=ON)·JS SDK는 dual-stack 모드를 제공하지만, System requirements 문서는 STUN/TURN IPv6 미지원이라고 적는다. 문서끼리 맞지 않으므로 대상 리전에서 실측한다
쓰지 않는 세션을 닫는다TURN 분은 데이터가 흐르는 동안 쌓인다탭이 숨겨진 채 20분 넘게 지나면 PeerConnection을 닫고 "계속 보기" 버튼을 띄운다(Page Visibility API). 디바이스 업링크도 같이 아낀다
relay 세션 비트레이트 상한TURN 분은 줄지 않지만 데이터 전송 GB가 준다relay로 판정되면 maxBitrate를 낮춘다(09장). 어차피 5 Mbps 상한이 있다

TURN 서버를 직접 운영하는 선택지(coturn, 07장)도 있지만, KVS 관리형 TURN은 채널 인증·자격증명 발급과 묶여 있다. 직접 TURN을 섞으면 그 인증과 가용성을 직접 책임져야 하므로, relay 트래픽이 정말 커졌을 때 비용을 비교해 판단한다.

6. 할당량 관리: 고정 한도와 증설 가능한 한도

할당량은 두 부류로 나눠 대한다. 증설 가능한 한도(soft)는 사용량 예측과 사전 신청으로 해결하고, 조정 불가 한도(hard)는 설계로 피한다.

대량 재연결의 동시성. 리전 쪽 순단이나 통신사 장애가 끝나면 디바이스 수백 대가 같은 순간에 재연결을 시도한다. 채널당 3 TPS는 디바이스 하나에게는 넉넉하지만, GetSignalingChannelEndpoint(계정 300 TPS)와 GetIceServerConfig(계정 100 TPS) 같은 계정 단위 한도는 함대 전체가 나눠 쓴다. 재연결에는 반드시 지수 백오프와 무작위 지터를 넣고, 엔드포인트는 캐시해서 재연결 때마다 다시 묻지 않게 한다.

master 연결 하나에 몰리는 메시지. SendIceCandidate 20 TPS와 SendSdpAnswer 5 TPS는 WebSocket 연결 단위다. viewer는 각자 연결이 있지만 master는 연결 하나로 모든 viewer에게 answer와 후보를 보낸다. 운영자 10명이 한꺼번에 같은 트랙터를 열면 master는 answer 10건과 후보 수십~백 건을 1~2초 안에 보내야 하고, 한도에 걸린다. viewer 입장 시점을 백엔드에서 조금씩 엇갈리게 하거나, 불필요한 후보(예: 쓰지 않는 인터페이스의 host 후보)를 줄인다.

할당량 확인과 신청. 채널 수처럼 문서마다 숫자가 다른 항목은 문서를 인용하지 말고 콘솔 값을 기준으로 한다. Service Quotas의 서비스 코드는 이름으로 먼저 찾는다.

aws service-quotas list-services --region ap-northeast-2 \
  --query "Services[?contains(ServiceName, 'Kinesis Video')]"
# 찾은 ServiceCode로 현재 값 조회
aws service-quotas list-service-quotas --service-code <위에서 찾은 코드> --region ap-northeast-2 \
  --query "Quotas[].{name:QuotaName,value:Value,adjustable:Adjustable}" --output table

7. 흔한 장애와 대응

장시간 켜져 있는 디바이스는 여러 개의 "만료 시계"를 동시에 돌린다. 장애 대부분은 이 중 하나를 놓쳐서 생긴다.

장애 표

증상원인확인대응
부팅 직후 모든 KVS 호출이 서명 오류·403시계 오차로 SigV4 실패. RTC 배터리가 없는 보드는 전원이 끊기면 1970년이나 빌드 시각으로 돌아간다. 서명 시각이 AWS 시각과 허용 범위 이상 벌어지면 요청이 거절된다. 시계가 크게 틀리면 TLS 인증서 유효기간 검증부터 실패하기도 한다디바이스 date와 NTP 상태, 오류 메시지의 시각 문구KVS SDK를 시작하기 전에 NTP/chrony 동기화를 기다린다. 농기계라면 GPS 시각을 보조 시간원으로 쓴다. 브라우저는 JS SDK SignalingClient의 systemClockOffset으로 보정한다
한동안 잘 되다가 재연결부터 실패임시 자격증명 만료. IoT role alias 자격증명은 기본 3,600초, 운영자 STS 자격증명은 발급 시 정한 시간이 지나면 만료된다자격증명 expiration과 실패 시각 비교디바이스는 만료 전에 credentials provider에서 다시 받는다. 환경변수에 고정한 임시 키(AWS_SESSION_TOKEN 포함)는 만료되면 프로세스를 다시 띄우기 전까지 복구되지 않는다. 브라우저는 재연결 직전에 백엔드에서 새 자격증명을 받는다
정확히 약 1시간마다 새 viewer가 못 붙음1시간 연결 한도에서 재연결 누락. 시그널링 연결은 최대 3,600초(조정 불가)다. 끊긴 뒤 다시 붙지 않은 master는 새 viewer의 offer를 받지 못한다Failure(ConnectAsMaster) 시각, 디바이스 로그의 close 시각1시간이 되기 전에 선제 재연결한다. GO_AWAY를 받으면 60초 안에 재연결하고, RECONNECT_ICE_SERVER를 받으면 ICE 서버 설정을 새로 받는다. 시그널링이 끊길 때 이미 맺어진 PeerConnection의 미디어가 바로 끊기는지는 문서에서 확인하지 못했으므로 두 경우 모두에 대비한다
viewer가 없을 때 디바이스가 조용히 오프라인10분 idle timeout. 메시지가 오가지 않으면 600초 후 서비스가 연결을 닫고 그 클라이언트를 offline으로 표시한다close 이벤트 간격이 약 10분close 이벤트마다 백오프 재연결하는 루프를 기본으로 둔다. "연결 유지"가 아니라 "끊기면 다시 붙기"로 설계한다
일부 운영자만 접속 실패viewer 한도 초과. 채널당 10명(조정 가능)을 넘으면 ClientLimitExceededException, 저장 세션은 3명이다. 같은 ClientId로 다시 연결하면 새 연결이 기존 연결을 대체하므로, 탭 두 개가 같은 ID를 쓰면 서로를 밀어낸다Failure(ConnectAsViewer), 오류 타입백엔드가 좌석을 관리하고 대기·거절 메시지를 준다. ClientId는 "운영자 + 탭" 단위로 안정적으로 만든다. 상시 10명 이상이 필요하면 증설보다 구조 변경(16장)을 먼저 검토한다
연결은 됐는데 검은 화면, 또는 answer 거절코덱 불일치. 디바이스가 보내는 H.264 프로파일·패킷화 모드를 상대가 받지 않거나, 저장 모드에 VP8·H.265를 보냈다SDP의 a=rtpmap·a=fmtp(profile-level-id), statusResponse양쪽 코덱 우선순위를 맞춘다(setCodecPreferences, 04장). 저장 모드는 H.264 + Opus만. 메시지에 correlationId를 넣어 거절 사유를 받는다
iceConnectionState가 failed, 특정 사무실·회선에서만NAT/방화벽의 UDP 차단. 직결도, UDP TURN도 막혔다getStats()의 후보 목록에 relay가 있는지, 어떤 전송인지System requirements 문서는 TURN 엔드포인트로 turn:과 turns:(TLS) 443을 함께 적는다. 브라우저가 TCP/TLS 443 relay로 붙을 수 있게 둔다. 디바이스 방화벽은 *.kinesisvideo.{region}.amazonaws.com의 443(TCP와 UDP)을 허용한다. IPv6만 열린 망은 System requirements 문서상 STUN/TURN 미지원임에 주의한다
디바이스 두 대가 번갈아 끊김master 중복 접속. 같은 채널에 master가 두 번 붙으면 가장 최근 요청이 이긴다같은 채널의 ConnectAsMaster 빈도thing 이름·채널 이름 중복(교체 장비에 옛 인증서 재사용 등)을 레지스트리에서 막는다
ICE restart나 재접속 후 relay만 실패TURN credential 만료. GetIceServerConfig의 자격증명은 300초 고정이다ICE 서버 설정을 받은 시각과 PeerConnection 생성 시각새 PeerConnection을 만들거나 ICE restart를 할 때마다 GetIceServerConfig를 다시 호출한다. 오래 캐시한 설정을 재사용하지 않는다

GetIceServerConfig의 SessionExpiredException 설명에는 "연결 후 세션은 45분간 유효하다"는 문장도 있다. 1시간 최대 연결 시간과 숫자가 달라 의미가 분명하지 않다. 선제 재연결 시점을 1시간보다 넉넉히 앞당겨 잡는 편이 이런 모호함에서도 안전하다.

진단 순서

장애 신고를 받으면 다음 순서로 범위를 좁힌다. 세부 도구 사용법은 15장에 있다.

  1. 시그널링 단계인가, 미디어 단계인가. CloudWatch Failure를 Operation별로 본다. ConnectAs 계열이 실패하면 자격증명·시계·한도 문제이고, 시그널링은 성공했는데 영상이 안 나오면 ICE·코덱 문제다.
  2. 시그널링이면: 디바이스 시계, 자격증명 만료 시각, IAM 정책의 리소스 이름(ThingName 헤더 포함), viewer 한도 순서로 확인한다.
  3. 미디어면: 브라우저 chrome://webrtc-internals와 getStats()로 후보 쌍 상태를 보고, 디바이스는 AWS_KVS_LOG_LEVEL을 올려 ICE 로그를 받는다. KVS_ICE_TRANSPORT_POLICY=relay로 TURN 경로만 따로 시험하면 "직결 실패"인지 "TURN까지 실패"인지 갈린다.
  4. 간헐적이면: 1시간·10분·5분 같은 주기성이 있는지 본다. 주기가 보이면 거의 항상 위 표의 만료 시계 중 하나다.

핵심 정리

  • IAM은 디바이스(MASTER)·운영자(VIEWER)·프로비저닝 백엔드로 역할을 나눈다. 디바이스는 ${credentials-iot:ThingName}으로 자기 채널에만, 운영자는 STS 세션 정책으로 채널 하나에만, 백엔드는 managed-by 태그 조건으로 자기 리소스에만 손대게 한다. 채널 ARN 끝에는 생성 시각이 붙으므로 이름 뒤를 와일드카드로 둔다.
  • 연결 없는 채널은 과금되지 않지만 할당량·보안·저장 비용 때문에 디바이스 폐기 시 지운다. 순서는 인증서 폐기 → 저장 모드 해제 → 채널 삭제 → 스트림 처리다.
  • CloudWatch는 시그널링 실패·지연·메시지, TURN 분, 저장 분을 보여 주지만 P2P 미디어 품질은 보여 주지 못한다. 품질은 브라우저 getStats()와 C SDK rtcPeerConnectionGetMetrics()로 양 끝에서 모은다. 네임스페이스는 list-metrics로 확인하고 추측하지 않는다.
  • 비용은 활성 채널 + 메시지 + TURN 분(+ 데이터 전송)이고, 대개 TURN이 지배한다. 서울 기준 200대 예시는 relay 20%에서 월 약 $32, 60%에서 약 $75이며 relay 데이터 전송료가 별도로 붙는다.
  • master 1, 연결 1시간, idle 10분, TURN 5 Mbps·300초는 조정할 수 없다. 재연결 루프·지터 백오프·credential 재발급을 설계에 넣고, 문서마다 다른 채널 수 한도는 Service Quotas 콘솔 값을 기준으로 한다.
