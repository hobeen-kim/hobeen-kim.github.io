Alertmanager 아키텍처

학습 목표

  • Prometheus의 룰 평가와 Alertmanager의 알림 라우팅이 왜 별도 컴포넌트로 분리돼 있는지 이해한다.
  • 알림이 발화한 뒤 dedup·group·inhibit·silence·route·notify를 거치는 파이프라인 흐름을 익힌다.
  • gossip 프로토콜 기반 HA 클러스터링이 중복 알림을 어떻게 막는지 파악한다.
  • Slack/PagerDuty/webhook 연동 방식과 Grafana Unified Alerting과의 선택 기준을 정리한다.

1. Prometheus와 Alertmanager의 역할 분리

Prometheus는 알림 규칙(alerting rule)을 주기적으로 평가해 조건이 참이면 알림을 발화(fire)시키는 역할만 한다. 발화된 알림을 누구에게, 어떤 채널로, 언제 보낼지는 전혀 모른다. 그 책임은 Alertmanager가 진다. 두 컴포넌트가 분리된 이유는 단순한 계층 분리가 아니라 운영상 실질적인 이점 때문이다.

첫째, 다대일 매핑이 가능해진다. 여러 Prometheus 서버(샤딩된 클러스터, 리전별 인스턴스, Mimir ruler 등)가 하나의 Alertmanager 클러스터로 알림을 보낼 수 있다. 룰 평가는 분산돼 있어도 라우팅 정책은 한 곳에서 일관되게 관리한다.

둘째, 중복 제거와 그룹핑은 룰 평가 로직과 무관한 별도 관심사다. 같은 장애로 수십 개의 알림이 동시에 발화해도, Alertmanager가 이를 하나의 알림으로 묶어 보낸다. 이 로직을 Prometheus 안에 넣으면 룰 평가 성능과 알림 처리 로직이 뒤섞인다.

셋째, 알림 자체의 생명주기 관리(재시도, 억제, 임시 음소거)가 룰 평가 주기와 독립적으로 동작해야 한다. Prometheus가 15초마다 룰을 재평가하는 동안, Alertmanager는 repeat_interval 같은 자신만의 시간 축으로 알림을 관리한다.

이 구조에서 Prometheus는 상태를 pending(조건은 참이지만 for 기간 미충족)과 firing(조건이 for 기간 동안 지속)으로만 관리하고, firing 상태가 된 알림만 Alertmanager로 전송한다.

2. 알림 파이프라인

Alertmanager에 도착한 알림은 여러 단계를 순차적으로 통과한 뒤에야 실제 채널로 나간다. 각 단계는 서로 다른 목적을 가진 필터라고 이해하면 된다.

  • Deduplicate: 알림의 라벨 집합에서 계산한 fingerprint가 같으면 동일 알림으로 취급한다. Prometheus가 재평가 때마다 같은 알림을 다시 보내도 중복 처리하지 않는다.
  • Group: route의 group_by에 지정한 라벨이 같은 알림끼리 하나의 알림 그룹으로 묶는다. 노드 100대에서 동시에 디스크 부족 알림이 뜨면 알림 100개가 아니라 그룹 알림 1개로 전달된다.
  • Inhibit: inhibit_rules에 정의한 조건에 따라, 더 상위 심각도 알림이 firing 중이면 하위 알림을 억제한다. 예를 들어 클러스터 전체 다운 알림이 뜨면 개별 Pod 알림은 억제한다.
  • Silence: 운영자가 등록한 matcher와 일치하는 알림을 지정 기간 동안 완전히 차단한다. 배포·점검 창구에 사용한다.
  • Route: route 트리를 루트부터 순회하며 라벨 matcher가 일치하는 가장 구체적인 노드를 찾아 receiver를 결정한다.
  • Notify: 결정된 receiver의 채널로 실제 전송한다. 실패하면 지수 백오프로 재시도한다.

라우팅·그룹핑·억제·silence의 세부 설정은 다음 챕터 라우팅·그룹핑·억제에서 자세히 다룬다.

3. HA 클러스터링과 gossip 프로토콜

Alertmanager를 단일 인스턴스로 운영하면 그 인스턴스가 죽는 순간 모든 알림이 유실된다. 그렇다고 단순히 여러 인스턴스를 띄우고 Prometheus가 모두에게 알림을 보내게 하면, 각 인스턴스가 독립적으로 그룹핑·라우팅을 수행해 동일 알림이 채널별로 중복 발송된다.

Alertmanager는 이 문제를 gossip 기반 클러스터링으로 해결한다. HashiCorp memberlist 라이브러리를 사용해 인스턴스끼리 실리케이션(silence)·알림 통지 상태를 P2P로 전파한다. 별도의 외부 저장소(etcd, Consul 등) 없이 메모리 상태만으로 동기화한다.

각 인스턴스는 --cluster.peer 플래그로 다른 피어의 주소(기본 gossip 포트 9094)를 알려주면 클러스터를 구성한다. Prometheus 쪽도 alerting.alertmanagers에 모든 Alertmanager 인스턴스를 등록해 동일 알림을 전체 인스턴스에 중복 전송하도록 설정한다. 중복 억제는 Alertmanager 클러스터 내부의 gossip으로 처리하는 구조다.

# alertmanager 실행 플래그 예
--cluster.listen-address=0.0.0.0:9094
--cluster.peer=alertmanager-1:9094
--cluster.peer=alertmanager-2:9094
--cluster.peer=alertmanager-3:9094

gossip 클러스터의 한계

gossip은 최종 일관성(eventual consistency) 모델이다. 네트워크 파티션이 발생하면 짧은 시간 동안 동일 알림이 여러 채널로 중복 발송될 수 있다. 완벽한 exactly-once를 보장하지 않으며, "중복보다 유실이 더 나쁘다"는 전제 위에 설계돼 있다는 점을 운영자가 인지해야 한다.

4. Notification Integrations

Alertmanager는 receivers 설정에 여러 알림 채널을 정의할 수 있다. 대표적으로 Slack, PagerDuty, 범용 webhook을 많이 쓴다.

receivers:
- name: 'slack-critical'
  slack_configs:
  - api_url: 'https://hooks.slack.com/services/XXX/YYY/ZZZ'
    channel: '#alerts-critical'
    title: '{{ .CommonAnnotations.summary }}'
    text: '{{ .CommonAnnotations.description }}'

- name: 'pagerduty-oncall'
  pagerduty_configs:
  - routing_key: '<PagerDuty Events API v2 integration key>'
    severity: '{{ .CommonLabels.severity }}'

- name: 'webhook-generic'
  webhook_configs:
  - url: 'https://internal-service.example.com/alerts'
    send_resolved: true
  • Slack: Incoming Webhook URL 기반. 채널·제목·본문을 Go 템플릿으로 커스터마이징한다.
  • PagerDuty: Events API v2의 routing_key로 서비스에 연결한다. severity를 라벨과 매핑해 PagerDuty 쪽 우선순위를 결정한다.
  • Webhook: 표준 JSON 페이로드를 POST로 전달하는 범용 통합. ChatOps 봇, 티켓 시스템, 커스텀 자동화(예: 자동 스케일 아웃 트리거)에 활용한다. send_resolved: true를 켜면 알림 해소(resolved) 이벤트도 전달한다.

receiver 템플릿과 severity/team 기반 라우팅 설계는 라우팅·그룹핑·억제에서 이어서 다룬다.

5. Prometheus Alertmanager vs Grafana Unified Alerting

실무에서 자주 부딪히는 선택이다. Grafana Unified Alerting은 Grafana 9 이상에 내장된 알림 엔진으로, Alertmanager와 호환되는 자체 구현체를 포함한다.

항목Prometheus + 별도 AlertmanagerGrafana Unified Alerting
룰 평가 위치Prometheus(또는 Mimir ruler)Grafana 서버 자체
지원 데이터소스PromQL(Prometheus/Mimir/Thanos)모든 Grafana 데이터소스(Prometheus, Loki, MySQL, CloudWatch 등) 혼합 쿼리 가능
알림 라우팅 엔진Alertmanager(gossip HA)내장 Alertmanager 호환 엔진, 또는 외부 Alertmanager로 위임 가능
설정 방식YAML(alertmanager.yml), GitOps 친화적UI 또는 provisioning YAML
강점대규모 메트릭 전용 환경, 세밀한 클러스터링 제어로그·DB 등 비메트릭 소스 기반 알림, 단일 UI 관리

선택 기준은 명확하다. 알림 조건이 PromQL 하나로 표현되고 Prometheus/Mimir 생태계 안에서 대규모로 운영한다면 전용 Alertmanager 클러스터가 유리하다. gossip HA, 세밀한 inhibition 규칙, GitOps로 관리하는 alertmanager.yml이 성숙한 생태계를 갖고 있다. 반대로 Loki 로그 기반 알림이나 여러 데이터소스를 조합한 알림, Grafana를 이미 알림 관리 허브로 쓰는 조직이라면 Unified Alerting이 학습 비용과 운영 컴포넌트 수를 줄여준다.

두 시스템은 배타적이지 않다. Grafana Unified Alerting에서 룰을 평가하되 알림 전달은 외부 Alertmanager로 위임하는 하이브리드 구성도 가능하다. 다만 라우팅 정책을 두 곳에 나눠 관리하면 운영 복잡도가 올라가므로, 팀 안에서 "라우팅 정책의 단일 진실 공급원(source of truth)"을 하나로 정하는 것이 중요하다.

6. 배포 형태

Alertmanager는 상태를 gossip으로만 공유하는 가벼운 컴포넌트라 배포 방식도 단순하다.

단일 바이너리 / Docker: 개발·소규모 환경에서는 alertmanager 바이너리 하나를 --config.file=alertmanager.yml로 실행한다.

Kubernetes(Prometheus Operator): kube-prometheus-stack을 쓰면 Alertmanager CRD가 StatefulSet으로 클러스터를 구성하고, AlertmanagerConfig CRD로 라우팅 설정을 네임스페이스별로 선언적으로 분리할 수 있다.

apiVersion: monitoring.coreos.com/v1
kind: Alertmanager
metadata:
  name: main
spec:
  replicas: 3
  resources:
    requests:
      cpu: 100m
      memory: 128Mi

replicas: 3으로 지정하면 Operator가 자동으로 --cluster.peer 플래그를 채워 StatefulSet 파드끼리 gossip 클러스터를 구성한다. Service는 헤드리스로 만들어 파드 간 직접 통신이 가능하게 한다.

사이드카 패턴: Prometheus와 같은 Pod에 사이드카로 배치하는 경우도 있으나, HA를 위해서는 Prometheus와 Alertmanager를 독립적으로 스케일링할 수 있는 별도 Deployment/StatefulSet 구조가 표준이다.

핵심 정리

  • Prometheus는 룰 평가와 firing까지만 담당하고, 라우팅·중복 제거·알림 전달은 Alertmanager의 책임이다.
  • 알림은 dedup → group → inhibit → silence → route → notify 순으로 파이프라인을 통과한다.
  • HA는 별도 저장소 없이 memberlist 기반 gossip으로 notification log를 동기화해 중복 알림을 억제한다.
  • Slack/PagerDuty/webhook을 receiver로 등록해 채널별 알림을 구성한다.
  • 순수 PromQL 기반 대규모 환경은 전용 Alertmanager, 다중 데이터소스·Grafana 중심 운영은 Unified Alerting이 유리하다.
  • kube-prometheus-stack에서는 Alertmanager CRD의 replicas만 지정하면 Operator가 클러스터링을 자동 구성한다.

다음 챕터

Alertmanager가 알림을 어디로 보낼지 결정하는 핵심 로직이 route 트리다. 다음 챕터 라우팅·그룹핑·억제에서는 matcher 기반 route 트리 설계, grouping 파라미터 튜닝, inhibition 규칙 작성법, silence 운영, 그리고 severity/team 기반 실전 라우팅 설계를 다룬다.
