CH3. 파티션과 파일시스템

학습 목표

  • 안드로이드 스토리지가 여러 파티션으로 쪼개진 이유를 업데이트 단위·마운트 정책·무결성 검증 단위 관점에서 이해한다.
  • A/B 슬롯과 super 동적 파티션이 어떤 문제를 풀기 위해 등장했는지, 어떻게 동작하는지 파악한다.
  • 마운트되는 파티션(system/vendor/product 등)과 마운트되지 않는 파티션(boot/vbmeta/misc 등)의 포맷과 용도를 구분한다.
  • 커널이 제공하는 pseudo-filesystem(procfs·sysfs·cgroupfs·tracefs 등)이 안드로이드에서 실제로 어디에 쓰이는지 안다.

파티션이 분리된 이유

안드로이드 기기의 플래시 스토리지는 하나의 큰 디스크지만, 그 위에는 수십 개의 파티션이 올라간다. PC 리눅스가 보통 /와 swap 정도로 끝나는 것과 대조적이다. 이 분리에는 세 가지 축이 있다.

업데이트 단위가 첫 번째 축이다. 커널(boot)과 시스템 프레임워크(system), 벤더 HAL(vendor)은 서로 다른 주체가, 서로 다른 주기로 갱신한다. 구글은 system을 매달 밀어주지만 SoC 벤더의 vendor는 몇 달에 한 번 바뀐다. 파티션을 나눠두면 각각을 독립적으로 교체할 수 있다. Project Treble(8.0)이 system과 vendor를 물리적으로 분리한 것이 이 철학의 정점이다.

마운트 정책이 두 번째 축이다. system·vendor는 무결성 보장을 위해 읽기 전용(read-only)으로 마운트한다. 반면 data는 앱이 계속 써야 하므로 읽기·쓰기(read-write)로 마운트한다. 이 둘을 한 파티션에 섞으면 "OS 영역은 불변, 사용자 영역은 가변"이라는 정책을 파일시스템 레벨에서 강제할 수 없다.

무결성 검증 단위가 세 번째 축이다. Verified Boot(AVB)는 파티션 단위로 해시 트리(dm-verity)를 계산해 서명한다. 파티션이 나뉘어 있어야 "이 system은 구글이 서명한 그대로인가"를 개별적으로 검증하고, 변조가 감지되면 그 파티션만 문제 삼을 수 있다. AVB의 상세는 CH16. SELinux와 Verified Boot에서 다룬다.

물리 스토리지는 대부분 eMMC(중저가) 또는 UFS(중고가 이상)다. 둘 다 NAND 플래시 기반이며, 컨트롤러가 wear leveling과 블록 관리를 대신한다. 파티션 테이블은 예전 MBR이 아니라 GPT(GUID Partition Table)를 쓴다. GPT는 파티션마다 이름(예: boot_a, system_a)을 붙일 수 있어, 부트로더와 fs_mgr가 이름으로 파티션을 찾는 안드로이드 방식에 잘 맞는다.

농기계 같은 임베디드 보드도 대개 eMMC를 쓴다. 진동·온도 스트레스가 크므로 pSLC 모드나 산업용 등급 eMMC를 선택하는 경우가 많고, 파티션 레이아웃 자체는 표준 안드로이드와 동일하게 잡는 것이 device bring-up(CH14)을 수월하게 한다.

A/B 슬롯 — seamless update의 기반

예전 안드로이드는 업데이트를 recovery 모드에서 했다. 재부팅해서 recovery로 진입하고, system에 패치를 덮어쓰는 동안 기기는 "업데이트 중" 화면에 멈춰 있었다. 이 방식은 두 가지가 나빴다 — 업데이트 시간 내내 기기를 못 쓰고, 쓰다가 전원이 나가면 system이 반쯤 망가져 부팅 불능(bricking)이 될 수 있었다.

A/B 슬롯(seamless update, 7.0 도입)은 이 문제를 스토리지를 두 벌로 복제해 푼다. boot, system, vendor 등 OS 파티션이 각각 _a, _b 접미사(slot suffix)를 달고 두 개씩 존재한다. 한쪽 슬롯으로 부팅해 정상 사용하는 동안, 업데이트는 사용하지 않는 다른 슬롯에 백그라운드로 기록된다. 다 쓰고 나면 다음 부팅 때 슬롯을 바꿔 새 버전으로 뜬다.

슬롯 상태는 bootctl HAL이 관리한다. 각 슬롯에는 세 가지 메타데이터가 붙는다.

  • active — 다음에 부팅할 슬롯
  • bootable — 부팅 시도가 허용된 슬롯(연속 실패하면 unbootable로 내려간다)
  • successful — 부팅 후 프레임워크까지 정상 기동해 "성공"으로 마킹된 슬롯

부팅 후 시스템이 안정적으로 뜨면 update_verifier가 슬롯을 successful로 표시한다. 만약 새 슬롯이 부팅에 실패하면 부트로더가 retry count를 소진한 뒤 자동으로 이전 슬롯으로 롤백한다. 이 롤백 능력이 A/B의 진짜 가치다.

# 현재 슬롯 확인
adb shell getprop ro.boot.slot_suffix      # _a 또는 _b
# bootctl로 슬롯 상태 조회
adb shell bootctl get-current-slot         # 0(a) 또는 1(b)
adb shell bootctl get-number-slots         # 2 (A/B면), 1 (non-A/B면)

non-A/B 기기는 여전히 존재한다(저가형, 일부 웨어러블). 이들은 슬롯이 하나뿐이라 앞서 말한 recovery 방식으로 업데이트하며, _a/_b 접미사도 없다. A/B는 슬롯 두 벌만큼 스토리지를 더 쓴다는 대가가 있어, 스토리지가 빠듯한 기기는 non-A/B를 택하기도 한다. 업데이트 경로의 상세 비교는 CH6. 시스템 이미지와 업데이트에서 다룬다.

Dynamic Partition — super 안의 논리 파티션

A/B로 system·vendor를 두 벌씩 두면 스토리지 파티셔닝이 골치 아파진다. 예전에는 각 파티션 크기를 공장에서 고정했는데, system_a를 크게 잡으면 system_b도 똑같이 커야 하고, OTA로 system이 커지면 미리 잡아둔 크기를 넘어 업데이트가 실패했다. 파티션 경계가 하드웨어에 박혀 있어 유연성이 없었다.

Dynamic Partition(동적 파티션, 10.0 도입)은 이 경직성을 없앤다. 물리 파티션은 super 하나로 통합하고, system·vendor·product·system_ext는 그 super 안의 논리 파티션(logical partition)이 된다. LVM(Logical Volume Manager)의 안드로이드판이라고 보면 정확하다. 논리 파티션은 super의 여유 공간 안에서 크기를 늘리거나 줄일 수 있어, OTA가 런타임에 파티션 크기를 재조정할 수 있다.

super의 메타데이터는 liblp(logical partition 라이브러리)가 관리한다. 파티션 이름·크기·슬롯 매핑이 super 앞부분의 메타데이터 영역에 기록되고, 부팅 시 init이 이를 읽어 /dev/block/mapper/ 아래에 device-mapper 타깃으로 각 논리 파티션을 만든다.

# super 안 논리 파티션 목록과 크기 덤프
adb shell lpdump
# 매핑된 논리 블록 디바이스 확인
adb shell ls -l /dev/block/mapper/
# system_a -> /dev/block/dm-0 같은 dm 노드로 연결돼 있다

lpdump는 super의 메타데이터를 사람이 읽을 수 있게 출력하고, 호스트에서 super 이미지를 만들 때는 lpmake를 쓴다. 10.0 이상 기기의 파티션 개수를 세보면 물리 파티션은 10여 개로 줄고 나머지가 전부 super 안으로 들어간 것을 볼 수 있다. Virtual A/B(스냅샷 기반 업데이트)도 이 동적 파티션 구조 위에서 동작하는데, 이는 CH6에서 이어간다.

마운트 가능한 파티션 — 역할 분담

super 안의 논리 파티션들은 각자 파일시스템을 담고 실제로 디렉토리 트리에 마운트된다. Treble 이후 역할이 명확히 나뉘었다.

  • system — AOSP 프레임워크·핵심 라이브러리·시스템 앱. 9.0부터 system-as-root 방식으로, 루트(/)가 곧 system 파티션이 됐다(별도 루트 ramdisk 없이 system을 /에 직접 마운트). 이후 GKI 도입으로 다시 ramdisk가 부활하는 변화가 있는데, 디렉토리 관점의 상세는 CH4에서 다룬다.
  • vendor — SoC/보드 벤더의 HAL, 커널 모듈, 펌웨어, 벤더 전용 바이너리. system과의 ABI 경계는 VNDK로 통제된다.
  • odm — ODM(제조 위탁사)이 보드 단위로 커스터마이즈하는 영역. 센서 보정값, 보드별 설정 등. 없으면 vendor에 포함된다.
  • product — 통신사/지역/브랜드별 커스터마이즈(선탑재 앱, 배경화면, 지역 설정). 같은 하드웨어로 여러 SKU를 만들 때 이 파티션만 갈아끼운다.
  • system_ext — system에 두기엔 AOSP 표준이 아니지만 OEM 프레임워크 확장이 필요한 부분. system을 순수 AOSP로 유지하려는 목적의 분리 파티션이다.

지원하는 파일시스템은 세 가지가 핵심이다.

  • ext4 — 오랜 기본값. 안정적이고 검증됐다. read-only 파티션은 ext4 + dm-verity 조합이 흔하다.
  • f2fs(Flash-Friendly File System) — NAND 플래시 특성에 맞춰 설계된 로그 구조 파일시스템. 주로 쓰기가 잦은 /data에 쓴다.
  • erofs(Enhanced Read-Only File System) — 읽기 전용 파티션 전용. 투명 압축을 지원해 system·vendor 크기를 크게 줄인다. 최신 기기의 read-only 파티션은 erofs로 넘어가는 추세다.
# 각 파티션이 어떤 파일시스템으로 어떻게 마운트됐는지
adb shell mount | grep -E 'system|vendor|product'
# 예: /dev/block/dm-0 on / type erofs (ro,...)

마운트 불가 파티션 — raw 데이터 영역

일부 파티션은 파일시스템을 담지 않는다. 부트로더나 특정 데몬이 raw 블록으로 직접 읽는 이미지·구조체이며, 디렉토리 트리에 마운트되지 않는다.

  • boot — 커널 + generic ramdisk + boot header. 부트로더가 여기서 커널을 로드한다. 포맷은 Android boot image(magic ANDROID!).
  • vendor_boot — GKI(11+)에서 벤더 ramdisk와 DTB를 boot에서 분리해 담는 파티션. GKI 커널과 벤더 리소스를 따로 갱신하기 위함.
  • init_boot — 13.0부터 generic ramdisk(= init과 첫 유저스페이스)를 boot에서 다시 분리한 파티션. boot는 순수 커널만 담게 됐다.
  • recovery — recovery 모드용 별도 커널+ramdisk. A/B 기기는 recovery를 boot에 합쳐 별도 파티션이 없기도 하다.
  • dtbo — Device Tree Blob Overlay. 베이스 DTB에 보드별 하드웨어 서술을 덧씌우는 오버레이.
  • misc — BCB(Bootloader Control Block)를 담는 작은 raw 파티션. "다음 부팅은 recovery로", "OTA 이어서 적용" 같은 부트로더-유저스페이스 간 커맨드를 주고받는 우편함이다.
  • frp — Factory Reset Protection. 공장 초기화 후에도 지워지지 않는 영역으로, 도난 기기의 무단 초기화를 막는 데 쓴다.
  • vbmeta — AVB 메타데이터. 각 파티션의 해시·서명·롤백 인덱스를 담는다. Verified Boot의 신뢰 사슬 루트다(CH16).
  • metadata — FBE(File-Based Encryption)의 암호화 메타데이터와 키 자료 일부. /data를 복호화하기 전에 필요한 정보가 들어 있다(CH4).
# misc(BCB)에 recovery 커맨드를 심어 recovery로 재부팅하는 예 (root 필요)
adb reboot recovery      # 내부적으로 BCB를 세팅하고 재부팅한다

칩셋별 파티션

앞의 파티션들은 AOSP 표준이지만, SoC 벤더는 자기 부트 체인과 펌웨어를 위한 파티션을 추가로 둔다.

  • Qualcomm — cdt(Configuration Data Table, 보드 식별), devinfo(기기 상태), splash(부팅 로고), xbl/abl(부트로더 스테이지), modem/dsp(무선·DSP 펌웨어) 등이 대표적이다. 파티션 수가 특히 많다.
  • Samsung Exynos — up_param, steady, keystorage 등 삼성 고유 파티션과 부트 스테이지가 붙는다.
  • MediaTek — preloader, lk(Little Kernel 부트로더), nvram/nvdata(캘리브레이션·설정), protect1/protect2 등이 있다.

농기계 보드에서 SoC를 고를 때 이 벤더별 파티션 구조가 부트 커스터마이징 난이도를 좌우한다. Qualcomm은 문서와 도구가 풍부하지만 파티션 체인이 복잡하고, MediaTek은 부트 흐름이 상대적으로 단순한 대신 공개 자료가 적다.

Linux pseudo-filesystem 총람

지금까지는 블록 디바이스에 실체가 있는 파일시스템이었다. 반면 안드로이드는 커널이 메모리 위에서 만들어내는 가상 파일시스템(pseudo-filesystem)에 크게 의존한다. 이들은 디스크에 아무것도 저장하지 않고, 파일처럼 보이는 인터페이스로 커널 상태를 노출하거나 커널 기능을 제어한다.

pseudo-fs마운트 지점안드로이드에서의 용도
procfs/proc프로세스별 상태(/proc/<pid>/), 커널 파라미터. dumpsys·top의 데이터 원천
sysfs/sys디바이스·드라이버 트리, 전원·클럭 노드. GPIO·배터리·CPU 거버너 제어
cgroupfs/sys/fs/cgroup앱·프로세스 그룹의 CPU·메모리·I/O·freezer 제어. 백그라운드 앱 제한의 기반
tracefs/sys/kernel/tracingftrace 기반 커널 트레이싱. atrace/Perfetto가 여기서 이벤트를 수집
debugfs/sys/kernel/debug드라이버 디버그 노출. 보안상 유저(user) 빌드에서는 마운트하지 않는다
configfs/config커널 객체를 유저스페이스에서 생성·구성. USB gadget 기능 정의에 사용
functionfs/dev/usb-ffs/adbUSB gadget의 기능 엔드포인트를 파일로 노출. adbd가 adb 인터페이스를 여기에 붙인다
bpf/sys/fs/bpfeBPF 맵·프로그램의 파일시스템 표현. 네트워크 트래픽 통계·전력 프로파일링
pstore/sys/fs/pstore커널 패닉·last-kmsg를 재부팅 후에도 읽도록 보존(RAM/플래시 백업)
tmpfs/dev, /mnt, /apex 일부RAM 기반 임시 파일시스템. 재부팅하면 사라지는 노드·마운트 포인트
overlayfssystem 위 오버레이adb remount 시 read-only 파티션 위에 쓰기 레이어를 얹어 개발용 수정 허용
FUSE / sdcardfs/storage/emulated외부 스토리지 에뮬레이션과 권한별 뷰. sdcardfs를 FUSE로 대체하는 추세
incremental-fs/data/incremental앱 전체가 내려오기 전에 실행 가능하게 하는 스트리밍 설치(Play)

이 중 몇 개는 뒤 챕터에서 깊게 다룬다. cgroup은 컨테이너 기술의 뿌리이기도 해 Kubernetes 스터디 CH1의 격리 개념과 통한다. bpf·tracefs 기반 관측은 관측성 CH26 — eBPF 프로파일링과 겹친다. 실제로 안드로이드의 리소스 제어·트레이싱은 리눅스 커널 기능을 거의 그대로 얹은 것이라, 백엔드에서 쓰던 지식이 대부분 재사용된다.

# 지금 이 기기에 마운트된 pseudo-fs만 골라보기
adb shell mount | grep -E 'proc|sysfs|cgroup|tracefs|tmpfs|bpf|pstore'
# 앱 하나의 cgroup 소속 확인
adb shell cat /proc/<pid>/cgroup

procfs·sysfs를 데몬 개발에 쓸 때

농기계용 네이티브 CAN 데몬(AgIsoStack++ 기반)을 올릴 때, /sys/class/net/can0/로 CAN 인터페이스 상태를 읽거나 /proc/net/can/으로 통계를 확인하는 식으로 pseudo-fs를 직접 활용하게 된다. SocketCAN 자체의 동작은 CAN 스터디 CH13에서 다룬다.

핵심 정리

  • 파티션 분리의 세 축은 업데이트 단위·마운트 정책·무결성 검증 단위다. Treble이 system/vendor를 갈라놓은 것이 대표적이다.
  • A/B 슬롯은 사용하지 않는 슬롯에 백그라운드로 업데이트하고 재부팅으로 전환하며, 실패 시 이전 슬롯으로 자동 롤백한다. bootctl이 슬롯 상태를 관리한다.
  • Dynamic Partition은 system·vendor 등을 super 안의 논리 파티션으로 만들어 크기를 유연하게 재조정한다. liblp/lpdump가 이를 관리한다.
  • 마운트되는 파티션(system·vendor·product·system_ext)은 ext4/f2fs/erofs를 담고, 마운트되지 않는 파티션(boot·vbmeta·misc·metadata 등)은 부트로더·데몬이 raw로 읽는다.
  • procfs·sysfs·cgroupfs·tracefs·bpf 같은 pseudo-filesystem은 커널 상태·제어를 파일 인터페이스로 노출하며, 안드로이드의 리소스 제어·트레이싱·USB·통계가 모두 이 위에서 돈다.
