# SAE J1939 입문

::: info 학습 목표
- CAN만으로는 부족한 이유와 J1939 같은 상위 프로토콜이 무엇을 더하는지 설명할 수 있다.
- J1939가 29비트 CAN ID를 Priority, EDP, DP, PF, PS, SA 여섯 칸으로 나눠 쓴다는 것을 설명하고, 16진수 ID 하나를 여섯 칸으로 나눌 수 있다.
- SA(보낸 장치의 주소)와 PGN(메시지 종류 번호)이 각각 무엇을 알려 주는지 구분할 수 있다.
- ISOBUS 표준이 J1939에서 물려받은 것과 따로 정한 것을 몇 가지 들 수 있다.
- (심화) 새 메시지의 PGN 자리를 고르고, 메시지가 버스를 얼마나 차지하는지 계산할 수 있다.
:::

::: tip 시작하기 전에
- 먼저 읽을 장: [4장 CAN 데이터 프레임](/study/isobus/04-can-data-frame), [5장 CAN 중재와 우선순위](/study/isobus/05-can-arbitration)
- 이 장에서 처음 나오는 말
  - 상위 프로토콜: CAN 위에서 "이 데이터가 무슨 뜻인지, 누가 보냈는지"를 정하는 약속이다.
  - SAE J1939: 트럭·버스·농기계용 상위 프로토콜이다. ISOBUS의 바탕이 된다.
  - SA(Source Address, 소스 주소): 메시지를 보낸 장치의 번호다. 택배 송장의 "보내는 사람" 칸에 해당한다.
  - PGN(Parameter Group Number): 메시지의 종류를 가리키는 번호다. 송장의 "물건 종류" 칸에 해당한다.
  - CF(Control Function, 제어 기능): 버스에서 주소 하나를 쓰는 기능 단위다. 보통 ECU(전자 제어 장치) 하나가 CF 하나지만, ECU 하나에 CF가 여럿 들어 있을 수도 있다.
:::

택배 상자에 붙은 송장처럼, CAN 프레임에도 "무엇이 들었고 누가 보냈는지"를 적는 칸이 필요하다. 그런데 CAN 규격은 프레임을 버스에 실어 나르는 방법만 정하고, 그 칸을 어떻게 쓸지는 정하지 않는다. 트럭·버스 업계가 함께 정한 그 사용법이 SAE J1939이고, 농기계 표준인 ISOBUS(ISO 11783)는 J1939를 바탕으로 만들어졌다. 이 장에서는 J1939가 CAN 위에 무엇을 더했는지 큰 그림을 잡는다.

## 1. 왜 CAN만으로는 부족한가

2~7장에서 본 CAN이 해 주는 일과 해 주지 않는 일을 나눠 본다. 해 주지 않는 일이 곧 상위 프로토콜이 채워야 할 빈칸이다.

### CAN은 데이터 전달만 담당한다

CAN 프로토콜은 물리 계층과 데이터 링크 계층만 정의한다. 메시지를 버스에 올리고 내리는 것, 에러를 감지하는 것까지가 CAN이 하는 일이다. 물리 계층은 전선 위의 전압으로 0과 1을 나타내는 층이고([3장](/study/isobus/03-can-physical)), 데이터 링크 계층은 그 비트를 프레임으로 묶고 오류를 잡는 층이다([4장](/study/isobus/04-can-data-frame), [6장](/study/isobus/06-can-error)).

다음 기능들은 CAN 규격 어디에도 없다.

| 필요 기능 | CAN 2.0 지원 여부 |
|---|---|
| 노드별 고유 주소 관리 | 없음 (29비트 ID를 자유롭게 사용) |
| 메시지 의미 해석 (온도, 압력 등) | 없음 |
| 8바이트 초과 데이터 전송 프로토콜 | 없음 |
| 네트워크 진단 / 장치 검색 | 없음 |
| 타임아웃, 재전송 정책 | 없음 |

표의 왼쪽은 실제 차량·농기계 네트워크에 필요한 기능이고, 오른쪽은 CAN 2.0 규격이 그 기능을 주는지다. 예를 들어 CAN은 어떤 ID의 프레임이 "엔진 회전수"인지 "냉각수 온도"인지 정하지 않는다. 장치끼리 따로 약속해야 한다. 노드는 버스에 연결된 장치 하나를 말한다.

### 택배 트럭과 물류 시스템 비유

> "CAN은 택배 트럭이고, J1939는 물류 시스템이다."

```
CAN (택배 트럭)
  - 소포를 버스에서 목적지까지 운반
  - 어떤 소포인지, 배송 순서, 반품 정책은 모름

J1939 (물류 시스템)
  - 소포에 송장(PGN/SPN) 붙이기
  - 발송지(SA)/수신지(DA) 주소 관리
  - 큰 짐을 여러 소포로 나누는 규칙(Transport Protocol)
  - 배송 실패 처리, 재전송 정책
```

트럭(CAN)은 상자를 실어 나르는 일만 한다. 상자에 송장을 붙이고, 보내는 곳과 받는 곳을 적고, 큰 짐을 여러 상자로 나누는 규칙은 물류 시스템(J1939)이 정한다. 송장에 적는 PGN은 메시지 종류 번호, SPN(Suspect Parameter Number)은 메시지 안의 값 하나하나에 붙은 번호, DA(Destination Address)는 받는 장치의 주소다. 셋 다 [9장](/study/isobus/09-j1939-message)에서 자세히 본다.

비유가 어긋나는 점도 하나 있다. 실제 CAN은 목적지를 정해 배달하지 않는다. 모든 프레임을 버스에 연결된 모든 장치 앞에 똑같이 내려놓고(방송), 받을지 말지는 각 장치가 송장을 보고 정한다([2장](/study/isobus/02-can-intro)).

CAN 위에 상위 프로토콜을 올려야 비로소 실용적인 차량 네트워크가 완성된다.

## 2. 상위 프로토콜 지도

CAN 위에 올라가는 상위 프로토콜은 J1939 하나가 아니다. 이 절에서는 여러 상위 프로토콜의 자리를 지도로 그려 J1939와 ISOBUS가 어디에 있는지 확인한다.

### OSI 7계층에서의 위치

OSI 7계층은 통신에 필요한 일을 일곱 층으로 나눈 참고 모델이다. 아래층일수록 전기 신호에 가깝고, 위층일수록 응용 프로그램이 다루는 의미에 가깝다. CAN은 맨 아래 두 층(1 물리, 2 데이터 링크)을 맡는다. CAN 기반 상위 프로토콜은 모두 OSI 모델의 3계층 이상을 담당한다.

![OSI 7계층 옆에서 CAN 2.0B가 1~2계층을 맡고, CANopen·DeviceNet·SAE J1939·ISOBUS가 그 위 3~7계층을 맡는 프로토콜 스택](/images/study-isobus/08-osi-protocol-stack-light.png)
![OSI 7계층 옆에서 CAN 2.0B가 1~2계층을 맡고, CANopen·DeviceNet·SAE J1939·ISOBUS가 그 위 3~7계층을 맡는 프로토콜 스택](/images/study-isobus/08-osi-protocol-stack-dark.png)

그림 왼쪽은 OSI의 일곱 층이고, 오른쪽은 실제 프로토콜이다. 아래 칸의 CAN 2.0B(29비트 ID까지 쓸 수 있는 CAN 규격, [4장](/study/isobus/04-can-data-frame))는 하나지만, 그 위에는 쓰임새가 다른 상위 프로토콜이 여럿 올라간다.

### 프로토콜별 적용 도메인

![CAN 물리·링크 계층 위에 CANopen(산업 자동화), DeviceNet(공장 자동화), SAE J1939(대형 차량·농기계)가 올라가고, ISOBUS(ISO 11783)는 J1939 위에 농기계 전용으로 올라가는 관계](/images/study-isobus/08-protocol-domains-light.png)
![CAN 물리·링크 계층 위에 CANopen(산업 자동화), DeviceNet(공장 자동화), SAE J1939(대형 차량·농기계)가 올라가고, ISOBUS(ISO 11783)는 J1939 위에 농기계 전용으로 올라가는 관계](/images/study-isobus/08-protocol-domains-dark.png)

화살표는 "무엇 위에 만들어졌나"를 뜻한다. 쓰임새를 정리하면 다음과 같다.

- CANopen: 산업 자동화(PLC, 모터 제어)
- DeviceNet: 공장 자동화(센서, 액추에이터 네트워크)
- SAE J1939: 대형 차량·농기계(트럭, 버스, 굴착기)
- ISOBUS(ISO 11783): 농기계 전용(트랙터-작업기 통신)

ISOBUS만 CAN에서 바로 오지 않고 J1939를 거친다.

> ISOBUS는 J1939를 기반으로 농기계 도메인에 특화한 확장 프로토콜이다. J1939를 이해하면 ISOBUS의 절반은 이해한 것이다.

## 3. J1939란

이 절에서는 J1939가 어떤 표준이고 무엇을 정하는지 한눈에 본다.

SAE(Society of Automotive Engineers, 미국 자동차공학회)가 정의한 <strong>대형 차량 및 작업 기계용 통신 상위 프로토콜</strong>이다.

```
표준명: SAE J1939
관리 기관: SAE International
기반 CAN: CAN 2.0B (29비트 확장 ID)
비트레이트: 250 kbps (표준) / 500 kbps (옵션)
주요 적용: 트럭, 버스, 굴착기, 트랙터, 농기계
```

"기반 CAN: CAN 2.0B (29비트 확장 ID)"는 J1939가 29비트 ID 프레임을 쓴다는 뜻이다. 250 kbps는 1초에 25만 비트를 보내는 속도이고, ISOBUS도 이 속도를 표준으로 쓴다([3장](/study/isobus/03-can-physical)).

J1939가 정의하는 것들:

- **PGN (Parameter Group Number)**: 메시지 종류 식별자. "엔진 온도 묶음", "차속 묶음"처럼 함께 보내는 값의 묶음(Parameter Group)마다 번호를 붙인다(4절, [9장](/study/isobus/09-j1939-message)).
- **SPN (Suspect Parameter Number)**: 데이터 필드 내 개별 파라미터 식별자. 냉각수 온도처럼 값 하나하나에 붙는 번호다([9장](/study/isobus/09-j1939-message)).
- **소스/목적지 주소 관리**: 장치마다 주소를 정하고, 겹치면 해결하는 규칙이다([12장](/study/isobus/12-j1939-address-name)).
- **Transport Protocol**: 8바이트 초과 데이터를 여러 프레임으로 분할 전송하는 방법이다([15장](/study/isobus/15-tp-bam-cmdt)).
- **네트워크 관리**: 주소 요청, 주소 충돌 감지 같은 절차다([13장](/study/isobus/13-j1939-address-claim)).

J1939 문서는 여러 권으로 나뉜다. 이 장에 이름이 나오는 것은 데이터 링크 계층을 정하는 J1939-21과 네트워크 관리를 정하는 J1939-81이다.

## 4. J1939와 CAN의 관계: 29비트 ID를 여섯 칸으로

[4장](/study/isobus/04-can-data-frame)에서 본 확장 프레임의 ID는 29비트다. CAN은 이 ID를 "프레임의 이름표이자 우선순위"로만 쓰고, 안을 어떻게 나눌지는 정하지 않는다. J1939는 이 29비트를 여섯 칸으로 나눠 칸마다 뜻을 붙인다. J1939를 이해하는 데 가장 중요한 그림이다.

### 29비트 CAN ID의 구조화

Classic CAN 2.0B는 29비트 확장 ID를 제공하지만, 이 ID를 어떻게 쓸지는 규정하지 않는다. J1939는 이 29비트를 다음과 같이 <strong>명확한 필드로 구조화</strong>한다.

![J1939 29비트 CAN ID 필드 구조: Priority(0-2), EDP(3), DP(4), PF(5-12), PS(13-20), SA(21-28)](/images/study-isobus/08-canid-fields-light.png)
![J1939 29비트 CAN ID 필드 구조: Priority(0-2), EDP(3), DP(4), PF(5-12), PS(13-20), SA(21-28)](/images/study-isobus/08-canid-fields-dark.png)

그림 읽는 법: 상자 하나가 칸 하나이고, 상자 폭은 비트 수에 비례한다. 상자 아래 숫자는 버스에 나가는 순서다. 맨 왼쪽 Priority의 첫 비트가 0번째로 가장 먼저 나가고, SA의 마지막 비트가 28번째로 가장 나중에 나간다. [9장](/study/isobus/09-j1939-message)에서는 같은 비트를 반대 방향으로, 즉 오른쪽 끝을 0번으로 세는 비트 번호(28~0)로 부른다. 세는 방향만 다를 뿐 칸의 위치는 같다.

| 필드 | 비트 수 | 설명 |
|---|---|---|
| **Priority** | 3 | 메시지 우선순위. 0이 최고, 7이 최저 |
| **EDP** | 1 | Extended Data Page. J1939에서는 보통 0 |
| **DP** | 1 | Data Page. PGN 공간을 두 배로 확장 |
| **PF** | 8 | PDU Format. 메시지 유형 결정 (PDU1 vs PDU2 구분) |
| **PS** | 8 | PDU Specific. PF < 240이면 목적지 주소, PF >= 240이면 그룹 확장 |
| **SA** | 8 | Source Address. 메시지를 보내는 노드의 주소 (0x00~0xFD) |

칸마다 쉽게 말하면 이렇다.

- Priority: 송장의 "급함" 표시다. 두 장치가 동시에 보내면 숫자가 작은 쪽이 먼저 나간다([5장](/study/isobus/05-can-arbitration)).
- EDP, DP: 메시지 번호표의 "쪽수" 표시다. EDP는 지금은 늘 0이고, DP는 0쪽과 1쪽 가운데 하나를 고른다(7절).
- PF: 메시지의 종류를 정하는 핵심 칸이다. PDU는 Protocol Data Unit의 줄임말로 "한 번에 보내는 데이터 묶음"이라는 통신 용어다. PF 값이 240보다 작은지 아닌지에 따라 다음 칸 PS의 뜻이 바뀐다.
- PS: PF가 240보다 작으면 받는 장치의 주소(DA)이고, 240 이상이면 메시지 종류 번호를 더 잘게 나누는 확장 번호(GE, Group Extension)다. 앞의 형식을 PDU1, 뒤의 형식을 PDU2라고 부른다([9장](/study/isobus/09-j1939-message)).
- SA: 송장의 "보내는 사람" 칸이다. 5절에서 본다.

### 29비트 ID 예시 해석

ID 하나를 직접 나눠 보자. 대상은 `0x18FEE000`이다. `0x`는 뒤의 숫자가 16진수라는 표시다. 16진수 한 자리는 2진수 네 자리와 같다(예: `8` = `1000`, `E` = `1110`, `F` = `1111`).

1. 16진수 여덟 자리를 한 자리씩 2진수로 바꾼다. hex → binary: 0x18FEE000 = 0001 1000 1111 1110 1110 0000 0000 0000 (32bit)
2. CAN ID는 29비트이므로 맨 앞 3비트(`000`)는 ID가 아니다. 버리면 하위 29비트가 남는다.
3. 남은 29비트를 왼쪽부터 3, 1, 1, 8, 8, 8비트로 자른다: `110` | `0` | `0` | `1111 1110` | `1110 0000` | `0000 0000`
4. 칸마다 값을 읽는다: Priority `110` = 6, EDP 0, DP 0, PF `0xFE` = 254, PS `0xE0` = 224, SA `0x00` = 0

![0x18FEE000 CAN ID 분해: Priority=6, EDP=0, DP=0, PF=0xFE(254), PS=0xE0(224), SA=0x00](/images/study-isobus/08-canid-example-light.png)
![0x18FEE000 CAN ID 분해: Priority=6, EDP=0, DP=0, PF=0xFE(254), PS=0xE0(224), SA=0x00](/images/study-isobus/08-canid-example-dark.png)

그림의 상자 안은 칸마다 잘라 낸 비트이고, 상자 아래는 그 값을 읽은 결과다. PF가 254로 240 이상이므로 이 메시지는 PDU2다. 그래서 PS 칸의 `0xE0`은 받는 주소가 아니라 메시지 종류의 일부(Group Extension)다. SA `0x00`은 보통 엔진 ECU가 쓰는 주소다(5절).

손으로 할 때 쓰는 지름길이 있다. 뒤쪽 세 칸(PF, PS, SA)은 8비트씩이라 16진수 두 자리와 딱 맞는다. 그래서 `18 FE E0 00`처럼 두 자리씩 끊으면 PF = `FE`, PS = `E0`, SA = `00`을 바로 읽을 수 있다. 2진수로 풀어야 하는 것은 맨 앞 `18`뿐이다. 이 지름길은 [9장](/study/isobus/09-j1939-message)에서 연습한다.

### PGN: ID 안에 든 메시지 종류 번호

여섯 칸 가운데 Priority와 SA를 뺀 가운데 부분(EDP, DP, PF, PS)이 "이 메시지가 무엇인가"를 알려 준다. J1939는 이 부분으로 만든 번호를 PGN(Parameter Group Number, 메시지 종류 번호)이라고 부른다. 같은 PGN이면 데이터 8바이트의 배치가 늘 같으므로, 받는 쪽은 PGN만 보고 데이터 읽는 법을 안다.

PGN을 만드는 규칙은 하나만 기억하면 된다.

- PDU2(PF가 240 이상)이면 PS까지 PGN에 들어간다. 위 예 `0x18FEE000`은 DP 0, PF `FE`, PS `E0`을 이어 붙인 `0xFEE0`(=65248)이 PGN이다.
- PDU1(PF가 240 미만)이면 PS는 받는 주소이므로 PGN에서 빠지고 그 자리를 0으로 둔다. 예를 들어 PF가 `0xEA`(=234)인 요청 메시지는 받는 주소가 무엇이든 PGN이 `0xEA00`(=59904)이다.

정리하면 PGN은 "ID에서 우선순위와 보낸 이를 떼어 낸 나머지"이고, PDU1일 때는 받는 이도 떼어 낸다. 계산 공식과 연습은 [9장](/study/isobus/09-j1939-message)에서 한다. 7절의 "PGN 공간"은 이 번호가 가질 수 있는 값 전체를 말한다.

29비트 ID의 구조를 이해했으니, 이제 이 ID 체계 위에서 실제 J1939 네트워크가 어떻게 구성되는지 살펴보자.

## 5. J1939 네트워크 구성

ID의 SA 칸에 들어갈 주소는 누가 정하는가? 이 절에서는 장치마다 주소를 붙이는 방식, 장치들이 버스에 연결되는 모양, 실제로 메시지가 오가는 흐름을 차례로 본다.

### 소스 어드레스(SA) 할당

J1939는 노드마다 <strong>고유한 소스 어드레스(SA)</strong>를 부여한다. SAE J1939-81(네트워크 관리) 규격이 주소 요청/충돌 감지 절차를 정의한다. SA는 8비트라서 0~255를 쓸 수 있고, 그 가운데 0~253(`0x00`~`0xFD`)이 실제 장치에 붙는 주소다.

기능별로 미리 정해 둔 주소 예시:

```
SA 0x00 (0)   : Engine #1
SA 0x03 (3)   : Transmission #1
SA 0x17 (23)  : Instrument Cluster #1
SA 0x28 (40)  : Cab Display #1
SA 0xF9 (249) : Diagnostic Tool (오프보드)
SA 0xFE (254) : Null Address (아직 주소 없음)
SA 0xFF (255) : Global (브로드캐스트 목적지)
```

Engine은 엔진, Transmission은 변속기, Instrument Cluster는 계기판, Diagnostic Tool(오프보드)은 정비할 때 차 밖에서 연결하는 진단 도구다. 마지막 두 값은 장치 번호가 아니라 특별한 표시다.

- `0xFE`(254) Null Address: 주소를 아직 얻지 못한 장치가 "주소 없음"을 나타낼 때 쓴다. 보내는 이(SA) 칸에만 쓴다.
- `0xFF`(255) Global: 받는 이(DA) 칸에 "모두에게"라는 뜻으로 쓴다. 보내는 이 칸에는 쓰지 않는다.

장치마다 쓰기 좋은 주소가 기능별로 정해져 있지만, 같은 주소를 쓰려는 장치가 둘이면 정해진 절차로 한쪽이 양보한다. 이 절차가 주소 클레임이다([13장](/study/isobus/13-j1939-address-claim)).

### 네트워크 토폴로지 예시

토폴로지(topology)는 장치들이 선으로 이어진 모양을 말한다.

![양 끝 120Ω 종단 저항 사이에 엔진 ECU(SA 0x00), 변속기 ECU(SA 0x03), 계기판(SA 0x17), 캡 디스플레이(SA 0x28), 진단 도구(SA 0xF9)가 한 줄 버스로 이어진 J1939 네트워크](/images/study-isobus/08-bus-topology-light.png)
![양 끝 120Ω 종단 저항 사이에 엔진 ECU(SA 0x00), 변속기 ECU(SA 0x03), 계기판(SA 0x17), 캡 디스플레이(SA 0x28), 진단 도구(SA 0xF9)가 한 줄 버스로 이어진 J1939 네트워크](/images/study-isobus/08-bus-topology-dark.png)

> J1939 버스는 단일 버스 토폴로지(daisy-chain 또는 stub 방식)로 구성하며, 양 끝에 120Ω 종단 저항을 달아야 한다. ISOBUS도 동일한 물리 구성을 따른다.

daisy-chain은 장치에서 장치로 줄줄이 잇는 방식이고, stub은 본선에서 짧은 가지선을 내어 장치를 붙이는 방식이다. 어느 쪽이든 전기적으로는 선 하나(버스)를 모든 장치가 나눠 쓴다. 종단 저항이 왜 양 끝에 필요한지는 [3장](/study/isobus/03-can-physical)에서 봤다.

### J1939 통신 흐름 예시

같은 버스 위에서 메시지가 실제로 오가는 모습을 보자.

![엔진 ECU가 PGN 65262 엔진 온도를 브로드캐스트하면 계기판과 진단 도구가 받고, 진단 도구가 엔진에게 PGN 59904 요청을 보내면 엔진이 PGN 65262로 다시 응답하는 시간 순서](/images/study-isobus/08-request-flow-light.png)
![엔진 ECU가 PGN 65262 엔진 온도를 브로드캐스트하면 계기판과 진단 도구가 받고, 진단 도구가 엔진에게 PGN 59904 요청을 보내면 엔진이 PGN 65262로 다시 응답하는 시간 순서](/images/study-isobus/08-request-flow-dark.png)

그림에서는 위에서 아래로 시간이 흐른다.

1. 엔진 ECU(SA `0x00`)가 PGN 65262(엔진 온도)를 모두에게 보낸다(브로드캐스트). 계기판은 받아서 수온 게이지에 표시하고, 진단 도구는 로그에 남긴다.
2. 진단 도구(SA `0xF9`)가 PGN 59904(Request, 요청)를 엔진 앞(DA `0x00`)으로 보낸다. 데이터에는 "PGN 65262를 보내 달라"고 적는다.
3. 엔진이 PGN 65262를 다시 보낸다. 이 메시지는 PDU2라서 받는 주소 칸이 없으므로, 요청한 진단 도구를 포함해 모두가 받는다.

이 그림은 요청과 응답의 모양을 보여 주려는 예다. 실제로는 이미 주기적으로 방송되는 메시지를 요청하는 것은 권장되지 않는다(8절). 요청과 응답의 규칙은 [10장](/study/isobus/10-j1939-request-ack)에서 자세히 본다.

::: tip 1~5절 정리
- CAN은 물리·링크 계층만 담당하므로 주소 관리, 메시지 의미, 대용량 전송은 상위 프로토콜이 필요하다.
- CANopen(산업), DeviceNet(공장), J1939(대형 차량·농기계), ISOBUS(농기계 전용) 모두 CAN 위에 올라가는 상위 프로토콜이다.
- J1939는 CAN 2.0B의 <strong>29비트 ID</strong>를 Priority + EDP + DP + PF + PS + SA 필드로 구조화한다.
- <strong>SA(Source Address)</strong>로 버스 내 노드를 구분하며, 0x00~0xFD가 일반 노드에 할당된다.
- ISOBUS는 J1939를 농기계 도메인에 맞게 확장한 프로토콜이다.
:::

여기까지가 J1939의 기본이다. 6절부터는 ISOBUS 표준이 J1939를 어떻게 받아들였는지, PGN 번호가 어떻게 배치되는지를 더 깊이 본다. 8절과 9절은 새 메시지를 설계하는 사람을 위한 심화 내용이다.

## 6. ISOBUS 표준은 J1939를 어떻게 받아들였나

ISOBUS는 J1939를 바탕으로 만들었다고 했다. 이 절에서는 ISOBUS 표준 문서가 J1939와 얼마나 같고 어디가 다른지 확인한다. 결론부터 말하면, 데이터 링크 계층의 규칙은 거의 같고 몇 가지만 ISOBUS가 따로 정했다.

### 공동 개발된 문서

ISO 11783은 여러 권(Part)으로 된 ISOBUS 표준이다. 그 가운데 데이터 링크 계층을 정하는 문서가 ISO 11783-3이고, 이 장에서는 2018년 판을 Part 3이라고 줄여 부른다. Part 3의 서문은 ISO 11783의 일부가 SAE J1939 문서에 기반한다고 밝힌다. 트럭·버스용 J1939 규격을 만족하는 전자 장치를 농업·임업 장비에서 최소한의 변경으로 쓸 수 있도록 공동 문서를 만들었다는 것이다. Part 3의 참고 문헌에는 J1939의 데이터 링크 계층 문서인 SAE J1939-21이 올라 있다.

Part 3이 스스로 정한 범위는 두 가지다.

- 응용 계층의 PDU(Protocol Data Unit, 프로토콜 데이터 단위)를 고전 CAN의 CEFF 데이터 프레임에 매핑하는 방법
- CEFF 프레임 하나에 담기지 않는 PDU를 위한 전송 계층 프로토콜(TP, ETP)과 그 CEFF 매핑

말을 풀면 이렇다. 고전 CAN(Classical CAN)은 CAN FD가 아닌 기존 CAN이다. CEFF(Classical Extended Frame Format)는 29비트 ID를 쓰는 고전 CAN 프레임, 즉 [4장](/study/isobus/04-can-data-frame)의 확장 프레임이다. 응용 계층은 "엔진 온도를 보내라"처럼 실제 일을 하는 프로그램 쪽이다. 그러니 첫째 항목은 "응용 프로그램이 보낼 데이터를 29비트 ID 프레임 하나에 어떻게 싣는가", 둘째 항목은 "프레임 하나에 다 들어가지 않는 긴 데이터를 어떻게 나눠 싣는가"다. 긴 데이터를 나눠 보내는 TP와 ETP는 [15장](/study/isobus/15-tp-bam-cmdt)과 [17장](/study/isobus/17-etp)에서 본다.

Part 3은 데이터 링크 계층의 역할을 "물리 링크를 거쳐 데이터를 신뢰성 있게 옮기는 것"으로 정의한다. 고전 CAN 데이터 프레임을 동기화·순서 제어·에러 제어·흐름 제어와 함께 보내는 것이고, 흐름 제어는 일관된 메시지 프레임 형식으로 이룬다.

### OSI 계층으로 본 ISO 11783

![송신 CF는 Priority·PG·SP를 PDU로 묶고, 8바이트 이하는 바로 CEFF 프레임으로, 9바이트 이상은 BAM·TP·ETP를 거쳐 여러 CEFF 프레임으로 보내며, 물리 계층은 ISO 11783-2 신호·부품이고 표현·세션·네트워크 계층은 비어 있는 구조](/images/study-isobus/08-osi-mapping-light.png)
![송신 CF는 Priority·PG·SP를 PDU로 묶고, 8바이트 이하는 바로 CEFF 프레임으로, 9바이트 이상은 BAM·TP·ETP를 거쳐 여러 CEFF 프레임으로 보내며, 물리 계층은 ISO 11783-2 신호·부품이고 표현·세션·네트워크 계층은 비어 있는 구조](/images/study-isobus/08-osi-mapping-dark.png)

Part 3이 OSI 7계층에 맞춰 그린 그림을 다시 그린 것이다. 왼쪽 열은 OSI 층 이름, 가운데는 보내는 CF, 오른쪽은 받는 CF다. 화살표는 데이터가 내려가는(송신) 길과 올라오는(수신) 길이다.

송신 CF는 Priority·PG(Parameter Group, 함께 보내는 값의 묶음)·SP(Suspect Parameter, 값 하나)를 PDU로 묶는다. 8바이트 이하면 PDU가 곧바로 CEFF 프레임 하나가 되고, 9바이트 이상이면 BAM·TP·ETP가 여러 CEFF 프레임으로 나눈다. BAM·TP·ETP는 모두 긴 데이터를 나눠 보내는 방법이다. 표현·세션·네트워크 계층 칸은 이 경로에서 비어 있다. 물리 계층은 ISO 11783-2(ISOBUS의 물리 계층을 정하는 문서)를 따르는 신호와 네트워크 부품이다.

눈여겨볼 점이 하나 있다. 그림은 TP를 전송 계층 칸에 그리지만, Part 3 본문은 TP를 "데이터 링크 계층의 일부로 기술한다"고 적는다. 문서 구성상 데이터 링크 파트에 실려 있을 뿐, 하는 일은 OSI의 전송 계층에 가깝다고 읽으면 된다. 네트워크 계층(NIU, 버스와 버스를 잇는 장치)은 ISO 11783-4가 맡는다([21장](/study/isobus/21-niu-network-layer)).

### Part 3이 J1939 위에 덧붙이거나 못박은 것

J1939-21 원문은 이 스터디의 근거 자료에 없다. 아래 표는 Part 3이 스스로 밝힌 J1939와의 관계, 그리고 Part 3이 명시한 ISO 11783 고유 규칙만 모은 것이다. 표준 문서에서 shall은 반드시 지켜야 하는 요구, should는 권고, may는 허용을 뜻한다.

| 항목 | Part 3의 규정 | 쉽게 말하면 |
|---|---|---|
| TP(BAM, RTS/CTS) | SAE와 조화(harmonized)됨 | 8바이트보다 긴 데이터를 나눠 보내는 방법은 J1939와 같다([15장](/study/isobus/15-tp-bam-cmdt)) |
| ETP(1785바이트 초과) | SAE와 조화되지 않음 | 1785바이트보다 큰 데이터를 보내는 방법은 ISOBUS만의 것이다([17장](/study/isobus/17-etp)) |
| Acknowledgement의 Byte 5 | J1939와의 최대 호환을 위해 PS 필드를 복제 | 확인 응답 메시지가 데이터 안에 받는 주소를 한 번 더 적는다([10장](/study/isobus/10-j1939-request-ack)) |
| CAN 규격과 충돌할 때 | Part 3이 우선 | CAN 규격과 다르면 ISOBUS 규칙을 따른다 |
| 프레임 형식 | CEFF 필수, CBFF는 제조사 독점용 최소 규칙, FD 금지 | 표준 통신은 29비트 ID 프레임만 쓴다. 11비트 ID 프레임(CBFF)은 제조사 전용이고 CAN FD는 금지다([4장](/study/isobus/04-can-data-frame), [7장](/study/isobus/07-can-fd)) |
| EDP | 송신 시 항상 0 | 지금은 쓰지 않는 칸이다(7절) |
| EDP = 1, DP = 1 | ISO 15765-2(DoCAN) 프레임. ISO 11783 정의를 따르지 않음 | 자동차 진단 통신용 프레임이므로 J1939 방식으로 읽지 않는다(7절) |
| 주소 자기 구성(self-configuring) | ISO 11783 컨트롤러는 지원해야 함(shall) | 주소가 겹치면 스스로 다른 주소를 고를 수 있어야 한다 |
| 2018년 4판의 변경 | CAN FD 배제 문구, BAM 패킷 10 ms 간격 허용, Request2 확장 식별자용 Acknowledgement | 최신판에서 바뀐 점이다. Request2는 [11장](/study/isobus/11-j1939-request2-timing)에서 본다 |

주소 자기 구성 필수 조항은 [13장 주소 클레임](/study/isobus/13-j1939-address-claim)의 절차와 이어진다.

## 7. 데이터 페이지와 PGN 공간

4절에서 PGN은 ID의 EDP, DP, PF, PS로 만든 번호라고 했다. 이 절에서는 그 번호가 가질 수 있는 값이 모두 몇 개이고 어떻게 나뉘는지 본다. 이 지도를 알면 PGN 번호만 보고도 그 메시지가 PDU1인지, 제조사 전용인지 짐작할 수 있다.

### EDP·DP 조합

4절의 표는 EDP를 "보통 0", DP를 "PGN 공간을 두 배로 확장"이라고만 적었다. Part 3은 두 비트의 조합을 이렇게 정한다.

| EDP | DP | 의미 |
|---|---|---|
| 0 | 0 | ISO 11783 page 0 PGN |
| 0 | 1 | ISO 11783 page 1 PGN |
| 1 | 0 | ISO 11783 예약 |
| 1 | 1 | ISO 15765-2가 정의하는 프레임 |

page는 PGN 번호표의 쪽수라고 생각하면 된다. 같은 PF·PS 값이라도 DP가 0이면 0쪽, 1이면 1쪽의 다른 메시지다. DP 하나로 번호표가 두 배가 된다. "예약"은 나중에 쓰려고 비워 둔 값이라는 뜻이다.

모든 ISO 11783 메시지는 EDP를 0으로 보내야 한다(shall). 표준은 나중에 EDP를 써서 PDU 형식을 새로 정의하거나 Priority 필드·주소 공간을 넓힐 가능성을 열어 둔다. EDP와 DP가 모두 1이면 ISO 15765-2(DoCAN, CAN 위 진단 통신) 프레임이다. 이 프레임은 식별자의 나머지 비트가 ISO 11783 형식이 아니므로, 수신 측은 여기서 PGN이나 SA를 뽑아내면 안 되고 ISO 15765-2대로 처리해야 한다.

EDP와 DP는 16진수 ID의 맨 앞 두 자리에 들어 있다. 예를 들어 `0x19`로 시작하는 ID는 `0x19` = `0001 1001`이고, 앞 3비트를 버리면 `110 0 1`이다. 즉 Priority 6, EDP 0, DP 1인 page 1 메시지다.

### 8672개의 PGN

PGN은 24비트다. 상위 6비트는 0, 그다음 10비트가 EDP·DP·PF, 마지막 8비트는 PF가 240 미만이면 0, 240 이상이면 PS다. 이 규칙으로 만들 수 있는 PGN은 페이지당 240 + 16 × 256 = 4336개, 두 페이지 합계 8672개다. 2¹⁷ = 131072가지 비트 조합 중 대부분은 PDU1의 DA 자리라서 PGN이 되지 못한다.

계산을 한 단계씩 풀면 다음과 같다.

1. 페이지 하나(DP 값 하나)에서 PF는 8비트이므로 0~255의 256가지다.
2. PF 0~239(240가지)는 PDU1이다. PS가 받는 주소라서 PGN에 들어가지 않으므로 PF 값 하나가 PGN 하나다. 그래서 240개다.
3. PF 240~255(16가지)는 PDU2다. PS도 PGN에 들어가므로 PF 값 하나마다 PS 256가지가 모두 다른 PGN이 된다. 그래서 16 × 256 = 4096개다.
4. 페이지 하나의 PGN은 240 + 4096 = 4336개다.
5. 페이지가 두 개(DP = 0, 1)이므로 4336 × 2 = 8672개다.

EDP를 0으로 고정하면 DP, PF, PS의 17비트로 2¹⁷ = 131072가지 값을 만들 수 있다. 그런데 PDU1에서는 PS 8비트가 주소로 쓰여 PGN 번호를 만들지 못한다. 그래서 실제로 쓸 수 있는 번호는 8672개뿐이다.

## 8. 새 메시지에 PDU 형식과 PGN 고르기 (심화)

::: info 처음 읽는다면
이 절은 직접 구현할 때 필요한 세부다. 처음에는 건너뛰고 장 끝의 핵심 정리로 가도 된다.
:::

새 메시지를 표준에 넣거나 제조사 독점 메시지를 설계할 때는 PDU1을 쓸지 PDU2를 쓸지, PF의 어느 자리를 쓸지 골라야 한다. 이 절은 그 기준을 본다. 표준 PGN이 왜 그 자리에 있는지 이해할 때도 같은 기준을 쓸 수 있다.

### 할당 기준

Part 3은 새 SA와 PGN을 배정하는 기준을 정한다. 대부분은 표준 위원회가 PGN을 배정할 때의 원칙이지만, 제조사 독점 메시지를 설계하거나 표준 PGN이 왜 그 자리에 있는지 이해할 때도 그대로 쓸 수 있다.

- PG는 PDU1과 PDU2 중 하나로만 배정하고, 정한 뒤에는 다른 형식을 쓸 수 없다. 특정 목적지로 보내야 하는 PG는 PDU1을 써야 한다.
- 배정할 때 따지는 특성은 우선순위, 갱신 주기, 다른 CF에게 그 데이터가 얼마나 중요한지, 데이터 길이 네 가지다.
- 목적지가 필요한 PGN은 "여러 특정 CF 중 하나를 직접 제어(명령)하는 파라미터"일 때만 배정한다. 그 밖에는 어느 CF든 데이터에 접근할 수 있도록 목적지 없는 PGN을 고른다(shall).
- 반복 주기가 10 Hz 이상(100 ms 이하)인 메시지는 multi-packet이 허용되지 않는다. multi-packet은 8바이트보다 길어서 여러 프레임으로 나눠 보내는 메시지이고, 10 Hz는 1초에 10번, 즉 100 ms마다 한 번이다.
- 어떤 PGN이든 요청할 수는 있지만, 이미 주기적으로 브로드캐스트되는 메시지를 요청하는 것은 강하게 비권장된다.
- 데이터 필드는 8바이트를 다 쓰도록 관련 파라미터를 묶는다. 데이터 필드를 듬성듬성 쓰는 PG에는 강한 정당화가 필요하다.
- 주소 공간은 256개를 넘을 수 없고, 새 주소 배정은 엔진·변속기·브레이크처럼 대다수 사용자에게 쓸모 있는 기능으로 제한된다.

Part 3은 세 통신 방법(PDU1, PDU2, 제조사 독점 PGN)을 언제 쓰는지 설명하고 판단 순서를 준다. 독점 정보이거나 일반적 관심사가 아니면 독점 방식, 일반적 관심사이고 특정 CF로 보낼 필요가 없으면 PDU2, 일반적 관심사인데 이 CF 또는 저 CF로 골라 보내야 하면 PDU1이다. 예로 드는 것은 엔진이 여럿인 차량의 토크 제어 메시지다. 원하는 엔진에만 보내야 하므로 목적지 지정 PG가 필요하다.

1. 일반적 관심사가 아니면(제조사만 쓰는 정보면) 왼쪽으로 가서 독점 메시지를 고른다. 목적지가 필요하면 Proprietary A·A2(PF 239, PS = DA), 아니면 Proprietary B(PF 255)다.

3. 마지막으로 주기가 100 ms 이하이면 구간 앞쪽(multi-packet 불가), 아니면 뒤쪽(multi-packet 허용)에서 번호를 받는다.

PF 값 안에서도 자리가 정해져 있다.

## 9. 버스 대역폭을 계산해 보기 (심화)

::: info 처음 읽는다면
이 절은 직접 구현할 때 필요한 세부다. 처음에는 건너뛰고 장 끝의 핵심 정리로 가도 된다.
:::

버스는 여러 장치가 함께 쓰는 길 하나다. 메시지를 너무 많이 보내면 길이 막혀 중요한 메시지가 늦어진다. 이 절에서는 메시지 목록으로 버스가 얼마나 차는지 계산하는 법을 본다. 버스 부하(bus load)는 1초 가운데 버스가 프레임을 나르느라 바쁜 시간의 비율(%)이다.

Part 3은 참고 부록에서 ISO 11783 같은 개방형 시스템은 메시지 수요가 네트워크 용량을 넘을 수 있다고 경고한다. 개방형 시스템은 여러 제조사의 장치가 섞여 붙는 네트워크라는 뜻이다. 손잡이는 세 가지다.

- 제조사 독점 PG와 CBFF 통신의 사용 제한
- 주기 메시지의 주기를 실용적인 한도에서 최대한 느리게
- PG의 기본 Priority. 주기가 짧은 메시지일수록 높은 우선순위(작은 숫자)를 권한다. 10~20 ms 주기는 1, 20~50 ms는 2, 50~100 ms는 3, 100~200 ms는 4, 200~400 ms는 5, 그보다 느린 메시지는 6, TP·ETP의 데이터 프레임은 7이다(권장표 전체는 [5장 CAN 중재와 우선순위](/study/isobus/05-can-arbitration) 참고).

강력 권고 사항은 두 가지다. 정상 운용 중 Proprietary A·A2·B의 합은 네트워크 용량의 2%를 넘지 않게 한다. Part 3의 다른 곳은 같은 권고를 "CF당" 합계로 적는다. 그리고 CBFF 트래픽은 서브넷(따로 떨어진 작은 네트워크)으로 분리한다.

### 계산의 전제

| 전제 | 값 | 어디서 온 값인가 |
|---|---|---|
| 비트레이트 | 250 kbit/s | [CAN 물리 계층](/study/isobus/03-can-physical) 챕터의 ISOBUS 표준 속도. 1초에 250000비트를 보낸다 |
| 프레임 하나의 길이 | 150비트 | Part 3 그림이 적은 CEFF 최대 길이(비트 스터핑 포함). 데이터 8바이트를 꽉 채우고 스터핑 비트가 가장 많이 들어간 경우다. 비트 스터핑은 [4장](/study/isobus/04-can-data-frame)에서 봤다 |
| 버스 부하 | 초당 프레임 수 × 150 ÷ 250000 | 프레임 사이 간격은 무시한 근사 |

이 전제로 2% 예산은 초당 5000비트, 프레임으로는 초당 약 33개다. 계산을 풀면 다음과 같다.

1. 250 kbit/s의 2%는 250000 × 0.02 = 5000비트다. 1초 동안 독점 메시지로 쓸 수 있는 비트가 5000개라는 뜻이다.
2. 프레임 하나가 150비트이므로 5000 ÷ 150 ≈ 33.3, 즉 초당 약 33개 프레임이다.

### 예제: 분무기 ECU의 메시지 설계 검토

분무기(약제를 뿌리는 작업기) ECU 하나가 다음 메시지를 내보내도록 설계됐다고 하자(예시 값).

| 메시지 | 주기 | 초당 프레임 |
|---|---|---|
| 표준 PGN 3개 | 각 100 ms | 30 |
| Proprietary B 2개 (자체 섹션 제어기용) | 각 20 ms | 100 |
| Proprietary A 1개 | 50 ms | 20 |

"초당 프레임" 열은 주기에서 바로 나온다. 1초는 1000 ms이므로 100 ms 주기 메시지는 1000 ÷ 100 = 10번, 20 ms 주기는 50번, 50 ms 주기는 20번 나간다. 메시지가 여러 개면 개수만큼 곱한다. 표준 PGN 3개는 10 × 3 = 30, Proprietary B 2개는 50 × 2 = 100이다.

- 표준 메시지: 30 × 150 = 4500 bit/s, 버스의 1.8%
- 독점 메시지: 120 × 150 = 18000 bit/s, 버스의 <strong>7.2%</strong>로 2% 권고의 3.6배

독점 메시지의 120은 Proprietary B의 100과 Proprietary A의 20을 더한 값이다. 백분율은 비트 수를 250000으로 나눠 구한다. 4500 ÷ 250000 = 0.018(1.8%), 18000 ÷ 250000 = 0.072(7.2%)이고, 7.2 ÷ 2 = 3.6배다.

고치는 방법은 앞에서 본 손잡이 그대로다. Proprietary B를 100 ms, Proprietary A를 200 ms로 늦추면 독점 메시지는 초당 25프레임(Proprietary B 10 × 2 + Proprietary A 5), 1.5%가 된다(25 × 150 = 3750 bit/s). 20 ms 제어 루프가 꼭 필요하다면 그 트래픽은 작업기 내부 네트워크로 옮겨 NIU 뒤에 두는 설계가 표준의 권고 취지에 맞는다(추론). NIU(Network Interconnect Unit)는 버스와 버스를 잇는 장치로, 작업기 안쪽 버스의 메시지가 트랙터 쪽 버스로 넘어오지 않게 거를 수 있다([21장](/study/isobus/21-niu-network-layer)).

### TP 전송의 부하

TP도 같은 방식으로 계산할 수 있다. TP(Transport Protocol)는 8바이트보다 긴 데이터를 7바이트씩 잘라 여러 프레임으로 보내는 방법이다. 모두에게 보내는 BAM 방식은 받는 쪽의 허락 없이 조각 프레임(TP.DT)을 일정 간격으로 보낸다([15장](/study/isobus/15-tp-bam-cmdt)).

1785바이트를 BAM으로 보내면 TP.DT가 255개다. BAM 패킷 간격은 10~200 ms이므로, 가장 빠르게 보내면 2.55 s 동안 초당 100프레임, 즉 버스의 6%를 쓴다. 가장 느리면 51 s가 걸린다.

1. 조각 수: 1785 ÷ 7 = 255개다.
2. 가장 빠를 때: 10 ms마다 하나이므로 초당 100프레임이다. 255개를 보내는 데 255 × 10 ms = 2.55 s가 걸리고, 그동안 부하는 100 × 150 ÷ 250000 = 6%다.
3. 가장 느릴 때: 200 ms마다 하나이므로 255 × 200 ms = 51 s가 걸린다.

특정 목적지 RTS/CTS 전송은 패킷 간 최소 간격이 없어 순간 부하가 훨씬 커질 수 있다. RTS/CTS는 받는 쪽이 "몇 개 보내라(CTS)"고 허락하면서 받는 방식이다. CTS 하나에 허용하는 패킷 수와 TP 데이터의 Priority 7이 다른 메시지와 버스를 나눠 쓰는 장치가 되는 이유다(추론). 흐름 제어의 세부는 [15장](/study/isobus/15-tp-bam-cmdt)과 [16장](/study/isobus/16-tp-connection-rules)에서 본다.

아래 코드는 이 장의 숫자(PGN 개수, EDP·DP 판별, 버스 부하)를 파이썬으로 다시 계산해 확인한다. `assert` 줄은 값이 틀리면 멈추므로, 끝까지 실행되면 계산이 모두 맞다는 뜻이다.

::: details 파이썬으로 검산: PGN 개수, EDP·DP 판별, 버스 부하
```python
from collections import Counter

# 1) 5.1.3 규칙으로 만들 수 있는 PGN 전부 세기 (EDP = 0, 5.2.3)
pgns = set()
for dp in (0, 1):
    for pf in range(256):
        for ps in range(256):
            pgns.add((dp << 16) | (pf << 8) | (ps if pf >= 240 else 0))
assert len(pgns) == 8672


def region(pgn):
    dp, pf = (pgn >> 16) & 1, (pgn >> 8) & 0xFF
    if pf < 239:
        return f"p{dp} PDU1"
    if pf == 239:
        return f"p{dp} PF239"
    return f"p{dp} PDU2" if pf < 255 else f"p{dp} PF255"


cnt = Counter(region(p) for p in pgns)
assert cnt["p0 PDU1"] == cnt["p1 PDU1"] == 239
assert cnt["p0 PF239"] == cnt["p1 PF239"] == 1
assert cnt["p0 PDU2"] == cnt["p1 PDU2"] == 3840
assert cnt["p0 PF255"] == cnt["p1 PF255"] == 256


# 2) EDP·DP로 프레임 종류 판별 (Table 3)
def classify(can_id):
    edp, dp = (can_id >> 25) & 1, (can_id >> 24) & 1
    return {(0, 0): "ISO 11783 page 0", (0, 1): "ISO 11783 page 1",
            (1, 0): "ISO 11783 reserved", (1, 1): "ISO 15765-2"}[(edp, dp)]


assert classify(0x18FEEE00) == "ISO 11783 page 0"
assert classify(0x19EF8180) == "ISO 11783 page 1"
assert classify(0x1BFE1234) == "ISO 15765-2"

# 3) 버스 부하 (가정: 250 kbit/s, 프레임당 150비트)
BITRATE, FRAME_BITS = 250_000, 150
load = lambda fps: fps * FRAME_BITS / BITRATE * 100      # %
fps = lambda periods_ms: sum(1000 / ms for ms in periods_ms)

assert round(load(fps([100, 100, 100])), 2) == 1.8        # 표준 PGN 3개
assert round(load(fps([20, 20, 50])), 2) == 7.2           # 독점 메시지 (원안)
assert round(load(fps([100, 100, 200])), 2) == 1.5        # 독점 메시지 (개선안)
assert -(-1785 // 7) == 255 and load(100) == 6.0          # 1785바이트 BAM, 10 ms 간격
print("2% 예산 =", 0.02 * BITRATE / FRAME_BITS, "프레임/s")
```

마지막 줄은 `2% 예산 = 33.333333333333336 프레임/s`를 출력한다. 코드 주석에 나오는 조항·표 번호는 ISO 11783-3 원문의 위치를 적어 둔 것이라 몰라도 코드를 읽는 데 지장이 없다.
:::

::: details 원문을 가진 독자를 위한 메모
- 250 kbit/s는 ISO 11783-2 소관이라 이 스터디의 원문 묶음으로는 확인하지 못했다. 3장의 값을 썼다.
- 150비트는 ISO 11783-3 Figure 1이 적은 CEFF 최대 길이(비트 스터핑 포함)다.
- 독점 메시지 2% 권고는 Annex D(Proprietary A·A2·B의 합)와 5.4.6.1(CF당 합계)에 있다. 주기별 권장 Priority는 Annex D의 Table D.1이다.
- BAM 패킷 간격 10~200 ms는 5.10.2.4와 5.13.3, 특정 목적지 전송의 패킷 간격 0~200 ms는 5.13.3에 있다.
:::

<small>근거: ISO 11783-3 5.4.6.1, 5.10.2.4, 5.13.3, Annex D, Figure 1</small>

::: tip 핵심 정리
- CAN은 프레임을 실어 나르는 일만 한다. 메시지의 뜻, 보낸 장치의 주소, 긴 데이터를 나눠 보내는 규칙은 상위 프로토콜인 J1939가 정하고, ISOBUS는 J1939를 바탕으로 만들어졌다.
- J1939는 29비트 ID를 Priority(3) + EDP(1) + DP(1) + PF(8) + PS(8) + SA(8)로 나눈다. PF가 240 미만이면 PS는 받는 주소(PDU1), 240 이상이면 메시지 종류의 일부(PDU2)다.
- PGN은 ID에서 Priority와 SA(PDU1이면 받는 주소도)를 떼어 낸 메시지 종류 번호이고, 두 페이지 합계 8672개다.
- ISOBUS의 데이터 링크 규칙(ISO 11783-3)은 J1939와 공동 개발됐다. TP는 J1939와 같고 ETP는 ISOBUS만의 것이다. EDP는 항상 0으로 보내고, EDP = 1·DP = 1인 프레임은 ISO 15765-2 프레임이므로 PGN으로 해석하지 않는다.
- (심화) 목적지가 필요한 PGN은 특정 CF를 직접 명령할 때만 쓰고, 100 ms 이하 주기 메시지는 multi-packet을 쓰지 않는다. 제조사 독점 메시지는 버스 용량의 2% 이하로 유지하고, CBFF는 서브넷으로 분리한다.
:::

::: details 확인 문제
1. (개념) CAN 규격만으로는 해결되지 않아 J1939가 더하는 기능 세 가지를 들어라.
2. (읽기) ID `0x0CF00400`을 Priority, EDP, DP, PF, PS, SA로 나누고, PDU1인지 PDU2인지 말하라.
3. (개념) 보내는 이(SA) 칸에 `0xFE`가 들어 있는 프레임은 어떤 장치가 보낸 것인가? 받는 이(DA) 칸의 `0xFF`는 무슨 뜻인가?
4. (판별형) 수신한 ID `0x1BFE1234`와 `0x19EF8180`의 EDP·DP를 읽고, 각각 어떻게 처리해야 하는지 말하라.
5. (설계형, 심화) 작업기의 섹션 상태 6바이트를 300 ms 주기로 여러 장치가 읽을 수 있게 내보내려 한다. PDU 형식, PF 구간, multi-packet 허용 여부, 주기별 권장 Priority를 고르라.
6. (계산형, 심화) 한 CF가 Proprietary B 메시지 4개를 각각 50 ms 주기로 보낸다. 250 kbit/s, 프레임당 150비트로 가정하면 2% 권고를 지키는가?

**답 가이드**
1. 메시지의 뜻을 정하는 번호(PGN, SPN), 장치 주소 관리(SA, DA와 주소 클레임), 8바이트보다 긴 데이터를 나눠 보내는 규칙(Transport Protocol), 진단·장치 찾기 같은 네트워크 관리, 타임아웃과 재전송 규칙 가운데 세 가지를 들면 된다.
2. 맨 앞 `0x0C` = `0000 1100`에서 앞 3비트를 버리면 `011 0 0`이므로 Priority 3, EDP 0, DP 0이다. 나머지는 두 자리씩 끊어 PF `0xF0`(240), PS `0x04`, SA `0x00`이다. PF가 240 이상이므로 PDU2이고, PS `0x04`는 받는 주소가 아니라 Group Extension이다.
3. `0xFE`(254)는 Null Address로, 아직 주소를 얻지 못한 장치가 보낸 프레임이다. DA 칸의 `0xFF`(255)는 Global, 즉 버스의 모든 장치에게 보낸다는 뜻이다.
4. `0x1BFE1234`는 맨 앞 `0x1B` = `0001 1011`이므로 EDP = 1, DP = 1이고 ISO 15765-2 프레임이다. PGN·SA로 해석하지 말고 ISO 15765-2 처리기로 넘긴다. `0x19EF8180`은 EDP = 0, DP = 1인 page 1 PGN이고, PF `0xEF`(239)이므로 Proprietary A2(126720), DA `0x81`, SA `0x80`이다.
5. 여러 장치가 읽고 특정 CF를 명령하는 메시지가 아니므로 PDU2다. 100 ms 초과이므로 PF 254(GE 255)부터 감소하는 구간이고, 이 구간은 multi-packet이 허용되지만 6바이트라 필요 없다. 200~400 ms 주기이므로 권장 Priority는 5다.
6. 4 × 20 = 초당 80프레임, 80 × 150 = 12000 bit/s로 버스의 4.8%다. 2% 권고를 넘으므로 주기를 늦추거나 메시지를 묶거나 서브넷으로 옮겨야 한다.
:::
