CH3. Control Function과 NAME

학습 목표

  • 주소만으로 장치를 식별하면 안 되는 이유를 설명할 수 있다
  • Control Function이 무엇이고 NAME과 어떤 관계인지 안다
  • 64비트 NAME을 구성하는 9가지 요소가 각각 무엇을 의미하는지 구분한다
  • 주소 클레임이 NAME과 주소를 어떻게 묶는지 이해한다

주소만으로는 부족하다

앞 챕터에서 1바이트 주소를 살펴봤다. 그런데 현실적으로 주소는 CAN 프레임을 채우거나 해석하는 것 말고는 거의 쓸모가 없다.

주소는 그 장치에 대해 아무것도 말해 주지 않는다.

  • 그 장치의 정체가 무엇인지
  • 무슨 일을 하는 장치인지
  • 누가 만들었는지
  • 심지어 내가 말을 걸어도 되는 상대인지

게다가 메시지를 보내는 수단으로도 신뢰할 수 없다. J1939와 ISOBUS 장치는 언제든 주소를 바꿀 수 있기 때문이다. 어제 0x26이었던 살포기가 오늘도 0x26이라는 보장이 없다.

Control Function

그래서 J1939와 ISO 11783은 CAN 네트워크의 기본 구성 단위를 Control Function(제어 기능, 줄여서 CF)으로 정의한다.

Control Function의 정의

Control Function은 주소를 갖지만, 무엇보다 먼저 NAME으로 식별된다. 그리고 그 주소는 주소 클레임과 중재라는 과정을 통해 언제든 바뀔 수 있다.

AgIsoStack++에서 이 개념은 그대로 클래스 이름이 된다. 내 장치를 나타내는 InternalControlFunction, 상대 장치를 나타내는 PartneredControlFunction 같은 타입들이 전부 이 정의를 따른다. 애플리케이션은 주소 값이 아니라 Control Function 객체를 붙잡고 통신하고, 그 뒤에서 주소가 바뀌는 것은 스택이 알아서 따라간다.

NAME

NAME은 네트워크 상에서 Control Function을 유일하게 식별하는 64비트 값이다. 주소가 임시 번호라면 NAME은 주민등록번호에 가깝다.

NAME은 다음 요소들로 구성된다.

Identity Number

보통 Control Function의 일련번호다. NAME의 나머지 값이 전부 같은 Control Function들 사이에서 서로 구별되도록 유일한 값이어야 한다.

같은 모델 트랙터 두 대가 같은 버스에 붙는 상황을 생각하면 이해가 쉽다. 제조사도 기능도 장치 종류도 같으니, 결국 이 값으로 갈린다.

Manufacturer Code

누가 이 Control Function을 만들었는지를 식별한다. 값은 임의로 정하는 게 아니라 등록된 목록에서 가져온다.

  • 제조사 코드 목록: https://www.isobus.net/isobus/manufacturerCode

ECU Instance

비슷한 NAME을 가진 Control Function들 사이에서 NAME 순서대로 증가하는 값이다. 이름이 비슷한 장치가 여러 개 있을 때, ISO NAME 안에서 서열을 세우는 데 쓴다.

Function

이 Control Function이 무슨 일을 하는지를 나타낸다. ISO 11783은 여기에 들어갈 수 있는 기능 목록을 정의해 두었고, 그 종류가 상당히 많다.

  • 기능 목록: https://www.isobus.net/isobus/nameFunction

Function Instance

해당 ECU의 기능 인스턴스다. Virtual Terminal 번호와 비슷한 개념이라고 보면 된다. 같은 기능을 하는 장치가 여럿일 때 몇 번째인지를 나타낸다.

Device Class

J1939에서 "vehicle system"이라고 부르던 것과 같다. "Sprayers(살포기)"나 "Backhoe(백호)"처럼 ECU의 일반적인 종류를 나타낸다.

Device Class Instance

이 장치 종류의 인스턴스 번호다. ECU Instance와 비슷하게, 필요할 때 비슷한 NAME들 사이의 서열을 세우는 데 쓴다.

Industry Group

이 ECU가 속한 산업 그룹이다. "agricultural(농업)" 같은 값이 들어간다.

  • 참고: https://www.isobus.net/isobus/nameFunction

Arbitrary Address Capability

이 ECU가 주소 중재(address arbitration)를 지원하는지를 나타낸다. 1비트짜리 플래그다.

이 값이 참이면, 원하던 주소를 다른 장치에 뺏겼을 때 다른 주소를 찾아 다시 시도할 수 있다. 거짓이면 정해진 주소를 쓰지 못할 경우 통신을 포기하게 된다.

Address Claiming

J1939와 ISOBUS는 address claiming(주소 클레임)이라는 과정을 정의한다. 이 과정은 Control Function의 NAME을 기준으로 매우 결정론적으로 주소를 할당한다.

라이브러리가 이 과정을 전부 대신 처리해 준다. 그래도 이 과정이 존재한다는 사실은 알아 둘 필요가 있다. NAME을 주소에 묶어 주는 것이 바로 이 과정이기 때문이다.

실제 코드에서 애플리케이션이 하는 일은 NAME 필드를 채워 넣고 희망 주소를 하나 지정하는 것까지다. 그 뒤로 클레임 메시지를 언제 보내고, 충돌이 나면 어떻게 재시도하고, 상대 장치의 주소 변화를 어떻게 추적할지는 스택의 몫이다.

관련 스터디

주소 클레임 메시지의 실제 형식과 중재 규칙, 그리고 Cannot Claim Address 같은 예외 흐름은 ISOBUS CH10. J1939 주소 체계와 CH14. ISOBUS 네트워크 관리에서 다룬다.

정리

지금까지의 관계를 한 줄로 이으면 이렇게 된다.

  1. Control Function은 NAME에 의해 영구적으로 식별된다.
  2. 이 NAME은 주소 클레임 과정에서 Control Function에 주소를 할당하는 데 쓰인다.
  3. 이 주소는 영구적이지 않으며, 어떤 이유로든 주소 클레임이 다시 일어나면 언제든 바뀔 수 있다.

여기까지 이해했다면 첫 Control Function을 만들어 기본 메시지를 보내 볼 준비가 된 것이다. 바로 실습으로 넘어가고 싶다면 CH7. ISOBUS Hello World로 건너뛰어도 되고, 개념을 더 쌓고 싶다면 다음 챕터로 계속 읽으면 된다.

핵심 정리

  • 주소는 프레임을 채우고 해석하는 용도 외에는 쓸모가 없다. 장치의 정체·기능·제조사를 알려 주지 않고, 언제든 바뀔 수 있다.
  • 그래서 J1939와 ISO 11783은 네트워크의 기본 단위를 Control Function으로 정의하고, NAME으로 식별한다.
  • NAME은 64비트이며 Identity Number, Manufacturer Code, ECU Instance, Function, Function Instance, Device Class, Device Class Instance, Industry Group, Arbitrary Address Capability로 구성된다.
  • 주소 클레임은 NAME을 기준으로 결정론적으로 주소를 할당하며, 라이브러리가 전 과정을 자동 처리한다.
