CH1. 안드로이드 아키텍처와 진화

학습 목표

  • 안드로이드가 "리눅스 배포판"과 어떻게 다른지, 커널은 공유하되 유저랜드 전체가 왜 갈렸는지 설명할 수 있다.
  • Cupcake부터 Android 16까지의 흐름에서 Treble·APEX·GKI 같은 구조 전환점이 무엇을 바꿨는지 안다.
  • 실제 기기의 시스템 이미지가 AOSP·external·커널·vendor·ODM·carrier 레이어의 합성물임을 이해한다.
  • Applications부터 Linux Kernel까지 이어지는 소프트웨어 스택의 각 층 역할과 경계를 파악한다.
  • HAL의 진화(Traditional → Treble)와 커널 Androidism의 존재 이유를 개괄하고, 상세 주제가 어느 챕터로 이어지는지 안다.
  • AOSP에 GMS가 없다는 사실과 그 전략적 함의, 그리고 "수정이 아니라 증축"이라는 커스텀 원칙을 이해한다.

안드로이드 버전 변천

안드로이드의 역사를 버전 번호와 디저트 코드네임만으로 외우는 건 의미가 없다. 중요한 건 어느 버전에서 OS 구조 자체가 바뀌었는가다. AOSP를 커스텀하는 입장에서는 "우리가 타겟하는 버전이 Treble 이후인가, GKI를 쓰는가, APEX 모듈로 뭐가 빠졌는가"가 실무를 좌우한다. 아래 표는 그 구조 전환점을 중심으로 정리한 것이다.

버전코드네임API level구조적 전환점
1.5Cupcake3코드네임 시작, 위젯·소프트 키보드
2.3Gingerbread9NDK 본격화, 네이티브 액티비티
4.0Ice Cream Sandwich14폰·태블릿 UI 통합
4.4KitKat19ART 런타임 실험적 도입(Dalvik과 선택)
5.0Lollipop21ART가 기본 런타임으로, 64비트 지원, SELinux enforcing 전면화
6.0Marshmallow23런타임 권한, Doze 전원 관리
7.0Nougat24seccomp 필터, 파일 기반 암호화(FBE) 도입
8.0Oreo26Project Treble — HAL을 binderized하고 /vendor 분리
9Pie28동적 파티션 준비, 백그라운드 제한 강화
10Q29APEX 모듈, 동적 파티션, scoped storage
11R30GKI(Generic Kernel Image) 본격화, 벤더 모듈 분리
12S31Material You, apexd 확대
13T33리소스·언어별 앱 설정, 사진 선택기
14U3416KB 페이지 크기 준비, 헬스 커넥트
15V3516KB 페이지 정식, 부분 화면 공유
16Baklava36최신 기준 — 데스크톱 모드·적응형 UI 강화

전환점만 뽑으면 세 개의 큰 분기가 보인다. Lollipop(5.0)에서 Dalvik이 ART로 넘어가며 런타임이 바뀌었고, Oreo(8.0)의 Treble에서 프레임워크와 벤더 구현이 분리됐으며, Q(10)~R(11)에서 APEX와 GKI로 OS 구성요소를 부품처럼 갈아 끼우는 모듈화가 자리 잡았다. 이 세 가지는 뒤 챕터에서 각각 ART, HAL·서비스, APEX·스토리지로 깊게 다룬다.

이 세 전환점이 왜 임베디드 커스텀에 직접 영향을 주는가를 한 줄로 요약하면 이렇다. Treble 이전(8.0 미만)을 타깃하면 프레임워크를 손댈 때마다 벤더 구현까지 통째로 다시 빌드해야 하고, GKI 이전(11 미만)을 타깃하면 SoC 벤더가 커널을 통째로 포크해줘야 한다. 반대로 Treble·GKI 이후를 타깃하면 우리가 건드릴 계층(/vendor, 커널 모듈, Device Tree)이 명확히 분리돼 유지보수가 수월해진다. 그래서 새 프로젝트라면 되도록 Android 11 이상, GKI 지원 SoC를 고르는 것이 정석이다.

기기에 올라간 버전 정보는 프로퍼티로 즉시 확인할 수 있다. 커스텀 이미지를 구울 때 이 값들을 우리가 채워 넣는다.

adb shell getprop ro.build.version.release   # 사용자용 버전 (예: 14)
adb shell getprop ro.build.version.sdk       # API level (예: 34)
adb shell getprop ro.product.device          # 디바이스 코드명 (lunch 타깃)
adb shell getprop ro.treble.enabled          # Treble 여부 (true/false)

API level과 버전의 관계

사용자에게 보이는 마케팅 버전(예: "Android 14")과 개발자가 코드에서 쓰는 API level(예: 34)은 별개다. AOSP 소스, AndroidManifest.xml의 minSdkVersion·targetSdkVersion, ro.build.version.sdk 프로퍼티는 모두 API level(정수)을 쓴다. 커스텀 OS를 만들 때 호환성 판단의 기준도 버전 이름이 아니라 API level이다.

Android vs Linux

안드로이드는 리눅스 커널 위에서 돈다. 그래서 "안드로이드는 리눅스다"라고 뭉뚱그리기 쉽지만, 시스템 프로그래밍 관점에서 보면 커널만 공유하고 유저랜드는 통째로 다른 OS다. 데스크톱 리눅스 배포판(Ubuntu, Fedora 등)의 상식을 그대로 들고 오면 곳곳에서 어긋난다.

핵심 컴포넌트가 어떻게 갈렸는지 대응시켜 보면 차이가 분명해진다.

역할데스크톱 리눅스안드로이드
C 표준 라이브러리glibcBionic (libc/libm/linker)
init 시스템systemd / SysV initinit (.rc 언어 기반)
디스플레이 서버X11 / WaylandSurfaceFlinger + Gralloc
IPCD-Bus, System V IPCBinder
패키지dpkg/rpm, /usr 계층APK + PackageManager
오디오PulseAudio / PipeWireAudioFlinger
로깅syslog / journaldlogd / logcat

공통점은 명확하다. 리눅스 커널의 프로세스·스레드 모델, 가상 메모리, VFS·파일시스템, 네트워크 스택, cgroup·namespace 같은 커널 기능은 그대로 쓴다. fork·exec·mmap·epoll 같은 시스템 콜은 안드로이드에서도 동일하게 동작하고, 이 커널 렌즈로 앱 프로세스를 다시 보는 관점은 CH11에서 다룬다.

차이도 분명하다. glibc가 아니라 Bionic이라는 점이 네이티브 개발에서 가장 먼저 부딪히는 벽이다. Bionic은 모바일을 위해 작고 빠르게 새로 쓴 libc로, 라이선스(glibc의 LGPL을 피하려 BSD 계열)와 크기·성능을 위해 갈아 끼운 것이다. 이 선택은 세 종류의 결과를 낳는다.

  • 누락 — 초기 Bionic은 System V IPC(shmget·semget 등)를 아예 지원하지 않았다. 대신 안드로이드는 ashmem·Binder 같은 자체 IPC를 쓴다. 완전한 로케일, 일부 POSIX 기능도 축소돼 있다.
  • 추가 — 리눅스 libc에 없는 안드로이드 고유 기능이 Bionic에 들어 있다. 시스템 전역 설정을 담는 프로퍼티 시스템(__system_property_get), 안드로이드 로깅(__android_log_print)이 대표적이다.
  • 포팅 이슈 — 데스크톱 리눅스용 C/C++ 라이브러리를 그대로 가져오면 System V IPC 부재, 헤더 차이, 심벌 누락으로 컴파일·링크가 깨지기 쉽다. AgIsoStack++ 같은 네이티브 스택을 안드로이드로 옮길 때 이 지점을 반드시 만난다. Bionic의 자세한 내부와 NDK 포팅은 CH15에서 다룬다.

이 차이는 추상적인 얘기가 아니라 첫 빌드에서 바로 부딪힌다. 예컨대 데스크톱 리눅스에서 흔한 아래 코드는 안드로이드에서 링크가 깨진다.

#include <sys/shm.h>          // System V 공유 메모리 — Bionic에 없다
int id = shmget(key, size, IPC_CREAT | 0666);   // undefined reference

같은 목적을 안드로이드에서는 ashmem/memfd나 Binder로 풀어야 한다. 반대로 안드로이드에만 있는 기능도 있다.

#include <sys/system_properties.h>
char value[PROP_VALUE_MAX];
__system_property_get("ro.build.version.sdk", value);   // 리눅스 libc엔 없음

#include <android/log.h>
__android_log_print(ANDROID_LOG_INFO, "agcand", "started");   // logcat으로 감

정리하면, 안드로이드는 "리눅스 커널을 심장으로 쓰되, 심장 위의 장기 전체를 모바일·임베디드용으로 새로 이식한 OS"다. 커널 지식은 통하지만 유저랜드 지식은 다시 배워야 한다.

안드로이드 코드의 출처

실제 기기에 올라간 시스템 이미지는 구글 한 곳이 만든 물건이 아니다. 여러 조직이 각자의 레이어를 얹어 합성한 결과물이다. 커스텀 OS를 만들 때 "이 코드는 어디서 왔고, 내가 고칠 수 있는가"를 판단하려면 이 출처 구분이 필수다.

  • AOSP — 구글이 오픈소스로 공개하는 안드로이드의 뼈대다. 코어 프레임워크(system_server, PackageManager 등), ART 런타임, init, Bionic이 여기 들어 있다. source.android.com에서 소스를 받는다. 우리가 가장 많이 읽고 참조하는 계층이다.
  • AOSP external/ — AOSP 트리 안의 external/ 디렉토리에 담긴 서드파티 오픈소스다. libc++, BoringSSL, zlib, FreeType 같은 upstream 프로젝트를 안드로이드 빌드에 맞게 포함시킨 것으로, 구글이 새로 쓴 게 아니라 외부 프로젝트를 가져온 것이다.
  • Linux Kernel — 커널 자체는 kernel.org의 mainline을 기반으로 하되, 안드로이드용 패치(뒤에서 다룰 Androidism)가 얹힌다. Android 11부터는 GKI로 "공통 커널 + 벤더 모듈" 구조가 표준이 됐다.
  • Platform / BSP (vendor) — SoC 벤더(Qualcomm, MediaTek 등)가 제공하는 BSP(Board Support Package)다. HAL 구현, 드라이버, 펌웨어 blob이 여기 있다. 상당수가 바이너리 blob이라 소스가 없고, /vendor 파티션에 들어간다. 임베디드 커스텀에서 가장 자주 부딪히고 가장 손대기 어려운 계층이다.
  • ODM — 실제 보드를 만드는 제조사(ODM/OEM)의 튜닝이다. 센서·카메라 캘리브레이션, 보드별 Device Tree, 전원 프로파일 같은 하드웨어 밀착 설정이 들어간다.
  • Carrier — 통신사가 얹는 커스터마이징으로, 사전 탑재 앱·네트워크 설정 등이다. 임베디드 장비에서는 대개 해당 없음이지만, 셀룰러 모뎀을 쓰는 기기라면 일부 관련된다.

이 레이어 구분이 실무에서 중요한 이유는 수정 가능성과 유지보수 부담이 레이어마다 다르기 때문이다. AOSP·external은 소스가 있어 직접 고칠 수 있지만 upstream과의 rebase 부담이 있고, vendor blob은 소스가 없어 벤더에 의존해야 하며, Device Tree 같은 ODM 계층은 우리가 보드에 맞춰 직접 작성한다. 각 파티션이 어떤 레이어에 대응하는지는 CH3·CH4에서, 이 코드를 실제로 빌드해 이미지로 굽는 과정은 CH14에서 이어진다.

아키텍처 조감

안드로이드 소프트웨어 스택은 위에서 아래로 여러 층이 쌓인 구조다. 앱에서 발생한 요청이 프레임워크·런타임·네이티브·커널을 거쳐 하드웨어에 도달하기까지, 각 층이 무슨 일을 하는지 조감하면 이후 챕터의 세부 주제들이 어디에 위치하는지 지도가 그려진다.

  • Applications — 사용자가 보는 앱이다. 홈·다이얼러 같은 시스템 앱과 서드파티 앱이 모두 APK로 배포되고, 각자 독립된 프로세스와 UID로 격리돼 실행된다. 앱의 내부 해부는 CH18에서 다룬다.
  • Java / System Framework — 안드로이드 API의 몸통이다. system_server 프로세스 안에서 ActivityManager, PackageManager, WindowManager 등 수십 개의 시스템 서비스가 돌며, 앱은 이들과 Binder로 통신한다. services.jar·framework.jar에 담겨 있다.
  • ART 런타임 — 앱과 프레임워크의 자바/코틀린 코드는 DEX 바이트코드로 컴파일돼 ART 위에서 돈다. AOT·JIT를 조합해 실행하며, Lollipop 이전의 Dalvik을 대체했다. AOT 컴파일(dex2oat)과 GC 등 내부는 CH19·CH20에서 다룬다.
  • JNI — 자바 세계와 네이티브(C/C++) 세계를 잇는 경계다. 프레임워크의 상당수 기능이 실제로는 JNI를 통해 네이티브 구현을 호출한다. 우리가 네이티브 데몬을 자바 서비스와 연결할 때도 이 경계를 넘는다.
  • Native 라이브러리 · 데몬 — SurfaceFlinger(디스플레이 합성), media 서버, libutils 같은 C/C++ 라이브러리와 각종 네이티브 데몬이 여기 산다. 우리가 올리려는 CAN 통신 데몬 같은 커스텀 네이티브 서비스도 이 층에 자리 잡는다.
  • Bionic — 위의 모든 네이티브 코드가 딛고 서는 C 표준 라이브러리다. 앞서 봤듯 glibc가 아니라 안드로이드 전용이며, 프로퍼티·로깅 같은 안드로이드 고유 기능의 통로이기도 하다.
  • HAL — Hardware Abstraction Layer. 프레임워크가 하드웨어를 다룰 때 벤더 구현을 감추는 추상화 계층이다. Treble 이후로는 Binder 기반(HIDL→AIDL HAL)으로 /vendor에 분리돼 있다. 바로 다음 절의 주제다.
  • Linux Kernel — 스택의 바닥이자 유일한 커널 공간 계층이다. 드라이버, 스케줄러, 메모리 관리에 더해 안드로이드 고유의 커널 확장(Binder 드라이버, ashmem, ION 등)이 들어 있다.

여기서 유저스페이스와 커널의 경계가 HAL과 Kernel 사이에 그어진다는 점이 중요하다. HAL은 유저스페이스에서 도는 벤더 코드이고, 그 아래 실제 드라이버가 커널에 있다. 이 경계 덕분에 벤더는 커널 드라이버는 그대로 두고 HAL만 교체하는 식의 유연성을 얻는다.

이 층들이 실제로 어떻게 이어지는지 한 가지 경로로 따라가 보자. 앱이 화면 밝기를 바꾸는 간단한 동작조차 스택을 관통한다.

앱 (setBrightness)
  → Framework: system_server의 DisplayManagerService (Binder로 수신)
  → JNI: 자바 서비스가 네이티브 구현 호출
  → Native: SurfaceFlinger / lights 관련 네이티브 코드
  → HAL: light HAL (AIDL) — /vendor의 벤더 구현을 Binder로 호출
  → Kernel: 백라이트 드라이버 (sysfs /sys/class/backlight/...)
  → Hardware: 실제 백라이트 PWM

우리가 CAN 데몬을 올릴 때 관심 있는 경로는 이 그림의 왼쪽 절반이다 — 자바 UI가 밝기 대신 "트랙터 속도"를 요청하면, 그 요청이 Binder를 타고 우리 네이티브 데몬에 닿고, 데몬은 커널의 SocketCAN 인터페이스를 통해 하드웨어와 통신한다. 즉 이 스택을 이해하는 것이 곧 "우리 데몬을 어느 층에 어떻게 끼워 넣을지"를 정하는 일이다.

HAL의 진화

HAL은 안드로이드 구조에서 가장 크게 바뀐 부분 중 하나다. 어느 방식이냐에 따라 벤더 코드의 위치·통신 방식·업데이트 정책이 전부 달라진다.

Traditional HAL (Android 2.2~8.0)은 단순했다. 프레임워크가 /system/lib/hw/에 있는 벤더 .so 파일을 dlopen으로 직접 로드해서, 정해진 구조체(hw_module_t)의 함수 포인터를 호출하는 방식이었다. 같은 프로세스 안에서 벤더 코드가 로드되니 빠르지만, 문제가 있었다. 프레임워크와 벤더 구현이 한 바이너리·한 파티션(/system)에 뒤섞여, OS를 업데이트하려면 벤더 코드까지 함께 다시 빌드해야 했다. 이것이 안드로이드 업데이트가 느렸던 구조적 원인 중 하나다.

Treble HAL (Android 8.0+)은 이 결합을 끊었다. Project Treble은 프레임워크와 벤더 구현을 파티션 단위로 분리했다.

  • 벤더 HAL 구현이 /vendor 파티션으로 나가고, 프레임워크는 /system에 남는다.
  • 둘 사이 통신이 dlopen 직접 호출이 아니라 binderized됐다. 초기에는 HIDL(HAL Interface Definition Language), 이후 AIDL HAL로 인터페이스를 정의하고 Binder로 프로세스 간 호출한다.
  • VINTF(Vendor Interface) 개념으로, /system이 기대하는 HAL 인터페이스 버전과 /vendor가 제공하는 버전이 호환되는지 매니페스트로 검증한다.

이 분리의 실익은 /system과 /vendor를 따로 업데이트할 수 있다는 것이다. 구글이 프레임워크만 담긴 GSI(Generic System Image)를 밀어도 벤더 구현이 그대로 붙어 돌 수 있고, 그 덕에 OS 업데이트 주기가 벤더 일정에서 어느 정도 독립됐다.

이 챕터의 범위 경계

HAL은 여기서 "왜·어떻게 분리됐나"까지만 개괄한다. HIDL/AIDL HAL 인터페이스를 실제로 정의하고 서비스로 등록하는 방법, servicemanager·hwservicemanager의 동작은 CH9. 서비스 아키텍처에서, VINTF 매니페스트 작성과 호환성 매트릭스, 커스텀 HAL을 붙이는 실전은 CH23. 네이티브 데몬 케이스 스터디에서 다룬다. 마찬가지로 /vendor 파티션의 물리적 구조는 CH3의 주제다. 이 챕터에서 이 이상 깊이 들어가지 않는 이유는, HAL 상세를 이해하려면 먼저 Binder(CH21)를 알아야 하기 때문이다.

커널의 Androidisms

안드로이드 커널은 순정 mainline 리눅스가 아니다. 모바일·임베디드 환경을 위해 구글과 벤더가 얹은 확장이 있는데, 이를 흔히 "Androidism"이라 부른다. 이들 중 상당수는 오랫동안 mainline 밖의 안드로이드 전용 패치였고, 일부는 이후 mainline에 흡수됐다.

  • Binder — 안드로이드 IPC의 핵심 드라이버(/dev/binder). 프로세스 간에 객체 참조를 넘기고, 스레드 풀을 커널이 관리하며, 한 번의 복사로 데이터를 전달한다. 안드로이드 전체가 이 위에서 돈다고 해도 과언이 아니다. 드라이버 내부는 CH22의 주제다.
  • ashmem (anonymous shared memory) — System V 공유 메모리 대신 도입된 익명 공유 메모리다. Bionic이 System V IPC를 뺀 자리를 메운다. 최근에는 memfd로 대체되는 추세다.
  • ION — 여러 하드웨어(GPU, 디스플레이, 카메라 ISP) 사이에서 공유할 큰 메모리 버퍼를 할당하는 메모리 관리자다. 이후 mainline의 DMA-BUF heaps로 통합됐다.
  • wakelock — 시스템이 절전(suspend)에 들어가는 것을 막아 특정 작업이 끝날 때까지 CPU를 깨워두는 메커니즘이다. 전원 관리의 근간으로, CH13에서 다룬다.
  • lmk (Low Memory Killer) — 메모리가 부족할 때 우선순위가 낮은 프로세스부터 종료하는 안드로이드식 OOM 관리다. 지금은 유저스페이스 데몬(lmkd)으로 옮겨졌다.
  • paranoid networking — 소켓 생성을 특정 GID(그룹)에 속한 프로세스로 제한하는 패치다. 앱이 네트워크를 쓰려면 INTERNET 권한이 필요한 것의 커널 쪽 근거다.

이 Androidism들은 추상적 개념이 아니라 기기에서 파일·노드로 확인된다. 커스텀 커널이 안드로이드에 필요한 확장을 제대로 담았는지 점검할 때 이 흔적들을 본다.

adb shell ls -l /dev/binder /dev/hwbinder /dev/vndbinder   # Binder 3종 노드
adb shell ls /dev/ashmem*                                  # ashmem (구버전)
adb shell ls /dev/dma_heap/                                # ION 후신 DMA-BUF heaps
adb shell dumpsys power | grep -i wake                     # wakelock 상태
adb shell cat /sys/kernel/debug/binder/stats               # Binder 트랜잭션 통계

이 노드나 기능이 없으면(예: 커널 config에서 CONFIG_ANDROID_BINDER_IPC를 빠뜨림) 안드로이드 유저스페이스가 아예 뜨지 못한다. 커스텀 커널 bring-up에서 가장 먼저 막히는 지점 중 하나가 이 Androidism 커널 옵션 누락이다.

이 Androidism들의 관리 방식도 진화했다. Android 11부터 본격화한 GKI(Generic Kernel Image)는 "구글이 유지하는 공통 커널(core)"과 "벤더가 제공하는 커널 모듈(vendor module)"을 분리한다. 예전에는 SoC 벤더마다 커널을 통째로 포크해서 파편화가 심했는데, GKI는 커널 코어를 표준화하고 하드웨어 의존 코드만 로드 가능한 모듈로 빼내 이 파편화를 줄인다. 임베디드 보드에서 커널을 다룰 때, 우리가 건드리는 건 대개 이 vendor module과 Device Tree 쪽이다. GKI와 vendor module의 구체적 경계는 CH2와 CH7에서 이어진다.

cgroup·namespace는 리눅스 공통 기반

Binder·ashmem 같은 건 안드로이드 고유지만, 프로세스 격리에 쓰이는 cgroup과 namespace는 리눅스 커널 공통 기능이다. 안드로이드는 이 위에 앱 격리를 얹는다. 같은 커널 기능을 컨테이너 관점에서 본 설명은 Kubernetes 스터디 CH1에 정리돼 있다.

안드로이드 파생 OS

AOSP는 오픈소스라, 구글 폰용 안드로이드 말고도 여러 파생 OS의 뿌리가 됐다. 우리처럼 임베디드 장비용으로 커스텀하는 것도 이 파생의 한 갈래다.

  • FireOS — 아마존이 AOSP를 포크해 만든 것으로, 구글 서비스(GMS) 대신 아마존 생태계를 얹었다. GMS 없이 AOSP만으로 완성된 제품을 만들 수 있음을 보여주는 대표 사례다.
  • Wear OS — 스마트워치용으로, 작은 화면·저전력·상시 표시에 맞춰 프레임워크가 다듬어졌다.
  • Android Auto vs Automotive (AAOS) — 둘은 다르다. Android Auto는 폰을 차량 화면에 미러링하는 앱이고, AAOS(Android Automotive OS)는 차량 하드웨어에 직접 설치되는 완전한 OS다. AAOS는 차량 신호(속도·기어 등)를 다루는 Vehicle HAL을 갖는데, 이는 우리가 농기계에서 CAN 신호를 다루는 구조와 개념적으로 닮아 있다. 차량용 신호 계층을 어떻게 HAL로 추상화하는지는 임베디드 커스텀에 좋은 참고 모델이다.
  • Headless Android — 화면·런처 없이 안드로이드를 도는 형태다. 키오스크, 산업용 게이트웨이, 셋톱박스처럼 UI가 없거나 단일 앱만 도는 장비에서 쓴다. 농기계 제어 유닛처럼 디스플레이가 부차적이고 백그라운드 서비스·네이티브 데몬이 본체인 장비에 특히 잘 맞는다. SurfaceFlinger·런처 같은 UI 스택의 상당 부분을 걷어내고, 부팅 후 곧바로 우리 데몬과 제어 로직이 도는 최소 구성으로 만들 수 있다.

임베디드 커스텀 관점에서 보면, AAOS의 신호 HAL 추상화와 Headless 구성은 그대로 우리 프로젝트의 설계 참고서가 된다. 차량·농기계 같은 기계 제어 도메인에서 안드로이드를 쓰는 이유는, 리치한 앱 생태계와 검증된 OS 인프라(전원 관리, 업데이트, 보안) 위에 도메인 특화 신호 계층만 얹으면 되기 때문이다. 그 신호 계층의 밑바탕이 되는 CAN·ISOBUS 통신은 CAN 스터디·ISOBUS 스터디에서 별도로 다룬다.

AOSP에는 GMS가 없다

여기서 커스텀 OS를 만들려는 사람이 가장 먼저 오해하는 지점을 짚어야 한다. AOSP는 "안드로이드"의 전부가 아니다. 우리가 흔히 폰에서 쓰는 Play 스토어, Play 게임, 지도, 로그인, 푸시(FCM), 위치 서비스 같은 것들은 AOSP에 들어 있지 않다. 이들은 GMS(Google Mobile Services)라는 구글의 비공개(closed-source) 컴포넌트이며, AOSP 소스를 아무리 뒤져도 없다.

GMS를 기기에 실으려면 구글과 별도 계약이 필요하다.

  • MADA(Mobile Application Distribution Agreement)를 맺어야 GMS 앱 묶음을 배포할 권리가 생긴다.
  • 기기가 CTS(Compatibility Test Suite)를 통과해 GMS 인증을 받아야 한다. 즉 아무 커스텀 이미지에나 GMS를 올릴 수 없고, 호환성 검증을 통과한 기기만 자격이 있다.
  • 이 인증·계약은 주로 소비자용 폰·태블릿 제조사(OEM)를 대상으로 하며, 절차와 비용이 만만치 않다.

그래서 AOSP만으로 만든 커스텀 OS는 처음부터 GMS 비의존을 전제로 설계하는 편이 현실적이다. 전략은 이렇다.

  • 앱 배포는 자체 마켓으로 — Play 스토어 대신 사내 앱 저장소나 MDM(기기 관리 솔루션)으로 APK를 배포·업데이트한다. 우리 SeamOS 마켓플레이스가 정확히 이 역할을 한다.
  • GMS API에 의존하지 않는 앱 설계 — 지도는 오픈소스(OSM 등), 푸시는 자체 MQTT/WebSocket, 로그인은 자체 인증으로 대체한다. FCM·Play Services 위치 API를 쓰는 앱은 GMS 없는 기기에서 그냥 죽는다.

다행히 임베디드·HMI(기계 조작 화면) 장비에는 GMS가 필요 없는 경우가 대부분이다. 농기계 단말은 Play 스토어에서 앱을 깔 일이 없고, 정해진 제어·모니터링 앱만 돌면 된다. GMS를 뺀다는 건 제약이 아니라 오히려 인증 비용·구글 의존·불필요한 백그라운드 서비스를 통째로 걷어내는 이점이다. 우리 프로젝트가 순정 AOSP 기반으로 가는 이유가 여기 있다.

커스텀의 대부분은 수정이 아니라 증축

AOSP를 커스텀한다고 하면 "SystemUI를 뜯어고치고 프레임워크 소스를 패치한다"를 떠올리기 쉽지만, 실전 원칙은 정반대다. 기존 AOSP 코드를 직접 고치는 것은 최후의 수단이고, 대부분의 커스텀은 "수정"이 아니라 "증축"으로 해결한다.

이유는 버전업 비용이다. frameworks/base나 SystemUI 같은 AOSP 소스를 직접 수정하면, 그 순간 우리는 AOSP를 포크한 셈이 된다. 다음에 구글이 새 안드로이드 버전을 내면, 우리가 고친 부분과 구글이 바꾼 부분이 충돌해 매번 수작업 rebase·conflict 해결을 해야 한다. 파일 몇 개면 몰라도, 이런 수정이 수십 곳에 흩어지면 버전업 자체가 불가능에 가까워진다.

그래서 정석은 건드리지 말고 옆에 짓는 것이다.

  • 우리 코드는 AOSP 트리 안의 자기 디렉토리에 둔다 — 관례적으로 vendor/<회사>/ (또는 device/<회사>/) 아래에 앱·데몬·HAL·설정을 모은다.
  • 이 디렉토리를 빌드 시스템에 등록해(Soong의 Android.bp, product makefile의 PRODUCT_PACKAGES) 이미지에 포함시킨다.
  • 기존 동작을 바꿔야 하면, 소스를 고치는 대신 AOSP가 제공하는 확장 지점을 쓴다 — 리소스는 RRO(Runtime Resource Overlay)로 덮어쓰고(CH10), HAL은 새 구현으로 갈아 끼우고(CH9), 부팅 동작은 우리 init.rc를 추가하는(CH8) 식이다.

이렇게 하면 구글이 버전업을 해도 우리 디렉토리는 그대로 얹히기만 하므로 rebase 지옥을 피한다. 우리가 올리려는 CAN 데몬도 AOSP를 고쳐 넣는 게 아니라, vendor/<회사>/ 아래 데몬 소스와 init.rc를 추가하고 빌드에 등록하는 증축 방식으로 붙인다.

그래도 기존 코드를 직접 수정할 수밖에 없는 지점은 남는다. 대표적으로 SystemUI(상태바·내비게이션바·잠금화면)나 런처는 확장 지점만으로 원하는 HMI 형태를 못 만드는 경우가 있어, 소스를 포크해 고쳐야 할 때가 있다. 이때 원칙은 수정 범위를 최소화하는 것이다 — SystemUI를 통째로 개조하기보다, 가능하면 우리 런처·HMI 앱으로 대체해 SystemUI 자체를 비활성화하거나(헤드리스·키오스크 구성), 꼭 고쳐야 하는 부분만 최소한의 패치로 국한해 다음 버전업 때 리베이스할 코드량을 줄인다. "무엇을 어디까지 고쳤는지"를 좁게 관리하는 것이 버전업 생존의 관건이다.

이 원칙을 실제 빌드 구조(디렉토리 추가·빌드 등록)로 구현하는 방법은 CH14. AOSP 소스 빌드와 device bring-up에서, SystemUI·런처를 포함한 패키지·앱 계층을 다루는 관점은 CH17. 패키지 관리에서, 데몬을 붙이는 전 과정은 CH23. 네이티브 데몬 케이스 스터디에서 이어진다.

핵심 정리

  • 안드로이드는 리눅스 커널만 공유하고 유저랜드(glibc→Bionic, systemd→init, X11→SurfaceFlinger, 패키지→APK)를 통째로 갈아 끼운 OS다. 커널 지식은 통하지만 유저랜드 지식은 새로 배워야 한다.
  • 버전 변천에서 중요한 건 코드네임이 아니라 구조 전환점 — Lollipop(ART), Oreo(Treble), Q~R(APEX·GKI)이 OS 구조를 바꿨다.
  • 실제 기기 이미지는 AOSP·external·Linux 커널·vendor(BSP)·ODM·carrier 여섯 레이어의 합성물이며, 레이어마다 수정 가능성과 유지보수 부담이 다르다.
  • 소프트웨어 스택은 Applications→Framework→ART→JNI→Native→Bionic→HAL→Kernel의 8층이고, 유저스페이스/커널 경계는 HAL과 Kernel 사이에 있다.
  • HAL은 Traditional(dlopen)에서 Treble(binderized, /vendor 분리)로 진화해 프레임워크·벤더 업데이트를 분리했고, 커널 Androidism(Binder·ashmem·ION·wakelock·lmk)과 GKI가 안드로이드 커널의 특성을 규정한다. 상세는 후속 챕터로 위임한다.
  • GMS(Play 스토어·FCM·지도 등)는 AOSP에 없는 구글 비공개 컴포넌트로 MADA 계약·GMS 인증(CTS)이 필요하며, 임베디드/HMI 장비는 대개 GMS가 필요 없어 자체 마켓 + GMS 비의존 앱으로 설계한다.
  • 커스텀의 정석은 AOSP 소스 수정이 아니라 증축 — vendor/<회사>/에 우리 코드를 두고 빌드에 등록하며, 기존 동작은 RRO·HAL 교체·init.rc 추가 같은 확장 지점으로 바꿔 버전업 rebase 비용을 피한다.
