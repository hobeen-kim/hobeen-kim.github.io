CH2. 하드웨어와 SoC

학습 목표

  • ARM의 AArch32/AArch64와 ARMv7~v9 흐름, Exception Level(EL0~EL3)과 TrustZone의 관계를 설명할 수 있다.
  • SoC 안에 CPU 클러스터·GPU·ISP·DSP·모뎀·메모리 컨트롤러가 어떻게 집적되는지, AP와 MCU의 차이를 안다.
  • 주요 SoC 벤더를 개괄하고, 임베디드 보드에서 왜 i.MX8·RK3588 같은 칩을 고르는지 이해한다.
  • Device Tree(DTS/DTB/DTBO)로 커널이 하드웨어를 발견하는 방법과 안드로이드의 dtbo 파티션을 설명할 수 있다.
  • 부트체인에 관여하는 펌웨어 이미지(PBL·XBL·TZ·modem 등)와 벤더 blob의 존재 이유를 안다.

ARM 아키텍처

안드로이드 기기의 절대다수는 ARM 아키텍처 위에서 돈다(x86 안드로이드도 있지만 소수다). AOSP를 커스텀하려면 ARM의 기본 골격을 알아야 커널 설정, 부트체인, 보안 세계를 이해할 수 있다.

먼저 실행 상태(execution state) 구분이다.

  • AArch64 — 64비트 실행 상태. ARMv8부터 도입됐고, 레지스터가 넓어지고(64비트 X0~X30) 주소 공간이 커졌다. 현재 안드로이드 앱·프레임워크의 기본이다.
  • AArch32 — 32비트 실행 상태. 예전 ARMv7의 명령어 세트(A32/T32, Thumb 포함)와 호환된다. 64비트 칩도 하위 호환으로 32비트 코드를 돌릴 수 있었지만, 최신 안드로이드와 일부 신형 코어는 32비트 지원을 아예 뺐다. 네이티브 라이브러리를 빌드할 때 arm64-v8a와 armeabi-v7a ABI를 구분하는 것이 바로 이 차이다.

아키텍처 리비전은 ARMv7 → ARMv8 → ARMv9로 이어진다. ARMv7은 32비트 시대, ARMv8이 64비트(AArch64)를 들여온 분수령, ARMv9는 보안(CCA)·머신러닝(SVE2) 확장을 더한 최신 세대다. 임베디드용 SoC를 고를 때 "몇 나노 공정이냐"보다 "어느 아키텍처 세대의 코어를 쓰느냐"가 지원 수명과 기능을 좌우한다.

가장 중요한 개념은 Exception Level(EL)이다. AArch64는 권한을 4개 레벨로 나눈다.

  • EL0 — 유저 앱. 가장 낮은 권한. 우리 네이티브 데몬도 여기서 돈다.
  • EL1 — OS 커널(리눅스 커널). 시스템 콜을 받아 하드웨어를 다룬다.
  • EL2 — 하이퍼바이저. 가상화를 담당한다. 안드로이드는 pKVM(protected KVM) 등으로 이 레벨을 활용한다.
  • EL3 — Secure Monitor. 가장 높은 권한으로, 보안 세계와 일반 세계를 오가는 문지기다.

이 EL 위에 TrustZone이 겹친다. TrustZone은 CPU를 Normal World와 Secure World로 물리적으로 분리하는 ARM의 보안 기술이다. 지문 데이터, 암호 키, DRM처럼 보호가 필요한 연산은 Secure World의 TEE(Trusted Execution Environment)에서 돌고, 일반 안드로이드는 Normal World에서 돈다. 둘 사이 전환은 EL3의 Secure Monitor를 거친다. 이 구조는 뒤에서 다룰 Verified Boot의 신뢰 사슬(root of trust)이 어디서 시작되는지와 직결된다 — 상세는 CH16. SELinux와 Verified Boot에서 다룬다.

기기에서 지금 도는 코어와 아키텍처는 간단히 확인할 수 있다. 커스텀 이미지에서 32/64비트 ABI가 제대로 잡혔는지 점검할 때 이 값들을 본다.

adb shell getprop ro.product.cpu.abilist     # 지원 ABI (예: arm64-v8a,armeabi-v7a)
adb shell cat /proc/cpuinfo | grep -m1 'CPU part'   # 코어 종류(Cortex 식별)
adb shell uname -m                            # aarch64

ro.product.cpu.abilist에 arm64-v8a만 있고 armeabi-v7a가 없으면 그 기기는 32비트 네이티브 라이브러리를 못 돌린다. 네이티브 데몬을 빌드할 때 타깃 ABI를 이 목록에 맞춰야 한다.

SoC의 구조

임베디드 안드로이드에서 "CPU를 산다"는 말은 부정확하다. 우리가 사는 건 SoC(System on Chip) — CPU를 포함해 시스템에 필요한 거의 모든 것을 한 칩에 집적한 물건이다. 이 SoC를 흔히 AP(Application Processor)라 부른다.

한 칩 안에 들어가는 주요 블록을 보자.

  • CPU 클러스터 (big.LITTLE) — 안드로이드 SoC는 성능·전력을 나눠 맡는 이기종 코어를 쓴다. 무거운 작업은 고성능 big 코어가, 대기·백그라운드는 저전력 LITTLE 코어가 처리한다(요즘은 big·middle·little 3티어도 흔하다). 스케줄러가 부하에 따라 태스크를 코어 사이로 옮긴다(EAS, Energy Aware Scheduling). 전력에 민감한 임베디드 장비에서 이 구조는 배터리·발열을 좌우한다.
  • GPU — 그래픽 렌더링. UI 합성(SurfaceFlinger)과 그래픽 앱이 쓴다. 헤드리스 장비라면 비중이 낮다.
  • NPU / DSP — NPU는 신경망 추론 가속기, DSP는 신호 처리 전용 프로세서다. 온디바이스 AI, 오디오·센서 전처리에 쓴다.
  • ISP (Image Signal Processor) — 카메라 센서 raw 데이터를 이미지로 가공하는 전용 블록이다.
  • 모뎀 (셀룰러) — LTE/5G 통신을 담당하는 베이스밴드다. 종종 별도 펌웨어(뒤에서 다룰 modem 이미지)로 도는 반독립 프로세서다.
  • 메모리 컨트롤러 — 외부 LPDDR DRAM과 통신한다.
  • 온칩 인터커넥트 (버스/NoC) — 위 블록들을 잇는 내부 고속 버스다. Network-on-Chip이라 부르기도 한다.
  • 보안·부트 블록 — 칩 안에 새겨진 BootROM(PBL), TrustZone용 보안 프로세서, 하드웨어 크립토 엔진이 여기 있다. 부팅의 신뢰 사슬이 여기서 출발한다.

여기서 AP와 MCU의 차이를 짚어야 한다. AP는 안드로이드 같은 리치 OS를 돌리는 고성능 프로세서다. 반면 MCU(Microcontroller Unit)는 RTOS나 베어메탈로 도는 작고 단순한 컨트롤러로, 실시간·저전력 제어에 쓴다. 농기계 같은 장비에서는 흔히 AP + MCU 조합을 쓴다 — 안드로이드는 AP에서 UI·연산·통신을 담당하고, 실시간성이 중요한 액추에이터 제어나 CAN 통신 프론트엔드는 별도 MCU가 맡아, 둘이 시리얼·SPI·CAN으로 통신하는 구조다. 우리가 AP 위 안드로이드에 CAN 데몬을 올릴 때, 그 반대편에 MCU가 있는 경우가 많다.

주요 SoC 벤더

SoC 시장은 몇몇 벤더가 나눠 갖고 있다. 커스텀 OS 관점에서 벤더 선택이 중요한 이유는, 앞 챕터에서 봤듯 BSP·HAL·펌웨어 blob·커널 지원이 전부 벤더에 묶이기 때문이다.

벤더대표 제품군특징
QualcommSnapdragon모뎀 통합 강점, 넓은 생태계, 폐쇄적 blob 많음
SamsungExynos자체 설계, 삼성 기기 중심
MediaTekDimensity/Helio가격 경쟁력, 중저가·다양한 폼팩터
HiSiliconKirin화웨이용, 제재 이후 위축

그런데 이 목록은 대부분 스마트폰용이다. 우리처럼 농기계·산업용 장비를 만들면 선택지가 달라진다. 폰용 SoC는 지원 수명이 짧고(2~3년), 산업 온도 범위나 장기 공급 보증이 약하다. 그래서 임베디드에서는 산업용 라인업을 쓴다.

  • NXP i.MX8 계열 — 산업·자동차용으로 널리 쓰인다. 넓은 동작 온도 범위, 10년 이상의 장기 공급 보증, 안전 인증(기능 안전) 지원이 강점이다. 문서와 mainline 커널 지원이 좋아 커스텀 부담이 상대적으로 적다.
  • Rockchip RK3588 — 강력한 성능(8코어, NPU 내장) 대비 저렴해서 산업용 안드로이드 보드에서 인기가 높다. 커뮤니티 자료가 많고 개발 보드가 다양해 프로토타이핑이 편하다.

농기계 제어 유닛 같은 장비에서 i.MX8이나 RK3588을 고르는 이유는 성능 순위표가 아니라 장기 공급·온도 범위·안전 인증·문서/커널 지원 때문이다. 폰용 최신 Snapdragon이 더 빠르더라도, 3년 뒤 단종되고 mainline 지원이 끊기면 10년 굴려야 하는 장비에는 못 쓴다. 벤더가 주는 BSP의 품질과 수명이 임베디드 SoC 선택의 실질 기준이다.

벤더 blob이 남기는 커스텀 부담

어느 벤더를 고르든, HAL·펌웨어의 상당수는 소스 없는 바이너리 blob이다. CH1에서 본 vendor 레이어가 바로 이것이다. blob이 특정 커널 버전·안드로이드 버전에 묶여 있으면, OS를 올리고 싶어도 벤더가 지원하는 조합을 벗어나기 어렵다. 그래서 임베디드 커스텀의 첫 단추는 "우리 SoC 벤더가 어느 안드로이드 버전용 BSP를 제공하는가"를 확인하는 일이다.

Device Tree

커널은 자기가 어떤 보드에서 도는지 태어날 때부터 알지 못한다. 같은 ARM 커널 바이너리가 수많은 보드에서 돌 수 있는데, 각 보드의 하드웨어 구성(어떤 I2C 버스에 어떤 센서가 붙었는지, 메모리가 얼마인지)은 보드마다 다르다. 이 하드웨어 정보를 코드가 아니라 데이터로 커널에 알려주는 방법이 Device Tree다.

파일 종류부터 정리하자.

  • .dts (Device Tree Source) — 사람이 읽고 쓰는 소스다. 트리 구조로 하드웨어를 기술한다. 공통 부분은 .dtsi(include)로 빼서 여러 보드가 공유한다.
  • .dtb (Device Tree Blob) — .dts를 dtc(Device Tree Compiler)로 컴파일한 바이너리다. 커널이 실제로 읽는 형식이다.
  • .dtbo (Device Tree Blob Overlay) — 베이스 DTB 위에 덧씌우는 오버레이다. 같은 베이스 보드에서 변형(다른 디스플레이, 다른 센서 구성)을 표현할 때 base를 통째로 복제하지 않고 차이만 얹는다.

DTS의 내용은 노드 트리다. 대략 이런 모습이다.

/ {
    memory@80000000 {
        device_type = "memory";
        reg = <0x80000000 0x40000000>;   // 시작주소, 크기(1GB)
    };

    soc {
        i2c@30a20000 {
            temp_sensor@48 {             // I2C 주소 0x48의 온도 센서
                compatible = "ti,tmp102";
                reg = <0x48>;
            };
        };
        spi@30820000 {
            can@0 {                      // SPI에 붙은 CAN 컨트롤러
                compatible = "microchip,mcp2515";
                reg = <0>;
                interrupt-parent = <&gpio1>;
                interrupts = <9 0x2>;
            };
        };
    };

    chosen {
        bootargs = "console=ttymxc0,115200 androidboot.hardware=myboard";
    };
};

핵심은 compatible 문자열이다. 커널은 부팅 중 DT를 파싱하면서 각 노드의 compatible 값을 보고, 그 값에 매칭되는 드라이버를 찾아 probe한다. 위 예시라면 microchip,mcp2515를 지원하는 SPI-CAN 드라이버가 등록돼 있으면 커널이 그 CAN 컨트롤러를 인식하고 can0 네트워크 인터페이스를 올린다. 이렇게 올라온 CAN 인터페이스를 유저스페이스에서 다루는 것이 SocketCAN인데, 이는 CAN 스터디 CH13에서 다룬다.

전체 흐름은 이렇다. .dts/.dtsi를 dtc로 컴파일해 .dtb(와 필요하면 .dtbo)를 만들고, 부트로더가 이 DTB와 DTBO를 메모리에서 병합한 뒤 커널에 넘긴다. 커널은 넘겨받은 최종 DT를 파싱해 드라이버를 하나씩 probe하며 하드웨어를 발견한다.

DTS를 다루는 도구는 dtc다. 소스를 blob으로 굽고, 반대로 기기에 올라간 DTB를 되짚어 볼 수도 있다.

dtc -I dts -O dtb -o myboard.dtb myboard.dts     # 소스 → blob 컴파일
dtc -I dtb -O dts -o dump.dts myboard.dtb         # blob → 소스 역변환(디버깅)
fdtdump myboard.dtb | less                        # blob 내용 덤프

# 기기에서 커널이 실제 인식한 최종 DT는 procfs로 노출된다
adb shell ls /proc/device-tree/soc/
adb shell cat /proc/device-tree/model             # 병합된 최종 트리 확인

보드를 bring-up할 때 흔한 함정은, DTS에 노드를 넣었는데도 compatible 문자열에 맞는 드라이버가 커널에 빌드돼 있지 않아 아무 일도 안 일어나는 경우다. dmesg에서 해당 드라이버의 probe 로그가 뜨는지, /proc/device-tree에 노드가 실렸는지를 대조하는 것이 진단의 출발점이다.

안드로이드는 이 오버레이를 위해 별도의 dtbo 파티션을 둔다. 베이스 DTB는 boot/vendor_boot 이미지에 들어가고, 보드·구성별 오버레이는 dtbo 파티션에 담겨 부팅 시 적용된다. 덕분에 하나의 베이스 이미지로 여러 하드웨어 변형을 커버할 수 있다. 임베디드에서 보드 리비전이 자주 바뀌는 상황(센서 추가, 커넥터 변경)에 특히 유용하다 — 베이스는 그대로 두고 dtbo만 새로 구우면 된다. 파티션 자체의 구조와 부팅 시 이미지 로딩은 CH3·CH7에서 이어진다.

펌웨어 이미지

커널이 뜨기 훨씬 전부터, SoC 안팎에서는 여러 펌웨어가 순서대로 실행되며 시스템을 깨운다. 이 부트체인에 관여하는 펌웨어들을 알아야 부팅이 어디서 막히는지 진단할 수 있다. 아래는 Qualcomm 계열의 이름을 예로 든 것이며, 벤더마다 명칭은 다르지만 역할 구조는 비슷하다.

  • PBL (Primary Boot Loader) — SoC 안 BootROM에 새겨진 최초 코드다. 칩 제조 시 각인돼 수정 불가능하며, 신뢰 사슬의 뿌리(root of trust)다. 전원이 들어오면 가장 먼저 이게 돌며 다음 단계를 검증·로드한다.
  • XBL / SBL (eXtensible / Secondary Boot Loader) — PBL 다음 단계 부트로더다. DRAM 초기화, 클럭 설정 등 저수준 하드웨어를 깨우고 그다음 부트로더를 로드한다.
  • TZ (TrustZone 이미지) — Secure World에서 도는 보안 OS/모니터 이미지다. 앞서 본 TEE의 실체가 이 단계에 로드된다. 이후 안드로이드가 지문·키 연산을 요청하면 이 세계로 넘어간다.
  • modem 이미지 — 셀룰러 모뎀(베이스밴드)용 펌웨어다. AP와 별개로 도는 반독립 프로세서라 자체 펌웨어를 갖는다. 헤드리스·비셀룰러 장비면 없을 수 있다.
  • ABL (Android Boot Loader) — 부트체인 후반의 안드로이드용 부트로더로, boot 이미지를 로드하고 검증(Verified Boot)한 뒤 커널로 제어를 넘긴다. fastboot 모드도 여기서 제공한다.

이 펌웨어들 상당수가 벤더 blob이다. 소스가 공개되지 않고 서명된 바이너리로만 제공되며, 벤더의 서명 키로 잠겨 있어 임의 교체가 안 된다. 커스텀 OS를 만들어도 이 저수준 펌웨어 계층은 대개 벤더가 준 것을 그대로 쓰고, 우리가 손대는 건 ABL 이후의 안드로이드 계층(boot·system·vendor 이미지)이라는 점을 기억해야 한다.

ABL이 제공하는 fastboot 모드가 우리가 이 계층과 상호작용하는 통로다. 커스텀 이미지를 굽고 나면 파티션 단위로 이렇게 flash한다.

adb reboot bootloader          # ABL의 fastboot 모드로 진입
fastboot devices               # 연결 확인
fastboot getvar all            # 부트로더가 아는 파티션·변수 조회
fastboot flash boot boot.img   # 우리가 빌드한 boot 이미지 기록
fastboot flash dtbo dtbo.img   # Device Tree 오버레이 파티션 기록
fastboot reboot

단, 벤더가 부트로더를 잠가 뒀다면(locked) 서명되지 않은 이미지는 거부된다. 개발 단계에서 fastboot flashing unlock으로 잠금을 풀어야 우리 이미지를 올릴 수 있는데, 이 잠금·해제와 서명 검증이 곧 다음 챕터들에서 다룰 Verified Boot의 실무 접점이다.

부트체인은 CH7에서 이어진다

이 절은 "부팅 전 어떤 펌웨어들이 관여하는가"를 하드웨어 관점에서 개괄만 한다. 각 단계가 다음 단계를 어떻게 검증하는지(Verified Boot 체인), boot/vendor_boot 이미지의 구조, ramdisk와 커널이 실제로 올라가는 과정은 CH7. 부트로더와 커널 부팅에서, 서명·검증의 암호학적 세부는 CH16에서 본격적으로 다룬다.

핵심 정리

  • 안드로이드 기기는 대부분 ARM이며, AArch64/AArch32 실행 상태와 ARMv7~v9 세대, 그리고 EL0~EL3 권한 레벨 위에 TrustZone(Normal/Secure World) 보안 모델이 겹쳐 있다.
  • 우리가 사는 건 CPU가 아니라 SoC(AP) — CPU 클러스터(big.LITTLE)·GPU·NPU/DSP·ISP·모뎀·메모리 컨트롤러·보안 블록을 한 칩에 집적한 물건이고, 실시간 제어는 별도 MCU가 맡는 AP+MCU 조합이 흔하다.
  • 임베디드 SoC 선택은 성능 순위가 아니라 장기 공급·온도 범위·안전 인증·BSP 품질로 결정되며, 농기계·산업용에서는 NXP i.MX8·Rockchip RK3588 같은 산업용 칩을 고른다.
  • Device Tree(.dts→dtc→.dtb, 오버레이는 .dtbo)는 커널이 compatible 문자열로 드라이버를 probe해 하드웨어를 발견하게 해주며, 안드로이드는 보드 변형을 위해 별도 dtbo 파티션을 둔다.
  • 커널 이전에 PBL(root of trust)→XBL→TZ→modem→ABL 순으로 펌웨어가 실행되고, 이들 저수준 펌웨어는 대개 서명된 벤더 blob이라 커스텀 대상은 ABL 이후 안드로이드 계층이다.
