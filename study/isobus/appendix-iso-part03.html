ISO 11783-3: Data link layer 정리

이 문서에 대해

ISO 11783-3 표준 원문을 학습 목적으로 재구성한 비공식 요약·해설이다. 규범적 판단이 필요할 때는 반드시 원문 표준을 확인해야 한다.

개요

ISO 11783-3은 ISO 11783 시리즈 중 데이터 링크 계층을 규정하는 파트다. ISO 11898-1에 정의된 CAN(Controller Area Network) 프로토콜 위에서 애플리케이션 계층의 PDU(Protocol Data Unit)를 Classical Extended Frame Format(CEFF) CAN 데이터 프레임으로 매핑하는 방법, 그리고 한 프레임(8바이트)을 초과하는 데이터를 나르기 위한 전송 계층 프로토콜(Transport Protocol, Extended Transport Protocol)을 정의한다.

이 문서(2018년 4판, ISO/FDIS 11783-3:2018)는 3판(2014)을 대체하며, 주요 변경점은 다음과 같다.

  • ISO 11898-1 관련 용어 정비(CAN FD 사용 배제)
  • BAM.TP의 패킷 전송 간격을 10 ms까지 허용
  • Request2가 사용될 때 ACKNOWLEDGEMENT PG가 Extended Identifier Type을 지원

ISO 11783 자체는 트럭·버스용으로 개발된 SAE J1939를 기반으로 하며, 농업·임업 장비의 ECU(전자 제어 장치)들이 표준화된 방식으로 상호 통신할 수 있는 개방형 시스템을 목표로 한다.

인용 규격

ISO 11783-1(일반), ISO 11783-5(네트워크 관리), ISO 11783-7(구현 메시지 응용 계층), ISO 11898-1(CAN), ISO 15765-2(DoCAN 진단 전송 프로토콜)가 규범 인용된다. 용어 정의는 ISO 11783-1과 ISO 11898-1을 따른다.

데이터 링크 계층의 역할은 물리 링크를 통한 신뢰성 있는 데이터 전송이다. 동기화, 순서 제어, 오류 제어, 흐름 제어를 갖춘 CAN classical data frame 송신으로 이를 달성하며, 흐름 제어는 일관된 메시지 프레임 포맷을 통해 이뤄진다.

5.1 Message frame format

CAN 프레임 포맷과 ISO 11783

메시지 프레임 포맷은 ISO 11898-1의 CAN 요구사항을 따르되, 두 문서가 다를 경우 ISO 11783-3이 우선한다. CAN 규격은 정보 라우팅 관점에서 노드 주소를 쓰지 않는다고 기술하지만, ISO 11783은 반대로 여러 control function이 같은 CAN identifier를 쓰는 것을 막기 위해 control function 주소 사용을 요구한다.

ISO 11898-1에는 두 가지 classical 프레임 포맷이 있다.

포맷identifier 길이ISO 11783에서의 위치
CBFF (Classical Base Frame Format)11 bitproprietary 용도로만 허용 (이 문서의 규칙을 따르는 조건)
CEFF (Classical Extended Frame Format)29 bit표준 통신의 기본 포맷. 모든 ISO 11783 컨트롤러는 CEFF 사용

FD Frame Format은 ISO 11783 네트워크에서 사용 금지다. 또한 ISO 11898-1을 따르지 않아 CEFF 메시지를 통과시키지 못하는 하드웨어는 네트워크에 연결해서는 안 된다.

프레임 구조 자체는 CAN 정의 그대로다. 참고로 비트 스터핑 포함 최대 프레임 길이는 CBFF 127 bit, CEFF 150 bit다. CEFF의 arbitration field는 32 bit(11 bit identifier + SRR + IDE + 18 bit identifier)이고 control field 6 bit, data field 0~8 byte, CRC 15 bit 순으로 이어진다.

CEFF 기반 PDU 매핑

CEFF 메시지 하나는 하나의 PDU를 담는다. PDU는 애플리케이션 계층이 제공하는 정보로부터 조립되는 7개 필드로 구성된다.

  • Priority
  • Extended Data Page (EDP)
  • Data Page (DP)
  • PDU Format (PF)
  • PDU Specific (PS) — Destination Address(DA), Group Extension(GE), 또는 proprietary
  • Source Address (SA)
  • Data

29 bit identifier에 대한 ISO 11783의 비트 할당은 다음과 같다(SOF 이후 전송 순서 기준).

SRR, IDE, RTR, FDF, r0, DLC 등 나머지 비트는 CAN 정의 그대로 유지된다(ISO 11783이 변경하지 않음). 11 bit identifier(CBFF)의 경우 상위 3 bit를 priority, 하위 8 bit를 SA로 파싱하는 최소 정의만 주어진다.

데이터 필드는 Byte 1~8로 기술한다. 각 바이트의 MSB(Bit 8)가 먼저 전송되며, Byte 1이 DLC에 가장 가깝고 Byte 8의 LSB(Bit 1)가 CRC 직전에 마지막으로 전송된다.

EDP=1, DP=1 프레임

EDP와 DP가 모두 1인 CAN 프레임은 ISO 15765-2(DoCAN) 포맷 프레임으로 식별된다. 이 프레임의 처리에는 ISO 11783 정의가 적용되지 않고 ISO 15765-2를 따라야 한다.

5.1.3 Parameter group number (PGN)

CAN 데이터 필드 안에서 parameter group을 식별해야 할 때는 24 bit 값으로 표현한다. 전송 순서는 LSB 먼저(LSB → 중간 바이트 → MSB 순)다. 24 bit PGN의 구성은 다음과 같다.

5.1.4 CBFF(11 bit) 메시지의 취급

ISO 11783 네트워크의 컨트롤러는 CBFF 메시지 포맷을 지원할 수 있으나, CBFF 메시지는 모두 proprietary로 정의된다. 두 포맷의 공존을 위해 11 bit identifier는 상위 3 bit를 priority, 하위 8 bit를 PDU의 SA로 파싱하는 최소 규칙을 따른다.

base frame과 extended frame이 동시에 버스에 접근하면 잘못된 중재가 일어날 수 있다. 11 bit 메시지에서는 SA가 상대적으로 높은 우선순위 위치에 오기 때문에, 29 bit 메시지의 EDP·DP·PF보다 우선해 버릴 수 있다. 따라서 올바른 버스 중재를 위해 3개의 priority bit를 사용해야 한다.

5.2 Protocol data unit (PDU)

5.2.1 구조

애플리케이션/네트워크 계층이 제공한 정보는 하나의 PDU로 조립된다. PDU는 위에서 본 7개 필드로 구성되고, classical CAN 데이터 프레임 1개당 PDU는 정확히 1개다. 다만 일부 PGN 정의는 데이터 전송에 여러 CAN 프레임을 요구한다(multi-packet).

SOF, SRR, IDE, RTR, FDF, CRC, ACK, EOF 및 control field 일부는 CAN 규격이 전적으로 관리하며 데이터 링크 상위 계층에는 보이지 않는다. ISO 11783은 이들을 변경하지 않는다.

비트 수311888최대 64

5.2.2 Priority (P)

  • 버스 전송 지연 최적화에만 쓰이며, 수신 컨트롤러는 전역적으로 마스킹(무시)해야 한다.
  • 0(000₂, 최고) ~ 7(111₂, 최저).
  • 기본값: 제어 지향(control oriented) 메시지 3(011₂), 그 외 정보·proprietary·request·NACK 메시지 6(110₂).
  • PGN이 응용 계층 표준에 추가될 때 권장 priority가 배정되지만, 네트워크 튜닝을 위해 제조사가 재프로그램할 수 있어야 한다.

5.2.3 Extended data page (EDP), 5.2.4 Data page (DP)

EDP와 DP의 조합이 CAN identifier의 구조를 결정한다. 모든 ISO 11783 메시지는 송신 시 EDP를 0으로 설정해야 한다.

5.2.5 PDU format (PF)

PF는 8 bit 필드로, PDU 포맷(PDU1/PDU2)을 결정하고 PGN 구성에 참여한다. PGN은 명령·데이터·요청·ACK·NACK 등을 식별·라벨링하는 데 쓰인다. 8바이트를 넘는 정보는 multi-packet 메시지로 보내야 하며, 8바이트 이하면 단일 CAN 프레임을 쓴다. 하나의 PGN은 하나 이상의 파라미터(예: 엔진 회전수)를 담을 수 있고, 8바이트 데이터 필드를 최대한 활용하도록 여러 파라미터를 묶는 것이 권장된다.

proprietary PGN은 PDU1·PDU2 양쪽 포맷에 하나씩 정의되어 있으며 해석은 제조사마다 다르다.

5.2.6 PDU specific (PS)

PS는 8 bit 필드이며 의미는 PF 값에 따라 달라진다.

PDU 포맷PF 범위PS의 의미
PDU10–239Destination Address (DA)
PDU2240–255Group Extension (GE)
  • DA: 메시지의 목적지 주소. 다른 컨트롤러는 이 메시지를 무시해야 한다. 전역 주소(255)는 모든 컨트롤러가 수신·대응해야 한다.
  • GE: PF의 하위 4 bit와 조합되어 데이터 페이지당 16 × 256 = 4 096개의 parameter group을 제공한다(PDU2 전용).

PDU1 포맷으로는 데이터 페이지당 240개 PG가 제공되어, 두 페이지 합계 [240 + (16 × 256)] × 2 = 8 672개의 PG를 정의할 수 있다.

5.2.7 Source address (SA)

SA는 8 bit이며, 네트워크에서 하나의 SA는 하나의 control function만 사용해야 한다. 주소 관리·할당과 SA 중복 방지 절차는 ISO 11783-5에 정의된다.

5.2.8 Data field

8바이트 이하 데이터: 한 프레임의 8바이트를 그대로 쓴다. 향후 확장을 위해 PGN 할당 시 8바이트 전부를 배정·예약하는 것이 권장된다. PGN에 연계된 데이터 바이트 수는 한 번 정해지면 바꿀 수 없다(원래 multi-packet으로 정의되지 않았다면 multi-packet으로 바뀔 수도 없다). CAN DLC는 데이터 길이가 8바이트 이하면 정의된 "data length" 값으로, 9바이트 이상이면 8로 설정한다. 예를 들어 REQUEST PGN(59 904)의 데이터 길이는 3바이트이므로 DLC는 3이다.

8바이트 초과 데이터(multi-packet): 여러 CAN 프레임으로 나눠 통신한다. multi-packet 가능으로 정의된 PG라도 실제 전송할 데이터가 9바이트 미만이면 DLC 8의 단일 프레임으로 보낸다. 9바이트 이상이면 transport protocol 기능을 사용한다 — connection management로 연결을 설정·종료하고, data transfer로 "패킷화"된 데이터를 나르며, destination-specific 전송에는 흐름 제어와 핸드셰이킹을 제공한다. multi-packet 응답의 모든 프레임은 DLC 8이어야 하고 미사용 바이트는 "Not Available"로 채운다. 패킷 수는 고정형·가변형 모두 존재한다(예: active diagnostic codes PGN은 가변형).

5.3 Protocol data unit (PDU) formats

5.3.1 두 포맷의 존재 이유

PDU1(PS = DA)은 특정 목적지로 프레임을 보낼 수 있게 하고, PDU2(PS = GE)는 목적지 지정이 없는 전역 메시지 전용이다. 목적지 지정 통신을 유지하면서 PGN 조합 수를 늘리기 위해 두 포맷을 분리했다. proprietary PG는 양쪽 포맷 모두에 할당돼 있어 충돌 없는 proprietary 통신 방법이 표준화되어 있다.

5.3.2 PDU1 format

  • PF 0~239가 PDU1이다. PS 필드는 DA.
  • 특정 또는 전역 목적지로 보낼 수 있고, 요청에 의한 응답과 비요청(unsolicited) 송신 모두 가능하다.
  • 목적지가 필요하고 지연이 중요한 PG는 PF = 0부터 증가 방향으로, 지연이 중요하지 않은 PG는 PF = 239부터 감소 방향으로 할당한다.
  • PF = 239(EDP 0, DP 0)는 proprietary 용도로, 이때 PS는 DA다. Proprietary A의 PGN은 61 184.
  • 현재 PDU1로 쓸 수 있는 PGN 수는 2 페이지 × 240 = 480개.

5.3.3 PDU2 format

  • PF 240~255가 PDU2다. PS 필드는 GE. 전역 메시지 전용이며, PGN 할당 시 PDU2 포맷을 선택하면 그 PGN은 영원히 특정 목적지로 보낼 수 없다.
  • 빠른 갱신 주기(대략 100 ms 미만)로 송신되는 메시지의 PGN은 PF = 240부터 증가 방향, 요청 시에만·변경 시에만·느린 주기(대략 100 ms 초과)로 보내는 메시지는 PF = 254부터 감소 방향으로 할당한다.
  • PF = 255(EDP 0, DP 0)는 proprietary 용도이며 PS는 제조사가 정의한다. Proprietary B의 PGN 범위는 65 280~65 535.
  • 현재 PDU2로 쓸 수 있는 PGN 수는 2 × 16 × 256 = 8 192개.

5.4 Message types

5.4.1 개요

현재 지원되는 메시지 타입은 다섯 가지다: Command, Request, Broadcast/Response, Acknowledgement, Group Function. 메시지 타입은 할당된 PGN으로 식별한다.

RTR 사용 금지

CAN의 remote frame용 RTR 비트를 recessive(논리 1)로 쓰는 것은 금지다. 즉 Remote Transmission Request는 ISO 11783 네트워크에서 사용할 수 없다. RTR은 CAN identifier만 알리고 데이터 없이 특정 CAN 객체를 "요청"하는 메커니즘인데, ISO 11783은 identifier의 일부를 priority와 SA로 쓰기 때문에 충돌이 생긴다(다른 장치의 SA로 메시지를 보내는 꼴이 됨). 대신 별도의 Request 메커니즘(5.4.3)을 사용한다.

데이터 필드에 들어가는 멀티바이트 파라미터는 LSB 먼저 배치한다(예외는 ASCII 데이터 등 별도 명시된 경우). 예를 들어 2바이트 파라미터가 Byte 7~8에 놓이면 LSB가 Byte 7, MSB가 Byte 8이다.

5.4.2 Command

특정 또는 전역 목적지에 특정 동작을 지시하는 메시지 타입이다. 수신 측은 이 메시지를 받으면 정해진 동작을 수행해야 한다. PDU1(PS = DA), PDU2(PS = GE) 모두 command에 쓸 수 있다. 예: Transmission Control, Address Request, Torque/Speed Control.

5.4.3 Request

PGN으로 식별되는 Request 메시지 타입은 정보를 전역 또는 특정 목적지에 요청하는 수단이다. 특정 목적지 대상 요청을 destination-specific request라 한다.

Request 재시도 정책

Response timeout 안에 응답(PG 또는 ACKNOWLEDGEMENT)을 받지 못하면 같은 Request를 재전송할 수 있다. 재시도는 2회로 제한하는 것이 권장된다(총 3회 발행). 2회 재시도 후에도 응답이 없으면 요청을 포기하거나, 수 분 단위의 긴 시간을 기다린 후 다시 시도한다.

5.4.4 Broadcast/Response

control function이 비요청(unsolicited)으로 정보를 브로드캐스트하거나, command·request에 대한 응답으로 보내는 메시지 타입이다.

5.4.5 Acknowledgement

acknowledgement에는 두 형태가 있다.

  1. CAN 프로토콜 수준: in-frame acknowledgement로 적어도 한 컨트롤러가 메시지를 수신했음을 확인하고, CAN error frame의 부재로 나머지 컨트롤러의 정상 수신을 확인한다.
  2. 응용 계층 수준: 특정 command·request에 대한 "normal broadcast", "ACK", "NACK" 응답. 어떤 PG에 어떤 acknowledgement가 필요한지는 응용 계층에서 정의한다.

Group Function PG의 경우 Group Function Value 파라미터로 어떤 group function에 대한 응답인지 식별한다(값은 해당 Group Function PG마다 고유, 0~250 범위 사용 권장). 또한 각 acknowledgement에는 원 요청 발신자의 SA를 담는 address acknowledge byte(Byte 5)가 있다. SAE J1939 호환을 위해 이 필드는 PS 필드의 복제다.

5.4.6 Group function

Group Function 메시지 타입은 기능 묶음(group of functions)에 쓰인다. proprietary 기능, multi-packet transport 기능, 네트워크 관리(ISO 11783-5), Virtual Terminal(ISO 11783-6), Task Controller(ISO 11783-10), File Server(ISO 11783-13), Sequence Controller(ISO 11783-14)가 Group Function 메시지를 사용한다.

  • 각 기능 그룹은 할당된 PGN으로 식별하고, 그룹 내 개별 기능은 데이터 구조(보통 데이터 필드의 첫 바이트)로 정의한다.
  • 이 문서에 정의된 메시지로 부족하면 group function이 자체 request·ACK·NACK 메커니즘을 제공할 수 있다.
  • PGN 59 904 요청으로 특정 Group Function PG의 지원 여부를 확인할 수 있다. 지원하면 control byte 0(ACK)·2·3으로, 지원하지 않으면 1(NACK)로 Acknowledgement PGN을 보낸다. 여기서도 "지원하지 않음"은 그 PG를 송신하지 않는다는 의미다.

proprietary group function은 제조사 간 CAN identifier 사용 충돌 없이 proprietary 메시지를 주고받는 수단을 제공한다. Proprietary A·A2·B 메시지의 데이터 길이는 제조사가 정하므로, 두 제조사가 같은 GE 값을 다른 DLC로 쓸 수 있다 — 수신 측이 제조사를 구분해야 한다. proprietary 메시지의 상시 사용은 최소화해야 하며, CF당 Proprietary A + A2 + B의 합이 네트워크 용량의 2 %를 넘지 않아야 한다(Annex D 참조).

5.5 Message priority ~ 5.8 Error detection

5.5 Message priority — CAN 데이터 프레임 우선순위는 ISO 11898-1을 따른다. CAN identifier 필드의 값이 우선순위를 결정한다: 값이 낮을수록(29 bit 모두 0이 최고) 우선순위가 높고, 클수록(모두 1이 최저) 낮다. 할당은 5.9의 지침을 따라 응용 계층에서 이뤄진다.

5.6 Bus access — 버스가 비어 있으면 어떤 컨트롤러든 송신을 시작할 수 있다. 둘 이상이 동시에 시작하면 CAN identifier를 이용한 contention-based arbitration으로 충돌을 해소한다. 정보도 시간도 잃지 않으며, 최고 우선순위 프레임의 발신 컨트롤러가 버스를 획득한다.

5.7 Contention-based arbitration — 중재 중 각 발신 컨트롤러는 자신이 보낸 비트와 버스에서 관측된 비트를 비교한다. 같으면 계속 송신한다. recessive를 보냈는데 dominant가 관측되면 중재에서 패배해 즉시 물러난다. dominant를 보냈는데 recessive가 관측되면 bit error로 검출한다.

5.8 Error detection — 오류 검출 수단: 송신 비트와 버스 관측 비트의 비교, CRC, 스터프 폭 5의 가변 비트 스터핑, 프레임 포맷 검사. 상세는 ISO 11898-1 참조.

5.9 Assignment process for SA and PGN

5.9.1 일반 원칙

parameter group은 PDU1 또는 PDU2 중 하나의 포맷으로만 할당되며, 한 번 정해지면 다른 포맷은 쓸 수 없다. 특정 목적지로 보내야 하는 PG는 반드시 PDU1을 쓴다. PG 할당 시 고려 요소: priority, 갱신 주기, 데이터의 타 CF에 대한 중요도, 데이터 길이.

  • PGN 할당 시 기본 priority가 배정되지만 OEM의 네트워크 튜닝을 위해 priority 필드는 프로그래머블할 수 있다.
  • 어떤 PGN이든 요청할 수 있지만, 이미 주기적으로 브로드캐스트되는 메시지에 대한 요청은 강하게 비권장된다.
  • 목적지가 필요한 PGN 할당은 여러 특정 CF 중 하나를 직접 제어(command)하는 파라미터에만 한다. 그 외에는 모든 CF가 접근할 수 있도록 목적지 없는 PGN을 선택한다.
  • 선호 SA는 message priority·갱신 주기·중요도와 무관하게 선형적으로 할당된다.
  • 반복 주기 10 Hz 이상인 메시지는 multi-packet이 허용되지 않는다.

PGN 템플릿(Table 7)의 구획은 다음과 같다. 데이터 페이지 0·1 각각에 대해 PDU1 고속(100 ms 이하, PF 0부터 증가, multi-packet 불가) → PDU1 저속(100 ms 초과, PF 238까지, multi-packet 허용) → Proprietary A(PF 239) → PDU2 고속(PF 240부터 증가, multi-packet 불가) → PDU2 저속(PF 254까지 감소, multi-packet 허용) → Proprietary B(PF 255) 순으로 배치된다.

5.9.2 Address assignment criteria

ISO 11783의 미할당 주소는 한정적이므로 새 주소 할당은 효율적이어야 한다. 시스템 내 최대 주소 수는 256을 넘을 수 없다. 주소 정의 추가는 트랙터·임플리먼트 내 특정 기능을 제공하는 장치(엔진·변속기·브레이크·연료 시스템처럼 현재 정의된 주소와 유사한 범위)로 제한되어야 하고, 대다수 ISO 11783 사용자에게 유용해야 한다. ISO 11783 컨트롤러는 ISO 11783-5에 따른 주소 자기 구성(self-configuring)을 지원해야 한다.

5.10 Transport protocol functions

5.10.1 개요

transport protocol 기능은 데이터 링크 계층의 일부로 기술되며 두 가지 주 기능으로 나뉜다: 메시지 "패킷화(packetization)"·재조립, 그리고 connection management. 여기서 originating control function은 RTS(Request to Send)를 보내는 쪽, receiving control function은 CTS(Clear to Send)를 보내는 쪽이다.

5.10.2 패킷화와 재조립

8바이트를 초과하는 메시지는 하나의 CAN 프레임에 담을 수 없으므로 여러 패킷으로 쪼개 개별 CAN 프레임으로 전송하고, 수신 측에서 sequence number 순으로 재조립한다.

  • 각 패킷의 데이터 필드 첫 바이트는 sequence number다. 1~255가 할당되므로 최대 메시지 크기는 255 패킷 × 7 byte = 1 785 byte다.
  • sequence number는 1부터 시작해 순차 증가하며, 패킷은 1번부터 오름차순으로 순서대로 전송해야 한다.
  • 마지막 패킷을 제외한 각 패킷은 원본 메시지의 7바이트를 담는다. 마지막 패킷도 데이터 필드는 8바이트로, sequence number + 최소 1바이트의 실데이터 + 남는 바이트는 FF₁₆으로 채운다.
  • multi-packet 브로드캐스트(BAM)의 패킷 간 간격은 10~200 ms다. 특정 목적지 대상 multi-packet에서는 (CTS가 2개 이상을 허용한 경우) 송신 측이 패킷 간 최대 200 ms를 유지해야 하며 최소 시간 요구는 없다.
  • 한 multi-packet 메시지의 모든 데이터 패킷은 같은 CAN identifier를 가진다는 점을 수신 측이 인지해야 한다.
  • 재조립: 패킷들을 sequence number 순으로 단일 바이트 열로 조립해 해당 대형 메시지를 담당하는 응용 개체에 전달한다.

5.10.3 Transport Protocol — Connection management

가상 연결

connection management는 destination-specific 전송을 위한 두 control function 간 가상 연결의 개설·사용·종료를 다룬다. 가상 연결은 단일 PGN으로 기술되는 하나의 대형 메시지 전송을 위한 두 CF의 일시적 결합이다. 일대다(브로드캐스트) 연결에는 흐름 제어와 종료 절차가 없다.

Multi-packet broadcast (BAM)

multi-packet 메시지를 브로드캐스트하려면 먼저 BAM(Broadcast Announce Message)을 전역 목적지 주소로 보낸다. BAM은 브로드캐스트할 대형 메시지의 PGN, 크기, 패킷 수를 담은 예고다. 관심 있는 CF는 수신·재조립에 필요한 자원을 할당해야 한다. 이후 Data Transfer PGN(60 160)으로 데이터를 보낸다.

Connection initiation (RTS/CTS)

  • 연결은 originating CF가 DA로 RTS를 보내며 시작된다. RTS에는 전체 메시지 크기(byte), 총 패킷 수, CTS 하나당 보낼 수 있는 최대 패킷 수, 전송할 메시지의 PGN이 담긴다.
  • RTS를 받은 CF는 연결을 수락하거나 거절할 수 있다. 수락하려면 CTS를 보낸다. CTS에는 받을 수 있는 패킷 수와 기대하는 첫 패킷의 sequence number가 담긴다. 수신 CF는 수락한 패킷 수를 처리할 충분한 자원을 확보해야 한다. 새로 열린 연결에서 첫 기대 sequence number는 1이다.
  • 거절하려면 Connection Abort로 응답한다. 사유는 무엇이든 될 수 있다(자원·메모리 부족 등). RTS를 검토하고 연결하지 않기로 했다면 Connection Abort를 보내는 것이 좋다 — originating CF가 타임아웃을 기다리지 않고 새 연결로 넘어갈 수 있다.
  • 연결 성립 시점: originating CF(RTS 측)는 대응 CTS를 수신했을 때, receiving CF(CTS 측)는 RTS에 대한 CTS를 성공적으로 송신했을 때.

Data transfer와 흐름 제어

  • 데이터 전송은 originating CF가 CTS를 받은 후 시작된다(BAM의 경우 CTS 없이 진행). Data Transfer 패킷은 Data Transfer PGN을 쓰지만 데이터 바이트는 RTS/BAM의 Byte 6~8에 예고된 PGN에 속한다. 데이터 필드 첫 바이트는 sequence number다.
  • destination-specific 전송의 흐름 제어는 receiving CF가 조정한다. 흐름을 잠시 멈추려면 패킷 수 0의 CTS(CTS(0))를 보낸다. 수 초간 멈춰야 하면 연결이 끊기지 않도록 Tₕ(0,5 s)마다 CTS(0)를 반복 송신해야 한다. 나머지 비트 필드는 모두 1("Don't care")로 채운다.

Connection closure

오류가 없을 때의 종료는 두 경우다.

  • 전역 목적지(BAM): 데이터 수신 외에 별도의 종료 절차가 없다. 연결 종료 시점 — originating CF가 마지막 패킷을 보냈을 때, receiving CF는 마지막 패킷을 받았거나 T1 타임아웃이 발생했을 때.
  • 특정 목적지(RTS/CTS): 마지막 패킷을 받은 receiving CF가 End of Message ACK(TP.CM_EndOfMsgACK)를 originating CF에 보낸다. 이것이 연결 종료 신호이며, 다른 CF가 연결을 재사용할 수 있도록 이 종료가 필요하다.

Connection Abort 규칙:

  • 전역 목적지 메시지에는 receiving CF의 Connection Abort 사용이 허용되지 않는다.
  • destination-specific 전송에서는 양측 어느 쪽이든 언제든 Connection Abort로 연결을 종료할 수 있다. 예를 들어 receiving CF가 처리 자원이 없다고 판단하면 abort reason 2로 abort할 수 있고, 이 메시지를 받으면 이미 전달된 패킷은 폐기된다.
  • 타임아웃 등 어떤 사유로든 연결을 닫기로 하면 abort reason 3의 Connection Abort를 보낸다.

한쪽 CF의 고장도 연결 종료를 유발한다. 예시: 추가 패킷이 기대되는 상황에서 마지막 패킷 수신 후 T1 초과, CTS 송신 후 T2 초과(originating CF 고장), 마지막 패킷 송신 후 T3 동안 CTS·ACK 없음(receiving CF 고장), CTS(0) 후 T4 동안 CTS 없음.

TP.CM_RTS

네트워크의 다른 CF가 자신과 가상 연결을 열고 싶다는 것을 알리는 메시지다. SA는 originating CF, DA는 수신 대상 CF다. Byte 5로 originating CF는 CTS 하나에서 지정할 수 있는 패킷 수를 제한할 수 있다 — receiving CF가 이 제한을 지키면, originating CF는 수신 측이 놓친 패킷을 항상 재전송할 수 있음이 보장된다. 같은 SA에서 같은 PGN에 대해 여러 RTS가 오면 가장 최근 RTS를 따르고 이전 RTS는 폐기한다(이 경우 abort 메시지는 보내지 않는다). RTS는 originating CF만 송신한다.

TP.CM_CTS

RTS에 대한 응답으로, 일정량의 대형 메시지 데이터를 받을 준비가 됐음을 알린다. 허용량은 RTS의 Byte 4·5 중 작은 값 이하여야 한다. 연결이 이미 성립된 후 CTS가 여러 개 수신되면 연결을 abort해야 하며, originating CF가 abort할 때는 abort reason 4를 쓴다. receiving CF는 이전 CTS의 마지막 데이터 패킷을 받았거나 타임아웃되기 전에는 다음 CTS를 보낼 수 없다. 타임아웃 시 receiving CF는 connection abort 또는 CTS 중 선택할 수 있다. 오류를 동반한 데이터 전송의 경우:

  • 누락·오류 패킷이 검출됐지만 마지막 패킷은 정상 수신 → 누락된 패킷부터 재전송을 요구하는 CTS를 보낸다.
  • 마지막 패킷을 포함한 누락으로 T1 타임아웃 → receiving CF는 CTS 또는 abort reason 4의 connection abort 중 선택한다.

CTS를 통한 재전송 요구는 2회 이하 권장이며, 한도 도달 시 abort reason 5의 Connection Abort를 보낸다. 연결이 성립되지 않은 상태에서 CTS를 받으면 무시한다. CTS는 흐름 제어일 뿐 아니라 그 CTS의 패킷 번호 이전 데이터의 정상 수신 확인이기도 하다. 따라서 이전 CTS 정보가 손상된 경우 다음 패킷으로 넘어가기 전에 그 손상 정보에 대한 CTS를 보내야 한다. CTS는 receiving CF만 송신한다.

TP.CM_EndOfMsgACK

전체 메시지가 정상 수신·재조립됐음을 receiving CF가 originating CF에 알리는 메시지다. receiving CF는 세션의 마지막 Data Transfer 후 EndOfMsgACK를 바로 보내지 않음으로써 연결을 유지할 수 있다(필요 시 패킷 재전송을 받기 위해). originating CF가 최종 Data Transfer 이전에 EndOfMsgACK를 받으면 무시한다. EndOfMsgACK는 receiving CF만 송신하며, 한 번만 보낸다.

TP.Conn_Abort

가상 연결에 참여한 어느 쪽이든 전송 완료 전에 연결을 닫거나 연결 성립 자체를 막기 위해 쓴다. RTS를 받은 CF는 자원이 충분한지 판단해야 하며(힙 메모리 확보 실패, 처리 여력 부족 등), 연결이 성립되지 않았어도 Connection Abort를 보낼 수 있다 — originating CF가 타임아웃을 기다리지 않고 다른 연결을 시도할 수 있게 하기 위함이다.

originating CF(RTS 측)는 Connection Abort 수신 즉시 송신을 중단해야 한다. 즉시가 불가능하면 중단 절차는 32개 데이터 패킷·50 ms를 넘지 않아야 한다. Connection Abort 송수신 후에는 관련해 수신된 모든 데이터 패킷을 무시한다. Conn_Abort는 양쪽 모두 송신할 수 있다.

5.10.6 Transport Protocol 연결 제약

  • 추가 세션을 처리할 수 없는 CF는 다른 CF의 연결 시도를 거절해야 한다. 같은 SA에서 같은 목적지로 기존 세션과 다른 PGN에 대한 RTS가 와도 거절해야 한다. 두 경우 모두 abort reason 1의 Connection Abort를 보내 요청 측이 타임아웃 없이 다른 연결로 넘어갈 수 있게 한다.
  • 각 CF는 특정 목적지당 동시에 하나의 destination-specific TP 연결만 시작할 수 있다. TP.DT에는 SA·DA만 있고 전송 중인 데이터의 PGN이 없기 때문이다. ETP 세션은 TP 연결과 병행해 열 수 있다.
  • 하나의 originating CF는 동시에 하나의 multi-packet BAM만 보낼 수 있다(TP.DT에 PGN·연결 식별자가 없기 때문). 반면 수신 측은 서로 다른 SA에서 온 여러 multi-packet 메시지가 상호 끼워 넣어져(interleaved) 수신될 수 있음을 인지해야 한다.
  • CF는 같은 SA로부터의 RTS/CTS 세션 1개와 BAM 세션 1개를 동시에 지원할 수 있어야 한다. 하나는 global DA, 다른 하나는 specific DA이므로 DA로 두 세션을 구분한다.
  • 다중 동시 세션 지원 여부와 무관하게, 같은 SA라도 DA가 다른 TP.DT/ETP.DT 메시지를 구별할 수 있어야 하며, 수신 데이터 관리는 DA와 SA를 함께 사용한다. 병렬 TP/ETP 세션의 송신자는 수신자가 세션 중 하나 또는 둘 다를 임의 기간 hold할 수 있어 어느 세션이 먼저 끝날지 예측할 수 없음을 인지해야 한다.
  • TP는 9바이트 이상 PGN 전송용이다. multi-packet 가능으로 정의된 PGN이라도 전송할 데이터가 9바이트 미만이면 DLC 8의 단일 CAN 프레임으로 보낸다.
  • 같은 PG가 8바이트 이하일 때는 비-TP 형태로, 8바이트 초과일 때는 TP 형태로 보내질 수 있고, 두 형태가 동시에 송신될 수도 있다. 비-TP 형태는 세션이 아니므로 같은 PGN의 TP 형태 세션을 닫지 않는다.

5.11 Extended transport protocol functions

5.11.1 개요

ETP는 TP와 유사한 방식으로 기술되며 5.10이 요구사항의 기반이다. 5.10에 대한 참조는 공통 동작·요구사항을 정의하고, 구현은 ETP 메시지로 한다(예: TP.CM_CTS에 대한 요구사항은 ETP.CM_CTS로 구현).

1 785바이트를 초과하는 메시지는 TP 세션에 담을 수 없으므로 ETP를 사용한다. ETP는 3바이트의 extended data packet offset을 사용해 최대 메시지 크기가 2²⁴ − 1 패킷 × 7 byte = 117 440 505 byte다. ETP의 타이밍은 TP와 동일하다.

5.12 PDU 처리 요구사항

PDU 해석의 권장 절차는 Annex A에, 메시지 타입·PDU 포맷 사용 예는 Annex C에 있다. 컨트롤러는 데이터 링크가 100 % 사용률일 때에도 메시지를 잃지 않을 만큼 빠르게 데이터 링크 메시지를 처리할 수 있어야 한다. 저사용률 상황에서도 back-to-back 메시지를 잃지 않아야 한다. "빠른 처리"가 즉시 응답 생성을 뜻하는 것은 아니며, 새 메시지가 이전 메시지를 덮어쓰지(overrun) 않아야 한다는 의미다.

5.13 Application notes

고속 데이터와 요청 스케줄링

  • High data rates: 갱신 주기가 빠르고 지연 요구가 엄격한 데이터는 가능하면 하드웨어 기반 메시지 필터링이 가능하도록 설계한다.
  • Request scheduling: 요청 예정 정보가 요청 송신 전에 이미 수신됐다면 요청을 취소해야 한다(예: 요청 스케줄링 50 ms 전에 정보가 수신되면 요청하지 않는다). 브로드캐스트가 권장되는 PG는 요청하지 않는다. 단 권장 브로드캐스트 주기가 특수한 필요를 초과하는 경우는 예외가 될 수 있다.

응답 시간·타임아웃 기본값

  • 응답이 요구되는 모든 컨트롤러는 0,20 s(Tr) 이내에 응답해야 한다.
  • 응답을 기다리는 모든 컨트롤러는 포기·재시도 전에 최소 1,25 s(T3)를 기다려야 한다. 이 값들은 버스 접근·브리지 경유 전달 지연이 원치 않는 타임아웃을 만들지 않도록 보장한다.
  • 필요 시 특정 응용에는 다른 시간 값을 쓸 수 있다(예: 고속 제어 메시지는 20 ms 응답 기대). 더 빠른 응답을 위해 버퍼된 메시지의 재정렬이 필요할 수 있다. 최소 응답 시간 제한은 없다.
  • destination-specific multi-packet의 패킷 간 시간은 0~200 ms(back-to-back 허용 — 같은 identifier를 가질 수 있음). CTS 메커니즘으로 패킷 간 간격을 강제할 수 있다(흐름 제어).
  • multi-packet 브로드캐스트의 패킷 간 시간은 10~200 ms. 최소 10 ms는 수신 CF가 CAN 하드웨어에서 메시지를 꺼낼 시간을 보장한다. 수신 CF는 T1 = 750 ms 타임아웃을 사용한다(최대 송신 간격 200 ms보다 큼).

T3 = 1,25 s의 산정 예: 브리지 하나의 최대 순방향 지연 50 ms × 브리지 10개(트랙터 1 + 트레일러 5 + 돌리 4) = 편도 500 ms의 네트워크 지연, 재전송 요구(CTS에 의한 재요청) 한도 2회(총 3회 요청, 한도 도달 시 abort reason 5), 타임아웃 마진 50 ms.

필수 응답 등

  • 전역 요청에는 해당 PG를 사용하는 모든 CF가 응답해야 하며, 요청자 자신도 포함된다. 전역 요청에 대한 Acknowledgement는 허용되지 않는다. 요청자가 스스로 응답하지 않으면 다른 CF들이 요청된 정보에 대해 잘못된 결론을 내릴 수 있기 때문이다(예: address request).
  • 주기적으로 브로드캐스트되는 PGN은 대부분 전역 목적지로 보내는 것이 바람직하다.
  • 일반적인 임플리먼트 운용 중 CTS당 최대 패킷 수는 16 권장.

  4. PF ≥ 240 (PDU2): 관심 PGN 점프 테이블 사용, SA가 특별 관심 대상이면 전용 버퍼에, 아니면 12바이트 메시지를 순환 큐에 저장.

  4. receiving CF가 CTS(0) — 연결은 유지하되 당장 수신 불가(hold). 최대 500 ms 후 다시 CTS를 보내야 한다.
  5. receiving CF가 TP.CM_CTS(패킷 2, 시작 3) → TP.DT 3(데이터 15~21), TP.DT 4(데이터 22~23 + 나머지 FF₁₆) 전송.
  6. receiving CF가 TP.CM_EndOfMsgACK(19, 23, 4, 255, 65 259) 송신 — 연결 종료.

각 구간에는 5.10.3.5의 타이밍(Tr ≤ 200 ms, T1 ≤ 750 ms, T2 = 1 250 ms, T3 = 1 250 ms, T4 ≤ 1 050 ms, Th ≤ 500 ms)이 적용된다.

B.2 오류를 동반한 전송 — 패킷 2가 체크섬 실패 등으로 오류 판정되면, receiving CF는 CTS(패킷 1개, 시작 2)로 패킷 2 재전송을 요구한다. 재전송 후 CTS(패킷 2, 시작 3)를 보내는데, 이는 패킷 1·2의 정상 수신 확인이기도 하다. 마지막 패킷까지 정상 수신하면 EndOfMsgACK를 보낸다.

B.3 브로드캐스트 전송 — tractor identification(PGN 65 260) 17바이트를 브로드캐스트하는 예. TP.CM_BAM(32, 17, 3, 255, 65 260) 송신 후 TP.DT 1~3을 각각 10~200 ms 간격으로 전송한다. 어떤 수신 CF도 acknowledgement를 하지 않는다. 수신 측은 패킷마다 T1(750 ms) 타임아웃을 적용한다.

B.4 / B.5 Maximum Number of Packets 파라미터 — B.4는 양쪽 모두 RTS Byte 5(CTS당 최대 패킷 수) 파라미터를 지원해 originating CF가 수신 측의 요구량을 제한하는 예다. B.5는 originating CF만 지원하고 receiving CF는 지원하지 않는 상황으로, 이때 originating CF는 수신 측 CTS 한도를 따라야 한다(5개씩 보내고 싶어도 CTS가 7개를 지시하면 7개 전송).

재전송 데이터의 일관성

B.5의 예에서 패킷 7 전송 후 수신 측이 패킷 1에 대한 CTS를 다시 보내면, originating CF가 정보를 재계산해야 할 수 있어 두 번째 전송의 패킷 1이 원래 패킷 1과 다른 데이터를 담을 수 있다. 동적 데이터를 가진 PGN(예: 65 227)은 이런 위험이 있고, 정적 데이터 PGN(예: 65 242)은 문제가 없다.

B.6 CTS 그룹의 마지막 패킷 누락 — receiving CF는 세션 abort를 피하기 위해 CTS(재전송 요구)를 보낸다.

B.7 타임아웃 시 CTS — 느린 송신 CF의 경우: 12패킷 CTS 그룹 전송 중 수신 측의 재전송 CTS가 마지막 데이터 패킷 송신 전에 도착하면, 송신 CF는 abort reason 4로 세션을 abort한다(재전송 CTS가 abort를 막지 못하는 사례). 빠른 송신 CF의 경우: 재전송 CTS가 마지막 데이터 패킷 송신 후·T3 타임아웃 전에 도착하면 송신 CF가 CTS를 수용해 세션 abort를 피할 수 있다.

Annex C (참고) — 통신 모드 예시

엔진 ECU를 예로 든 메시지 타입 사용 시나리오다.

  1. BROADCAST/RESPONSE: 엔진 시리얼 번호(Component ID, PGN 65 259 = 00FEEB₁₆)를 브로드캐스트한다.
  2. DESTINATION SPECIFIC REQUEST (PGN 59 904): 엔진 시리얼 번호에 대한 특정 요청을 받으면, 데이터를 담은 RESPONSE 또는 NACK로 응답한다.
  3. GLOBAL REQUEST: 전역 요청을 받으면 데이터를 가진 특정 CF가 RESPONSE를 보낸다. 전역 요청에는 acknowledgement를 쓰지 않는다.
  4. COMMAND: 일부 command는 작업 완료의 확인이 필요할 수 있다. 이때 ACK(= COMMAND COMPLETE) 또는 NACK(= COMMAND NOT ABLE TO BE COMPLETED)를 돌려보낼 수 있다.
  5. ACK/NACK: command·request를 처리할 수 없으면(잘못된 요청) NACK를 보내며, NACK 데이터 필드에는 문제된 PGN이 담긴다. COMMAND·REQUEST의 PGN을 목적지가 인식하지 못해도 NACK를 보내야 한다. PGN은 인식하지만 파라미터가 가용하지 않으면 데이터 값을 255로 채운 정상 응답을 보낸다.

ACK 생략 가능

command에는 항상 동작 성공 여부를 확인할 수단이 있다. 다른 확인 수단이 있으면 ACK 메시지는 필수가 아니며, 이는 버스 트래픽 최소화에 도움이 된다. 예를 들어 엔진에 대한 torque command는 엔진이 내보내는 torque mode 비트와 torque 값으로 확인할 수 있다.

Annex D (참고) — 네트워크 대역폭 활용

ISO 11783 같은 개방형 시스템에서는 CAN 네트워크 대역폭 활용이 매우 중요하다. 설계가 부주의하면 메시징 수요가 네트워크 용량을 초과할 수 있다. 대역폭·지연을 관리하는 수단은 proprietary PG·CBFF 통신 사용 제한, 주기 메시지의 주기를 실용적인 한도에서 최대한 느리게 설정, PG의 기본 priority다. 강력 권장 사항:

  • 정상 운용 중 proprietary 메시지 사용 최소화 — Proprietary A + A2 + B의 합이 네트워크 용량의 2 % 이하.
  • CBFF 메시징은 CEFF와 공존할 수 있지만, CEFF ISO 11783 네트워크 대역폭 보존을 위해 CBFF 트래픽은 서브넷으로 격리하는 것이 권장된다.
  • 기본 priority는 아래 분류에 따라 적용한다.
