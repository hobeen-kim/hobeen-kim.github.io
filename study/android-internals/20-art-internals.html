CH20. ART 내부 구조

ART(Android Runtime)는 앱의 DEX 바이트코드를 실제로 실행하는 엔진이다. CH19에서 본 DEX가 입력이라면, ART는 그것을 인터프리터로 돌리거나, JIT로 컴파일하거나, dex2oat로 미리 네이티브 코드로 굽는 다층 실행 시스템이다. 이 챕터는 ART를 구성하는 APEX와 파일 포맷들, 컴파일 전략의 진화, GC, 그리고 임베디드 기기에서 부팅 시간을 좌우하는 dexopt 실무를 파고든다. first-boot에 몇 분이 걸리는 문제를 다뤄야 하는 커스텀 OS 개발에 직결된다.

학습 목표

  • com.android.art APEX가 무엇을 담고 왜 Mainline로 업데이트되는지 이해한다.
  • OAT/ART(이미지)/VDEX/CDEX 파일과 boot image, dalvik-cache의 역할을 구분한다.
  • 순수 AOT에서 인터프리터+JIT+프로파일 기반 AOT 하이브리드로의 진화와 compiler filter를 파악한다.
  • JIT 코드 캐시·OSR·프로파일(profman)·baseline profile의 동작을 안다.
  • CC GC의 구조와 dexopt 상태 확인, first-boot 단축 전략을 익힌다.

ART 개관

ART는 Android 5.0에서 Dalvik을 대체했고, Android 10부터는 com.android.art APEX로 패키징돼 Mainline을 통해 OS 전체 업데이트 없이 독립적으로 갱신될 수 있다. 런타임의 핵심 버그 수정이나 성능 개선이 플랫폼 릴리스 주기와 분리되는 것이다.

APEX 안에는 ART를 이루는 삼각 편대가 들어 있다.

  • dex2oat — DEX를 네이티브 코드·최적화 산출물로 변환하는 AOT 컴파일러.
  • dexopt(오케스트레이션) — 언제 무엇을 어떤 수준으로 컴파일할지 결정하고 dex2oat를 호출하는 로직(현대의 artd/odrefresh 등).
  • 런타임(libart) — 인터프리터, JIT 컴파일러, GC, 클래스 로더, JNI 구현을 담은 실행 코어.

이 셋이 협업해 "설치 시 얼마나 미리 컴파일하고, 실행 중엔 무엇을 JIT로 굽고, 유휴 시엔 무엇을 다시 최적화할지"를 조율한다.

파일 포맷들

ART는 DEX 하나에서 여러 파생 파일을 만든다. 각 파일이 무슨 역할인지 구분하는 것이 dexopt를 이해하는 출발점이다.

  • OAT (.odex)는 dex2oat가 만든 AOT 네이티브 코드를 담은 ELF 컨테이너다. 미리 컴파일된 메서드의 기계어가 여기 들어가, 실행 시 인터프리터를 거치지 않고 바로 뛴다.
  • VDEX (.vdex)는 검증된(verified) DEX와 quicken 정보를 담는다. DEX 검증(verification)은 비싼 작업인데, 한 번 검증한 결과를 VDEX에 저장해두면 재부팅이나 재최적화 시 재검증을 생략할 수 있다. 컴파일을 하지 않는 verify 필터에서도 VDEX는 생성된다.
  • ART 이미지 (.art)는 미리 초기화된 힙 이미지다. 자주 쓰는 클래스와 객체를 미리 만들어 메모리 맵으로 담아두어, 실행 시 클래스 초기화·객체 생성 비용을 줄인다.
  • CDEX (Compact DEX)는 여러 DEX의 공유 데이터를 묶어 중복을 줄인 압축 포맷으로, VDEX 안에 담겨 저장 공간을 절약한다.

이 산출물들의 저장 위치는 두 곳이다. 앱별 산출물은 /data/app/<pkg>-<rand>/oat/<abi>/에, boot image와 시스템 컴포넌트 산출물은 /data/dalvik-cache/<abi>/에 놓인다. boot image(boot.art/boot.oat)는 프레임워크의 핵심 클래스를 미리 컴파일·초기화해 둔 것으로, 모든 앱 프로세스가 Zygote를 통해 공유한다. 그래서 boot image 재생성은 부팅 시간에 큰 영향을 준다.

# 앱의 dexopt 산출물 확인
ls -l /data/app/*/com.example.app*/oat/arm64/

# boot image·시스템 dex 캐시
ls -l /data/dalvik-cache/arm64/ | head

런타임 초기화

앱 프로세스가 Zygote fork로 태어날 때 ART 런타임은 이미 부모 Zygote에서 초기화돼 있다. Zygote는 부팅 시 boot image를 메모리에 매핑하고, preloaded-classes 목록의 클래스들을 미리 로드하며, 자주 쓰는 리소스를 준비한다. 이 상태를 fork로 물려받으므로 각 앱은 ART를 처음부터 세우는 비용을 치르지 않는다.

런타임 동작은 런타임 플래그로 조정된다. dalvik.vm.* 시스템 프로퍼티(CH10 참고)로 힙 크기, GC 종류, JIT 활성화 여부, 이미지 로딩 방식을 설정한다.

# 주요 런타임 프로퍼티 확인
getprop dalvik.vm.heapsize
getprop dalvik.vm.image-dex2oat-filter
getprop dalvik.vm.dex2oat-filter

컴파일 전략의 진화

ART의 컴파일 전략은 극단 사이를 오가며 균형점을 찾아왔다.

  • Android 5.0 — 순수 AOT. 설치 시점에 앱의 모든 DEX를 dex2oat로 컴파일했다. 실행은 빠르지만 설치가 느리고(모든 메서드 컴파일), 저장 공간을 많이 먹고, 앱 대부분이 실제로는 안 쓰이는 코드까지 굽는 낭비가 있었다.
  • Android 7.0+ — 하이브리드. 인터프리터 + JIT + 프로파일 기반 AOT를 결합했다. 설치 시엔 컴파일을 거의 안 하고, 실행하면서 실제로 hot한 메서드만 프로파일에 기록하고, 유휴·충전 시 그 프로파일을 근거로 필요한 부분만 AOT 컴파일한다. 설치는 빠르고, 시간이 지날수록 자주 쓰는 경로가 최적화된다.

이 전략의 핵심 다이얼이 compiler filter다. dex2oat에 "얼마나 깊이 컴파일할지"를 지시한다.

  • verify — 컴파일하지 않고 DEX 검증만 한다(VDEX 생성). 실행은 인터프리터.
  • quicken(구버전) — 일부 바이트코드를 빠른 변형으로 치환. 최신 버전에서는 verify에 통합·정리됐다.
  • speed-profile — 프로파일에 있는 hot 메서드만 AOT 컴파일. 하이브리드의 기본값으로, 균형이 가장 좋다.
  • speed — 프로파일 무시하고 전부 AOT 컴파일. 순수 AOT에 해당하며, 컴파일 시간·용량이 크지만 콜드 실행이 빠르다.

baseline profile은 앱 개발자가 "이 메서드들은 처음부터 hot이다"라고 미리 제공하는 프로파일이다. 앱에 동봉되거나 Play가 배포하며, 사용자가 앱을 쓰기 전에도 중요한 경로를 speed-profile로 컴파일해 첫 실행부터 빠르게 만든다.

JIT

하이브리드에서 인터프리터로 실행되던 메서드가 자주 불리면(hot) ART의 JIT 컴파일러가 개입한다.

  • hot method 감지. 런타임이 메서드·기본 블록의 실행 카운터를 세다가 임계치를 넘으면 컴파일 후보로 올린다.
  • JIT 코드 캐시. JIT가 생성한 네이티브 코드는 프로세스별 JIT 코드 캐시(실행 가능 메모리 영역)에 담긴다. 프로세스가 죽으면 사라지지만, 실행 중엔 인터프리터보다 훨씬 빠르다.
  • OSR(On-Stack Replacement). 오래 도는 루프가 있으면, 그 메서드가 리턴하기를 기다리지 않고 실행 중인 스택 프레임을 컴파일된 코드로 교체해 루프 도중에 최적화 코드로 전환한다. 긴 루프의 성능 절벽을 막는 장치다.

JIT는 실행 중 프로파일을 함께 기록해, 이 정보가 나중에 speed-profile AOT의 입력이 된다. 즉 JIT와 AOT가 프로파일을 매개로 연결돼 있다.

프로파일

프로파일은 "이 앱에서 무엇이 hot한가"를 담은 데이터로, 하이브리드 전략의 심장이다.

  • profman은 프로파일을 생성·병합·검사하는 도구다. JIT가 실행 중 관찰한 hot 메서드·클래스를 프로파일 파일로 만든다.
  • 프로파일은 /data/misc/profiles/에 저장된다. cur/에 현재 실행 프로파일이, ref/에 AOT에 반영된 기준 프로파일이 있다.
  • cloud profile(집계 프로파일). Play는 여러 사용자의 프로파일을 익명 집계해 "이 앱은 대체로 이 경로가 hot하다"는 baseline을 만들어 배포한다. 개별 사용자가 앱을 충분히 쓰기 전에도 좋은 초기 프로파일을 갖게 한다.
# 앱 프로파일을 사람이 읽는 형태로 덤프
profman --dump-only \
  --profile-file=/data/misc/profiles/cur/0/com.example.app/primary.prof

# 프로파일 기반 재컴파일 강제
pm compile -m speed-profile -f com.example.app

GC

ART의 기본 가비지 컬렉터는 CC(Concurrent Copying) collector다. 앱의 반응성을 지키는 것이 최우선 목표다.

  • 동시성(Concurrent). GC 작업 대부분을 앱 스레드와 동시에 수행해, 앱을 멈추는 stop-the-world 구간을 아주 짧게(수백 마이크로초 수준) 유지한다. 프레임 드랍을 막는 핵심이다.
  • 복사(Copying). 살아있는 객체를 새 영역으로 복사하면서 힙을 압축(compaction)해 단편화를 없앤다. 복사 방식이라 할당이 포인터 증가만으로 빠르다.
  • region-based heap. 힙을 고정 크기 region으로 나눠 관리한다. region 단위로 비우고 복사해 큰 객체·작은 객체를 효율적으로 다룬다.
  • young / full GC. 대부분의 객체는 금방 죽는다는 세대 가설에 따라, 새로 할당된 객체 위주로 자주 도는 가벼운 GC와, 힙 전체를 훑는 무거운 full GC를 구분한다.

GC 로그는 logcat에 남아 성능 문제 진단에 쓰인다. Background concurrent copying GC freed ... paused 0.5ms처럼 해제량과 일시정지 시간이 찍힌다.

# GC 관련 로그만 필터
adb logcat -s art | grep -i gc

# 힙 상태 스냅샷
dumpsys meminfo com.example.app | sed -n '1,25p'

일시정지가 길거나 GC가 잦으면 메모리 누수나 과도한 객체 할당을 의심한다. 리눅스 관점의 메모리 지표는 CH11, CH12와 함께 본다.

실무 팁 — 임베디드 기기의 dexopt

임베디드·커스텀 안드로이드에서 ART가 가장 크게 체감되는 지점이 first-boot 시간이다. 공장 초기화나 OTA 직후 첫 부팅에서 boot image와 프리로드 앱을 컴파일하느라 몇 분씩 걸리는 일이 흔하다. 대응 전략을 정리한다.

dexopt 상태 확인. 어떤 앱이 어떤 필터로 컴파일됐는지부터 본다.

# 앱별 dexopt 상태·사용된 compiler filter
dumpsys package dexopt | grep -A2 com.example.app

# 전체 dexopt 상태 요약
dumpsys package dexopt | sed -n '1,20p'

부팅 후 bg-dexopt. 시스템은 유휴·충전 중에 background dexopt 잡을 돌려, 그동안 쌓인 프로파일로 앱을 speed-profile 재컴파일한다. 수동 트리거도 가능하다.

# 백그라운드 dexopt 즉시 실행
pm bg-dexopt-job

# 특정 앱만 재컴파일
pm compile -m speed -f com.oem.dashboard

first-boot 단축 전략. 커스텀 OS에서 쓰는 실전 접근은 다음과 같다.

  • 빌드 시 dexpreopt. 프리로드 앱과 boot image를 빌드 타임에 미리 컴파일해 시스템/제품 이미지에 심는다(WITH_DEXPREOPT := true). 기기의 first-boot에서 컴파일할 양이 줄어든다.
  • 필터 선택. 자주 쓰는 시스템 앱은 speed로 dexpreopt해 콜드 실행을 빠르게 하고, 나머지는 speed-profile/verify로 두어 이미지 크기와 부팅 시간을 절충한다. 스토리지가 빠듯한 기기에서는 특히 이 트레이드오프가 중요하다.
  • boot image 프로파일 관리. preloaded-classes와 boot image 프로파일을 기기 실사용에 맞게 조정해, boot image에 꼭 필요한 것만 넣어 재생성 비용을 줄인다.
  • A/B와의 조합. A/B 업데이트에서는 비활성 슬롯에 대해 OTA 적용 중 dexopt를 미리 수행해, 재부팅 후 first-boot 컴파일을 없애는 것이 표준이다.

농기계처럼 부팅 즉시 CAN 통신·계기판이 떠야 하는 기기라면, 핵심 UI 앱을 빌드 시 dexpreopt(speed)로 굽고 boot image를 실사용 프로파일에 맞춰 최소화하는 것이 first-boot 체감을 좌우한다. 네이티브 CAN 데몬 자체는 DEX가 아니라 네이티브 실행 파일이므로 dexopt 대상이 아니며, 이는 CH23 케이스 스터디에서 다룬다.

핵심 정리

  • ART는 com.android.art APEX로 패키징돼 Mainline로 독립 업데이트되며, dex2oat·dexopt·libart 런타임으로 구성된다.
  • DEX에서 파생되는 OAT(네이티브 코드)·VDEX(검증된 DEX)·ART 이미지(초기화된 힙)·CDEX(압축)가 oat 디렉토리와 dalvik-cache에 저장된다.
  • 컴파일 전략은 순수 AOT(5.0)에서 인터프리터+JIT+프로파일 기반 AOT(7.0+)로 진화했고, compiler filter(verify/speed-profile/speed)로 조절한다.
  • JIT는 hot 메서드를 코드 캐시에 굽고 OSR로 루프를 최적화하며, profman 프로파일과 baseline/cloud profile이 AOT를 이끈다.
  • CC GC는 동시·복사·region 기반으로 일시정지를 최소화하며, 임베디드 기기는 빌드 시 dexpreopt와 bg-dexopt로 first-boot를 단축한다.
