ISO 11783-14: Sequence control 정리

이 문서에 대해

ISO 11783-14 표준 원문을 학습 목적으로 재구성한 비공식 요약·해설이다. 규범적 판단이 필요할 때는 반드시 원문 표준을 확인해야 한다.

개요

ISO 11783-14:2013은 ISO 11783 시리즈의 열네 번째 파트로, Sequence Control(시퀀스 제어) 시스템을 정의한다. 대표적인 적용 예가 headland management system(두렁 관리 시스템)이다. 트랙터가 두렁(headland)에 도달해 선회할 때마다 오퍼레이터가 매번 수동으로 반복하는 일련의 조작 — PTO 정지, 히치 상승, 밸브 전환 등 — 을 한 번 기록(recording)해 두고, 이후 오퍼레이터의 명령 한 번으로 재생(play back)할 수 있게 하는 것이 이 파트의 목적이다.

핵심 아이디어는 다음과 같다.

  • 오퍼레이터가 기록 모드를 시작한 뒤 평소처럼 각 기능을 수동 조작한다.
  • 각 기능을 보유한 ECU(SCC, Sequence Control Client)가 조작 정보를 client command 형태로 네트워크에 알린다.
  • 마스터(SCM, Sequence Control Master)가 이 명령들을 trigger 정보(시간·거리 등)와 함께 저장한다.
  • 재생 시 SCM이 저장된 시점(trigger point)에 도달할 때마다 해당 client command를 SCC에 전송하고, SCC는 오퍼레이터가 수동 조작한 것과 동일하게 그 기능을 실행한다.

SCC들은 서로 독립적이며 SCC 간 직접 통신은 필요 없다. 문서 구성은 본문(4장 기술 요구사항)과 normative 부속서 6개(A: SCD 데이터 정의, B: 메시지 정의, C: technical data 메시지, D: SCD operation 메시지, E: sequence control 메시지, F: status 메시지)로 이루어진다.

문서 기본 정보

  • 표준 번호: ISO 11783-14:2013(E), 1판(2013-09-15 발행)
  • 담당 위원회: ISO/TC 23(농림업용 트랙터·기계) / SC 19(농업 전자)
  • CAN(ISO 11898-1) 기반이며, SAE J1939와 공동 개발된 문서 체계를 따른다.

1~2장: 적용 범위와 인용 표준

ISO 11783 전체는 농림업용 트랙터와 mounted/semi-mounted/towed/자주식 작업기를 위한 직렬 제어·통신 데이터 네트워크를 규정한다. Part 14는 그중 시퀀스 제어 시스템을 규정하며, 트랙터·작업기 기능을 하나의 시스템으로 묶어 오퍼레이터 조작 시퀀스를 기록하고 명령에 따라 재생하는 기능을 다룬다.

4.1 기술 요구사항 — 일반

시퀀스 제어 시스템은 headland turn이나 waterway 횡단 제어처럼 반복 구간에서 기계가 자동 기능을 수행하게 한다. 동작 개요는 다음과 같다.

  1. 기록: 오퍼레이터가 기록 단계를 시작하고, 자동화할 client function들을 각 SCC의 조작 인터페이스로 평소처럼 활성화한다. SCM은 활성화된 기능 정보를 client command로 수신하고, 자신이 부여한 trigger 정보와 함께 저장한다.
  2. 재생: 저장된 시퀀스는 여러 번 재생할 수 있다. SCM은 재생 시작 후 각 기능의 trigger point에 도달하면 해당 client command를 SCC에 전송한다. SCC는 수신한 명령을 오퍼레이터가 자기 고유 입력장치로 수동 조작한 것과 동일한 방식으로 실행한다.

시퀀스 식별·관리에 대한 규칙은 다음과 같다.

  • 각 시퀀스는 SC 내에서 유일한 번호를 가진다. 다중 시퀀스 지원 시 오퍼레이터가 시퀀스를 어떻게 식별하게 할지는 SCM 구현에 달렸다(예: 시퀀스별 이름 부여).
  • SCM은 여러 시퀀스를 하나의 descriptor(예: "Seeding")로 묶어 저장할 수 있다(예: 두렁 접근용 + 이탈용).
  • SCM은 SCC가 제공한 아이콘·텍스트 designator로 기록된 시퀀스를 UI에 표시할 수 있다.
  • 구현에 따라 오퍼레이터가 시퀀스를 수동 정의하거나, trigger point 타이밍 등 파라미터를 편집할 수 있다.
  • SCM은 특정 기계 구성(트랙터-작업기 조합)에 대한 시퀀스 저장·재로드 기능을 제공할 수 있다.

SCM의 필수/선택 기능 구분:

구분기능
필수(shall)시퀀스 설정 수단(RECORD 또는 EDIT), 선택한 시퀀스의 재생 활성화(PLAY BACK)
선택(may)SCM 구성(CONFIG) 수단, 식별된 SCC와 그 기능·trigger 옵션의 표시, 특정 SCC의 enable/disable 수단

SCC enable/disable은 기록·편집 시 시스템 구성 복잡도와 버스 부하를 줄이기 위한 것이며, SCM은 enabled SCC만 시퀀스 관리에 포함해야 한다. 시퀀스 제어 지원은 네트워크에 연결된 어떤 CF든 구현할 수 있다.

4.2 Sequence control 사용자 인터페이스

SCM은 경고 표시와 오퍼레이터 상호작용을 위해 VT에 접속하고 자신의 메인 화면 레이아웃(object pool)을 업로드해야 한다.

시퀀스 상세 보기 같은 선택적 SCM 기능을 위해, SCC는 자기 기능의 그래픽·텍스트 표현을 SCM에 제공해야 한다. SCD 오브젝트마다 텍스트 designator와 그래픽이 모두 있으므로, SCM은 텍스트만, 그래픽만, 또는 둘 다 조합해 SCC 오브젝트를 표시하는 방식을 자유롭게 구현할 수 있다.

External Object Pointer 개념

이 통신 개념은 VT version 5에서 도입된 External Object Pointer를 사용한다. 핵심 동기는 SCM이 개별 SCC의 대형 그래픽 오브젝트나 언어 업데이트를 직접 처리하지 않게 하는 것이다.

  • 각 SCC(또는 그 working set master)는 그래픽·텍스트 오브젝트를 자신의 SCCOP에 담아 SCM이 사용하는 것과 같은 VT에 업로드한다.
  • SCC는 SCD에는 참조 정보(object ID)만 담아 SCM에 전달한다.
  • SCM은 자신의 data mask에서 해당 오브젝트를 보여줄 자리에 External Object Pointer 참조를 넣는다. 이 참조가 SCCOP 내 오브젝트를 가리키므로 VT가 SCM 화면 안에 SCC의 오브젝트를 표시할 수 있다.

SCM과 SCCWS의 working set master는 function instance 0인 VT에 접속해 object pool을 업로드해야 한다. SCM과 SCC가 서로 다른 VT를 고르면 동기화 오버헤드가 생기기 때문이다. 이로 인해 SCCWS의 주 오퍼레이터 UI가 다른 VT(function instance > 0)에서 처리되는 경우, SCCWS는 두 개의 VT 연결을 병렬로 유지해야 할 수 있다. 이 개념은 ISO 11783-6의 Auxiliary Control 정의를 따르며, SCCWS가 하나의 SCCOP 안에서 두 기능(주 UI + SC용 오브젝트)의 오브젝트를 병합·공유할 수 있게 한다. 또한 텍스트 표현 오브젝트에 Unicode 등 ISO 11783-6의 언어·문자셋 능력을 SCM 개입 없이 SCC-VT 간 직접 사용할 수 있다.

4.2.1 사용자 인터페이스 초기화

초기화 과정에서 SCM은 새 object pool을 업로드하거나 이전에 로드한 pool을 재활성화한다. 외부 참조 메커니즘은 NAME 기반으로 동작한다.

  • External object pointer 개념은 NAME 기반이다. object 참조에서 SCCOP와 SCCWS를 확실히 식별하기 위함이다.
  • SCMOP는 External Reference NAME Object를 포함한다. 참조 변경 때마다 완전한 NAME(8바이트)을 통신하는 것을 피하기 위해, SCM–VT 통신에는 External Reference NAME Object의 2바이트 object ID를 대신 쓴다.
  • SCM은 SCD에 담긴 개별 object 참조의 타입을 검사할 수단이 없고 object ID만 안다. 따라서 그래픽·텍스트 표현에 적절한 오브젝트를 쓰는 책임은 SCC에 있다. SCM은 VT가 object 참조를 거부하는 경우에 대한 대비책을 갖추어야 한다.
  • 초기 SCMOP 업로드 시 External Reference NAME Object는 disabled 상태여야 하고, External Object Pointer 속성은 NULL Object ID(FFFF16)로 설정해야 한다.

초기화 후 참조가 확립되는 절차는 다음과 같다.

  1. SCCWS는 active SCM의 NAME을 검증한 뒤, Change Attribute 명령으로 자신의 External Object Definition object의 NAME 필드를 갱신·활성화한다(Option = enabled). 이로써 VT가 SCMOP에서 SCCOP 내 정의된 오브젝트로의 참조를 확립할 수 있다.
  2. SCM도 참조하는 SCC들의 NAME을 검증하고, 자신의 External Reference NAME object의 NAME 필드를 갱신·활성화한다. 이것이 SCCOP로의 일반 연결을 확립한다.
  3. SCM은 SCD로 받은 참조 데이터로 자신의 External Object Pointer 오브젝트를 구성한다. 보통 포인터 하나당 Change Attribute 두 번이 필요하다 — 하나는 External Reference NAME object ID 설정, 하나는 원하는 External Object ID 설정.

External Object Definition object는 접근 허가 검사 역할도 한다. 그 목록에 등재된 오브젝트만 SCM이 참조할 수 있다.

4.4 시퀀스 관리 기능

시퀀스 관리 기능은 네트워크에 연결된 임의 CF에 상주하는 소프트웨어 논리 엔터티다. 기본 규칙:

  • SCM은 메모리 제약 등으로 SCC의 접근·SCD 업로드를 제한할 수 있다.
  • SCM은 SCC당 SCD를 하나만 비휘발성 메모리에 보관해야 한다.
  • 각 SCM은 기록된 시퀀스를 자율적으로 저장·관리한다. SCM 간 또는 데스크톱 컴퓨터로의 시퀀스 이동 방식은 이 파트에서 정의하지 않는다.

4.4.2 초기화

시스템 시동 시 SCM·SCC들은 ISO 11783-5의 주소 클레임 절차에 따라 독립 유닛으로 자신을 식별한다. 기본 규칙:

  • 모든 SCM은 inactive로, 모든 SCC는 disabled로 시작해야 한다.
  • SCM·SCC 모두 상태 메시지(F.2, F.3)의 송신 상태를 initialization으로 설정해 시동을 알려야 한다. 이로써 다른 참여자들이 예기치 않은 리셋을 감지할 수 있다.

SCM 초기화 절차

  1. SCM은 function instance 0인 VT에 자신을 식별시키고 object pool을 업로드한다. 기본적으로 모든 external object pointer는 비활성(파라미터 FFFF16)이다.
  2. 모든 SCM은 오퍼레이터가 UI로 활성화할 때까지 inactive를 유지해야 한다. 오퍼레이터는 언제든 active SCM을 바꿀 수 있어야 한다.
  3. 선택된 SCM은 SCMasterStatus 메시지를 연속 송신하여(active SCM 상태 + 해당 sequence state 표시) 활성화·시동을 알려야 한다.
  4. 시동 후 active SCM은 휘발성 메모리의 SCD 정보를 모두 삭제하고, SCC가 시동 표시를 하기 전까지는 시동 표시 이외의 SCClientStatus 메시지를 모두 NACK해야 한다. (예외: SCMasterStatus 주기 내의 quick reset 직후에는 바로 수신 가능)
  5. SCDActivationCommand(D.8)를 받으면 SCM은 SCD 파싱을 시작하고, 파싱 활동을 SCMasterStatus 메시지에 표시한다.

SCC 초기화 절차

  1. active SCM의 SCMasterStatus 메시지를 수신하면, SCC는 자신의 SCClientStatus 메시지를 disabled 상태로 연속 송신하기 시작해야 한다. 첫 SCClientStatus 메시지는 client initialization을 표시해야 한다(F.3 byte 2). SCC는 active SCM이 enable 명령을 내릴 때만 enabled로 전이할 수 있다. SCC가 SCM보다 먼저 부팅되면 SCMasterStatus 수신 전까지 자신의 SCClientStatus 송신을 시작하지 않고 기다려야 한다.
  2. SCC는 active SCM의 capability를 요청(C.2/C.3)하여 표준 버전이 서로 맞는지 확인하고, 자신의 object pool이 SCM의 그래픽 오브젝트 크기 요구(C.3 byte 3~4)와 폰트 정의(C.3 byte 5~10)를 만족하는지 확인해야 한다. 오브젝트가 정의보다 크면 VT에서 중요한 정보가 잘릴 수 있기 때문이다.
  3. SCC의 working set master는 function instance 0인 VT에 자신을 식별시키고, 색상/모노크롬·언어 설정 등 VT capability를 조회해 object pool을 그에 맞게 조정한 뒤 업로드한다. 자체 UI를 이 VT로 제공하지 않는 경우라도, SCMOP에서 쓸 텍스트·그래픽 오브젝트를 담은 SCCOP만큼은 최소한 업로드해야 한다.
  4. SCC는 자신의 SCD가 SCM에 이미 있는지 확인한다(D.2/D.3). SCM은 SCD basic object의 NAME Mask 정보(A.3)를 사용해 저장된 SCD가 요청한 SCC와 일치하는지 식별해야 한다.
  5. NAME이 일치하는 SCD가 있으면 SCC는 버전 응답과 configuration label을 검사해(A.3, D.4, D.5) 그 SCD가 현재 SCC의 client function 구성을 실제로 반영하는지 확인한다(SCC의 SW 업데이트로 저장된 SCD가 무효해질 수 있다). version label·configuration label의 내용은 SCC 제조사 고유이다.
  6. SCC는 SCMasterMemoryRequest(C.4)로 로드/업로드할 SCD 크기를 알린다. SCM은 SCMasterMemoryResponse(C.5)로 응답하며, 이 응답의 status code가 00이면 SCC는 진행할 수 있다.
    • SCD 업로드 경로: 사용 가능한 SCD가 없거나 버전·구성이 불일치하면 SCC는 SCDTransfer(D.6)로 유효한 SCD를 업로드한다. status code가 01이면 업로드가 허용되지 않으며 처리 방법은 SCC 설계에 달렸다. SCM은 SCDTransferResponse(D.7)로 전송 성공·실패를 알린다.
    • SCD 로드 경로: SCM 비휘발성 메모리에 유효한 SCD가 있으면 SCC는 SCDLoadCommand(D.14)로 SCD를 휘발성 메모리에 로드시키고, SCM은 SCDLoadResponse(D.15)로 결과를 알린다.
  7. SCD 전송/로드에 성공하면 SCC는 SCDActivationCommand(D.8)로 SCD를 활성화한다. 이것이 SCM의 SCD 무결성 파싱을 개시한다. SCC는 긍정 피드백(D.9)을 받을 때까지 SCClientStatus 이외의 SC 통신을 계속해서는 안 된다.
  8. 매 시동 시 SCD 업로드를 피하기 위해, SCC는 SCDStoreCommand(D.12)로 파싱 성공한 SCD를 SCM 비휘발성 메모리에 저장시킬 수 있다. 부정 응답(D.13)의 처리는 SCC 설계에 달렸다.
  9. 초기화가 성공적으로 끝나도 SCC는 active SCM이 enable을 명령할 때까지 disabled 상태로 남는다.
  10. SCC가 자신의 status 메시지에 NACK을 받으면 언제든 disabled로 복귀해야 하며, SCM과의 연결을 재초기화할 수 있다.

  2. 오퍼레이터가 SCM 선택 → active SCM이 SCMasterStatus 연속 송신 (state "active", sequence state "Ready")
  3. 4.4.3 SCM/SCC 상태 동작

active SCM이 시스템 상태를 통제한다. SCM은 실제 sequence state("Ready"/"Recording"/"Recording Completion"/"Play Back"/"Abort")를 SCMasterStatus 메시지로 네트워크에 송신해야 한다. enabled SCC는 SCClientStatus 메시지에 다음 중 하나를 실어 보낸다.

  • 재생을 중단시켜야 하면 "Abort"
  • SCM이 "Recording Completion"인데 자신의 기능 실행이 아직 안 끝났으면 "Recording"
  • SCM이 "Recording Completion"이고 자신의 기능 실행이 끝났으면 "Ready"
  • 그 외 모든 경우: SCMasterStatus에 실린 것과 같은 sequence state (client function 일부가 고장이어도 동일)

주요 규칙:

  • "Recording", "Recording Completion", "Play Back", "Abort" 상태 동안 SCM은 선택된 시퀀스 번호를 SCMasterStatus에 실어야 한다. SCM·SCC가 보내는 시퀀스 번호는 양쪽 동기화 이탈 감지 등 진단 목적으로 쓰이며, 불일치 시 대응은 구현 고유이다.
  • active SCM은 SCClientStatus에 "Recording" 상태를 반영한 enabled SCC의 client command만 저장해야 한다.
  • active SCM은 SCC의 SCClientStatus가 "Play Back" 또는 "Ready"를 표시하지 않는 한 client command를 보내면 안 된다.
  • active SCM은 "Play Back" 상태 중에만 SCClientAbort(E.3)를 수용해야 한다.
  • 시퀀스 선택 시 active SCM은 참여 SCC 전부를 enabled로, 그 외 SCC 전부를 disabled로 명령할 수 있다(SCStateCommand, Figure 9). enable은 시퀀스 집합 로드 후 한 번에 수행할 수도 있다.

SCC의 enable/disable은 SCStateCommand(E.2)로 이루어지며, 오퍼레이터 입력에 의한 경우와 SCM 주도(선택된 SCS 소속 여부)의 경우 모두 reason indication이 함께 전달된다.

4.4.4 종료 (shutdown)

SCM 종료

  • SCM은 오퍼레이터가 비활성화할 수단을 제공해야 하며, 비활성화하려면 "Ready" 상태여야 한다.
  • 다른 SCM을 활성화하려면 먼저 현재 active SCM을 비활성화해야 한다. 다른 SCM이 아직 active인데 새 SCM을 활성화하려 하면, inactive SCM이 오퍼레이터에게 기존 active SCM을 먼저 해제하라고 알려야 한다.
  • 비활성화 입력을 받은 active SCM은 enabled SCC들에게 disable 명령을 보내는 동안 "Ready" 상태를 계속 송신한다.
  • 모든 SCC가 disabled를 반영하면, SCM은 status 메시지 송신을 멈추기 전에 inactive 상태를 한 번 알린다. SCC가 이 알림을 놓치면 SCMasterStatus timeout으로 이전 active SCM의 비활성화를 판단한다.
  • 비활성화된 SCM은 더 이상 SCMasterStatus를 보내면 안 된다.
  • disabled SCC는 SCMasterStatus timeout에 대해 오퍼레이터 경고를 띄우지 말고, 사라진 SCMasterStatus를 정상 종료(graceful shutdown)로 해석해 자신의 SCClientStatus 송신도 멈춰야 한다(새 SC 통신이 시작될 때까지).

SCC 종료

SCC는 SC 통신에서 빠지기 위한 수단(VT 화면, 전용 버튼 등)을 제공할 수 있다. 불필요한 경고를 피하기 위해, 오퍼레이터가 SCC를 disable하면 SCC는 먼저 status 메시지의 상태를 disabled로 바꿔 active SCM에 알리고, timeout 경고를 피하기 위해 이 메시지에 대한 첫 NACK을 받을 때까지 SCClientStatus 송신을 계속해야 한다.

4.4.5 시퀀스 설정

SCM은 연결된 SCC들의 SCD 정보 기반으로 시퀀스를 정의하는 방법을 최소 하나 제공해야 한다. 예: 오퍼레이터의 수동 정의(EDIT), 오퍼레이터가 기능을 직접 조작하며 SCM이 기록하는 기록 단계(RECORDING). SCM은 운용 중 활성화될 수 있는 모든 시퀀스에 유일한 시퀀스 번호를 보장해야 한다.

SCS의 구성 요소 (4.4.5.1)

하나의 SCS는 다음으로 구성되어야 한다.

  • SCS에 관련된 모든 SCC의 NAME, SCD Version Label, SCD Configuration Label
  • 각 스텝(step)별: SCC 참조, SCC function ID, state ID, trigger point, function value

시퀀스 기록 (4.4.5.2)

  • SCM은 기록의 시작·정지 수단을 제공해야 한다. 오퍼레이터는 새 시퀀스를 기록하거나 기존 시퀀스를 다시 기록할 수 있다.
  • SCM은 모든 enabled SCC가 존재하고 SCClientStatus로 "Ready"를 표시할 때만 "Recording" 상태에 진입할 수 있다.
  • SCM이 SCMasterStatus의 상태를 "Recording"으로 바꾸면 SCC들은 즉시 따라야 한다. ClientFunctionErrorState가 일부 기능 오류를 표시하더라도 마찬가지다. 한 시점에 활성화될 수 있는 SCS·기록 단계는 하나뿐이다.
  • SCM은 status 메시지에 "Recording"을 반영한 enabled SCC의 client function만 기록해야 한다. SCC가 timeout 내에 SCM 상태를 따르지 않으면 4.5.3.4의 조치를 취한다.

기록되는 client function은 보통 오퍼레이터 조작에 대한 반응이다. 오퍼레이터가 수동으로 기능을 활성화하면 SCC가 SCExecutionIndication(E.4)을 SCM에 보낸다. 세부 규칙:

  • 고장 난 기능에 대해서는 SCExecutionIndication을 보내면 안 된다.
  • SCC는 일시적·영구적 제약이 있으면 특정 오퍼레이터 조작을 client command로 보고하지 않기로 선택할 수 있다.
  • 간접적 오퍼레이터 조작의 결과(예: 조작 한 번으로 스프레이어 붐 상승 + 유량 차단이 동시에 일어나는 경우)는 별도 client command 두 개로 보고하거나 하나의 복합 client command로 보고할 수 있다.
  • Task Controller 등 다른 시스템의 명령으로 발생한 동작은 보통 보고하지 않는다.

기록 저장 규칙:

  • SCM은 "Recording" 상태를 반영 중인 enabled SCC의 SCExecutionIndication마다 4.4.5.1의 스텝 정보를 기록한다.
  • trigger는 SCC가 기능 실행 시작을 보고할 때 기록한다.
  • function value는 SCC가 기능 실행 완료를 표시할 때 기록한다.
  • client function은 'started'와 'completed' 표시를 둘 다 받은 경우에만 SCS에 저장된다.
  • SCC는 기능 활성화마다 function ID, state ID, function value를 담은 SCExecutionIndication을 보내며, 이 최초 client command의 TAN은 그 SCC의 직전 TAN + 1이다.
  • SCC는 SCM이 "Ready"로 돌아가거나, timeout이 되거나, SCM이 SCExecutionIndicationResponse(E.5)로 client command를 확인할 때까지 같은 TAN의 SCExecutionIndication을 100 ms 간격으로 반복해야 한다.

기록 중 SCC client command의 다섯 가지 시나리오:

시나리오function execution state 흐름
(a) 시작·완료 동시00 (started and completed simultaneously) 한 번. 짧은 트리거로 켠 뒤 계속 도는 기능 등
(b) 시작·완료 분리01 (started) → 이후 같은 내용·같은 TAN으로 10 (completed). 두 번째 표시에 function value(process variable)를 담을 수 있다
(c) 실행 중 오류01 (started) → 같은 TAN으로 11 (error during execution). 이후 완료 표시는 보내지 않는다
(d) 완료 전 같은 기능 재조작01 (started) → 같은 TAN으로 완료 표시 → 즉시 TAN+1로 새 SCExecutionIndication ((a)~(c) 중 해당 케이스로)
(e) 이전 기능 미완료 중 다른 기능 시작기능별 개별 TAN으로 구분 (예: 히치 하강 진행 중에 특정 히치 높이에서 PTO 활성화)

(c)에서 기능이 고장이면 SCC는 SCClientStatus에도 오류를 표시해야 한다. ClientFunctionErrorState(F.3 byte 5)가 03(오퍼레이터 확인 필요)이면 SCM은 SCClientFunctionErrorRequest(E.9)로 상세 정보를 요청하고 SCClientFunctionErrorResponse(E.10)에 표시된 고장 기능을 오퍼레이터에게 알려야 한다. 확인이 불필요한 경우 상세 정보 요청은 선택이며, 고장 기능을 무시하고 기록을 계속할지 전체를 취소할지는 SCM에 달렸다.

SCM은 SCExecutionIndication 수신 시 SCExecutionIndicationResponse(E.5)로 응답한다. 응답에는 수신한 것과 같은 function ID, state ID, function execution state, TAN, 그리고 byte 4에 기록 여부(또는 폐기 사유)를 담는다. 폐기된 경우 SCC가 오퍼레이터에게 알릴 수 있다.

기록 중 SCM은 모든 enabled SCC의 SCClientStatus 수신을 검증해야 하며, 어떤 SCC가 disabled로 떨어지거나 어떤 SC 메시지가 timeout 되면 기록 전체를 취소하고 상태를 "Ready"로 바꿔 취소를 알린다.

기록 정지 시 동작:

  • 아직 완료 표시를 기다리는 기능이 있으면 "Recording Completion" 진입 → 전부 수신하면 "Ready"
  • 아니면 즉시 "Ready" 진입, SCC들도 즉시 반영

"Recording Completion"을 받은 SCC는 자기 기능이 모두 완료됐으면 "Ready"로, 아니면 "Recording"에 남아 진행 중 실행을 마치고 완료 표시를 보낸 뒤 "Ready"로 간다. 이때 새 client command 표시는 금지된다. 기록·수동 정의된 시퀀스의 비휘발성 저장 여부·방식은 SCM 설계에 달렸다. SCM은 "Ready"로 직접 진입해 기록을 취소할 수도 있으며, SCC는 시퀀스 제어가 아닌 오퍼레이터에 의해 활성화된 자기 기능을 계속 수행해도 된다.

수동 시퀀스 편집 (4.4.5.3)

"Manual Edit"는 기록 모드에서 기능을 실제 수행하지 않고 기존 시퀀스를 수정하거나 새 시퀀스를 정의하는 기능이다.

  • Manual Edit는 SCM의 내부 상태이며 SCC에 알리지 않는다. 이때 SCM이 제공하는 전역 시스템 상태는 "Ready"이고 sequence number는 FF로 설정한다.
  • 편집 화면에서 SCM은 enabled SCC들의 client function, 관련 function state, SCD function object의 표시 설정(A.4)에 따른 function value, 기능별 가용 trigger 방법을 제공해야 한다.
  • Manual Edit는 SCS 각 스텝에 대해 4.4.5.1의 정보를 설정할 수단을 제공해야 한다.
  • SCC가 function value를 오퍼레이터 변경 불가로 정의했다면(A.4), 새 스텝 생성 시 FFFFFFFF로 설정하고 기존 스텝 편집 시에는 기존 값을 보존한다.

4.4.6 시퀀스 검증

active SCM은 다음 경우에 선택된 시퀀스(집합)를 재생 허용 전에 검증해야 한다.

  • 저장된 시퀀스 로드 후
  • 어떤 SCClientStatus 메시지의 timeout 발생 시
  • 수동 시퀀스 정의·편집 완료 후
  • 어떤 SCC의 예기치 않은 상태 변화 후
  • 어떤 SCD 업로드 후

검증 요건(하나라도 불충족이면 재생을 허용하지 않아야 함):

  • SCD에 나열된 연결 SCC·working set master의 64bit NAME이 시퀀스에 저장된 것과 일치 (A.3의 SCC NAME Mask 적용)
  • SCD Version Label·Configuration Label이 시퀀스에 저장된 것과 일치
  • 선택된 시퀀스의 모든 기능이 로드된 SCD들에 포함

SCM은 오퍼레이터가 검증 요건을 맞추도록 SCS를 적절히 수정할 수 있게 해야 한다. 검증 성공 후 SCM은 참여 SCC 전부의 enable을 보장하고 그 외 SCC를 SCStateCommand로 disable할 수 있다.

4.4.7 시퀀스 재생

일반 (4.4.7.1)

  • 재생 활성화 방법은 active SCM 고유이다(VT 소프트키, Auxiliary Input, 전용 버튼 등).
  • 재생 전 SCS 검증이 성공해야 한다. 검증 실패 시(예: 시퀀스에 포함된 SCC가 네트워크에 없음) SCM은 오퍼레이터가 SCS에서 해당 기능을 제거하는 등 시퀀스를 유효화할 수단을 제공할 수 있다.
  • "Ready"→"Play Back" 전이는 선택된 시퀀스에 포함된 모든 SCC가 SCClientStatus로 "Ready"를 표시할 때만 허용된다.
  • 단, 빠른 반응을 위해 SCM은 이전 재생이 완전히 끝나기 전에 다음 재생을 시작하는 수단을 제공할 수 있다. 이 경우 SCM은 첫 시퀀스의 명령 송신을 멈추고 SCMasterStatus의 시퀀스 번호를 먼저 바꿔 SCC들에게 변경을 알린 뒤 다음 시퀀스의 명령을 보내야 한다(활성 시퀀스는 한 번에 하나만 허용). 이전 시퀀스의 명령을 아직 수행 중인 SCC가 그 활동에 대한 피드백을 보낼 수 있는데, 이는 fault로 간주하면 안 된다.
  • SCM은 SCMasterStatus 상태를 "Play Back"으로 바꿔 재생 시작을 알리고, enabled SCC들은 SCClientStatus에서 이를 따른다. SCM은 아직 "Ready"를 보고 중인 SCC에게도 즉시 시작을 위해 client command를 보낼 수 있다. SCM 상태 변화를 놓치고 첫 client command를 받은 SCC는 이를 "Play Back" 전이 트리거로 해석하고 명령을 실행해야 한다. SCC는 항상 SCM의 최신 명령을 따라야 하며, timeout 내에 따르지 않으면 SCM은 4.5.3.4대로 처리한다.

재생 중 SCM·SCC 동기 유지 규칙 — 저장된 trigger 이벤트에 도달할 때마다:

  1. SCM은 해당 기능을 소유한 SCC에 function ID, state ID, function value를 담은 SCMasterExecutionCommand(E.6)를 보낸다. TAN은 SCM의 직전 TAN + 1.
  2. SCM은 SCC가 SCClientExecutionStatus(E.7)로 응답하거나 timeout 될 때까지 같은 TAN으로 100 ms 간격 반복한다.
  3. SCC는 SCM의 모든 명령에 SCClientExecutionStatus로 응답한다(수신한 function ID, state ID, sequence number 포함). 이 응답도 SCM이 "Abort"로 바뀌거나, timeout(E.1)이거나, 기능 실행 완료 보고 시점에 도달하거나, 중단이 필요한 조건에 도달하거나, SCM이 SCClientExecutionAcknowledgement(E.8)로 확인할 때까지 100 ms 간격으로 반복한다.
  4. SCM은 모든 SCClientExecutionStatus에 SCClientExecutionAcknowledgement로 응답한다(같은 function ID, state ID, function execution state, 관련 SCMasterExecutionCommand의 TAN).

SCClientExecutionStatus 시나리오 (4.4.7.2)

시나리오동작
(a) 시작·완료 동시state 00으로 응답 (모멘터리 버튼 같은 명령). TAN은 SCMasterExecutionCommand의 것과 동일
(b) 시작·완료 분리state 01 응답 → 완료 시 같은 내용으로 state 10 응답
(c) 실행 중 오류state 01 응답 → 같은 TAN으로 state 11 응답. 완료 표시는 보내지 않음
(d) 고장 기능에 대한 실행 명령기능 오류·오퍼레이터 입력으로 실행 불가 시, Error Code를 담아 state 11로 보고. 완료 표시는 보내지 않음
(e) 같은 기능에 대한 중첩 명령실행 중 같은 기능에 새 명령 수신 시: 먼저 첫 명령의 TAN으로 완료(state 10)를 보내고, 즉시 둘째 명령의 TAN으로 (a)~(d)에 해당하는 상태를 보냄

기능이 고장이면 SCC는 SCClientExecutionStatus 외에 SCClientStatus에도 표시해야 한다. ClientFunctionErrorState가 03(오퍼레이터 확인 필요)이면 SCM은 SCClientFunctionErrorRequest로 상세를 요청하고 오퍼레이터에게 알린다. 재생을 계속할지 "Abort"로 전체를 멈출지는 SCM에 달렸다.

재생 중 추가 규칙:

  • SCM이 timeout 내에 올바른 TAN·function ID·state ID의 응답을 받지 못하면 재생을 중단(halt)해야 한다.
  • SCM은 모든 enabled SCC의 SCClientStatus 수신을 검증하고, 어떤 SCC가 disabled로 떨어지거나 메시지가 timeout 되면 재생 전체를 중단해야 한다.
  • 재생 중 오퍼레이터가 client function을 수동 조작하면 SCC는 SCExecutionIndication의 function execution state 11로 SCM에 알린다. 조작된 기능이 실행 중인 SCS에 속하면 SCM은 전체 재생을 멈추거나, 이번 재생 동안 그 기능에 새 명령을 보내지 않기로 하거나, 그냥 무시할 수 있다(단 메시지 통신 자체는 무시 불가). SCC는 이 SCExecutionIndication을 SCM이 "Ready"로 돌아가거나 timeout 되거나 SCExecutionIndicationResponse로 확인할 때까지 100 ms 간격으로 반복한다.
  • 재생은 보통 마지막 기능 실행 완료 표시로 끝난다. 미결 function execution state를 모두 완료로 수신했거나 내부 조건에 따라, SCM은 "Ready"로 진입하고 SCC들이 이를 반영한다. 모든 완료를 받지 못했어도(예: 재생 단계 내부 timeout) "Ready"로 갈 수 있다.

재생 중단 — Abort (4.4.7.3)

  • active SCM은 오퍼레이터가 재생을 중단시킬 수단을 제공해야 하며, 내부 조건 발생 시 오퍼레이터 입력 없이 "Abort"를 개시할 수도 있다.
  • SCC가 재생을 중단시켜야 하면 전역 SCClientAbort(E.3)를 active SCM에게서 "Abort" 상태를 받을 때까지 반복 송신하고, SCClientStatus에 "Abort" 상태를 보고해야 한다.
  • active SCM은 "Play Back" 중에만 SCClientAbort 수신(또는 어떤 SCC의 "Abort" 상태 송신 인지) 즉시 시스템 상태를 "Abort"로 바꿔야 한다. SCM 스스로 중단이 필요하면 "Abort" 상태로 진입하고 SCC들이 즉시 반영한다.
  • "Abort" 상태 동안 SCC들은 현재 시퀀스에서 SCM이 명령했던 client function들을 SCC가 정의한 safe state로 전환할 책임이 있다. SCM이 명령하지 않은 기능은 SCM의 중단에 영향받지 않아야 한다. "Abort" 시 SCM은 오퍼레이터에게 통지할 수 있다.
  • SCM이 모든 enabled SCC로부터 "Abort" 상태를 받으면 "Ready"로 복귀하고 SCC들도 이를 반영한다.

4.4.8 Function value

SCS의 각 스텝에는 4바이트 function value(process variable)를 연결할 수 있다. SCC가 기능 실행마다 특정 설정·공정 파라미터를 SCS에 저장해 두고, 재생 시 명령과 함께 돌려받아 같은 방식으로 다시 수행할 수 있게 하는 장치다. 이 4바이트의 의미는 기능을 소유한 SCC 고유이다.

  • 보통 기록 중 "function execution completed"를 표시하는 SCExecutionIndication에 실려 오거나, 편집 모드에서 오퍼레이터가 수동 정의한다.
  • SCC가 시작만 표시하는 경우 function value는 FFFFFFFF로 설정해야 한다.
  • SCM 화면에 function value를 표시할지·어떻게 표시할지는 SCC가 SCD function object(A.4)에서 정의한다.
  • function value는 각 스텝의 trigger 타이밍·ID와 함께 저장되고, 재생 시 SCMasterExecutionCommand의 일부로 SCC에 돌아간다.
  • SCM은 하나 또는 여러 시퀀스 안에서 특정 client function의 다중 활성화를 서로 독립적으로 허용해야 하며 각 스텝을 개별 취급해야 한다(예: 히치 최고 높이에 여러 스텝에 걸쳐 도달).

function value 활용 예 — 히치 위치

기록 중 오퍼레이터가 3점 히치를 특정 위치까지 올리면, SCC는 조작 시작 시 SCExecutionIndication을 보내고, 히치가 목표 위치에 도달해 조작을 멈추면 도달 위치를 function value로 담아 완료를 보고한다. SCM은 이 값을 스텝과 함께 저장했다가 재생 시 SCMasterExecutionCommand에 실어 돌려주고, SCC는 기록 때와 똑같은 히치 위치에서 멈춘다.

4.4.9 시퀀스 관리

SCM 메뉴는 저장된 시퀀스의 검토·저장·로드·교체와 재생 활성화 입력에의 연결 수단을 제공할 수 있으며 방식은 SCM 고유이다.

항목요지
저장 (4.4.9.1)단일 시퀀스 또는 시퀀스 집합(예: 두렁 진입용 + 본답 복귀용)을 고유 텍스트 descriptor와 함께 저장할 수 있다. 저장을 제공하는 SCM은 나중에 로드할 때 데이터 무결성 검사가 가능하도록 조치해야 한다(예: 체크섬 동반 저장)
로드 (4.4.9.2)저장을 제공하면 로드도 제공해야 한다. 로드 시 무결성을 검사하고 손상된 시퀀스는 로드를 불허해야 한다. 로드 후에는 4.4.6대로 검증해야 한다
편집기 (4.4.9.3)두 기능 사이의 시간·거리, 기능별 trigger 이벤트(예: 거리 기반→시간 기반) 변경 수단을 제공할 수 있다. 한 기능이 앞 기능 완료를 기다리게 수동으로 체이닝하는 수단도 제공할 수 있다(예: 히치가 특정 위치에 도달하기 전에는 PTO를 켤 수 없음). "Edit-Mode" 제공 시 수동 시퀀스 정의(4.4.5.3)에도 사용할 수 있다

4.5 오류 처리

장애 유형에 따라 SCM, 하나 이상의 SCC, 또는 양쪽이 함께 적절한 조치를 취해야 한다.

기본 보고 경로: SCC는 client function 상태를 SCClientStatus로 보고한다. SCM이 마지막 보고 이후 오류 상태 변화를 인지하면(F.3 byte 5 = 02) SCClientFunctionErrorRequest(E.9)로 상세를 요청할 수 있고, 오퍼레이터 확인이 필요한 변화(03)면 요청해야 한다. SCClientFunctionErrorResponse(E.10)로 SCM은 최소한 오퍼레이터 확인이 필요한 결함을 파악하고(E.10 error structure의 해당 비트), 고장 기능이 시퀀스에 포함되는지 또는 사용하지 않는 다른 기능만 영향인지 판별할 수 있다. 보고 후 SCC는 ClientFunctionErrorState를 01로 되돌린다. SCM은 확인 필요 비트가 설정된 고장 기능을 즉시 오퍼레이터에게 보고해야 하며, 이후 진행 결정에 오퍼레이터를 참여시킬 수 있다.

4.5.1 기능 장애

  • SCC가 보고한 client function 장애에는 SCC·SCM 양쪽이 대응한다. 적절한 조치의 책임은 SCC에 있으며, 예로 현재 실행 중 동작의 정지나 추가 명령 무시가 있다.
  • SCM은 SCC가 장애 해소를 보고할 때까지 현재 시퀀스에서 그 기능의 스텝들을 건너뛸 수 있다. 장애가 이어지면 후속 시퀀스에서도 계속 건너뛸 수 있다.
  • 오류 해소는 SCC 책임이며 SCC UI를 통한 오퍼레이터 상호작용을 포함할 수 있다.
  • 고장 기능이 로드된 시퀀스에 포함되는지에 따라 시스템 반응이 달라질 수 있다.

4.5.2 통신 장애

  • SCC가 통신 오류를 감지하면 일반 안전 요구를 고려해 적절히 조치해야 한다.
  • SCM이 선택된 시퀀스에 속한 client function과의 통신 장애를 감지하면, 기록·재생을 불허하거나, 이미 활성이면 기록을 즉시 취소하거나 재생을 중단해야 한다. 통신 문제는 간헐적일 수 있으므로 SCM은 재기록·재재생 허용 전에 오퍼레이터 개입을 요구할 수 있다.

4.5.3 참여자의 비준수 동작

상황조치
예기치 않은 SCC 메시지 (4.5.3.1)SCM은 유효한 연결(4.4.2 기준)이 아닌 SCC의 SC 메시지를 모두 NACK해야 한다. 로드·검증된 SCD가 초기화 완료의 일부이므로, SCM이 SCD를 삭제한 SCC와의 연결은 무효로 간주한다. 초기화 후에도 보내면 안 되는 메시지(예: disabled SCC의 SCExecutionIndication)는 NACK한다. SCC는 예기치 않은 NACK을 받으면 연결을 재확립할 수 있다
SCC 응답 누락 (4.5.3.2)timeout(E.1, Annex F) 내 무응답이거나 주기 status 미송신인 SCC의 SCD를 SCM이 휘발성 메모리에서 삭제한다. 이후 그 SCC의 모든 SC 메시지가 NACK되므로 SCC는 연결을 재확립할 수밖에 없다
다중 active SCM (4.5.3.3)SCC가 서로 다른 SCMasterStatus 수신으로 둘 이상의 active SCM을 인지하면 즉시 disabled로 전환해야 한다
SCC가 SCM 상태를 안 따름 (4.5.3.4)timeout(F.3) 내에 sequence state를 따르지 않으면 SCM은 그 SCC의 SCD를 삭제하고 SC 메시지를 NACK해 재연결을 유도한다. 오퍼레이터에게 알릴 수 있다. 유일한 예외는 SCC 상태의 이탈이 오히려 요구되는 "Recording Completion"
잘못된 SCC 동작 (4.5.3.5)enable/disable 명령 후 timeout(E.1) 내에 상태를 안 바꾸면 SCM은 SCD 삭제, SCClientStatus 포함 모든 SC 메시지 NACK, 그리고 SCC가 명령된 상태를 보고할 때까지 어떤 메시지도 보내지 않는다
예기치 않은 disabled 전환 (4.5.3.6)SCM은 그 SCC의 SCD를 삭제하고 메시지를 NACK해 재연결을 유도한다. 그 SCC가 선택된 시퀀스에 속하면 시퀀스 무결성을 책임지는 active SCM이 관련 기능을 시퀀스에서 제거하는 등의 조치를 해야 하며, 오퍼레이터 상호작용이 필요할 수 있다

4.6 통신 전략 — TAN

SCM–SCC 통신에서는 일시적 통신 문제로 명령에 대한 응답이 유실될 수 있다. 유실이 명령 쪽(SCM이 client command를 못 받음)인지 응답 쪽(SCC가 SCM의 응답을 못 받음)인지 명령의 개시자는 구분할 수 없고, 필요한 동작을 얻기 위해 명령을 반복하게 된다.

그래서 Annex E의 일부 메시지 쌍에 TAN(transaction number) 사용이 요구된다.

  • 반복된 명령을 감지하고 응답을 원래 명령과 연관 지을 수 있게 한다. 송신자는 명령을 반복할 때 같은 TAN을 쓰고, 수신자는 명령에서 받은 TAN을 응답에 그대로 쓴다.
  • SCM/SCC는 응답 메시지를 받으면 먼저 TAN이 자신의 원래 명령과 일치하는지 확인하고, 일치하면 client function ID·state ID도 일치하는지 확인한다. 셋 다 일치할 때만 메시지를 처리하고, 아니면 무시한다.
  • TAN 덕분에 여러 client command가 동시에 활성일 수 있다. 예를 들어 한 SCC가 SCExecutionIndication을 동시에 여러 개 걸어 둘 수 있다(한 명령의 완료가 미결인 채 오퍼레이터가 다음 명령을 조작).
  • SC 통신의 각 참여자는 자기만의 TAN 카운터를 가지며, 새 client command 송신을 개시할 때마다(기록 중 실행 표시, 재생 중 실행 명령 등) 1씩 증가시킨다.

Annex A: Sequence control data definition (SCD)

A.1 개요와 표기

SCD는 시스템 초기화 때 각 SCC가 SCM에 로드하는 데이터로, 해당 SCC의 기록 가능한 기능 전부의 정의와 각 기능의 시각화용 그래픽·텍스트 참조를 포함한다.

  • 오브젝트 정의 방식은 ISO 11783-6의 object 사용법과 유사하며, SCD 전송은 ISO 11783 transport protocol 또는 extended transport protocol로 이루어진다.
  • 모든 object ID는 SCD 전체에서 유일해야 하며 범위는 0~65534, 65535(FFFF)는 "NULL" object ID로 예약된다.
  • SCC마다 자신의 SCD를 active SCM에 제시해야 한다. 네트워크상 여러 장치·CF 간 의존성은 working set 안에서 처리해야 하며, 그중 하나만 SCC로서 SCM과 통신할 수 있다.

데이터 타입 표기: Bitmask(1바이트, Bit 0이 LSB), Byte Array(정의된 길이의 1바이트 무부호 정수열), Float(IEEE 754-1985 32비트, 4바이트), Integer(부호/무부호, 1·2·4바이트).

  • SCD Configuration Label은 SCD가 반영하는 기계 구성(예: 장착 옵션) 식별용이다. 두 레이블의 내용은 SCC 제조사 고유이며, 활성화 전 검사 책임은 SCC에 있다. 단 SCS 무결성을 위해 SCM은 SCS 정의에 사용 중인 두 레이블을 추적해야 한다. 레이블 길이는 SCS 메모리 크기 급증을 피하기 위해 각각 최대 64자로 제한된다.

  • 텍스트 오브젝트의 폰트 타입·크기·색 등 레이아웃 정보는 SCCOP에 담기므로, SCM은 원하는 폰트 크기 등을 SCMasterCapabilityResponse(C.3)로 SCC에 알려 SCCOP를 조정하게 해야 한다.

  • Preferred trigger는 SCC 제조사가 이 기능 운용에 가장 적합한 트리거 모드를 밝히는 수단일 뿐, SCM이 모든 트리거 모드를 지원할 의무도, 이 선호를 존중할 의무도 없다.

    • Displayed Value = (Value Attribute + Offset) × Scaling Factor
    • Transmitted Value = (Displayed Value / Scaling Factor) − Offset
    • 한계값도 같은 식으로 스케일링되며, value attribute는 Lower/Upper Limit 사이여야 한다.
  • 하나의 function object는 여러 state object를 참조할 수 있다. 예: 스프레이어 마스터 밸브 기능은 designator·그래픽으로 표현되고 on/off 두 상태가 각각의 state object로 표현된다. SCM은 시퀀스 편집 화면에서 참조된 state object의 designator·그래픽 기반 input list 등으로 상태 수동 변경 수단을 제공할 수 있다.
  • designator 최소 가시 32자, SCCOP 레이아웃 정보 규칙은 basic object와 동일하다.

고장 난 client function의 실제 상태를 요청한다. SCC들은 status 메시지로 client function 사용 불가 여부를 알리고, SCM은 이 메시지로 개별 SCC에 상세를 요청한다. SCC는 SCClientFunctionErrorResponse(E.10)로 응답해야 한다. Byte 1 = 35, 나머지는 예약(FF)이다.

E.10 SCClientFunctionErrorResponse (SCC→SCM, code 35)

SCC는 고장 난 client function들의 function ID를 오류 상태 코드와 함께 보고한다(기능당 2바이트). 활성 오류 수에 따라 transport protocol이 필요할 수 있고, 고장 기능이 3개 미만이면 8바이트까지 FF로 패딩한다.

  • 기본 전제는 client function 불가·고장 시 SCC가 스스로 오퍼레이터에게 알리는 것이다. 그러나 SCC가 자체 UI가 없는 등의 이유로 SCM이 대신 알리도록 요청할 수 있다(Bit 8). SCM은 오퍼레이터 확인 필요 비트가 설정된 error structure를 수신하면 즉시 오퍼레이터에게 알려야 하며, 관련 SCD의 designator·그래픽을 활용할 수 있다.
  • 이 메시지를 송신하면 SCC는 SCClientStatus의 ClientFunctionErrorState를 01로 리셋하고, 기능 상태가 다시 바뀔 때까지 유지한다.

F.2 SCMasterStatus (SCM→전체 broadcast, code 95)

active SCM이 모든 CF에게 broadcast하는 메시지다. 송신 규칙:

  • byte 2~5 중 하나라도 바뀌면 즉시 송신
  • "Ready" 상태에서는 초당 1회
  • active "Recording" / "Recording Completion" / "Play Back" / "Abort" 상태에서는 초당 5회
  • 개별 메시지 사이 최소 100 ms 보장
  • inactive SCM은 시동 직후 initialization 표시로 1회, 상태 변화(오퍼레이터 입력) 직후 inactive 표시로 1회만 송신한다
  • 다른 SCM이 active 상태를 알리는 동안 inactive SCM은 자기 상태 변경을 허용하면 안 되고, active SCM은 기록·재생 진행 중 자기 status 변경을 허용하면 안 된다

F.3 SCClientStatus (SCC→SCM destination-specific, code 96)

시퀀스 제어를 지원하는 모든 SCC가 네트워크에서 active SCM을 감지하는 동안 송신한다. 송신 규칙:

  • byte 2~5 중 하나라도 바뀌면 즉시 송신
  • "Ready" 상태이거나 SCC가 disabled면 초당 1회
  • active "Recording" / "Recording Completion" / "Play Back" / "Abort" 상태에서는 초당 5회
  • 개별 메시지 사이 최소 100 ms 보장
  • 시동 직후 initialization을 1회 표시해 SCM이 빠른 재시작(quick start-up)을 즉시 감지할 수 있게 한다
  • active SCM에게서 SCClientStatus에 대한 NACK을 받는 것은 SCM이 이 SCC와 동기화되어 있지 않다는 표시다. SCC는 active SCM과의 연결을 재확립해야 한다
