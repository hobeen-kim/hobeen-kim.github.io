캡스톤: 농기계 원격 영상·제어 플랫폼

학습 목표

  • 농기계 원격 영상·제어의 기능·비기능 요구를 수치 목표로 바꾸고, 그 수치가 설계를 어떻게 제약하는지 설명할 수 있다.
  • 디바이스·AWS·백엔드·브라우저 네 구역의 책임을 나누고, 영상·조작·신뢰 명령이 각각 어느 경로로 흐르는지 그릴 수 있다.
  • 부팅부터 시청·조작·1시간 재연결까지의 시퀀스를 자격증명 수명과 함께 설명할 수 있다.
  • 미디어 플랫폼, 녹화 방식, 제어 채널, 자격증명 발급의 네 가지 결정을 ADR 형식으로 근거와 함께 기록할 수 있다.
  • 네트워크 열화·장애 시나리오마다 감지 신호와 대응을 정의하고, 가정을 명시한 월 비용을 계산할 수 있다.

이 장은 새 개념을 소개하지 않는다. 앞의 24개 장에서 다룬 부품을 하나의 실제 시스템으로 조립하면서 "왜 이 부품을 이렇게 골랐는가"를 기록한다. 각 기술의 동작 원리는 해당 장 링크로 넘기고, 여기서는 선택지와 트레이드오프, 그리고 운영에서 무엇이 먼저 터지는지에 집중한다.

그림에서 바로 드러나지 않는 구조적 결정이 네 가지 있다.

첫째, 기체 1대 = 채널 1개이고 채널 이름은 IoT thing 이름이다. KVS C SDK README가 "iot thing name as channel name"을 권장하고, IAM 정책 변수 ${credentials-iot:ThingName}을 쓰면 역할 하나로 300대가 각자 자기 채널만 쓰게 만들 수 있다. 카메라가 2대인 기체도 채널을 2개 만들지 않는다. 한 PeerConnection에 비디오 트랙 2개를 싣는다(C SDK에 kvsWebrtcClientMaster_4Video_1Audio 샘플이 있다). 그러면 ICE·DTLS 핸드셰이크와 TURN allocation이 하나로 끝나고 채널 요금도 절반이 된다. 보조 카메라는 기본적으로 저화질로 두고, 운영자가 DataChannel로 전환을 요청할 때만 올린다.

둘째, 디바이스는 채널을 만들지 않는다. C SDK README의 예시 IoT 역할 정책에는 kinesisvideo:CreateSignalingChannel이 들어 있다. 이 설계는 그것을 빼고, 채널 생성은 백엔드 프로비저닝이 맡는다. 펌웨어 버그나 탈취된 기체가 채널을 마구 만들어 할당량을 소진하는 일을 막고, 채널 수명을 기체 등록·폐기와 일치시킨다.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "kinesisvideo:DescribeSignalingChannel",
      "kinesisvideo:GetSignalingChannelEndpoint",
      "kinesisvideo:GetIceServerConfig",
      "kinesisvideo:ConnectAsMaster"
    ],
    "Resource": "arn:aws:kinesisvideo:ap-northeast-2:123456789012:channel/${credentials-iot:ThingName}/*"
  }]
}

이 정책은 role alias가 가리키는 IAM 역할에 붙인다. ${credentials-iot:ThingName}은 IAM 정책에서만 동작하고, 디바이스가 x-amzn-iot-thingname 헤더를 보낼 때만 채워진다. 헤더의 thing 이름이 인증서에 붙은 thing과 다르면 403이 나므로, 기체가 남의 채널 이름을 사칭할 수 없다.

셋째, 제어는 두 경로로 나눈다. 시청 세션 안의 저지연 조작은 DataChannel(P2P), 세션과 무관하게 전달돼야 하는 신뢰 명령·상태·오프라인 큐는 MQTT(IoT Core)다. 역할 분담 원칙은 11장의 DataChannel vs MQTT 표를 그대로 따르고, 명령별 배치는 §4 ADR-3에 적는다.

넷째, 운영자 브라우저는 IoT Core에 직접 붙지 않는다. 신뢰 명령은 백엔드 API를 거쳐 publish한다. 그래야 명령마다 인가와 감사 로그를 한곳에서 남길 수 있다. 텔레메트리 대시보드는 백엔드가 SSE나 WebSocket으로 내려준다(WebSocket 과 SSE). 시청 중 영상 위에 겹치는 고빈도 오버레이(속도·조향각, 10Hz)만 DataChannel로 받는다.

3. 핵심 시퀀스: 부팅에서 원격 조작까지

① 부팅: 시계가 맞아야 모든 것이 시작된다

부팅 직후 첫 작업은 네트워크 연결이 아니라 시계 동기화다. IoT Credential Provider와의 상호 TLS는 인증서 유효기간을 검사하고, KVS API는 SigV4 서명 시각을 검사한다. RTC 배터리가 없는 보드는 부팅 직후 시각이 1970년이거나 마지막 종료 시각에 멈춰 있다. 그대로 연결하면 TLS가 실패하거나 서명이 거부되는데, 로그에는 "인증 실패"로만 남아 원인을 찾기 어렵다(13장).

농기계에는 이 문제를 푸는 좋은 시간원이 이미 있다. 위치 측정용 GNSS 수신기다. chrony에 NTP와 GNSS(gpsd 경유)를 함께 시간원으로 등록하면, NTP가 막힌 망에서도 위성 신호만 잡히면 시계가 맞는다. 서비스는 동기화가 끝날 때까지 기다렸다가 시작한다.

시계가 맞으면 디바이스는 인증서로 Credential Provider의 /role-aliases/<alias>/credentials를 호출해 임시 자격증명을 받는다. role alias의 credentialDurationSeconds는 기본 3,600초(900~43,200초)다. 이어서 DescribeSignalingChannel → GetSignalingChannelEndpoint(MASTER) → GetIceServerConfig → ConnectAsMaster 순서로 시그널링 채널에 붙어 대기한다. 이 흐름은 C SDK를 -DIOT_CORE_ENABLE_CREDENTIALS=ON으로 빌드하면 SDK가 처리한다(19장).

디바이스 서비스 설정 예 (환경 변수 + systemd)
# /etc/farm/kvs-master.env
AWS_DEFAULT_REGION=ap-northeast-2
AWS_IOT_CORE_CREDENTIAL_ENDPOINT=c1abcd2efgh3ij.credentials.iot.ap-northeast-2.amazonaws.com
AWS_IOT_CORE_CERT=/etc/farm/certs/device.pem.crt
AWS_IOT_CORE_PRIVATE_KEY=/etc/farm/certs/private.pem.key

② 시청: 백엔드가 권한을 확인하고 채널 하나만 열어 준다

운영자가 기체를 클릭하면 브라우저는 백엔드에 시청 권한(view grant)을 요청한다. 백엔드는 세 가지를 확인한다. 이 운영자가 이 기체의 농장에 배정돼 있는가(ACL), 이 기체의 동시 시청 리스가 3개 미만인가, 그리고 기체가 온라인인가(Shadow reported 상태)다. 통과하면 STS AssumeRole에 세션 정책을 붙여 그 채널 ARN 하나에 대한 VIEWER 권한만 있는 15분짜리 자격증명을 발급한다(코드는 §4 ADR-4).

브라우저는 이 자격증명으로 GetSignalingChannelEndpoint(VIEWER)와 GetIceServerConfig를 호출하고 ConnectAsViewer로 붙는다. 그다음은 표준 JSEP 흐름이다(04장). KVS 모델에서는 viewer가 offer를 만들고 master가 answer한다. 두 가지 구현 디테일이 시청 시작 시간을 좌우한다.

  • DataChannel은 offer를 만들기 전에 생성한다. 그래야 첫 offer에 m=application 라인이 들어가 재협상 없이 조작 채널까지 한 번에 열린다(11장).
  • 첫 프레임은 키프레임을 기다린다. 연결 직후 브라우저가 PLI를 보내고 디바이스 인코더가 즉시 IDR을 만들게 한다. 인코더의 IDR 간격(예: 2초)에만 의존하면 첫 화면이 그만큼 늦어진다(09장).

ICE 결과는 기체가 붙은 통신사의 CGNAT 동작에 달려 있다. 매핑이 endpoint-independent면 srflx 후보끼리 직결되고, 주소·포트 의존 매핑이면 TURN 릴레이로 간다(05장, 06장). 이 비율은 통신사·지역마다 달라서 실측해야 하고, §6에서 보듯 비용을 가장 크게 흔드는 변수다.

③ 유지와 재연결: 1시간 한도는 반드시 온다

KVS 시그널링 연결에는 조정할 수 없는 제약이 있다. 연결 최대 1시간, idle timeout 10분, GO_AWAY 이후 유예 60초다(18장). 기체는 하루 종일 MASTER로 대기하므로 시그널링 재연결은 예외 처리가 아니라 정상 흐름이다.

대상수명갱신 시점
디바이스 임시 자격증명role alias 설정값(기본 3,600초)만료 전 여유를 두고 Credential Provider 재호출
시그널링 WSS 연결최대 3,600초(SessionExpiredException에는 45분 서술도 있음)약 40분 + 기체별 무작위 지연(0~5분)에 계획 재연결(18장 권장값), GO_AWAY 수신 시 즉시
브라우저 STS 자격증명900초(AssumeRole 최솟값)캐시하지 않는다. 시그널링 재연결·ICE restart마다 백엔드에 새로 요청
TURN 자격증명300초(고정)새 PeerConnection·ICE restart마다 GetIceServerConfig 재호출. RECONNECT_ICE_SERVER 수신 시 새 ICE 서버로 ICE restart

계획 재연결 시각에 무작위 지연을 섞는 이유는 300대가 같은 시각에 부팅했을 때 재연결이 한 순간에 몰리지 않게 하려는 것이다. 브라우저가 재연결할 때마다 백엔드에서 자격증명을 다시 받는 구조에는 부수 효과가 있다. 권한 회수가 최대 15분 안에 반영된다. 운영자를 농장에서 빼면 다음 재연결 때 403이 난다.

시그널링이 끊기는 순간 이미 맺어진 PeerConnection의 미디어가 어떻게 되는지는 공식 문서에서 확인하지 못했다. 원리상 미디어는 시그널링과 별개 경로지만, 설계는 어느 쪽이든 견디게 만든다. 미디어가 살아 있으면 그대로 두고, connectionState가 disconnected나 failed로 가면 새 시그널링 연결 위에서 ICE restart offer를 보낸다.

let signaling = null;
let plannedTimer = null;

async function connectSignaling(deviceId, onReady) {
  const res = await fetch(`/api/devices/${deviceId}/view-grants`, { method: 'POST' });
  if (res.status === 403) return showRevoked();            // ACL 회수가 여기서 반영된다
  if (res.status === 409) return showViewerFull(await res.json());
  if (!res.ok) throw new Error(`view-grant ${res.status}`);
  const grant = await res.json();
  const { wssEndpoint, iceServers } = await resolveEndpoints(grant); // 20장: Endpoint(VIEWER) + GetIceServerConfig

  const client = new KVSWebRTC.SignalingClient({
    channelARN: grant.channelArn,
    channelEndpoint: wssEndpoint,
    clientId: grant.clientId,            // 탭마다 고유해야 한다. 같은 clientId면 기존 연결이 밀려난다
    role: KVSWebRTC.Role.VIEWER,
    region: grant.region,
    credentials: grant.credentials,      // 채널 1개로 좁힌 15분짜리 STS 자격증명
    systemClockOffset: grant.serverTimeMs - Date.now(),
  });
  client.on('open', () => onReady(client, iceServers));
  client.on('close', () => {
    if (signaling !== client) return;    // 계획 재연결로 이미 교체된 연결
    scheduleRetry(deviceId, onReady);    // 지수 백오프
  });

  const previous = signaling;
  signaling = client;
  client.open();
  previous?.close();

  clearTimeout(plannedTimer);            // 1시간 한도 전에, 탭마다 흩어지게
  plannedTimer = setTimeout(() => connectSignaling(deviceId, onReady),
    40 * 60 * 1000 + Math.random() * 5 * 60 * 1000);
}

systemClockOffset에 백엔드가 응답에 실어 준 서버 시각을 쓰는 이유는 운영자 PC의 시계도 틀릴 수 있어서다. 브라우저의 SigV4 서명도 디바이스와 똑같이 시각 검사를 받는다.

@Service
class ViewGrantService(
    private val sts: StsClient,
    private val acl: DeviceAclRepository,
    private val leases: ViewLeaseStore,
    @Value("\${farm.kvs.viewer-role-arn}") private val viewerRoleArn: String,
) {
    fun issue(operator: Operator, thingName: String): ViewGrant {
        val device = acl.findAccessibleDevice(operator.id, thingName)
            ?: throw AccessDeniedException("no access to $thingName")

        val clientId = "op-${operator.id}-${UUID.randomUUID().toString().take(8)}"
        if (!leases.tryAcquire(thingName, clientId, max = 3, ttl = Duration.ofMinutes(15))) {
            throw TooManyViewersException(thingName, leases.holders(thingName))  // → 409
        }

        val sessionPolicy = """
            {"Version":"2012-10-17","Statement":[{"Effect":"Allow",
              "Action":["kinesisvideo:DescribeSignalingChannel",
                        "kinesisvideo:GetSignalingChannelEndpoint",
                        "kinesisvideo:GetIceServerConfig",
                        "kinesisvideo:ConnectAsViewer"],
              "Resource":"${device.channelArn}"}]}
        """.trimIndent()

        val creds = sts.assumeRole {
            it.roleArn(viewerRoleArn)
                .roleSessionName("op-${operator.id}")
                .durationSeconds(900)
                .policy(sessionPolicy)
        }.credentials()

        return ViewGrant(device.channelArn, clientId, creds, serverTimeMs = System.currentTimeMillis())
    }
}

기본 역할(viewer-role-arn)에는 같은 4개 동작을 channel/*에 허용하고, 신뢰 정책으로 백엔드 역할만 assume할 수 있게 한다. 세션 정책의 평문 길이 한도는 2,048자라 채널 ARN 하나는 넉넉히 들어간다. clientId에 무작위 접미사를 붙이는 이유는 ConnectAsViewer가 같은 ClientId의 새 연결로 기존 연결을 대체하기 때문이다. 운영자가 탭을 두 개 열었을 때 서로를 밀어내지 않게 한다. ClientId는 AWS_로 시작할 수 없다는 제약도 있다(18장).

  • 내릴 때는 빠르게, 올릴 때는 느리게. 히스테리시스가 없으면 셀 경계에서 단계가 초 단위로 오르내리며 키프레임이 폭발하고, 그 키프레임이 다시 혼잡을 만든다. WebRTC 혼잡 제어 자체도 이렇게 동작하지만(09장), 해상도·카메라 수 같은 큰 단위 전환은 애플리케이션이 결정해야 한다.

  • 영상 품질과 조작 권한을 묶는다. 360p10에 1초 가까운 지연으로 보이는 화면을 보고 5톤 트랙터를 조그하게 두면 안 된다. 단계와 측정 RTT를 조건으로 디바이스가 스스로 조작 권한을 낮추고, 운영자 화면은 그 상태를 보여주기만 한다. 권한 판정을 브라우저에 두면 조작된 클라이언트나 버그가 안전 장치를 우회할 수 있다.

둘째, LTE 업링크가 AWS보다 먼저 상한에 닿는다. P2P라서 기체는 시청자마다 따로 보낸다. 기체당 월 업링크는 120분 × 30일 × 1.5명 × 9 MB = 48.6 GB로, 상한 50 GB에 거의 붙어 있다. 카메라 2대를 L0로 상시 보내면 두 배가 된다. 시청자 3명 상한과 보조 카메라 기본 저화질 정책은 품질 정책이면서 동시에 비용 정책이다.

셋째, 대안과 비교하면 P2P가 왜 싼지가 드러난다. 같은 시나리오를 다른 방식으로 돌리면 다음과 같다.

IVS 요율의 두 번째 구간 경계는 확인하지 못해 범위로 적었다. 저장 모드에서 릴레이 송신 요금이 따로 붙는지도 확인하지 못했다. 그래도 결론은 흔들리지 않는다. 서버를 경유하는 세 방식은 업링크를 1/1.5로 줄여 주지만 AWS 비용이 몇 배에서 열 배 넘게 뛴다. P2P의 비용 이점은 직결된 70%의 트래픽이 AWS를 전혀 거치지 않는다는 데서 나온다. 반대로 시청자가 늘어 업링크가 병목이 되는 순간 계산이 뒤집힌다. ADR-1의 재검토 조건이 바로 그 지점이다.

IoT Core 쪽은 텔레메트리 메시지가 대부분이다. 저장 목적 텔레메트리를 Basic Ingest($aws/rules/<규칙 이름> 토픽)로 보내면 메시지 요금 없이 규칙·액션 요금만 붙어 월 약 $78을 줄일 수 있다. 다만 Basic Ingest 토픽은 다른 구독자에게 전달되지 않으므로, 실시간 구독이 필요한 상태 메시지는 일반 토픽으로 남긴다.

스터디를 마치며 남는 교훈은 세 가지다.

WebRTC 설계의 대부분은 WebRTC 바깥에 있다. RTCPeerConnection 호출 자체는 몇십 줄이면 끝난다. 이 장의 분량 대부분은 시그널링, 자격증명 수명, 재연결, 권한, 관측, 비용이었다. 표준이 시그널링을 비워 둔 이유(03장)가 곧 설계자가 채워야 할 몫이다.

P2P는 공짜가 아니라 비용을 디바이스 쪽으로 옮긴 것이다. 서버 비용과 지연은 줄지만, 업링크가 시청자 수만큼 늘고 서버 측 녹화·분석 지점이 사라진다. 1:소수에서는 좋은 거래이고 1:다수에서는 나쁜 거래다.

안전은 네트워크에 맡기지 않는다. 워치독, 재부팅 후 비무장 상태, 품질에 묶인 조작 권한은 모두 디바이스가 스스로 판정한다. 원격 영상·제어는 사람이 더 잘 판단하게 돕는 도구일 뿐, 링크가 끊긴 순간의 안전을 보장하는 수단이 아니다.

다음 단계

  • 1:N이 필요해지면 송출을 한 번으로 줄인다. 교육·시연이나 농장주 앱 공개처럼 시청자가 수십 명 이상이 되면, 기체가 SFU나 IVS Real-Time에 한 번만 올리고 서버가 복제하게 한다. 이때도 1:소수 조작 세션은 KVS P2P로 남기는 하이브리드가 자연스럽다. 조작은 지연이 중요하고, 방송은 규모가 중요하기 때문이다(12장, 24장).
  • 송출 프로토콜은 WHIP으로 표준화한다. WHIP은 2025년 3월 RFC 9725로 발행됐다. 디바이스가 WHIP으로 송출하면 IVS, 오픈소스 SFU, 다른 벤더 사이를 디바이스 코드 변경 없이 오갈 수 있다. 재생 쪽 WHEP는 2026년 10월 현재 아직 IESG 단계의 드래프트다(14장).
  • 서버 측 영상 분석을 붙일 지점을 정한다. 실시간 분석이 필요하면 SFU에서 트랙을 분기하는 것이 자연스럽다. 사후 분석이면 사건 구간 S3 업로드나 저장 모드 스트림의 이미지 생성(GetImages)을 쓴다.
  • 코덱을 바꿔 LTE를 아낀다. C SDK 샘플은 H.265 인자를 받고, 차세대 보드는 AV1 하드웨어 인코더를 갖추기 시작했다. 같은 화질에 더 적은 비트레이트를 쓰면 §6의 LTE 상한에 여유가 생긴다. 다만 브라우저 디코딩 지원 범위를 먼저 확인해야 한다(08장).
  • 디바이스 쪽 관측을 서버로 모은다. 디바이스의 송신 통계(대역폭 추정, 손실, 사다리 단계, TURN 여부)를 MQTT로 시계열 저장소에 보내면 통신사·지역별 TURN 비율과 열화 패턴이 보인다. 지표 설계는 관측성 스터디의 방법론을 그대로 쓸 수 있다.

핵심 정리

  • 요구사항을 수치로 바꾸면 설계가 정해진다. 기체당 시청 3명 상한과 LTE 업링크 50 GB 상한이 P2P 채택, 사다리, 조작권 설계를 모두 제약했다.
  • 구조는 기체 1대 = 채널 1개(이름 = thing 이름)다. 디바이스는 인증서 → Credential Provider로 자격증명을 받아 MASTER로 대기하고, 백엔드는 ACL을 확인한 뒤 채널 하나로 좁힌 15분짜리 STS 자격증명을 브라우저에 준다.
  • 시그널링 1시간·TURN 자격증명 300초·브라우저 자격증명 900초라는 수명 차이 때문에 재연결은 정상 흐름이다. 계획 재연결에 무작위 지연을 섞고, 재연결 때마다 권한을 다시 확인한다.
  • 녹화는 로컬 링 버퍼 + 사건 업로드로 한다. 저장 모드는 켜는 순간 P2P가 사라지는 토폴로지 변경이다. 제어는 세션 안 조작은 DataChannel, 신뢰 명령은 MQTT, 비상정지는 둘 다로 보낸다.
  • 비용은 TURN 비율이 지배한다. 서울 기준 300대·하루 2시간 시청·TURN 30% 가정에서 월 약 $768이고, 그중 72%가 릴레이 데이터 송신이다. 서버 경유 대안은 업링크를 줄이는 대신 AWS 비용이 몇 배로 뛴다.
