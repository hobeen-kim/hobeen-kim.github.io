Task Controller와 DDOP

학습 목표

  • Task Controller(TC)가 ISOBUS 네트워크에서 담당하는 역할과, TC와 작업기가 주고받는 대화의 성격을 설명할 수 있다.
  • Device Descriptor Object Pool(DDOP)이 무엇이고 왜 필요한지 말할 수 있다.
  • DDOP를 구성하는 5종 오브젝트(DVC·DET·DPD·DPT·DVP)의 역할과 차이를 구분할 수 있다.
  • DDI가 무엇을 지정하는지 이해하고, DDI 값만으로는 데이터를 해석할 수 없는 이유를 설명할 수 있다.
  • DeviceDescriptorObjectPool API로 가장 단순한 DDOP를 직접 만들 수 있다.

Task Controller 개요

Task Controller는 ISO 11783 표준 안에 자기 몫의 파트를 통째로 갖고 있는 표준 ISOBUS 제어 기능(Control Function)이다. 해당 파트는 ISO 11783-10이고, TC는 작업기의 여러 기능을 기록(log)하고 제어(control)하는 데 쓰인다.

TC가 관리하는 데이터는 작업 경계(task boundaries), 커버리지 맵, 작업 상태 같은 태스크 데이터 전반이다. 여기에 더해, 작업기가 지리 정보와 함께 남기고 싶어 하는 모든 것도 TC가 맡는다.

일반적으로 TC는 다음 두 가지를 한다.

  • 지리 정보(geospatial data)를 사용해 작업기가 가변 살포량 처방(variable rate prescription) 작업을 수행하도록 계획하고 명령한다.
  • 작업기에 섹션 제어(section control)를 제공해, 이미 지나간 구역에 제품이 중복 살포되지 않게 한다.

TC와 작업기 사이의 통신은 상태를 가진(stateful) 프로토콜이다. TC는 명령을 보내고 필요한 데이터를 요청하며, 작업기는 상태 업데이트를 돌려보낸다.

이 통신의 상당 부분을 AgIsoStack이 대신 처리한다. 덕분에 개발자는 자기 비즈니스 로직에만 집중하면 된다.

TC의 개념적 배경과 프로세스 데이터 메시지의 바이트 수준 구조는 ISOBUS 스터디에서 다룬다.

Device Descriptor Object Pool (DDOP)

Virtual Terminal 클라이언트가 오브젝트 풀로 디스플레이에 "무엇을 그려야 하는지" 알려주는 것과 꼭 같은 방식으로, 작업기는 오브젝트 풀로 TC에 "내가 무엇을 할 수 있는지" 알려준다. 다만 이 풀에 들어가는 오브젝트 종류는 VT 풀과 다르다. DDOP는 작업기가 TC에 접속하는 과정에서 TC로 업로드된다.

다시 말해 DDOP는 작업기의 능력을 서술하는 오브젝트의 모음이다. 섹션이 몇 개인지, 각 섹션의 폭은 얼마인지, 살포하는 제품의 종류가 무엇인지 같은 것들이 여기에 들어간다. DDOP는 머신 위에서 작업기 기하 정보의 권위 있는 출처(authoritative source)다.

AgIsoStack에서의 위치는 이렇다.

  • TC 클라이언트를 쓴다면, 작업기를 TC에 설명하는 DDOP를 직접 만들어야 한다.
  • TC 서버를 쓴다면, 클라이언트 작업기들로부터 DDOP를 받게 되고, 그것이 무슨 뜻인지 해석할 줄 알아야 한다.

잘 만들어진 DDOP 예제를 보기 전에, 용어부터 정리한다.

DDOP 오브젝트 종류

DDOP에 들어갈 수 있는 오브젝트 타입은 몇 가지 안 되지만, 조합하는 방식이 자유로워서 온갖 종류의 작업기를 꽤 자유 형식으로 서술할 수 있다.

Device (DVC) — DDOP의 루트 오브젝트다. 나머지 모든 오브젝트를 담는다. DDOP 하나에 오직 하나만 존재하며, 작업기 전체에 대한 정보를 TC에 알린다. 필드는 다음과 같다.

  • Device Designator: 작업기를 식별하는 문자열. 보통 작업기 이름이다.
  • Device Software Version: 작업기의 소프트웨어 버전 문자열.
  • Device Serial Number: 작업기의 시리얼 번호 문자열.
  • Device Structure Label: 특정 버전의 DDOP를 가리키는 고유 식별자. DDOP가 바뀌면 이 라벨도 바뀌어야 한다. 그래야 TC 클라이언트가 "TC가 들고 있는 DDOP는 낡았으니 다시 올려야 한다"는 것을 알 수 있다.
  • Device Localization Label: 언어, 국가 코드, 단위계를 서술하는 특수 포맷의 바이너리 바이트 모음. TC와 작업기가 같은 단위와 언어를 쓰도록 보장한다.
  • 선택적으로 Extended Structure Label: TC 버전 4의 선택 필드로, 최대 32바이트짜리 더 긴 구조 라벨을 제공할 수 있다. 대개는 무시해도 된다.

Device Element (DET) — 작업기의 논리적 구조를 세우는 데 쓴다. 섹션, 빈(bin), 기능 같은 것들이 여기 해당하고, 각각이 붐·제품·섹션의 계층을 만든다. 요소 타입은 다음과 같다.

  • Device: DDOP 안에 하나만 존재하며, 요소 계층의 루트를 서술한다.
  • Function: 밸브, 센서, 붐처럼 개별적으로 접근 가능한 장치 구성 요소를 정의한다.
  • Bin: 탱크처럼 제품을 담는 용기를 정의한다. 보통 이 빈 안의 제품과 관련된 오브젝트들의 루트로 쓰인다. 예를 들어 부모가 빈인 살포량(rate)은 곧 그 빈에 담긴 제품의 살포량이라는 뜻이 된다.
  • Section: 붐 섹션 같은 작업기의 섹션을 정의한다. 섹션 폭처럼 그 섹션에 대한 정보를 제공하는 오브젝트들의 부모로 쓴다. DDOP 안에 섹션은 여러 개 있을 수 있다.
  • Unit: 예컨대 스프레이 붐 노즐, 파종기 오프너, 플랜터 로우 유닛에 쓴다.
  • Connector: 장치의 장착/연결 위치를 지정한다.
  • NavigationReference: GNSS 수신기 같은 장치의 항법 기준 위치를 정의한다.

Device Process Data (DPD) — DDOP 안의 "변수"에 해당한다. 현재 살포량, 섹션의 현재 상태처럼 장치의 현재 상태를 서술하고, 작업기의 현재 상태를 TC에 업데이트하는 데 쓴다.

  • DPD의 값은 DDOP에 저장되지 않는다. 특정 조건에 따라 별도 메시지로 TC에 전송된다.
  • 작업기에서 런타임에 변할 수 있는 것은 전부 이 타입을 쓴다.
  • DPD는 어떤 조건에서 TC로 전송될지도 함께 알린다. 예를 들어 살포량이 1% 넘게 바뀔 때마다, 혹은 1초마다, 혹은 머신이 1미터 주행할 때마다 보내도록 설정할 수 있다. 이것을 측정 트리거(measurement trigger)라고 한다.
  • DPD는 그 값이 "총계(total)" 값인지도 알린다. 살포량은 총계가 아니지만, 총 작업 면적은 총계다.

Device Property (DPT) — 섹션 폭처럼 장치의 정적 속성을 서술한다. DPD와 함께 써서 작업기를 TC에 설명한다.

  • DPT의 값은 DDOP에 저장된다. DDOP를 업로드할 때 TC로 함께 전달된다. 런타임에 바꾸려면 DDOP를 다시 업로드해야 한다.
  • DDOP를 만드는 시점에 고정되는 것은 전부 이 타입을 쓴다.

Device Value Presentation (DVP) — DPD를 사용자에게 어떻게 보여줄지 서술한다.

  • 단위, 스케일 팩터, 오프셋, 소수 자릿수 등 TC가 DPD나 DPT를 사용자에게 표시할 때 적용할 정보를 담는다.
  • 선택 사항이다. 없으면 TC가 기본값으로 DPD/DPT를 표시한다.

추가로, 각 오브젝트는 0에서 65534 사이의 고유 ID를 갖는다. DDOP 안에서 오브젝트를 구별하는 데 쓰인다.

이 오브젝트들을 조합하면 아주 다양한 작업기를 TC에 서술할 수 있고, TC는 표준화된 방식으로 작업기를 제어하고 모니터링할 수 있게 된다.

Data Dictionary Identifier (DDI)

DDOP 안의 DPD와 DPT 오브젝트는 DDI(Data Dictionary Identifier)라는 번호로 자신이 표현하는 데이터가 무엇인지 식별한다.

기본적으로 DDI는 TC에게 "이 데이터가 무엇이고, 어떻게 해석해야 하는지"를 알려준다.

전체 DDI 목록은 AEF가 관리하며 isobus.net에서 볼 수 있다. AgIsoStack도 편의를 위해 포괄적인 DDI 목록을 제공한다.

DDI 134를 예로 들어 그 의미를 보자. isobus.net의 ISOBUS 데이터베이스에는 이렇게 정의돼 있다.

  • DDI: 134
  • Name: "Device Element Offset X"
  • Definition: "X direction offset of a DeviceElement relative to a Device"
  • Unit symbol: "mm"
  • Bit Resolution: 1

즉 DDI 134를 쓰는 DPT나 DPD는 장치 기준점(device reference point)에 대한 요소의 X 방향 오프셋을 서술하며, 전송되는 값은 밀리미터로 해석해야 한다는 뜻이다.

다르게 말하면, 어떤 섹션이 있고 그 섹션 아래에 이 DDI를 가진 자식 DPT가 있다면, 그 DPT의 값은 곧 작업기 장치 기준점에 대한 해당 섹션의 X 오프셋이라는 것을 TC에 알려주는 것이다.

장치 기준점이 무엇인지 궁금할 텐데, 견인식(trailed) 작업기라면 작업기 앞 차축의 중심이고, 자주식 후방 장착(self-propelled rear-mounted) 작업기라면 작업기 뒤 차축의 중심이다.

DDI 참고

ISOBUS 스터디의 DDI 목록에 자주 쓰이는 DDI가 정리돼 있다.

DDI 목록은 살아 있는 문서다

DDI 목록은 living document다. ISOBUS 표준에 새 기능이 추가되면 새 DDI도 추가된다. 작업기에 맞는 DDI를 쓰고 있는지 확인하려면 최신 버전의 DDI 목록을 확인하는 것이 중요하다.

DDI만으로는 데이터를 해석할 수 없다

DDI와 그것을 사용하는 DPT/DPD 사이의 연결 관계를 반드시 이해해야 한다. ISOBUS CAN 트레이스를 보면서 버스 위를 오가는 여러 DDI를 들여다보고 있다면, 그 데이터가 무슨 의미인지 알기 위해 DDOP의 전체 구조를 반드시 알고 있어야 한다.

예를 들어 섹션이 10개인 작업기라면 각 섹션마다 DDI 134를 가진 DPT가 있을 수 있고, 각각의 값은 다 다를 것이다. 즉 어떤 DDI 134 값이 어느 섹션을 가리키는지 알려면 그 섹션의 요소 번호(element number)와 DDOP에서 오는 나머지 맥락을 알아야 한다.

결국 TC에 업로드된 DDOP를 갖고 있지 않은 이상, 다른 장치와 TC의 연결을 스니핑해서 데이터 의미를 자신 있게 파악하기란 매우 어렵다.

DDOP 만들기

이제 DDOP 예제 몇 개를 보면서, 여러 작업기를 어떻게 서술할 수 있고 AgIsoStack으로 어떻게 만드는지 살펴본다.

가장 단순한 예제

만들 수 있는 가장 단순한 TC-BAS DDOP는 다음 구성이다.

  • Device 오브젝트 1개
  • Device Element 1개
  • DDI 119(Total Time)를 가진 DPD 1개

분명히 이 DDOP는 하는 일이 거의 없다. 하지만 TC에 업로드할 수 있는 유효한 DDOP다. 제어할 수 있는 것은 아무것도 없지만 작업기가 활성 상태였던 총 시간은 보고하는 작업기를 서술한다.

AgIsoStack으로 이 DDOP를 만드는 코드는 이렇다.

#include "isobus/isobus/isobus_device_descriptor_object_pool.hpp"

isobus::DeviceDescriptorObjectPool OurDDOP; // This creates a blank DDOP

// We can use a LanguageCommandInterface to quickly generate a Localization Label.
LanguageCommandInterface OurLanguageInterface(nullptr, nullptr);

// Add a device object to the DDOP
OurDDOP.add_device("My Device", "1.0.0", "123", "MIV1.0", OurLanguageInterface.get_localization_raw_data(), std::vector<std::uint8_t>(), 1234);
OurDDOP.add_device_element("My Implement", 0, 0, task_controller_object::DeviceElementObject::Type::Device, 1);
OurDDOP.add_device_process_data("Total Time", 119, 0xFFFF, 0, static_cast<std::uint8_t>(task_controller_object::DeviceProcessDataObject::AvailableTriggerMethods::Total), 2);

보다시피 먼저 빈 DDOP를 만들고, 거기에 device 오브젝트·device element·DPD를 차례로 추가한다.

device 오브젝트는 이름/designator가 "My Device", 소프트웨어 버전 "1.0.0", 시리얼 번호 "123", 구조 라벨 "MIV1.0", 전부 미터법 기본값으로 설정된 로컬라이제이션 라벨, 빈 확장 구조 라벨, 그리고 ISO NAME 1234를 갖는다. AgIsoStack을 쓸 때 device는 항상 오브젝트 ID 0이다.

device element 오브젝트는 designator "My Implement", 요소 번호 0, 부모 오브젝트 ID 0, 타입 Device, 오브젝트 ID 1을 갖는다.

device process data 오브젝트는 designator "Total Time", DDI 119, presentation 오브젝트 ID 0xFFFF(연결된 DVP 오브젝트가 없다는 뜻), 특별한 속성 없음(0), 트리거 방식 Total, 고유 오브젝트 ID 2를 갖는다.

이론상 이제 이 DDOP를 AgIsoStack TC 클라이언트에 넘기면 클라이언트가 TC로 업로드하고, TC는 이 가상의 작업기에 대한 모든 정보를 갖게 된다.

TC 클라이언트 사용법은 다음 챕터에서 다루지만, DDOP를 만들 줄 아는 것이 그 첫걸음이다.

제품 1개 · 섹션 1개 파종기

제품 하나와 섹션 하나를 가진 파종기처럼 조금 더 복잡한 작업기라면 DDOP는 훨씬 커진다. 앞의 예제와 비교하면 복잡도 차이가 확연하다.

작업기가 복잡할수록, TC가 그것을 제어하고 모니터링하는 데 필요한 정보를 정확히 제공하기 위해 DDOP에 들어가는 오브젝트 수도 늘어난다.

이 정도로 복잡한 DDOP를 만들 때 참고하기 좋은 자료가 AgIsoStack의 파종기 예제다. 파종기용의 더 복잡한 DDOP를 만드는 코드가 들어 있다.

구조를 보면 앞서 설명한 오브젝트들이 어떻게 조립되는지 감이 온다. 파종기 예제에서 발췌한 뼈대는 다음과 같다.

// English, decimal point, 12 hour time, ddmmyyyy, all units imperial
constexpr std::array<std::uint8_t, 7> localizationData = { 'e', 'n', 0b01010000, 0x00, 0b01010101, 0b01010101, 0xFF };

// Make a pool with 1 granular product
// Set up device and device element
retVal &= poolToPopulate->add_device("Isobus Seeder", "1.0.0", "123", "IS1.2", localizationData, std::vector<std::uint8_t>(), clientName.get_full_name());
retVal &= poolToPopulate->add_device_element("Seeder", elementCounter, 0, isobus::task_controller_object::DeviceElementObject::Type::Device, static_cast<std::uint16_t>(ImplementDDOPObjectIDs::MainDeviceElement));
retVal &= poolToPopulate->add_device_process_data("Actual Work State", static_cast<std::uint16_t>(isobus::DataDescriptionIndex::ActualWorkState), isobus::NULL_OBJECT_ID, static_cast<std::uint8_t>(isobus::task_controller_object::DeviceProcessDataObject::PropertiesBit::MemberOfDefaultSet), static_cast<std::uint8_t>(isobus::task_controller_object::DeviceProcessDataObject::AvailableTriggerMethods::OnChange), static_cast<std::uint16_t>(ImplementDDOPObjectIDs::DeviceActualWorkState));
elementCounter++; // Increment element number. Needs to be unique for each element.

// Set up Boom element
retVal &= poolToPopulate->add_device_element("AgIsoStack Example", elementCounter, static_cast<std::uint16_t>(ImplementDDOPObjectIDs::MainDeviceElement), isobus::task_controller_object::DeviceElementObject::Type::Function, static_cast<std::uint16_t>(ImplementDDOPObjectIDs::MainBoom));
retVal &= poolToPopulate->add_device_property("Offset X", 0, static_cast<std::uint16_t>(isobus::DataDescriptionIndex::DeviceElementOffsetX), static_cast<std::uint16_t>(ImplementDDOPObjectIDs::ShortWidthPresentation), static_cast<std::uint16_t>(ImplementDDOPObjectIDs::BoomXOffset));
elementCounter++;

// Set up bin/tank element
retVal &= poolToPopulate->add_device_element("Product", elementCounter, 9, isobus::task_controller_object::DeviceElementObject::Type::Bin, static_cast<std::uint16_t>(ImplementDDOPObjectIDs::GranularProduct));
retVal &= poolToPopulate->add_device_process_data("Target Rate", static_cast<std::uint16_t>(isobus::DataDescriptionIndex::SetpointCountPerAreaApplicationRate), static_cast<std::uint16_t>(ImplementDDOPObjectIDs::CountPerAreaPresentation), static_cast<std::uint8_t>(isobus::task_controller_object::DeviceProcessDataObject::PropertiesBit::MemberOfDefaultSet) | static_cast<std::uint8_t>(isobus::task_controller_object::DeviceProcessDataObject::PropertiesBit::Settable), static_cast<std::uint8_t>(isobus::task_controller_object::DeviceProcessDataObject::AvailableTriggerMethods::OnChange), static_cast<std::uint16_t>(ImplementDDOPObjectIDs::TargetRate));
elementCounter++;

// Set up sections for section control
retVal &= poolToPopulate->add_device_element("Section " + isobus::to_string(static_cast<int>(i)), elementCounter, static_cast<std::uint16_t>(ImplementDDOPObjectIDs::MainBoom), isobus::task_controller_object::DeviceElementObject::Type::Section, static_cast<std::uint16_t>(ImplementDDOPObjectIDs::Section1) + i);
retVal &= poolToPopulate->add_device_property("Width", individualSectionWidth, static_cast<std::uint16_t>(isobus::DataDescriptionIndex::ActualWorkingWidth), static_cast<std::uint16_t>(ImplementDDOPObjectIDs::LongWidthPresentation), static_cast<std::uint16_t>(ImplementDDOPObjectIDs::Section1Width) + i);

// Set up presentations
retVal &= poolToPopulate->add_device_value_presentation("mm", 0, 1.0f, 0, static_cast<std::uint16_t>(ImplementDDOPObjectIDs::ShortWidthPresentation));
retVal &= poolToPopulate->add_device_value_presentation("seeds/ha", 0, 1.0f, 0, static_cast<std::uint16_t>(ImplementDDOPObjectIDs::CountPerAreaPresentation));

여기서 눈여겨볼 점이 몇 가지 있다.

  • 요소 번호(elementCounter)는 각 요소마다 고유해야 하고, 섹션 하나하나가 각자 독립된 요소다.
  • DDI는 매직 넘버 대신 isobus::DataDescriptionIndex 열거형으로 쓴다.
  • DPD의 속성 비트(PropertiesBit::MemberOfDefaultSet, PropertiesBit::Settable)와 트리거 방식(AvailableTriggerMethods::OnChange, ::TimeInterval, ::Total)은 비트 OR로 조합한다.
  • DVP가 없는 DPD/DPT는 presentation 자리에 isobus::NULL_OBJECT_ID를 넣는다.
  • 부모-자식 관계는 요소 생성 시의 부모 ID뿐 아니라, add_reference_to_child_object로도 명시적으로 연결한다.
auto boom = std::static_pointer_cast<isobus::task_controller_object::DeviceElementObject>(poolToPopulate->get_object_by_id(static_cast<std::uint16_t>(ImplementDDOPObjectIDs::MainBoom)));
boom->add_reference_to_child_object(static_cast<std::uint16_t>(ImplementDDOPObjectIDs::BoomXOffset));
boom->add_reference_to_child_object(static_cast<std::uint16_t>(ImplementDDOPObjectIDs::ActualWorkingWidth));

AgIsoDDOPGenerator

Open-Agriculture는 AgIsoDDOPGenerator라는 도구를 만들었다. 작업기용 바이너리 DDOP를 만들고, 보고, 편집할 수 있는 도구다. 이 도구로 DDOP 오브젝트의 계층 구조를 눈으로 보면 구조를 이해하는 데 큰 도움이 된다.

AgIsoDDOPGenerator로 만든 DDOP는 AgIsoStack에서 그대로 쓸 수 있고, AgIsoStack TC 클라이언트를 통해 TC로 업로드할 수 있다.

핵심 정리

  • TC는 ISO 11783-10에 정의된 제어 기능으로, 태스크 데이터를 기록하고 작업기를 제어한다. 대표적으로 가변 살포량 처방과 섹션 제어를 제공한다.
  • DDOP는 작업기의 능력을 서술하는 오브젝트 풀이고, 접속 과정에서 TC로 업로드된다. 머신 위에서 작업기 기하 정보의 권위 있는 출처다.
  • 오브젝트는 5종이다. DVC(루트, 1개), DET(요소 계층), DPD(런타임 값, DDOP에 값 저장 안 됨), DPT(고정 값, DDOP에 값 저장됨), DVP(표시 방법, 선택).
  • 각 오브젝트는 0~65534의 고유 ID를 갖는다.
  • DPD/DPT는 DDI로 데이터의 정체와 해석 방법을 지정한다. 다만 DDI 값만으로는 의미를 알 수 없고 DDOP 전체 구조를 알아야 한다.
  • DeviceDescriptorObjectPool의 add_device, add_device_element, add_device_process_data, add_device_property, add_device_value_presentation으로 DDOP를 만든다.
  • AgIsoDDOPGenerator로 바이너리 DDOP를 만들고 보고 편집할 수 있다.
