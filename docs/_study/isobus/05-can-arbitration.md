# CAN 중재와 우선순위

::: info 학습 목표
- 여러 노드가 동시에 보내기 시작해도 CAN 버스가 충돌 없이 메시지 하나를 고르는 과정(중재)을 설명할 수 있다.
- ID를 비트로 펼쳐 놓고 몇 번째 비트에서 누가 이기는지 따라갈 수 있다.
- ID 값이 작을수록 우선순위가 높은 이유를 Dominant와 Recessive로 설명할 수 있다.
- ISOBUS의 Priority 기본값(제어 3, 그 밖 6, TP·ETP 7)과 "받는 쪽은 Priority를 보지 않는다"는 규칙을 설명할 수 있다.
- (심화) 권고표로 새 메시지의 Priority를 고르고, 11비트 ID 프레임과 29비트 ID 프레임이 함께 중재할 때 승자를 계산할 수 있다.
:::

::: tip 시작하기 전에
- 먼저 읽을 장: [3장 CAN 물리 계층](/study/isobus/03-can-physical), [4장 CAN 데이터 프레임](/study/isobus/04-can-data-frame)
- 3장에서 본 말: Dominant(0)와 Recessive(1)는 버스 위의 두 상태다. 한 노드라도 Dominant를 보내면 버스 전체가 Dominant가 된다(Wired-AND).
- 이 장에서 처음 나오는 말
  - 중재(Arbitration): 여러 노드가 동시에 보내려 할 때 하나만 골라 보내게 하는 과정
  - 비파괴적 중재: 진 노드도 데이터를 잃지 않고 나중에 다시 보내는 중재 방식
  - 라운드: ID 비트 하나를 비교하는 한 번의 차례. 1라운드는 ID의 첫 비트다
  - Priority(우선순위 필드): 29비트 ID 맨 앞 3비트. 0이 가장 급하고 7이 가장 느긋하다
  - 기아 상태(Starvation): 우선순위가 낮은 메시지가 계속 져서 오래 나가지 못하는 상태
  - CBFF와 CEFF: 11비트 ID 프레임과 29비트 ID 프레임의 정식 이름. 4장의 Standard 프레임과 Extended 프레임이다
:::

회의에서 두 사람이 동시에 입을 열면 보통 둘 다 멈추고 서로 눈치를 본다. CAN 버스는 다르게 해결한다. 여러 노드가 동시에 보내기 시작해도 더 급한 메시지 하나만 끝까지 이어서 나가고, 양보한 노드는 아무것도 잃지 않은 채 다음 차례에 다시 보낸다. 이 장에서는 이 양보가 ID의 비트 하나하나로 어떻게 정해지는지, 그리고 ISOBUS가 메시지의 급한 정도를 ID에 어떻게 적는지 본다.

## 1. 버스 중재란 무엇인가

이 절에서는 여러 노드가 버스 하나를 나눠 쓸 때 생기는 문제와, CAN이 그 문제를 푸는 방식의 이름을 본다.

<strong>문제 상황</strong>: CAN에서는 여러 노드가 전선 한 쌍(버스)을 함께 쓴다. 이때 두 노드가 <strong>동시에</strong> 메시지를 보내기 시작하면 어떻게 될까?

이더넷(사무실 컴퓨터를 잇는 유선 네트워크)의 경우 충돌(Collision)이 발생하면 두 노드 모두 전송을 멈추고 임의의 시간 뒤 재전송한다. 이 방식은 충돌 후 데이터가 손실된다.

<strong>CAN의 해답</strong>: CAN은 <strong>CSMA/CD+AMP</strong> 방식을 사용해 충돌 없이 우선순위가 높은 메시지가 이기도록 한다. 이름은 길지만 세 부분으로 나눠 읽으면 된다.

| 용어 | 의미 |
|---|---|
| **CSMA** (Carrier Sense Multiple Access) | 전송 전 버스가 사용 중인지 확인한다 |
| **CD** (Collision Detection) | 전송 중 충돌(다른 신호)을 감지한다 |
| **AMP** (Arbitration on Message Priority) | 메시지 우선순위에 따라 중재한다 |

풀어 말하면 보내기 전에 버스가 조용한지 듣고(CSMA), 보내는 동안에도 버스를 계속 듣고(CD), 겹치면 메시지 우선순위로 승부를 낸다(AMP).

<strong>핵심 차이</strong>: 이더넷은 충돌 후 <strong>모두 재전송</strong>하지만, CAN은 중재 패배 노드만 재전송한다. 승리한 노드는 전송을 <strong>중단 없이 계속</strong>한다.

::: info
중재는 ID 필드 전송 구간에서만 일어난다. 중재에서 이긴 노드의 메시지는 데이터 손실 없이 그대로 버스에 전달된다.
:::

회의 비유와 다른 점이 하나 있다. 사람은 상대가 누구인지 보고 양보하지만, CAN 노드는 상대가 누구인지 모른다. 자기가 보낸 비트와 버스에서 읽은 비트만 비교해서 물러날지를 정한다.

### "노드 ID"가 아니라 "메시지 ID"

한 가지 주의할 점이 있다. CAN에서 ID는 <strong>노드(장치)를 식별하는 것이 아니라 메시지의 종류를 식별한다.</strong> 하나의 ECU(Electronic Control Unit, 전자 제어 장치)가 여러 종류의 메시지를 보낼 수 있으며, 각각 다른 ID를 가진다. 아래는 엔진 ECU 하나가 세 종류의 메시지에 서로 다른 ID를 붙여 보내는 예다.

```
엔진 ECU (하나의 노드)가 보내는 메시지들:
  ID=0x100: 엔진 RPM 정보
  ID=0x101: 엔진 온도 정보
  ID=0x102: 엔진 토크 정보
```

따라서 중재에서 비교되는 것은 노드의 고유번호가 아니라, <strong>그 순간 전송하려는 메시지의 ID</strong>다. 같은 노드라도 어떤 메시지를 보내느냐에 따라 우선순위가 달라진다.

정리하면, CAN은 동시에 보내기 시작한 노드들 가운데 가장 급한 메시지 하나만 끝까지 보내게 하고, 나머지 노드는 데이터를 잃지 않고 물러나게 한다. 급한 정도를 정하는 것은 메시지의 ID다.

## 2. 비트 단위 중재 과정

이 절에서는 두 노드가 같은 순간 보내기 시작했을 때, ID 비트를 하나씩 비교하며 승부가 갈리는 모습을 본다.

중재는 ID를 다 보낸 뒤에 비교하는 것이 아니다. 각 노드가 ID를 MSB(Most Significant Bit, 가장 큰 자리의 비트, 즉 맨 왼쪽 비트)부터 <strong>한 비트씩 버스에 보내면서, 동시에 버스를 읽어 실시간으로 비교</strong>한다. 아래는 노드B가 비트8에서 졌다고 가정하고, 두 노드가 시간 순서대로 내보내는 비트를 나란히 적은 도식이다(바로 뒤의 예제에서는 비트9에서 갈린다).

```
시간 →
노드A: [SOF][비트10][비트9][비트8]...[비트0] → 승리 시 [DLC][Data]... 계속
노드B: [SOF][비트10][비트9][비트8] ← 여기서 탈락하면 즉시 중단
```

SOF(Start of Frame, 프레임 시작을 알리는 비트) 다음부터 ID 비트가 차례로 나간다. ID 구간이 끝나면 중재도 끝나고, 승자만 나머지(DLC, Data, CRC 등)를 전송한다. 구체적인 예시를 보자. 노드A(ID=0x100, 10진수 256)와 노드B(ID=0x200, 10진수 512)가 동시에 전송을 시작하는 상황이다.

<strong>ID를 이진수로 펼치기</strong>

0x100과 0x200을 11비트 이진수로 바꾸면 아래 그림과 같다. 0x100은 `001 0000 0000`, 0x200은 `010 0000 0000`이다. 칸 위의 숫자는 비트 번호이고, 왼쪽 비트10(MSB)이 가장 먼저 나간다.

![노드A(0x100)와 노드B(0x200)의 11bit ID를 비트별로 나열한 비교: bit10은 동일, bit9에서 노드A=0 노드B=1](/images/study-isobus/05-id11-compare-light.png)
![노드A(0x100)와 노드B(0x200)의 11bit ID를 비트별로 나열한 비교: bit10은 동일, bit9에서 노드A=0 노드B=1](/images/study-isobus/05-id11-compare-dark.png)

그림에서 노드A의 1은 비트8에, 노드B의 1은 비트9에 있다. 왼쪽(비트10)부터 같은 자리끼리 비교하면 비트9에서 처음으로 값이 달라진다.

<strong>비트별 중재 과정</strong>

표는 위에서 아래로 시간 순서다. 각 줄에서 두 노드가 보낸 값과, 두 값이 합쳐져 버스에 나타난 값을 함께 본다.

| 비트 위치 | 노드A | 노드B | 버스 상태 | 결과 |
|---|---|---|---|---|
| 비트 10 (MSB) | 0 (Dominant) | 0 (Dominant) | Dominant | 동점, 계속 |
| 비트 9 | 0 (Dominant) | 1 (Recessive) | <strong>Dominant</strong> | <strong>노드B 탈락</strong> |
| 비트 8 | 1 (Recessive) | 보내지 않음 | Recessive | 노드A 혼자 계속 |

비트 9에서 노드A는 0(Dominant)을, 노드B는 1(Recessive)을 전송한다. 버스는 Dominant 값인 0이 된다. 노드B는 자신이 1을 보냈는데 버스가 0이 된 것을 감지하고, <strong>즉시 전송을 중단</strong>한다. 노드A는 아무것도 모른 채 전송을 계속한다. 비트 8부터는 노드A 혼자 보낸다. 노드A의 비트 8은 1(Recessive)이지만 이제 경쟁자가 없으므로 버스도 1이 되고, 노드A는 일치를 확인하며 계속 보낸다.

아래 그림은 같은 과정을 시간 순서로 그린 것이다. 가운데 세로줄이 버스다. 각 노드는 비트를 보낸 뒤(실선) 버스 값을 다시 읽어(점선) 자기가 보낸 값과 비교한다.

![노드A(0x100)와 노드B(0x200)가 SOF, 비트10, 비트9를 버스에 보내고 다시 읽는 순서: 비트10은 둘 다 0으로 일치하고, 비트9에서 노드B는 1을 보냈는데 0을 읽어 즉시 중단한다. 노드A는 나머지 프레임을 끝까지 보내고 노드B는 버스가 비면 처음부터 재전송한다](/images/study-isobus/05-arbitration-sequence-light.png)
![노드A(0x100)와 노드B(0x200)가 SOF, 비트10, 비트9를 버스에 보내고 다시 읽는 순서: 비트10은 둘 다 0으로 일치하고, 비트9에서 노드B는 1을 보냈는데 0을 읽어 즉시 중단한다. 노드A는 나머지 프레임을 끝까지 보내고 노드B는 버스가 비면 처음부터 재전송한다](/images/study-isobus/05-arbitration-sequence-dark.png)

정리하면, 각 노드는 비트를 보낼 때마다 버스를 다시 읽는다. 1을 보냈는데 0이 읽히면 진 것이므로 그 자리에서 멈춘다. 진 노드는 이긴 프레임이 끝나고 버스가 비면 처음부터 다시 보낸다.

## 3. ID 값과 우선순위의 관계

이 절에서는 2절의 규칙에서 바로 나오는 결론, 즉 어떤 ID가 더 급한 메시지인지를 정리한다.

<strong>원칙: ID 숫자가 작을수록 우선순위가 높다.</strong>

이유는 간단하다. CAN 버스에서 <strong>0(Dominant)이 1(Recessive)을 이긴다</strong>. ID의 상위 비트부터 비교할 때, 먼저 0을 보내는 노드가 버스를 차지한다. 아래는 가장 작은 쪽 ID 0x001(10진수 1)과 가장 큰 ID 0x7FF(10진수 2047)를 11비트로 적은 것이다.

```
ID = 0x001: 0000 0000 001  ← 앞쪽이 0으로 가득 참 → 버스 독점 유리
ID = 0x7FF: 1111 1111 111  ← 앞쪽이 1로 가득 참 → 버스 독점 불리
```

11비트 ID 전체를 우선순위 순서로 늘어놓으면 다음 그림과 같다. 화살표 방향으로 갈수록 우선순위가 낮아진다. 각 ID 아래에 적은 이진수를 보면, 앞쪽에 0이 많을수록 왼쪽(높은 우선순위)에 놓인다.

![11비트 ID를 우선순위 순서로 늘어놓은 그림: 높은 우선순위 쪽에 0x000(최고 우선순위), 0x001, 0x100, 낮은 우선순위 쪽에 0x600, 0x700, 0x7FF(최저 우선순위)가 있고 각 ID 아래에 11비트 이진수를 적었다](/images/study-isobus/05-id-priority-scale-light.png)
![11비트 ID를 우선순위 순서로 늘어놓은 그림: 높은 우선순위 쪽에 0x000(최고 우선순위), 0x001, 0x100, 낮은 우선순위 쪽에 0x600, 0x700, 0x7FF(최저 우선순위)가 있고 각 ID 아래에 11비트 이진수를 적었다](/images/study-isobus/05-id-priority-scale-dark.png)

0x000은 11비트가 모두 0이라 어떤 ID와 맞붙어도 먼저 물러나는 일이 없다. 0x7FF는 모두 1이라 다른 어떤 ID와 맞붙어도 이기지 못한다.

<strong>29bit Extended ID에서의 우선순위</strong>

ISOBUS는 29bit Extended ID를 사용하며, ID의 상위 3비트가 Priority 필드다. 29비트 ID를 이루는 필드는 다음과 같다(자세한 뜻은 [9장 J1939 메시지 구조](/study/isobus/09-j1939-message)에서 본다).

- Priority(3비트): 메시지의 급한 정도. 0~7
- EDP(Extended Data Page, 1비트)와 DP(Data Page, 1비트): 메시지 번호 공간을 나누는 비트
- PF(PDU Format, 8비트)와 PS(PDU Specific, 8비트): 메시지 종류를 나타내는 번호. PS는 메시지에 따라 받는 쪽 주소로도 쓴다
- SA(Source Address, 8비트): 보낸 장치의 주소

![29bit Extended ID 구조: Priority 3bit, R 1bit, DP 1bit, PF 8bit, PS 8bit, SA 8bit. Priority는 0~7이며 낮을수록 우선순위가 높다](/images/study-isobus/05-id29-structure-light.png)
![29bit Extended ID 구조: Priority 3bit, R 1bit, DP 1bit, PF 8bit, PS 8bit, SA 8bit. Priority는 0~7이며 낮을수록 우선순위가 높다](/images/study-isobus/05-id29-structure-dark.png)

그림의 R은 EDP 자리다. 예전 J1939 문서에서는 이 비트를 예약(Reserved) 비트 R로 표기했다.

Priority 0이 가장 높고, Priority 7이 가장 낮다. 이를 통해 메시지 종류별 우선순위를 명시적으로 설정할 수 있다.

### Priority가 같으면 어떻게 되는가

Priority 필드는 29비트 ID의 최상위 3비트일 뿐이다. Priority가 같으면 중재가 끝나는 것이 아니라, <strong>나머지 비트(EDP → DP → PF → PS → SA)로 계속 비교</strong>한다. 결국 29비트 ID 전체가 하나의 우선순위 값이다.

아래 그림은 Priority가 둘 다 3인 메시지A(0x0CF00400)와 메시지B(0x0CFEEE00)를 비트별로 나란히 놓은 것이다. 앞부분이 모두 같다가 PF 필드 안에서 처음으로 값이 갈린다.

![메시지A(0x0CF00400)와 메시지B(0x0CFEEE00)의 29비트 ID 비트 비교: Priority·EDP·DP는 동점, PF의 5번째 비트에서 A=0, B=1로 메시지A 승리](/images/study-isobus/05-arbitration-bit-compare-light.png)
![메시지A(0x0CF00400)와 메시지B(0x0CFEEE00)의 29비트 ID 비트 비교: Priority·EDP·DP는 동점, PF의 5번째 비트에서 A=0, B=1로 메시지A 승리](/images/study-isobus/05-arbitration-bit-compare-dark.png)

메시지A의 PF는 0xF0(`11110000`), 메시지B의 PF는 0xFE(`11111110`)다. 앞 네 비트는 둘 다 1이고, 다섯 번째 비트에서 A는 0, B는 1을 보내므로 A가 이긴다.

| 상황 | 중재 방식 |
|------|-----------|
| Priority가 다름 | Priority가 작은 쪽이 즉시 승리 |
| Priority가 같음 | PF → PS → SA 순서로 계속 비교 |
| 29비트 전체가 같음 | 발생할 수 없음 (같은 PGN+SA 조합은 네트워크에 하나뿐) |

표의 마지막 줄에서 PGN(Parameter Group Number)은 메시지 종류 번호이고, SA는 보낸 장치의 주소다. 한 장치가 같은 종류의 메시지를 두 개 동시에 보내지는 않으므로 29비트가 완전히 같은 프레임 두 개가 맞붙는 일은 없다.

이 원칙을 이해하면, 실제 시스템에서 메시지 ID를 어떻게 배정해야 하는지가 자연스럽게 도출된다.

## 4. 메시지 설계 시 고려사항

이 절에서는 중재 규칙을 메시지 설계에 적용한다. 어떤 메시지에 작은 ID(높은 우선순위)를 줄지가 핵심이다.

중재 메커니즘을 이해하면 <strong>ID 배정 전략</strong>이 명확해진다. 아래 배정은 일반 CAN 설계에서 흔히 쓰는 예다. ISOBUS 표준의 권고는 조금 다르며(예: 0은 쓰지 않는다), 7절에서 비교한다.

<strong>안전 관련 메시지에는 낮은 ID를 배정</strong>

```
Priority 0 (ID 앞자리 000): 브레이크, 조향, 비상 정지
Priority 1 (ID 앞자리 001): 엔진 제어, 변속기
Priority 2 (ID 앞자리 010): 차량 속도, 자세 제어
Priority 3 (ID 앞자리 011): 일반 제어 데이터
Priority 6 (ID 앞자리 110): 진단, 설정
Priority 7 (ID 앞자리 111): 정보성 메시지, 로그
```

"ID 앞자리"는 29비트 ID 맨 앞 3비트, 즉 Priority 필드를 이진수로 적은 값이다.

<strong>주기적 메시지 vs 이벤트 메시지</strong>

| 구분 | 특징 | ID 전략 |
|---|---|---|
| **주기적 메시지** | 일정 주기(예: 10ms, 100ms)로 반복 전송 | 중간 우선순위 배정. 너무 낮은 ID는 다른 중요 메시지를 방해할 수 있음 |
| **이벤트 메시지** | 특정 조건 발생 시에만 전송 | 안전 관련이면 낮은 ID, 정보성이면 높은 ID |

<strong>버스 부하 고려</strong>

중재에서 계속 패배하는 메시지는 버스가 바쁠수록 더 오래 기다려야 한다. 높은 우선순위 메시지가 너무 자주 전송되면, 낮은 우선순위 메시지는 <strong>기아 상태(Starvation)</strong>에 빠질 수 있다. 줄 서기로 치면, 급한 사람이 끝없이 끼어드는 바람에 뒷사람 차례가 오지 않는 상황이다.

::: tip 실무 설계 원칙
- 안전 관련 메시지: Priority 0~2
- 실시간성이 중요한 제어 데이터: Priority 3~4
- 진단, 설정, 정보: Priority 5~7
- 동일 Priority 내에서는 기능별로 ID 범위를 구분해 관리한다
:::

정리하면, 급한 메시지일수록 작은 ID(작은 Priority 값)를 주되, 높은 우선순위 메시지가 버스를 독차지하지 않도록 전송 빈도도 함께 따져야 한다.

## 5. 중재 과정 따라가기

지금까지는 2절에서 2개 노드짜리 예시로 중재 원리를 봤다. 이번에는 노드 3개가 동시에 전송을 시작하는 실제 ISOBUS 메시지 조합으로, ID의 첫 비트부터 승부가 갈리는 순간까지 끝까지 따라가 본다.

### 1단계: 노드 3개가 동시에 전송을 시작한다

이 단계에서는 세 노드가 각각 어떤 메시지를 보내려 하는지 정한다. 버스가 유휴 상태였다가, 세 노드가 <strong>같은 순간</strong> SOF를 보내며 전송을 시작한다.

| 노드 | 메시지 | PGN | 어디서 나온 메시지인가 | Priority | SA |
|---|---|---|---|---|---|
| A (엔진 ECU) | EEC1(엔진 속도) | 61444 (0xF004) | [4장 CAN 데이터 프레임](/study/isobus/04-can-data-frame)에서 이미 파싱해 본 PGN | 3 | 0x00 |
| B (차속 센서) | Wheel-based Speed and Distance(차속·거리) | 65096 (0xFE48) | 트랙터와 작업기 사이 메시지를 정하는 ISO 11783-7의 차속 메시지([23장](/study/isobus/23-implement-messages-basics)) | 6 | 0x1C |
| C (진단 도구) | DM1(활성 고장 코드) | 65226 (0xFECA) | 진단을 정하는 ISO 11783-12의 DM1([28장](/study/isobus/28-diagnostics-dm-fmi)) | 6 | 0xF9(오프보드 진단 도구 주소) |

SA 값을 10진수로 바꾸면 0x00=0, 0x1C=28, 0xF9=249다. 오프보드 진단 도구는 기계 밖에서 진단 커넥터에 꽂는 장비를 말한다.

Priority는 두 값만 쓴다. EEC1처럼 <strong>제어와 직결된 상태 메시지</strong>는 기본값 3, 진단처럼 <strong>제어 명령이 아닌 상태·기록 메시지</strong>는 기본값 6이다. 차속 메시지의 ISO 11783-7 기본값은 3이지만, 이 예제에서는 제조사가 6으로 재설정했다고 가정한다. 재설정이 허용되는 이유는 6절에서, 기본값 3일 때의 결과는 7절에서 본다.

### 2단계: 각 메시지의 29비트 ID를 만든다

이 단계에서는 1단계 표의 PGN, Priority, SA를 이어 붙여 버스에 실제로 나갈 29비트 ID를 만든다.

PGN을 PF/PS로 역산하고 SA를 붙이면 29비트 ID가 나온다. 이 예제의 PGN은 모두 PF가 240 이상인 종류라서, PGN을 256으로 나눈 몫이 PF, 나머지가 PS다(예: 61444 = 240×256 + 4이므로 PF=240=0xF0, PS=4=0x04). Priority(3bit) + EDP(1bit) + DP(1bit) + PF(8bit) + PS(8bit) + SA(8bit) = 29bit다.

표의 각 칸은 그 필드의 비트를 먼저 나가는 비트부터(왼쪽부터) 적은 것이다.

| 노드 | ID(hex) | Priority(3) | EDP(1) | DP(1) | PF(8) | PS(8) | SA(8) |
|---|---|---|---|---|---|---|---|
| A | `0x0CF00400` | `011` | `0` | `0` | `11110000`(0xF0) | `00000100`(0x04) | `00000000`(0x00) |
| B | `0x18FE481C` | `110` | `0` | `0` | `11111110`(0xFE) | `01001000`(0x48) | `00011100`(0x1C) |
| C | `0x18FECAF9` | `110` | `0` | `0` | `11111110`(0xFE) | `11001010`(0xCA) | `11111001`(0xF9) |

각 칸을 왼쪽부터 순서대로 이으면(비트28→비트0) 위 ID(hex)가 그대로 나온다. 표의 16진수를 10진수로 바꾸면 PF 0xF0=240, 0xFE=254, PS 0x04=4, 0x48=72, 0xCA=202다. 29비트 ID는 16진수로 적는 것이 관례다. 16진수 한 자리가 이진수 네 자리와 딱 맞아서 비트를 읽기 쉽기 때문이다.

::: tip 비트 번호 규칙
29비트 ID는 SOF 다음으로 <strong>맨 처음 나가는 비트를 비트28(MSB, Priority 최상위)</strong>, <strong>맨 마지막에 나가는 비트를 비트0(LSB, SA 최하위)</strong>이라 부른다. Priority는 비트28~26, EDP는 비트25, DP는 비트24, PF는 비트23~16, PS는 비트15~8, SA는 비트7~0이다.
:::

### 3단계: 첫 비트에서 갈리는 승부

이 단계에서 보는 것은 세 노드가 동시에 내보낸 ID의 첫 비트(비트28)와, 그 결과 버스에 나타난 값이다. 세 노드가 SOF 직후 ID의 첫 비트(비트28, Priority 최상위 비트)를 동시에 내보낸다.

| 라운드 | 비트 위치 | 노드A 송신 | 노드B 송신 | 노드C 송신 | 버스(wired-AND) | 판정 |
|---|---|---|---|---|---|---|
| 1 | 비트28 | 0 (Dominant) | 1 (Recessive) | 1 (Recessive) | **Dominant(0)** | A 계속 · <strong>B, C 동시 탈락</strong> |

Priority 3은 이진수로 `011`, Priority 6은 `110`이다. 최상위 비트만 봐도 A는 0, B와 C는 1이다. 버스는 세 값을 wired-AND로 합친 결과이므로, 하나라도 Dominant(0)를 내보내면 버스는 무조건 0이 된다. B와 C는 자신이 1을 보냈는데 버스가 0으로 관측되는 것을 <strong>동시에</strong> 감지하고, <strong>같은 라운드에서</strong> 각자 독립적으로 전송을 중단하고 수신 모드로 전환한다. 서로의 존재와 무관하게, 자신이 보낸 값과 버스 값을 비교하는 것만으로 판단이 끝난다는 점이 핵심이다.

::: tip 중재는 반드시 한 명씩 떨어지지 않는다
2개 노드짜리 예시(2절)에서는 매 라운드 최대 1개 노드만 탈락했다. 하지만 노드가 3개 이상이면, Dominant를 보낸 노드를 제외한 <strong>Recessive 노드 전부가 한 라운드에 동시에</strong> 탈락할 수 있다. 중재는 승자를 한 명씩 좁혀가는 토너먼트가 아니라, 매 비트마다 "그 순간 버스 값과 다르게 보낸 노드는 전부 탈락"하는 규칙이 반복될 뿐이다.
:::

A는 자신이 보낸 0과 버스 값 0이 일치하는 것을 확인하고 <strong>중단 없이</strong> 나머지 28비트(Priority 나머지 2비트 + EDP + DP + PF + PS + SA)를 마저 보낸다. 이어서 제어 비트와 DLC, Data, CRC, ACK, EOF까지 프레임 전체를 끝까지 전송한다. 이 과정에서 A의 데이터는 한 비트도 다시 보내지 않는다. 중재에서 이긴 메시지는 처음부터 끝까지 그대로 버스에 실린다.

### 4단계: 패배한 노드는 어떻게 되는가

이 단계에서는 진 노드 B와 C가 그다음에 무엇을 하는지 본다.

B와 C는 전송을 중단한 순간부터 수신 노드로 동작하며, A가 보내는 프레임을 끝까지 수신한다(다른 목적지로 가는 메시지라도 버스에 실린 이상 모든 노드가 물리적으로 수신한다). A의 EOF까지 끝나고 버스가 다시 유휴 상태가 되면, B와 C는 각자 <strong>처음부터 다시</strong> SOF를 보내며 재전송을 시도한다. 이번에는 둘 다 이전과 동일한 ID를 다시 내보내므로, 3절에서 정리한 원칙대로 <strong>같은 우선순위 관계가 그대로 반복</strong>된다.

여기서 이 절 전체를 관통하는 결론이 나온다. B와 C는 이번 라운드에서 메시지를 <strong>보내지 못했을 뿐, 데이터 자체를 잃어버리지는 않았다.</strong> 재시도해서 버스가 비는 다음 기회에 다시 온전히 보낼 수 있다. 이것이 1절에서 이더넷과 대비해 언급한 <strong>비파괴적 중재(non-destructive arbitration)</strong>다. 충돌이 나도 아무도 데이터를 버리지 않는다.

### 5단계: 우선순위가 같다면 몇 라운드까지 가는가

이 단계에서는 A가 없다고 가정하고, Priority가 같은 B와 C만 비트별로 비교한다.

방금 예시는 A의 Priority(3)가 B·C(6)보다 낮아 1라운드 만에 끝났다. 그렇다면 <strong>Priority가 완전히 같은 두 메시지</strong>는 몇 라운드까지 가야 승부가 갈릴까? A가 잠시 버스에 없었다고 가정하고, B와 C만 놓고 계속 비교해보자.

B와 C는 둘 다 Priority 6, EDP 0, DP 0이고, PGN이 둘 다 65000번대라 <strong>PF도 0xFE로 완전히 같다.</strong> 즉 비트28부터 비트16까지 13비트가 전부 동일하다. 승부는 PS 필드로 넘어가서야 갈린다.

| 구간 | 비트 위치 | 노드B | 노드C | 비고 |
|---|---|---|---|---|
| Priority(3bit) | 비트28~26 | `110` | `110` | 완전히 동일, 계속 |
| EDP | 비트25 | `0` | `0` | 동일, 계속 |
| DP | 비트24 | `0` | `0` | 동일, 계속 |
| PF(8bit) | 비트23~16 | `11111110`(0xFE) | `11111110`(0xFE) | 완전히 동일, 계속 |
| PS 최상위 비트 | 비트15 | `0` (Dominant, PS=0x48) | `1` (Recessive, PS=0xCA) | <strong>여기서 갈림</strong>: B 승, C 탈락 |

<strong>ID의 14번째 비트(14라운드, 비트15, PS 필드 최상위 비트)</strong>에 가서야 승부가 갈린다. B의 PS(0x48 = `01001000`)는 최상위 비트가 0이고, C의 PS(0xCA = `11001010`)는 최상위 비트가 1이기 때문이다. 이 예시가 3절에서 정리한 "Priority가 같으면 EDP → DP → PF → PS → SA 순서로 계속 비교한다"는 원칙을 실제 비트로 보여준다. Priority와 PF까지 같아도, PS 한 비트 차이로 승부가 갈린다.

라운드는 ID 비트만 센 번호다. 실제 프레임에서는 비트18과 비트17 사이에 SRR·IDE 두 비트가 끼어 있으므로, 비트15는 SOF를 1번으로 센 프레임 비트로는 17번이다([4장의 프레임 비트 표](/study/isobus/04-can-data-frame) 참고). 29비트 ID 프레임끼리는 SRR·IDE 값이 늘 같아서 이 두 비트는 승부에 영향을 주지 않는다.

### 6단계: 파이썬으로 검산하기

이 단계에서는 지금까지의 계산을 코드로 확인한다. 아래 코드는 세 노드의 29비트 ID를 만들고, 비트28부터 한 비트씩 버스 값(0이 하나라도 있으면 0)을 계산해 탈락자를 찾는다. 마지막 부분은 B와 C만 남았을 때 몇 번째 비트에서 갈리는지 센다.

:::details 파이썬으로 검산해 보기
```python
def build_id(priority, edp, dp, pf, ps, sa):
    return (priority << 26) | (edp << 25) | (dp << 24) | (pf << 16) | (ps << 8) | sa


def pgn_to_pf_ps(pgn):
    return pgn // 256, pgn % 256          # PF>=240(PDU2) 기준: PGN = PF*256 + PS


def bits29(v):
    return [(v >> i) & 1 for i in range(28, -1, -1)]   # 비트28(MSB) -> 비트0(LSB)


# 노드 정의: (이름, priority, PGN, SA)
defs = [
    ("A_엔진(EEC1)",  3, 61444, 0x00),
    ("B_차속",        6, 65096, 0x1C),
    ("C_진단(DM1)",   6, 65226, 0xF9),
]

ids = {}
for name, prio, pgn, sa in defs:
    pf, ps = pgn_to_pf_ps(pgn)
    ids[name] = build_id(prio, 0, 0, pf, ps, sa)
    print(f"{name}: PF=0x{pf:02X} PS=0x{ps:02X} ID=0x{ids[name]:08X}")

# 3-way 중재 시뮬레이션
alive = set(ids)
bitstreams = {k: bits29(v) for k, v in ids.items()}
for i in range(29):
    vals = {k: bitstreams[k][i] for k in alive}
    bus = min(vals.values())              # 하나라도 0(Dominant)이면 버스는 0
    losers = [k for k, v in vals.items() if v != bus]
    if losers:
        print(f"round {i+1} (bit{28-i}): bus={bus}, 탈락={losers}")
    for l in losers:
        alive.discard(l)
    if len(alive) == 1:
        print("최종 승자:", alive)
        break

# B vs C만 남았다면 (Priority가 같을 때) 몇 라운드까지 가는가
bB, bC = bitstreams["B_차속"], bitstreams["C_진단(DM1)"]
for i in range(29):
    if bB[i] != bC[i]:
        print(f"B vs C 결정 라운드: {i+1} (bit{28-i}), B={bB[i]} C={bC[i]}")
        break
```

실행하면 다음이 출력된다. 탈락 목록의 순서는 실행할 때마다 바뀔 수 있다(남은 노드를 집합으로 관리하기 때문이다).

```
A_엔진(EEC1): PF=0xF0 PS=0x04 ID=0x0CF00400
B_차속: PF=0xFE PS=0x48 ID=0x18FE481C
C_진단(DM1): PF=0xFE PS=0xCA ID=0x18FECAF9
round 1 (bit28): bus=0, 탈락=['B_차속', 'C_진단(DM1)']
최종 승자: {'A_엔진(EEC1)'}
B vs C 결정 라운드: 14 (bit15), B=0 C=1
```

노드A가 round 1(bit28)에서 즉시 승리하고, B와 C만 남길 경우 결정 라운드가 14(bit15)로 나온다. 위 표와 정확히 일치한다.
:::

::: tip 여기까지 정리 (1~5절)
- CAN의 <strong>CSMA/CD+AMP</strong> 방식은 비트 단위로 중재해, 우선순위 높은 메시지가 데이터 손실 없이 전송된다.
- Dominant(0)이 Recessive(1)을 이기므로, <strong>ID 값이 작을수록 우선순위가 높다</strong>.
- 중재 패배 노드는 즉시 전송을 중단하고 버스가 빌 때까지 대기 후 재시도한다.
- ISOBUS의 29bit ID에서 상위 3비트(Priority)로 메시지 우선순위를 명시한다.
- 안전 관련 메시지(브레이크, 조향)에는 낮은 ID를, 정보성 메시지에는 높은 ID를 배정한다.
:::

<small>근거: ISO 11783-7 B.3, ISO 11783-12 Annex B</small>

## 6. ISOBUS가 정한 Priority 규칙

3~5절은 CAN 중재 원리와 Priority 필드를 봤다. 이 절에서는 ISOBUS 표준이 이 필드를 보내는 쪽이 어떻게 쓰고 받는 쪽이 어떻게 읽을지까지 정해 둔 내용을 본다.

이 규칙을 정한 문서는 ISO 11783-3:2018이다. ISOBUS 표준 묶음 가운데 데이터 링크 계층, 즉 CAN 프레임을 어떻게 쓰고 메시지를 어떻게 주고받는지 정하는 문서다. 이 장에서는 줄여서 Part 3이라고 부른다. 표준 문장에서 shall은 반드시 지켜야 하는 규칙, should는 지키기를 권하는 규칙이다. 이 장에서는 원문의 강도를 보여 주려고 괄호 안에 그대로 적는다.

### 표준 문장으로 다시 읽는 중재 규칙

Part 3은 이 장 1~3절의 내용을 규범 문장으로 다시 적는다.

| 주제 | 내용 |
|---|---|
| 메시지 우선순위 | 우선순위는 ISO 11898-1(CAN 자체를 정하는 국제 표준)을 따른다. CAN 식별자 값이 낮을수록(29비트 전부 0이 최고) 우선순위가 높고, 클수록(전부 1이 최저) 낮다. 할당은 응용 계층이 표준의 할당 지침에 따라 정한다 |
| 버스 접근 | 버스가 비어 있으면 어느 컨트롤러든 송신을 시작할 수 있다. 동시에 시작하면 식별자로 경합 중재(contention-based arbitration)를 하므로 정보도 시간도 잃지 않는다 |
| 경합 중재 | 보낸 비트와 버스에서 읽은 비트가 같으면 계속 보낸다. recessive를 보냈는데 dominant를 읽으면 중재에서 진 것이고, 비트를 하나도 더 보내지 않고 물러나야 한다(shall). dominant를 보냈는데 recessive를 읽으면 비트 에러다 |

표의 응용 계층은 메시지의 내용과 번호를 정하는 위쪽 표준 문서들을 말한다. 마지막 문장은 [6장 CAN 에러 처리](/study/isobus/06-can-error)의 Bit Error와 이어진다. 중재 구간이라도 "dominant를 보냈는데 recessive를 읽음"은 패배가 아니라 에러다.

### 보내는 쪽: 기본값과 재설정

Priority 필드는 버스에 오를 때의 지연을 줄이는 데만 쓴다. 값은 0(최고)~7(최저)이고, Part 3이 정한 기본값은 다음과 같다.

| 메시지 성격 | 기본 Priority | 자세히 다루는 장 |
|---|---|---|
| 제어 지향(control oriented) 메시지 | 3 (`011`) | 이 장 |
| 그 밖의 정보성·제조사 독점·요청·NACK 메시지 | 6 (`110`) | 이 장 |
| Request(59904), Acknowledgement(59392), Proprietary A·A2·B | 6 | [10장](/study/isobus/10-j1939-request-ack) |
| TP.CM(60416)·ETP.CM(51200) 연결 관리 | 7 | [15장](/study/isobus/15-tp-bam-cmdt), [17장](/study/isobus/17-etp) |
| TP.DT(60160)·ETP.DT(50944) 데이터 전송 | 7 (운반하는 PGN과 무관) | [15장](/study/isobus/15-tp-bam-cmdt), [17장](/study/isobus/17-etp) |

표에 나온 메시지 이름을 짧게 풀면 다음과 같다. 자세한 내용은 표의 장에서 본다.

- Request: 다른 장치에 특정 메시지를 보내 달라고 요청하는 메시지
- Acknowledgement: 요청이나 명령에 대한 응답. NACK은 "처리할 수 없다"는 부정 응답이다
- Proprietary A·A2·B: 제조사가 내용을 마음대로 정하는 제조사 독점 메시지
- TP·ETP: 8바이트보다 긴 데이터를 여러 프레임으로 나눠 보내는 전송 프로토콜. CM은 연결을 맺고 끊는 관리 메시지, DT는 데이터를 실어 나르는 메시지다

각 PGN에는 응용 계층 표준에 추가될 때 권장 Priority가 붙는다. 그래도 Priority 필드는 제조사가 네트워크를 조정(tuning)할 수 있도록 다시 설정할 수 있어야 한다(should). 기본값을 코드 상수로 박아 두지 말고 PGN별 설정값으로 두라는 뜻이다.

### 받는 쪽: Priority는 보지 않는다

수신 컨트롤러는 Priority 비트를 모든 메시지에서 일괄로 마스킹해 무시하는 것이 좋다(should). 마스킹(masking)은 특정 비트를 지워 비교에서 빼는 것이다. 표준 부록에 실린 전형적인 수신 루틴 예시도 "3개 priority 비트는 중재에만 쓰이므로 수신 측은 쓰지 않는다"고 적는다. 이 수신 루틴은 [11장](/study/isobus/11-j1939-request2-timing)에서 따라간다.

이 규칙은 수신 필터를 설정할 때 중요하다. 같은 PGN이 Priority 3으로 오든 6으로 오든 같은 메시지다. 하드웨어 수락 필터나 PGN 디스패치 테이블을 29비트 ID 전체로 비교하면, 송신 측이 Priority를 재설정하는 순간 메시지를 놓친다.

아래 코드는 29비트 ID에서 비트 28~26(Priority)만 0으로 지운 뒤 비교하는 함수다. 같은 메시지를 Priority 3과 6으로 보낸 두 ID가 Priority를 빼면 같아지는 것을 확인한다.

::: details 파이썬: Priority를 빼고 비교하기
```python
PRIO_MASK = 0x1C000000          # 29비트 ID의 비트 28~26


def without_priority(can_id):
    return can_id & 0x1FFFFFFF & ~PRIO_MASK


# 같은 PGN(65096)·같은 SA(0x1C)를 Priority 3과 6으로 보낸 두 ID
a, b = 0x0CFE481C, 0x18FE481C
assert a != b                                        # ID 전체로 비교하면 다른 메시지
assert without_priority(a) == without_priority(b) == 0x00FE481C
```

두 `assert`가 모두 통과한다. 0x1C000000은 비트 28~26만 1인 값이라, `~PRIO_MASK`와 AND하면 그 세 비트만 0이 된다. 하드웨어 필터라면 마스크 레지스터에서 비트 28~26을 "무관(don't care)"으로 두는 것과 같다.
:::

정리하면, 보내는 쪽은 기본값(제어 3, 그 밖 6, TP·ETP 7)으로 시작하되 PGN별로 바꿀 수 있게 만들고, 받는 쪽은 Priority 비트를 빼고 메시지를 알아본다.

<small>근거: ISO 11783-3 5.2.2, 5.4.3, 5.4.5, 5.4.6, 5.5~5.7, 5.9.1, 5.10.4.1, 5.10.5, 5.11.5.2, 5.11.6, Annex A</small>

## 7. 권고표로 Priority 고르기 (심화)

::: info 처음 읽는다면
이 절은 직접 구현할 때 필요한 세부다. 처음에는 건너뛰고 다음 절로 가도 된다.
:::

이 절에서는 새 메시지를 만들 때 Priority를 몇으로 할지 고르는 표준의 권고표를 보고, 4절의 일반 CAN 예시와 비교한다.

### 표준의 권고표와 4절 예시 비교

Part 3은 문서 끝 부록(참고용이라 반드시 지켜야 하는 규칙은 아니다)에 메시지 주기로 Priority를 고르는 권고표를 싣는다. 주기가 짧은 메시지가 느린 메시지보다 먼저 나갈 수 있게 하려는 것이다. 4절의 "ID 배정 전략"은 일반 CAN 설계 예이므로, ISOBUS 메시지를 설계할 때는 이 권고표와 다른 점을 알아 둬야 한다.

| Priority | 4절의 예시 배정 | 표준의 권고 (주기·용도) |
|---|---|---|
| 0 | 브레이크·조향·비상 정지 | 예약(쓰지 않는다) |
| 1 | 엔진 제어·변속기 | 10~20 ms, 기계 간 제어 |
| 2 | 차량 속도·자세 제어 | 20~50 ms, 시스템 보호 |
| 3 | 일반 제어 데이터 | 50~100 ms, 운전자 기반 제어 |
| 4~5 | (없음) | 100~200 ms / 200~400 ms, 시스템 상태 |
| 6 | 진단·설정 | 400 ms 이상, 낮은 상태·UI·E/TP.CM |
| 7 | 정보성 메시지·로그 | TP·ETP 데이터, 대용량 전송 |

표의 E/TP.CM은 ETP.CM과 TP.CM을 함께 이르는 말이다. 용도 이름과 SAE J1939 대응까지 담은 전체 표는 [Part 3 정리 부록](/study/isobus/appendix-iso-part03)에 있다. 비교에서 눈여겨볼 점은 세 가지다.

- <strong>0은 예약</strong>이다. 가장 급한 메시지도 1부터 쓴다.
- <strong>7은 TP·ETP 데이터 전송 자리</strong>다. 주기적 로그 메시지를 7에 두면 대용량 전송 프레임과 같은 자리에서 경쟁한다. 표준이 이유를 적지는 않지만, 수백~수천 프레임이 이어지는 대용량 전송을 가장 낮은 자리에 둬 다른 모든 메시지에 버스를 양보하게 한 배치로 보인다(추론).
- 새 메시지는 이 표로 Priority를 정하고, 기존 메시지를 새 시스템에 쓸 때는 기본값이 맞는지 다시 검토하라고 표준은 권한다.

::: warning 표준 안에서 값이 엇갈리는 곳: TP.CM의 Priority
TP.CM·ETP.CM의 메시지 정의는 기본 Priority를 7로 적는다. 그런데 같은 문서 끝의 권고표는 E/TP.CM을 Priority 6의 용도에 넣고, 7은 TP·ETP 데이터에만 둔다. 메시지 정의는 지켜야 하는 본문(규범)이고 권고표는 참고용 부록이므로, 구현은 메시지 정의의 7을 기본값으로 쓰고 권고표는 튜닝의 참고로 보는 편이 안전하다(추론). 수신 측은 어차피 Priority를 무시하므로 어느 쪽이든 수신 호환성 문제는 없다.
:::

### 5절 예제를 표준 기본값으로 다시 보기

5절의 3노드 예제는 차속 메시지(PGN 65096)를 Priority 6으로 보냈다. ISO 11783-7은 이 메시지의 기본 Priority를 3, 송신 주기를 100 ms로 정한다. 기본값 3으로 다시 중재하면 결과가 달라진다.

| 노드 | ID(hex) | Priority |
|---|---|---|
| A (EEC1) | `0x0CF00400` | 3 |
| B (차속, 기본값) | `0x0CFE481C` | 3 |
| C (DM1) | `0x18FECAF9` | 6 |

라운드별로 따라가면 다음과 같다.

1. 1라운드(비트 28): A와 B는 0, C는 1을 보낸다. 버스가 0이 되어 C만 탈락한다.
2. 2~5라운드(비트 27~24): A와 B는 Priority 나머지 두 비트(`11`), EDP(`0`), DP(`0`)가 같아 계속한다.
3. 6~9라운드(비트 23~20): PF 앞 네 비트가 A `1111`(0xF0의 앞부분), B `1111`(0xFE의 앞부분)로 같다.
4. 10라운드(비트 19): PF 다섯 번째 비트에서 A는 0, B는 1을 보낸다. B가 탈락하고 A가 이긴다.

A와 B는 Priority·EDP·DP가 같고 PF가 `0xF0`(`11110000`)과 `0xFE`(`11111110`)라서, PF의 다섯 번째 비트인 비트 19(10라운드)에서 B가 진다. Priority를 6으로 재설정했던 5절에서는 B가 1라운드에 졌다. Priority 재설정이 중재 순서를 실제로 바꾼다는 것을 보여 주는 예다.

::: details 파이썬으로 검산: 기본값 3으로 다시 중재
5절의 검산 코드에서 `defs`의 차속 줄만 `("B_차속", 3, 65096, 0x1C),`로 바꿔 실행하면 다음 줄들이 출력된다(나머지 줄은 생략했다).

```
B_차속: PF=0xFE PS=0x48 ID=0x0CFE481C
round 1 (bit28): bus=0, 탈락=['C_진단(DM1)']
round 10 (bit19): bus=0, 탈락=['B_차속']
최종 승자: {'A_엔진(EEC1)'}
```
:::

정리하면, ISOBUS에서 새 메시지의 Priority는 권고표의 주기 구간으로 고르고(0은 쓰지 않고 7은 TP·ETP 데이터 자리), 같은 메시지라도 Priority를 바꾸면 중재 순서가 바뀐다.

<small>근거: ISO 11783-3 Annex D, 5.10.4.1, 5.11.5.2, ISO 11783-7 B.3</small>

## 8. CBFF와 CEFF가 함께 중재할 때 (심화)

::: info 처음 읽는다면
이 절은 직접 구현할 때 필요한 세부다. 처음에는 건너뛰고 다음 절로 가도 된다.
:::

이 절에서는 11비트 ID 프레임(CBFF)과 29비트 ID 프레임(CEFF)이 같은 순간 중재에 들어가는 드문 경우를 본다. 비교되는 필드가 서로 달라서 결과가 직관과 다르게 나온다.

[4장 CAN 데이터 프레임](/study/isobus/04-can-data-frame)에서 본 것처럼 ISO 11783은 11비트 CBFF 메시지를 제조사 독점용으로 허용한다. 11비트 ID는 Priority 3비트와 SA(보낸 장치의 주소) 8비트로 이뤄진다. 이 프레임이 29비트 CEFF 프레임과 같은 순간 중재에 들어가면 어떻게 될지 Part 3이 직접 경고한다.

### 비교되는 비트가 다르다

중재는 SOF 다음 비트부터 차례로 비교한다. [4장의 프레임 비트 표](/study/isobus/04-can-data-frame)에서 두 형식의 앞부분만 나란히 놓으면 다음과 같다. 프레임 비트는 SOF를 1번으로 센 번호다.

| 프레임 비트 | CBFF(11bit) | CEFF(29bit) |
|---|---|---|
| 2~4 | Priority | Priority |
| 5 | SA8 | EDP |
| 6 | SA7 | DP |
| 7~12 | SA6~SA1 | PF8~PF3 |
| 13 | RTR (dominant) | SRR (recessive) |
| 14 | IDE (dominant) | IDE (recessive) |

SA8은 SA의 최상위 비트, SA1은 최하위 비트다. PF8~PF3도 같은 방식으로 PF의 위쪽 여섯 비트를 뜻한다.

Priority가 같으면 CBFF의 SA가 CEFF의 EDP·DP·PF 상위 6비트와 맞붙는다. Part 3은 이를 "11비트 메시지의 SA가 29비트 메시지의 EDP·DP·PF보다 높은 우선순위를 나타낼 수 있다"고 표현하고, 올바른 중재를 위해 Priority 3비트를 쓰라고 권고한다(should).

![CBFF(P6, SA 0x00)와 CEFF(0x18FEEE00)를 프레임 비트 2~14로 비교: 비트 2~6은 같고 비트 7에서 CBFF는 SA6=0, CEFF는 PF8=1을 보내 CEFF가 탈락](/images/study-isobus/05-cbff-ceff-arbitration-light.png)
![CBFF(P6, SA 0x00)와 CEFF(0x18FEEE00)를 프레임 비트 2~14로 비교: 비트 2~6은 같고 비트 7에서 CBFF는 SA6=0, CEFF는 PF8=1을 보내 CEFF가 탈락](/images/study-isobus/05-cbff-ceff-arbitration-dark.png)

그림의 예는 Priority 6, SA `0x00`인 CBFF 메시지와 Priority 6인 Engine Temperature(`0x18FEEE00`)의 대결이다. 프레임 비트 2~6은 같고, 비트 7에서 CBFF는 SA6 = 0을, CEFF는 PF8 = 1을 보낸다. 같은 Priority의 표준 메시지가 제조사 독점 메시지에 진다.

하나가 더 있다. 앞 12비트가 모두 같으면 13번 비트에서 CBFF는 RTR(dominant), CEFF는 SRR(recessive)을 보낸다. 따라서 <strong>끝까지 비기면 언제나 CBFF가 이긴다</strong>. 위 프레임 비트 표에서 그대로 따라 나오는 결과다.

| CBFF | CEFF | 승자 | 갈린 프레임 비트 |
|---|---|---|---|
| P6, SA `0x00` | `0x18FEEE00` (P6, PF `0xFE`) | CBFF | 7 |
| P6, SA `0x00` | `0x0CF00400` (P3) | CEFF | 2 |
| P7, SA `0x00` | `0x1CEB2623` (TP.DT, P7) | CBFF | 7 |
| P7, SA `0x80` | `0x1CEB2623` (TP.DT, P7) | CEFF | 5 |
| P6, SA `0x00` | `0x18000000` (P6, PF 0, PS 0, SA 0) | CBFF | 13 (RTR 대 SRR) |

표의 P6, P7은 Priority 6, 7이다. 넷째 줄을 예로 읽어 보자. CBFF의 SA `0x80`(10진수 128)은 이진수 `10000000`이라 최상위 비트 SA8이 1이다. 같은 자리(프레임 비트 5)에서 CEFF는 EDP 0을 보내므로 CBFF가 진다.

같은 Priority라면 승패는 CBFF 송신자의 SA 값에 따라 바뀐다. SA는 주소라서 마음대로 바꿀 수 없으니, 설계자가 쓸 수 있는 손잡이는 CBFF 메시지의 Priority뿐이다. Part 3은 권고 부록에서 한 걸음 더 나가 CBFF 트래픽을 별도 서브넷(다른 버스로 떼어 낸 작은 네트워크)으로 분리하라고 강하게 권고한다.

아래 코드는 두 형식이 프레임 비트 2~14에 내보내는 비트열을 만들고, 처음으로 다른 비트에서 0을 보낸 쪽을 승자로 돌려준다. 끝의 `assert` 다섯 줄은 위 표의 다섯 줄과 같다.

::: details 파이썬으로 검산: CBFF와 CEFF의 비트 대결
```python
def cbff_stream(p, sa):
    s = [(p >> i) & 1 for i in (2, 1, 0)]          # 프레임 비트 2~4
    s += [(sa >> i) & 1 for i in range(7, -1, -1)]  # 5~12 = SA8..SA1
    s += [0, 0]                                     # 13 RTR(d), 14 IDE(d)
    return s


def ceff_stream(can_id):
    b = lambda n: (can_id >> n) & 1
    s = [b(n) for n in range(28, 17, -1)]           # 2~12 = P3..P1, EDP, DP, PF8..PF3
    s += [1, 1]                                     # 13 SRR(r), 14 IDE(r)
    return s


def cbff_vs_ceff(p, sa, can_id):
    for i, (u, v) in enumerate(zip(cbff_stream(p, sa), ceff_stream(can_id))):
        if u != v:
            return ("CBFF" if u < v else "CEFF"), i + 2   # 0(dominant)을 보낸 쪽이 이긴다
    raise AssertionError("14비트 안에서 갈리지 않음")


assert cbff_vs_ceff(6, 0x00, 0x18FEEE00) == ("CBFF", 7)
assert cbff_vs_ceff(6, 0x00, 0x0CF00400) == ("CEFF", 2)
assert cbff_vs_ceff(7, 0x00, 0x1CEB2623) == ("CBFF", 7)
assert cbff_vs_ceff(7, 0x80, 0x1CEB2623) == ("CEFF", 5)
assert cbff_vs_ceff(6, 0x00, 0x18000000) == ("CBFF", 13)
```

다섯 `assert`가 모두 통과하면 표의 승자와 갈린 프레임 비트가 맞다는 뜻이다.
:::

정리하면, CBFF와 CEFF가 맞붙으면 CBFF의 SA가 CEFF의 EDP·DP·PF와 비교되고, 끝까지 비기면 CBFF가 이긴다. 설계자가 조절할 수 있는 것은 CBFF의 Priority와 서브넷 분리다.

::: details 원문을 가진 독자를 위한 메모
6절 "표준 문장으로 다시 읽는 중재 규칙" 표를 ISO 11783-3:2018의 절 번호와 함께 적으면 다음과 같다. 할당 지침은 5.9다.

| 절 | 내용 |
|---|---|
| 5.5 메시지 우선순위 | 우선순위는 ISO 11898-1을 따른다. CAN 식별자 값이 낮을수록(29비트 전부 0이 최고) 우선순위가 높고, 클수록(전부 1이 최저) 낮다. 할당은 응용 계층이 5.9의 지침에 따라 정한다 |
| 5.6 버스 접근 | 버스가 비어 있으면 어느 컨트롤러든 송신을 시작할 수 있다. 동시에 시작하면 식별자로 경합 중재(contention-based arbitration)를 하므로 정보도 시간도 잃지 않는다 |
| 5.7 경합 중재 | 보낸 비트와 버스에서 읽은 비트가 같으면 계속 보낸다. recessive를 보냈는데 dominant를 읽으면 중재에서 진 것이고, 비트를 하나도 더 보내지 않고 물러나야 한다(shall). dominant를 보냈는데 recessive를 읽으면 비트 에러다 |

::: tip 핵심 정리
- 여러 노드가 동시에 보내기 시작해도 CAN은 ID를 한 비트씩 비교해 하나만 남긴다. 진 노드는 데이터를 잃지 않고 버스가 비면 다시 보낸다(비파괴적 중재).
- 0(Dominant)이 1(Recessive)을 이기므로 ID 값이 작을수록 우선순위가 높다. 29비트 ID에서는 맨 앞 3비트 Priority가 먼저 비교되고, 같으면 나머지 비트로 계속 비교한다.
- ISOBUS의 기본 Priority는 제어 메시지 3, 그 밖 6, TP·ETP 7이다. Priority는 PGN별로 다시 설정할 수 있어야 한다.
- 받는 쪽은 Priority 비트를 무시한다. 수신 필터와 PGN 비교에서 비트 28~26을 빼야 한다.
- 표준 권고표는 주기로 Priority를 고르게 한다. 0은 예약이고 7은 TP·ETP 데이터 자리다.
- (심화) CBFF와 CEFF가 맞붙으면 CBFF의 SA가 CEFF의 EDP·DP·PF와 비교되고, 끝까지 비기면 CBFF가 이긴다. 손잡이는 CBFF의 Priority와 서브넷 분리다.
:::

::: details 확인 문제
1. (개념) 두 노드가 같은 순간 보내기 시작했다. 한 노드는 11비트 ID 0x123, 다른 노드는 0x0FF를 보낸다. 누가 이기고, 몇 번 비트에서 갈리는가?
2. (개념) 중재에서 진 노드의 메시지는 어떻게 되는가? 이더넷의 충돌 처리와 무엇이 다른가?
3. (개념) Priority 필드가 같은 두 29비트 메시지는 어떻게 승부를 내는가?
4. (설명형) 수신 필터를 29비트 ID 전체로 걸면 안 되는 이유를 Part 3의 규칙으로 설명하라.
5. (계산형, 심화) Priority 6, SA `0x10`인 CBFF 메시지와 CEFF 메시지 `0x18FEEE00`이 동시에 중재에 들어간다. 누가 몇 번째 프레임 비트에서 이기는가?
6. (설계형, 심화) 80 ms 주기로 작업기의 특정 CF(Control Function, 네트워크에서 주소를 가진 제어 기능) 하나에 목표값을 명령하는 새 메시지를 만든다. 표준 권고표 기준 Priority는 몇이 적절한가? 송신 코드에서 이 값을 어떻게 다뤄야 하는가?

**답 가이드**
1. 0x0FF가 이긴다. 0x123은 `001 0010 0011`, 0x0FF는 `000 1111 1111`이다. 비트10과 비트9는 둘 다 0이고, 비트8에서 0x123 쪽은 1(Recessive), 0x0FF 쪽은 0(Dominant)을 보낸다. 버스가 0이 되므로 0x123을 보낸 노드가 물러난다. 1의 개수가 더 많아도 앞쪽 비트에서 먼저 0을 보낸 쪽이 이긴다.
2. 진 노드는 그 비트에서 바로 송신을 멈추고 수신 노드로 바뀌어 이긴 프레임을 끝까지 받는다. 버스가 비면 같은 메시지를 처음부터 다시 보내므로 데이터는 잃지 않는다. 이더넷은 충돌하면 양쪽이 모두 멈추고 다시 보내지만, CAN은 이긴 메시지가 중단 없이 그대로 전달된다.
3. Priority가 같으면 EDP, DP, PF, PS, SA 순서로 계속 비교한다. 29비트 전체가 하나의 우선순위 값이므로, 처음으로 값이 다른 비트에서 0을 보낸 쪽이 이긴다.
4. Priority는 송신 지연을 줄이는 용도이고 수신 측은 마스킹해 무시해야 한다(6절의 받는 쪽 규칙과 표준 부록의 수신 루틴). 송신 측은 Priority를 재설정할 수 있으므로, 비트 28~26까지 비교하면 같은 PGN·SA인데도 Priority가 바뀐 프레임을 놓친다.
5. 프레임 비트 2~4는 둘 다 `110`이고, 비트 5·6은 SA8·SA7(0, 0)과 EDP·DP(0, 0)로 같다. 비트 7에서 CBFF는 SA6 = 0, CEFF는 PF8 = 1을 보내므로 CBFF가 이기고 CEFF가 물러난다.
6. 50~100 ms 구간이므로 표준 권고표 기준 Priority 3(운전자 기반 제어)이 맞고, 제어 지향 메시지의 기본값 3과도 일치한다. 이 값은 상수가 아니라 PGN별 설정값으로 둬서 OEM(완성 기계 제조사)이 네트워크 튜닝으로 바꿀 수 있게 한다(6절의 재설정 권고).
:::
