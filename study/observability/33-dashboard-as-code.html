대시보드 as-code

학습 목표

  • 대시보드를 UI로만 관리할 때 생기는 버전관리·재현성 문제와 as-code 접근의 이점을 이해한다.
  • 파일 기반 provisioning으로 데이터소스·대시보드를 선언적으로 등록하는 방법을 익힌다.
  • jsonnet/grafonnet으로 재사용 가능한 대시보드 컴포넌트를 작성하는 패턴을 안다.
  • Grafana Operator CRD와 Terraform provider 중 어떤 상황에 무엇을 쓸지 판단한다.
  • 대시보드 JSON model의 핵심 구조(uid, schemaVersion, panels, templating)를 이해한다.
  • 쿠버네티스 환경에서 GitOps로 대시보드를 배포하는 파이프라인을 그릴 수 있다.

1. 왜 as-code인가

Grafana UI에서 패널을 드래그해 대시보드를 만드는 방식은 빠르지만 세 가지 문제를 안고 있다. 첫째, 버전관리 부재다. 누가 언제 어떤 쿼리를 바꿨는지 UI 히스토리만으로는 추적하기 어렵고, 되돌리기도 수동이다. 둘째, 재현성 부재다. 새 환경(스테이징, DR 클러스터)에 같은 대시보드를 다시 만들려면 손으로 다시 클릭해야 한다. 셋째, 리뷰 불가능이다. 코드 변경은 PR로 리뷰하면서, 정작 알림 임계치나 SLO 패널 같은 운영 핵심 자산은 리뷰 없이 UI에서 바로 바뀐다.

as-code 접근은 대시보드·데이터소스 정의를 텍스트(JSON/jsonnet/HCL)로 리포지토리에 두고, CI/CD가 이를 Grafana에 반영하게 한다. 이렇게 하면 대시보드도 애플리케이션 코드와 동일한 신뢰 수준(리뷰, diff, 롤백)을 갖는다.

flowchart LR
    subgraph UI["UI 전용 관리"]
        U1["클릭으로 패널 수정"] --> U2["변경 이력 없음"] --> U3["재현 불가"]
    end
    subgraph Code["as-code 관리"]
        C1["jsonnet/JSON 수정"] --> C2["Git PR 리뷰"] --> C3["CI가 Grafana에 반영"] --> C4["롤백 = git revert"]
    end

2. provisioning — 파일 기반 데이터소스/대시보드

Grafana는 컨테이너 시작 시 지정된 디렉터리를 읽어 데이터소스와 대시보드를 자동 등록하는 provisioning 기능을 내장하고 있다(Grafana provisioning 문서). 31장에서 다룬 데이터소스 YAML도 이 메커니즘이다.

# /etc/grafana/provisioning/dashboards/dashboards.yaml
apiVersion: 1
providers:
  - name: 'default'
    orgId: 1
    folder: 'SRE'
    type: file
    disableDeletion: false
    updateIntervalSeconds: 30
    allowUiUpdates: false
    options:
      path: /var/lib/grafana/dashboards
      foldersFromFilesStructure: true

allowUiUpdates: false가 핵심 옵션이다. 이 값을 끄면 UI에서 대시보드를 수정해도 저장이 막히고(또는 다음 provisioning 주기에 파일 내용으로 덮어써져), 리포지토리 파일이 유일한 진실 소스(source of truth)가 된다. updateIntervalSeconds는 Grafana가 디스크의 파일 변경을 감지하는 주기이며, foldersFromFilesStructure를 켜면 디렉터리 구조가 Grafana 폴더 트리로 그대로 매핑된다.

3. jsonnet/grafonnet

대시보드 JSON을 손으로 직접 작성하면 패널 하나마다 필드 수십 개를 반복해야 한다. jsonnet은 JSON의 상위 집합 템플릿 언어로, 함수·상속·변수를 지원해 이 반복을 없앤다. Grafana 커뮤니티가 유지하는 grafonnet 라이브러리는 패널·타깃·변수를 함수 호출로 조립할 수 있게 해준다.

local g = import 'github.com/grafana/grafonnet/gen/grafonnet-v11.0.0/main.libsonnet';

local redPanel(title, expr) =
  g.panel.timeSeries.new(title)
  + g.panel.timeSeries.queryOptions.withTargets([
      g.query.prometheus.new('Prometheus', expr)
    ]);

g.dashboard.new('service-red')
+ g.dashboard.withUid('svc-red-001')
+ g.dashboard.withPanels([
    redPanel('요청률', 'sum(rate(http_requests_total{service="$service"}[$__rate_interval]))'),
    redPanel('에러율', 'sum(rate(http_requests_total{service="$service", status=~"5.."}[$__rate_interval]))'),
  ])

이 방식의 진짜 이점은 재사용이다. redPanel 같은 함수를 라이브러리로 만들어두면, 새 서비스마다 대시보드를 처음부터 그리는 대신 서비스 이름만 바꿔 호출하면 된다. kube-prometheus 프로젝트의 mixin 패턴(alerts.libsonnet, dashboards.libsonnet을 하나의 jsonnet 패키지로 묶어 배포하는 방식)이 이 접근의 대표 사례다. jsonnet 파일은 jsonnet CLI나 Grafana의 Tanka(tk export)로 최종 JSON으로 컴파일한 뒤 provisioning 디렉터리에 배치한다.

jsonnet -J vendor service-red.jsonnet > dashboards/service-red.json

4. Grafana Operator · Terraform provider

쿠버네티스 네이티브 환경이라면 Grafana Operator가 대시보드·데이터소스를 CRD로 다룬다. GrafanaDashboard, GrafanaDatasource, GrafanaFolder 커스텀 리소스를 클러스터에 적용하면, Operator가 이를 감시해 대상 Grafana 인스턴스의 API를 호출해 동기화한다.

apiVersion: grafana.integreatly.org/v1beta1
kind: GrafanaDashboard
metadata:
  name: service-red
spec:
  instanceSelector:
    matchLabels:
      dashboards: "sre"
  json: |
    { "uid": "svc-red-001", "title": "Service RED", "panels": [] }

멀티 클러스터가 아니라 Grafana Cloud나 여러 독립 Grafana 인스턴스를 함께 관리해야 한다면 Terraform grafana provider가 더 적합하다. grafana_dashboard, grafana_data_source, grafana_folder 리소스로 상태(state)를 관리하며, 여러 스택(온프레미스 + Cloud)을 하나의 Terraform 워크스페이스에서 동시에 다룰 수 있다.

resource "grafana_dashboard" "service_red" {
  config_json = file("${path.module}/dashboards/service-red.json")
  folder      = grafana_folder.sre.id
}

두 도구의 선택 기준은 단순하다. 쿠버네티스 안에서 GitOps 컨트롤러(ArgoCD/Flux)가 이미 모든 리소스를 관리하고 있다면 Grafana Operator가 그 흐름에 자연스럽게 들어맞는다. Grafana 인스턴스 자체나 Grafana Cloud 스택, 알림 채널 같은 SaaS 리소스까지 함께 관리해야 한다면 Terraform provider가 더 넓은 커버리지를 준다.

5. dashboard JSON model

grafonnet이든 Operator든 Terraform이든, 최종적으로 Grafana가 받아들이는 형태는 결국 dashboard JSON model이다. 핵심 필드를 이해해두면 디버깅과 마이그레이션이 쉬워진다.

필드역할
uid대시보드 고유 식별자. 링크·provisioning의 안정적 참조 키가 되므로 재생성해도 값이 바뀌면 안 된다
schemaVersion대시보드 스키마 버전. Grafana 업그레이드 시 자동 마이그레이션의 기준이 된다
panels[]패널 배열. 각 패널은 type, targets(쿼리), gridPos(위치/크기)를 가진다
templating.list[]31장에서 다룬 변수 정의 목록
time / refresh기본 조회 시간 범위와 자동 새로고침 주기
annotations.list[]배포 마커 같은 주석 오버레이 쿼리 정의

uid를 고정해두지 않으면 as-code 파이프라인이 매번 새 대시보드를 만드는 사고가 난다 — provisioning은 uid 기준으로 기존 대시보드를 갱신할지 새로 만들지 판단하기 때문이다. schemaVersion은 낮은 버전의 JSON을 최신 Grafana에 올리면 자동으로 마이그레이션되지만, 반대로 최신 스키마를 구버전 Grafana에 올리면 실패하므로 Grafana 버전 업그레이드 시 반드시 함께 확인해야 한다.

6. GitOps 배포

쿠버네티스 클러스터에서 가장 널리 쓰이는 패턴은 ConfigMap + 사이드카 조합이다. kube-prometheus-stack이 기본 채택하는 방식으로, 대시보드 JSON을 담은 ConfigMap에 grafana_dashboard: "1" 같은 라벨을 붙이면 Grafana Pod 옆의 사이드카 컨테이너(kiwigrid/k8s-sidecar)가 이를 감시해 provisioning 디렉터리로 자동 동기화한다.

flowchart LR
    subgraph Git["Git 리포지토리"]
        JSONNET["jsonnet 대시보드 정의"]
    end
    subgraph CI["CI 파이프라인"]
        BUILD["jsonnet 컴파일 → JSON"]
        CM["ConfigMap 매니페스트 생성"]
    end
    subgraph CD["GitOps 컨트롤러 (ArgoCD/Flux)"]
        SYNC["클러스터에 동기화"]
    end
    subgraph Cluster["쿠버네티스 클러스터"]
        CONFIGMAP["ConfigMap\n(label: grafana_dashboard=1)"]
        SIDECAR["k8s-sidecar"]
        GRAFANA["Grafana"]
        CONFIGMAP -->|"watch"| SIDECAR
        SIDECAR -->|"파일 동기화"| GRAFANA
    end
    JSONNET --> BUILD --> CM --> SYNC --> CONFIGMAP

이 파이프라인은 44장 쿠버네티스 스터디의 Kustomize/GitOps에서 다룬 선언적 배포 원칙을 그대로 관측성 스택에 적용한 것이다. jsonnet 컴파일 결과를 Kustomize overlay로 관리하면 환경별(스테이징/운영) 대시보드 변형(예: 알림 임계치 차이)도 base + patch 구조로 깔끔하게 표현할 수 있다.

핵심 정리

  • UI 전용 대시보드 관리는 버전관리·재현성·리뷰 가능성이 없어, 운영 핵심 자산을 as-code로 옮기는 것이 표준이다.
  • provisioning은 allowUiUpdates: false로 파일을 유일한 진실 소스로 만든다.
  • jsonnet/grafonnet은 패널 정의를 함수로 재사용 가능하게 만들어 서비스별 반복 작업을 없앤다.
  • Grafana Operator는 쿠버네티스 GitOps 흐름에, Terraform provider는 멀티 스택·SaaS 리소스 관리에 적합하다.
  • 대시보드 JSON model에서 uid는 고정, schemaVersion은 Grafana 버전과 함께 관리해야 한다.
  • 쿠버네티스에서는 ConfigMap + 사이드카 패턴으로 GitOps 컨트롤러가 대시보드를 자동 동기화하는 구성이 사실상 표준이다.

다음 챕터

대시보드와 상관관계 설정까지 코드로 관리할 수 있게 됐다면, 이제 관측성 스택 자체를 운영하는 단계로 넘어간다. 다음 챕터부터는 운영 심화(SRE) 영역으로, 카디널리티 관리와 비용에서 카디널리티 폭발을 탐지·차단하고 비용을 최적화하는 방법을 다룬다.
