Faro — 프런트엔드 관측성 (RUM)

학습 목표

  • 서버 관측성만으로는 사용자 경험을 알 수 없는 이유와 RUM(Real User Monitoring)의 역할을 이해한다.
  • Faro Web SDK가 수집하는 신호(에러, 로그·이벤트, Web Vitals, 세션, 트레이스)를 안다.
  • Alloy faro.receiver로 브라우저 신호를 받아 Loki·Tempo로 라우팅하는 파이프라인을 구성할 수 있다.
  • traceparent 전파로 프런트엔드 클릭부터 백엔드 DB 쿼리까지 하나의 트레이스로 잇는 원리를 이해한다.
  • 소스맵, PII, 카디널리티 등 프런트엔드 신호 특유의 운영 포인트를 안다.

1. 서버 관측성의 사각지대 — 사용자의 브라우저

지금까지의 스택은 전부 서버 쪽을 본다. 그런데 서버가 50ms 만에 200 OK를 돌려줘도 사용자 화면에서는 JS 번들 로딩에 4초가 걸리고, 특정 브라우저에서만 터지는 JS 에러로 버튼이 죽어 있을 수 있다. 서버 대시보드가 온통 초록색인데 CS 채널에 "안 돼요"가 쌓이는 상황 — 이것이 서버 관측성의 사각지대다.

RUM(Real User Monitoring)은 실제 사용자의 브라우저 안에서 신호를 수집해 이 사각지대를 메운다. 4대 신호의 관점으로 보면, 지금까지의 신호 발생원이 "내 인프라"였다면 RUM은 발생원을 사용자의 기기까지 확장하는 것이다. Faro는 Grafana 스택의 RUM 솔루션으로, 브라우저용 SDK(@grafana/faro-web-sdk)와 수집 서버(Alloy faro.receiver)로 구성된다.

2. Faro Web SDK — 무엇을 수집하나

SDK 초기화는 몇 줄이면 된다.

import { initializeFaro, getWebInstrumentations } from '@grafana/faro-web-sdk';
import { TracingInstrumentation } from '@grafana/faro-web-tracing';

const faro = initializeFaro({
  url: 'https://faro-collector.example.com/collect', // Alloy faro.receiver
  app: { name: 'checkout-web', version: '1.4.2', environment: 'production' },
  instrumentations: [
    ...getWebInstrumentations(),      // 에러·콘솔·Web Vitals·세션 자동 수집
    new TracingInstrumentation(),     // fetch/XHR에 OTel 트레이스 계측
  ],
});

// 커스텀 이벤트·측정값도 직접 보낼 수 있다
faro.api.pushEvent('checkout_started', { cartSize: '3' });
faro.api.pushMeasurement({ type: 'cart_value', values: { krw: 42000 } });

자동으로 수집되는 신호는 다섯 갈래다.

신호내용적재 대상
에러·예외JS error, unhandled rejection, 스택트레이스Loki
로그·이벤트console 캡처, pushEvent() 커스텀 이벤트Loki
Web VitalsLCP, CLS, INP, TTFB 등 사용자 체감 성능 지표Loki (측정값)
세션·메타session id, 브라우저·OS, URL, 로그인 사용자모든 신호에 부착
트레이스fetch/XHR 자동 계측 span (OTel)Tempo

Web Vitals가 핵심이다. LCP(최대 콘텐츠 렌더링), CLS(레이아웃 흔들림), INP(입력 반응성)는 서버에서는 절대 측정할 수 없는, 사용자가 실제로 체감하는 성능이다. 세션 id가 모든 신호에 붙기 때문에 "이 에러를 겪은 사용자가 직전에 무슨 이벤트를 밟았는가"를 세션 단위로 재구성할 수 있다.

3. 수집 경로 — Alloy faro.receiver

브라우저는 신뢰할 수 없는 공개 인터넷이므로, 신호를 백엔드에 직접 쓰게 하지 않고 수집 엔드포인트를 사이에 둔다. Alloy의 faro.receiver 컴포넌트가 그 역할이다.

faro.receiver "web" {
  server {
    listen_address = "0.0.0.0"
    listen_port    = 12347
    cors_allowed_origins = ["https://checkout.example.com"]  // 필수
    api_key        = env("FARO_API_KEY")
    rate_limiting {
      rate = 100   // 초당 요청 제한 — 공개 엔드포인트 보호
    }
  }
  output {
    logs   = [loki.write.default.receiver]     // 에러·로그·이벤트·측정값
    traces = [otelcol.exporter.otlp.tempo.input] // 프런트엔드 span
  }
}

Alloy 파이프라인의 다른 컴포넌트와 동일한 그래프 모델이다 — 로그류는 Loki로, 트레이스는 Tempo로 분기한다. 공개 엔드포인트라는 특성상 CORS 허용 도메인 제한, API key, rate limiting은 선택이 아니라 필수다. 이것이 없으면 아무나 가짜 신호를 쏟아부어 Loki를 rate limit 상태로 만들 수 있다.

Loki에 쌓인 신호는 LogQL로 바로 지표화할 수 있다. 예를 들어 P75 LCP는:

quantile_over_time(0.75,
  {app="checkout-web"} | logfmt | kind="measurement" | measurement_name="lcp"
  | unwrap value [5m]) by (browser)

4. 프런트-백엔드 트레이스 연결

Faro의 TracingInstrumentation은 브라우저의 fetch/XHR 호출에 W3C traceparent 헤더를 자동 주입한다. 백엔드가 OTel SDK로 계측돼 있으면 이 헤더를 이어받아, 사용자의 클릭 → 브라우저 fetch → API 게이트웨이 → 마이크로서비스 → DB 쿼리가 전부 하나의 trace로 묶인다.

이것이 실무에서 갖는 의미는 크다. "결제 버튼이 느리다"는 제보가 오면, 시그널 상관관계에서 다룬 도구가 프런트엔드까지 확장된다 — Faro가 남긴 세션에서 느린 fetch span을 찾고, trace id로 Tempo에 점프하면 지연이 브라우저(번들 로딩)인지 네트워크인지 백엔드(느린 쿼리)인지 한 번에 갈린다. 프런트 팀과 백엔드 팀이 서로 "우리 쪽은 정상"이라며 핑퐁하던 문제가 데이터로 종결된다.

5. 운영 포인트

  • 소스맵 — 프로덕션 JS는 minify돼 있어 스택트레이스가 a.js:1:38271처럼 나온다. 빌드 시 소스맵을 업로드(Grafana Cloud Frontend Observability의 소스맵 업로드, 또는 셀프호스팅 시 별도 심볼리케이션)해야 에러 스택이 원본 코드 위치로 복원된다.
  • PII(개인정보) — URL 쿼리스트링, 에러 메시지, 커스텀 이벤트에 이메일·토큰이 섞여 들어가기 쉽다. SDK의 beforeSend 훅으로 전송 전에 마스킹하고, 수집 항목을 개인정보 처리방침에 반영해야 한다.
  • 샘플링 — 트래픽 많은 서비스에서 전체 세션을 수집하면 Loki 볼륨이 폭증한다. SDK의 세션 샘플링 비율을 설정해 비용과 가시성을 조율한다 — 카디널리티와 비용의 원칙이 프런트엔드 신호에도 그대로 적용된다.
  • 라벨 설계 — app, environment 정도만 Loki 라벨로 두고, URL·브라우저 버전 같은 고카디널리티 값은 로그 본문/structured metadata에 둔다. Loki 라벨 철학과 동일한 원칙이다.

핵심 정리

  • 서버 관측성은 사용자 브라우저에서 벌어지는 일(JS 에러, 느린 LCP)을 보지 못한다 — RUM이 이 사각지대를 메운다.
  • Faro Web SDK는 에러·로그·이벤트·Web Vitals·세션·트레이스를 자동 수집하고, 세션 id로 사용자 여정을 재구성할 수 있게 한다.
  • 수집은 Alloy faro.receiver가 받아 로그류는 Loki, 트레이스는 Tempo로 분기한다 — 공개 엔드포인트이므로 CORS·API key·rate limit이 필수다.
  • traceparent 자동 주입으로 브라우저 클릭부터 백엔드 DB 쿼리까지 하나의 분산 트레이스로 이어진다.
  • 소스맵 업로드, PII 마스킹, 세션 샘플링, 저카디널리티 라벨 설계가 운영의 핵심 포인트다.

다음 챕터

RUM은 실제 사용자가 겪은 일을 기록하는 수동적(passive) 관측이다 — 사용자가 없으면 신호도 없고, 문제는 사용자가 겪은 뒤에야 보인다. k6와 Synthetic Monitoring에서는 반대편 접근을 다룬다 — 합성 트래픽을 직접 만들어, 사용자가 겪기 전에 외부 관점에서 문제를 먼저 발견하는 능동적(active) 관측이다.
