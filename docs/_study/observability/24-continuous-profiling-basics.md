# 연속 프로파일링 기초

::: info 학습 목표
- 샘플링 기반 프로파일링의 원리와 계측 기반 프로파일링과의 차이를 이해한다.
- 연속 프로파일링이 "사후 분석(post-hoc analysis)"을 가능케 하는 이유를 안다.
- 프로파일 데이터가 메트릭·트레이스와 다르게 어떤 질문에 답하는지 파악한다.
- 샘플링 주기와 오버헤드의 트레이드오프, pprof 데이터 모델의 기본 구조를 이해한다.
:::

## 1. 프로파일링이란 무엇인가

<strong>프로파일링(profiling)</strong>은 프로그램이 실행되는 동안 어느 함수, 어느 코드 라인이 CPU·메모리 같은 리소스를 얼마나 소비하는지 측정하는 기법이다. 메트릭이 "무엇이 얼마나"를 집계된 숫자로 보여주고, 트레이스가 "요청이 어느 서비스·스팬에서 시간을 썼는가"를 보여준다면, 프로파일은 그보다 한 단계 더 깊이 들어가 <strong>정확히 어느 함수·라인이 리소스를 소비했는가</strong>를 보여준다.

프로파일링에는 크게 두 접근이 있다. <strong>계측 기반(instrumentation-based)</strong> 프로파일링은 모든 함수의 진입·종료 지점에 코드를 삽입해 정확한 호출 횟수와 소요 시간을 기록한다. 정확하지만 오버헤드가 커서(수 배~수십 배 느려짐) 프로덕션에서 상시 켜두기 어렵다. <strong>샘플링 기반(sampling-based)</strong> 프로파일링은 타이머로 실행을 주기적으로 인터럽트해(예: 100Hz, 10ms마다) 그 순간의 콜 스택만 캡처한다. 특정 함수가 리소스를 많이 소비할수록 더 많은 샘플에 등장하므로, 충분히 많은 샘플을 모으면 통계적으로 실제 소비 비중에 수렴한다. 오버헤드가 낮아 프로덕션에 상시 적용 가능한 방식이 바로 이 샘플링 기반이다.

![샘플링 타이머가 10ms마다 애플리케이션 런타임에 인터럽트를 걸어 콜 스택을 캡처하고 프로파일러가 동일 스택 빈도를 누적해 통계적 프로파일을 생성하는 시퀀스](/images/study-observability/24-sampling-sequence.png)

동일한 콜 스택이 여러 샘플에서 반복해서 잡히면 하나로 병합되고 빈도만 누적된다. 이 "스택 + 빈도" 집계 결과가 플레임그래프의 원재료가 된다(자세한 해석은 [27장](/study/observability/27-flamegraph-trace-integration)). 또한 샘플링 시점에 따라 <strong>on-CPU 프로파일링</strong>(실제로 CPU를 점유 중인 순간만 샘플링)과 <strong>off-CPU/wall-clock 프로파일링</strong>(I/O 대기·락 대기로 블록된 시간까지 포함)으로 나뉘는데, 이 구분은 [26장](/study/observability/26-profile-types-ebpf)에서 프로파일 타입별로 다룬다.

## 2. 왜 연속(continuous) 프로파일링인가

전통적인 프로파일링 워크플로우는 문제가 의심될 때 엔지니어가 수동으로 프로파일러를 켜서 짧은 구간(예: 30초)만 캡처하는 방식이다. 이 방식의 근본적 한계는 <strong>과거를 프로파일링할 수 없다</strong>는 점이다. 새벽에 발생한 지연 스파이크는 이미 끝나버렸고, 그 순간 어떤 함수가 CPU를 먹고 있었는지는 그때 프로파일러가 켜져 있지 않았다면 영원히 알 수 없다. [1장](/study/observability/01-monitoring-to-observability)에서 다룬 known-unknowns 모델의 한계가 여기서도 그대로 반복된다 — 문제를 미리 예상해 프로파일러를 켜둬야만 답을 얻을 수 있다.

<strong>연속 프로파일링</strong>은 낮은 오버헤드의 샘플링 에이전트를 프로덕션에 상시 구동해, 메트릭을 스크레이핑하듯 프로파일 데이터를 계속 수집·저장한다. 그 결과 장애가 발생한 뒤에도 "그 시각의 프로파일"을 그대로 조회할 수 있는 <strong>사후 분석(post-hoc analysis)</strong>이 가능해진다. 이는 미리 질문을 준비하지 않아도 되는 관측성의 핵심 가치와 정확히 같은 구조다.

![온디맨드 프로파일링은 장애 발생 후 수동 트리거 시점엔 이미 상황이 종료돼 재현이 불가한 반면, 연속 프로파일링은 24/7 상시 샘플링을 타임스탬프와 함께 저장해 장애 이후에도 과거 시점 프로파일을 사후 조회할 수 있음을 대비한 다이어그램](/images/study-observability/24-ondemand-vs-continuous.png)

## 3. 프로파일이 답하는 질문

프로파일은 메트릭·트레이스가 답하지 못하는 수준의 질문에 답한다.

- "지금 이 서비스에서 어느 함수가 CPU를 가장 많이 쓰고 있는가" — CPU 프로파일이 답한다.
- "메모리를 어디서 할당했고, 지금 무엇이 그 메모리를 물고 있어서 못 해제되는가" — alloc/inuse 메모리 프로파일이 답한다(메모리 누수 진단에 결정적이다).
- "트레이스에서 이 스팬이 200ms 걸린 건 봤는데, 그 200ms 중 정확히 어느 코드 줄이 시간을 먹었는가" — 트레이스는 서비스·스팬 단위 해상도까지만 보여주지만, 프로파일은 함수·라인 단위 해상도로 파고든다.

즉 트레이스가 "어디서(where) 시간을 썼는가"를 서비스 토폴로지 관점에서 답한다면, 프로파일은 같은 질문을 코드 관점에서 답한다. 이 둘을 연결하는 span profiles는 [27장](/study/observability/27-flamegraph-trace-integration)에서 다룬다. 프로파일 타입별로 구체적으로 어떤 질문에 답하는지는 [26장](/study/observability/26-profile-types-ebpf)에서 표로 정리한다.

## 4. 오버헤드와 프로덕션 안전성

연속 프로파일링을 상시 켜두려면 오버헤드가 무시할 만한 수준이어야 한다. 이 오버헤드는 <strong>샘플링 주기</strong>에 정비례한다.

| 샘플링 주기 | 오버헤드 | 통계적 해상도 |
|---|---|---|
| 짧음 (예: 1000Hz, 1ms) | 높음 | 짧게 실행되는 함수까지 정밀하게 포착 |
| 표준 (예: 100Hz, 10ms) | 낮음 (보통 1~5%) | 대부분의 프로덕션 워크로드에 충분 |
| 김 (예: 19Hz) | 매우 낮음 | 짧게 실행되는 함수는 샘플에 안 잡혀 누락될 수 있음 |

CPU 프로파일링은 관례적으로 100Hz(10ms 간격)를 기본값으로 삼는 경우가 많다. Google의 대규모 프로덕션 프로파일링 사례(Google-Wide Profiling)에서 검증된 이래, 대부분의 연속 프로파일러가 비슷한 기본값을 채택하고 있다. 이 주기는 [Prometheus의 `scrape_interval`](/study/observability/07-scraping-service-discovery) 트레이드오프와 본질적으로 같은 문제다 — 촘촘할수록 정밀하지만 비용이 늘고, 성길수록 저렴하지만 짧게 실행되는 함수를 놓칠 확률이 커진다.

프로덕션 안전장치로는 프로파일 크기 상한, 캡처 타임아웃, 전송 레이트 제한이 함께 적용되는 것이 일반적이다. 이런 가드레일이 없으면 급격한 트래픽 증가 시 프로파일러 자체가 부하의 원인이 될 수 있다.

## 5. 프로파일 데이터 모델

대부분의 연속 프로파일링 도구는 <strong>pprof</strong> 포맷을 데이터 모델로 채택한다. pprof는 원래 Google의 gperftools와 Go 런타임의 `runtime/pprof` 패키지에서 쓰이던 프로토콜 버퍼(protobuf) 기반 스키마로, 이후 사실상 업계 표준이 됐다. Pyroscope도 pprof를 기본 저장·교환 포맷으로 쓰고, OpenTelemetry가 새로 추가한 프로파일링 시그널도 pprof 계열 스키마를 기반으로 설계됐다.

| 필드 | 의미 |
|---|---|
| `sample_type` | 값 컬럼이 무엇을 의미하는지 정의(예: `cpu`/`nanoseconds`, `alloc_space`/`bytes`) |
| `Sample` | 하나의 고유한 콜 스택과 그에 대응하는 값(샘플 수, CPU 시간, 바이트 등) |
| `Location` | 스택 프레임 하나. 메모리 주소와 소스 라인 정보를 담는다 |
| `Function` | 함수 이름, 소스 파일 경로 |
| `Mapping` | 바이너리/공유 라이브러리의 주소 범위. 심볼라이제이션(주소 → 함수명 변환)에 쓰인다 |
| `string_table` | 문자열 중복 저장을 피하기 위한 인터닝 테이블 |

핵심은 <strong>"스택 + 값"</strong> 구조다. 하나의 `Sample`은 콜 스택(Location들의 배열)과 그 스택에 누적된 값(샘플 횟수, CPU 나노초, 할당 바이트 등)의 쌍으로 이뤄지고, 이 Sample들의 집합이 하나의 프로파일을 이룬다.

```bash
# Go 애플리케이션에서 CPU 프로파일을 30초간 캡처
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30

# 대화형 셸에서 CPU 비중 상위 함수 확인
(pprof) top10
(pprof) web    # 플레임그래프/콜 그래프를 브라우저로 시각화
```

## 6. 4번째 신호로서의 자리

관측성을 흔히 메트릭·로그·트레이스 "세 개의 기둥"으로 설명하지만, 프로파일은 최근 <strong>4번째 신호</strong>로 자리 잡았다. 코드 라인 단위까지 파고드는 리소스 소비 정보는 다른 세 신호가 채울 수 없는 공백을 메운다. 4대 신호 전체의 역할과 관계는 [2장 관측성의 4대 신호](/study/observability/02-four-signals)에서 다룬다.

![관측성 4대 신호인 메트릭·로그·트레이스·프로파일의 역할을 나누고, 프로파일이 함수·라인 단위 해상도로 4번째 신호 자리를 차지하며 트레이스와 span profiles로 연결되는 구조](/images/study-observability/24-four-signals.png)

메트릭 스파이크가 알림을 울리고, 트레이스가 어느 스팬이 느려졌는지 좁혀주면, 마지막으로 프로파일이 그 스팬 안에서 정확히 어느 함수가 원인인지 짚어준다. 이 상관관계 흐름은 [27장](/study/observability/27-flamegraph-trace-integration)에서 span profiles로, [32장](/study/observability/32-signal-correlation)에서 신호 전체의 상관관계로 확장해서 다룬다.

::: tip 핵심 정리
- 프로파일링은 샘플링으로 콜 스택을 주기적으로 캡처해 통계적으로 집계하는 기법이며, 계측 기반 방식보다 오버헤드가 훨씬 낮다.
- 연속 프로파일링은 상시 수집·저장을 통해 이미 지나간 장애 시점의 프로파일도 사후에 조회 가능하게 만든다.
- 프로파일은 메트릭·트레이스가 답하지 못하는 "정확히 어느 함수·라인이 리소스를 먹었는가"를 함수/라인 해상도로 답한다.
- 샘플링 주기는 오버헤드와 통계적 정확도의 트레이드오프이며, CPU 프로파일링은 100Hz(10ms) 안팎이 실무 기본값이다.
- pprof는 "스택 + 값" 구조의 protobuf 기반 표준 데이터 모델로, Pyroscope를 포함한 대부분의 도구가 채택한다.
- 프로파일은 메트릭·로그·트레이스에 이어 관측성의 4번째 신호로 자리 잡았다.
:::
