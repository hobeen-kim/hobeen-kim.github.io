ISO 11783-5: Network management 정리

이 문서에 대해

ISO 11783-5 표준 원문을 학습 목적으로 재구성한 비공식 요약·해설이다. 규범적 판단이 필요할 때는 반드시 원문 표준을 확인해야 한다.

처음 읽는다면

이 페이지는 네트워크 관리(Part 5: 장치 이름인 NAME, 주소 클레임, 초기화 절차)를 원문의 절 구조대로 요약한 참고 자료다. 주소 클레임 타이밍이나 NAME 필드의 정확한 규칙을 확인할 때 펼쳐 본다. 처음이라면 12장 주소와 NAME: 누가 보냈는지 알아보는 법과 13장 주소 클레임: 주소를 정하는 절차를 먼저 읽는다.

개요

ISO 11783-5(3판, 2019-06)는 ISO 11783 네트워크에서 ECU의 CF(Control Function)가 사용하는 소스 주소(SA, Source Address)의 관리를 규정하는 파트다. 구체적으로 다음을 다룬다.

  • CF를 네트워크상에서 유일하게 식별하는 64비트 NAME의 구조와 생성 규칙
  • NAME과 주소(SA)를 연결하는 주소 클레임(address claim) 절차
  • 네트워크 관련 오류의 감지·보고
  • 네트워크에 연결된 ECU의 초기화(initialization) 절차

ISO 11783 시리즈는 ISO 11898(CAN) 기반이며, SAE J1939와 공동으로 개발되어 트럭·버스용 J1939 장비를 최소 변경으로 농림업 장비에 쓸 수 있게 설계되었다. 이 문서는 SAE J1939/81(Network Management)과 조화(harmonized)되어 있다.

3판의 주요 변경

2판(ISO 11783-5:2011) 대비 가장 큰 변경은 물리 계층 요구사항이 ISO 11783-2로 이동한 것이다. 3판에는 네트워크 관리 로직만 남았다.

인용 규격은 ISO 11783-1(일반), ISO 11783-2(물리 계층), ISO 11783-3(데이터 링크 계층)이다.

용어정의

4.1 일반 요구사항

네트워크 관리의 핵심 원칙은 다음과 같다.

  • 모든 CF는 자신의 유일한 64비트 NAME을 제공할 수 있어야 한다.
  • CF는 네트워크에서 다른 어떤 메시지를 보내기 전에 먼저 주소 클레임에 성공해야 한다.
  • 여러 CF가 협력해 하나의 기능을 수행할 수 있지만, 각 CF는 각자 자신의 주소를 클레임해야 한다.
  • 주소 클레임에 실패한 CF는 그 사실을 네트워크에 보고해야 한다(cannot-claim-source-address).

4.2 주소 구성 능력 (Address configuration capabilities)

CF가 주소 클레임에 쓸 SA를 결정하는 방식을 주소 구성 능력이라 한다. 기본 능력 2가지와 확장 능력 2가지가 있다.

구분능력설명
기본Non-configurable address주소 클레임 과정에서 초기 주소를 바꿀 수 없다. 같은 주소를 두 non-configurable CF가 다투면 NAME 우선순위가 높은 쪽만 주소를 얻고, 나머지는 클레임 불가를 알린다
기본Self-configurable address독자 알고리즘으로 초기 주소를 선택하고, 충돌 시 주소를 재계산해 재클레임할 수 있다(128~247 범위 120개가 모두 사용 중이 아닌 한)
확장Service-configurable address서비스 기사가 "service" 모드에서 서비스 툴 등으로 주소를 바꿀 수 있다
확장Command-configurable addresscommanded-address 메시지로 언제든 주소를 바꿀 수 있다. 서비스 툴이나 특수 모드 없이 동작하지만, 해당 명령을 보낼 CF가 네트워크에 있어야 한다

핵심 규칙:

  • 기본 능력 2가지는 NAME 최상위 비트인 "self-configurable address" 필드 값으로 구분된다.
  • ISO 11783 적합 CF는 self-configurable address 능력이 필수다. Non-configurable CF는 구판(2001)과 SAE J1939 호환을 위해 허용(tolerate)될 뿐이다.
  • self-configurable 비트가 NAME의 최상위 비트이므로, non-configurable(0) CF가 self-configurable(1) CF보다 항상 NAME 우선순위가 높다. 즉 충돌 시 self-configurable CF가 밀려나 다른 주소를 클레임하게 된다.
  • self-configurable CF는 주소 중재에서 졌을 때만 초기 주소를 바꿔야 하며, 사용 주소는 128~247 범위로 제한된다. 단, 할당된 preferred address가 있는 기능이면 그 주소도 쓸 수 있다.
  • 확장 능력(command/service)은 CF가 하나 이상 선택적으로 구현할 수 있다.

4.3 NAME과 주소 요구사항

4.3.1 개념

  • NAME: 64비트 엔티티로, CF가 수행하는 기능을 기술하며 그 수치값이 주소 중재의 우선순위로 쓰인다(값이 낮을수록 우선순위가 높다). 네트워크 통합자와 ECU 제조사는 한 네트워크 안에서 NAME이 중복되지 않도록 보장해야 한다.
  • 주소(SA): CF가 보내는 모든 메시지의 CAN 식별자에 포함되는 1바이트 값. 메시지의 유일성과 발신원 식별을 제공한다.
  • address-claimed 메시지가 NAME과 SA를 담아 둘의 연결을 네트워크에 알린다. SA는 전원 인가 시마다, 네트워크 연결마다 달라질 수 있지만 NAME의 정의는 SA와 무관하게 일관되게 유지된다.
  • 하나의 ECU가 여러 CF를 구현할 수 있고, 이때 CF마다 주소 구성 능력이 달라도 된다. 각 CF는 각자 유일한 SA를 클레임해야 한다.

4.3.2 64비트 NAME 구조

NAME은 우선순위 순서(최상위 → 최하위)로 다음 10개 필드로 구성된다. Byte 8이 최상위 바이트다.

필드SPN비트 수바이트 위치의미
Self-configurable address28441Byte 8, bit 8자기구성 가능 여부(1=가능, 0=불가)
Industry group28463Byte 8, bit 7~5ISO가 정의·할당. 산업군 식별(농업 장비 등)
Device class instance28434Byte 8, bit 4~1네트워크 내 특정 device class의 발생 순번. 해석은 industry group에 의존
Device class28427Byte 7, bit 8~2ISO가 정의·할당. 기능 그룹의 공통 NAME("agricultural equipment"의 "planter" 등)
Reserved-1Byte 7, bit 1ISO 예약. 0으로 설정해야 한다
Function28418Byte 6ISO가 정의·할당. 0~127은 다른 필드와 무관하게 정의되고, 128~253은 device class에 따라 해석이 달라진다
Function instance28395Byte 5, bit 8~4네트워크의 특정 장치 시스템에서 해당 function의 발생 순번
ECU instance28403Byte 5, bit 3~1한 function에 연결된 ECU 그룹 중 어느 ECU인지 식별
Manufacturer code283811Byte 4 bit 8~1(상위 8비트) + Byte 3 bit 8~6(하위 3비트)위원회가 할당(ISO 11783-1 참조). ECU 제조사 식별. 다른 필드와 독립
Identity number283721Byte 3 bit 5~1(최상위 5비트) + Byte 2(중간 8비트) + Byte 1(최하위 8비트)ECU 제조사가 할당

바이트 순서는 NAME을 하나의 숫자로 다룰 수 있도록 배치되어 있다(ISO 11783-7과 일치). 각 industry group, device class, function, manufacturer code의 실제 수치는 ISO 11783-1이 관리한다.

필드 간 의존 관계

독립 필드와 의존 필드로 나뉜다.

  • 독립: self-configurable address, industry group, reserved, function 0~127, manufacturer code
  • 의존: device class는 industry group에, device class instance는 device class에, function 128~253은 device class에, function instance·ECU instance는 function에, identity number는 manufacturer code에 각각 의존해 해석된다.

인스턴스 필드 운용 규칙:

  • NAME의 instance 필드들은 ECU 설치 시 또는 네트워크에 다중 인스턴스가 존재할 때 NAME management 메시지로 재구성할 수 있다.
  • function instance의 해석은 제조사와 시스템 통합자 간 합의로 정할 수 있다(예: 위치나 특수 기능 표시). 예를 들어 엔진 2개·변속기 2개 구성에서 engine instance 0 ↔ transmission instance 0을 물리적으로 연결하기로 합의하는 식이다.
  • 하나의 function을 두 ECU가 나눠 맡으면 첫 ECU의 ECU instance는 0, 둘째는 1로 둔다.
  • ECU 제조사는 전원이 제거되어도 NAME이 유일하고 변하지 않도록 보장해야 한다. 다른 필드가 모두 같아질 수 있는 경우 identity number(제품 일련번호, 날짜/시간 코드 등)로 유일성을 확보한다.

4.3.3 주소

주소용도
0~127, 248~253preferred address 영역. 이 범위를 클레임하는 CF는 해당 주소에 정의된 기능을 수행해야 하고 NAME에도 그 기능을 명시해야 한다
128~247self-configurable address 범위. preferred address가 없거나 클레임에 실패한 CF가 사용
254NULL address. 소스 주소로만 사용하며, 네트워크 관리 통신 전용
255Global address. 목적지 주소로만 사용
  • Preferred address: CF는 할당된 preferred address로 동작할 수 있다. 이미 다른 CF가 그 주소를 클레임했다면, 주소 구성 능력과 빈 주소 유무에 따라 다른 SA를 클레임하거나 cannot-claim-source-address 메시지를 보낸다. 다른 주소를 클레임하게 되면 그 새 주소를 이후 모든 전원 인가에서 쓸 초기 주소로 저장해야 한다. preferred address 목록은 ISO 11783-1에 있다.
  • 기능은 SA만으로 추론해서는 안 되고, 반드시 NAME으로 판단해야 한다. (2001년 초판은 주소-기능 관계를 강제하지 않았다.)
  • 128~247 범위의 상단 일부는 Industry Group 2 기능의 preferred address로 정의되어 있으나 그 기능에 고정된 것은 아니어서 어느 self-configurable CF든 쓸 수 있다. 다만 다른 주소를 강제로 클레임하게 된 CF는 범위 하단부터 시도하고, 하단이 모두 사용 중일 때만 preferred 영역을 쓰는 것이 권장된다.
  • Initial address: 생산 시점에는 preferred address로 설정한다(전원 인가 시 처음 클레임을 시도하는 주소). 시스템 구성을 위해 재프로그램될 수 있다. service/command/self-configurable CF가 새 주소를 클레임하게 되면 그 주소를 initial address로 저장해 이후 전원 인가에 사용한다.

4.4 네트워크 관리 절차

4.4.1 일반

네트워크 관리 프로토콜의 주 역할은 주소 관리(4.4.2)와 네트워크 오류 관리(4.4.4)다. 네트워크 관리 메시지는 NULL 주소 사용 제한을 제외하면 다른 ISO 11783 메시지와 같은 특성·요구사항을 따른다(예: request-for-address-claimed는 ISO 11783-3의 request PGN 메시지다).

NULL 주소(254)는 request-for-address-claimed 또는 cannot-claim-source-address 메시지의 SA 필드에서만 허용된다.

Request-for-address-claimed (PGN 59904)

  • 어느 CF든 다른 CF의 NAME·주소를 조회하기 위해 송신할 수 있다.
  • 수신한 CF는 자신의 주소·NAME을 담은 address-claimed 메시지로 응답해야 하고, 주소를 클레임하지 못한 CF는 cannot-claim-source-address로 응답한다. 예외: 아직 클레임을 시도한 적 없는 CF는 cannot-claim을 보내지 않으며, 클레임 시도 전에는 (request-for-address-claimed 외의) 어떤 네트워크 통신에도 참여하지 않는다.
  • 아직 주소를 클레임하지 못한 CF가 보낼 때는 SA를 NULL(254)로 한다.
  • 목적지는 Global(255) 또는 특정 주소 모두 가능하다. Global로 보내면 응답들을 조사해 특정 NAME을 가진 CF의 존재를 파악할 수 있고, 특정 주소로 보내면 그 주소가 이미 클레임되었는지 조회할 수 있다. Global로 보낸 경우 자기 자신의 요청에도 응답해야 한다.

  • 자신의 SA를 클레임하는 address-claimed 메시지를 수신하면, 자신의 NAME과 수신 NAME을 비교해 우선순위(수치가 낮은 쪽이 높음)를 판정한다. 자신이 높으면 자기 NAME·주소로 address-claimed를 재송신하고, 낮으면 새 주소를 클레임하거나 cannot-claim-source-address를 보낸다.
  • 클레임 성공 판정: address-claimed 송신 후 최소 250 ms 동안 경합 클레임을 받지 않아야 성공이다.
  • 네트워크 상호연결 유닛(NIU)은 자기 주소 클레임에 성공하기 전에는 자기 주소로 통신해서는 안 된다. 단, 다른 ECU 간 메시지 포워딩은 자기 주소 클레임 전에도 할 수 있다(ISO 11783-4 참조).

Cannot-claim-source-address (PGN 60928, SA=254)

  • 초기 주소를 클레임하지 못했고 self-configurable 능력이 없는 CF, 또는 self-configurable이지만 쓸 수 있는 주소가 하나도 없는 CF가 (request-for-address-claimed나 address-claimed에 대한 응답으로) 송신한다.
  • address-claimed와 같은 PGN을 쓰지만 SA가 NULL(254)이라는 점으로 구분된다. 송신 주기는 "응답 시에만".
  • 응답을 유발한 메시지 수신과 응답 송신 사이에 RTxD를 삽입해야 한다. 두 CF가 동시에 응답해 버스 오류를 일으킬 가능성을 줄이기 위함이다.
  • 주소를 클레임하지 못한 CF는 cannot-claim-source-address와 request-for-address-claimed 외의 메시지를 보내서는 안 된다. 다만 Global 메시지(commanded-address 등)의 수신·처리는 계속할 수 있다.

Commanded-address (PGN 65240)

  • 지원은 선택 사항이다. 지원하지 않는 CF는 이 절의 나머지를 무시하면 된다.
  • 한 CF(브리지 같은 NIU나 서비스 툴 등)가 다른 CF(commanded CF)에게 특정 SA를 쓰도록 명령한다.
  • 데이터 9바이트: Byte 1~8 = 대상 CF의 NAME, Byte 9 = 새 SA. 9바이트이므로 BAM(broadcast announce message) 전송 프로토콜로 Global(255)에 송신해야 하며, 따라서 commanded-address를 지원하는 CF는 BAM도 지원해야 한다. PGN 65240(00FED8₁₆), 기본 우선순위 6.
  • 수락한 CF는 명령받은 주소를 새 SA로 하는 address-claimed 메시지를 발행해야 하며, 이때 주소 클레임 요구사항(4.5.2)이 적용된다.
  • 수신했지만 변경할 수 없는 CF는 현재 SA를 클레임하는 address-claimed로 응답한다. 그 뒤 운용자·기사가 다른 방법으로 SA를 바꿀 수 있다.
  • ECU 제조사는 브리지·서비스 툴 이외의 CF가 보낸 commanded-address를 거부하거나, 수락 전 보안 검증을 요구하도록 제품을 설계할 수 있다.

4.4.3 NAME management 메시지와 절차

4.4.3.1 개념

NAME management(NM) 메시지는 CF의 NAME 필드를 런타임에 바꾸는 수단이다. 용도:

  • function·ECU·device class의 다중 인스턴스가 있는 네트워크 구성 시 instance 필드 설정(주 용도)
  • 범용(generic) ECU의 function 변경
  • CF를 유일하게 식별할 다른 방법이 없을 때
  • 수동 설정 단계나 commanded-address와 병행한 네트워크 구성

규칙:

  • commanding CF가 target CF에게 특정 NAME 사용을 명령하는 구조로, target CF의 NAME 필드 일부를 새 값으로 교체하도록 지시한다.
  • Identity Number 필드는 변경 불가(최초 제조 후 불변). 나머지 모든 필드는 이 메시지로 수정할 수 있다.
  • CF의 NM 메시지 지원은 선택 사항이다. 지원하더라도 제조사는 서비스 툴·NIU 외의 발신자를 거부하거나, 보안 검증을 추가하거나, 변경 가능 필드를 instance 필드 등 일부로 제한할 수 있다.
  • commanding CF는 명령 전에 대상 CF들의 SA를 정확히 파악해야 한다. 명령은 SA를 향해 전달된다.

Qualifier flags

모드에 따라 의미가 달라진다.

  • Mode 0 (set pending NAME): flag가 0이면 pending NAME의 해당 필드를 메시지의 commanded 값으로 설정하고, 1이면 그 필드를 바꾸지 않는다.
  • Mode 4 (NAME NACK): error code가 1 또는 2일 때, 오류를 일으킨 항목의 flag를 1로, 아닌 항목을 0으로 설정해 원인 항목을 알린다. error code가 1·2가 아니면 모두 1.
  • Mode 8 (request NAME address claim): flag가 0인 commanded 파라미터만 current NAME 매칭에 사용하고, 1인 파라미터는 매칭에서 제외한다.
  • 그 외 모드에서는 적용되지 않으며 모두 1로 설정한다.

NM Control Mode (Byte 3 하위 4비트, SPN 5666, 값 범위 0~15)

  • Mode 0: Set Pending NAME: CAN 식별자의 목적지 주소에 있는 target CF에게 pending NAME 변경을 명령한다. 모든 데이터 필드 필수. commanded 필드가 새 NAME 값이며 qualifier flag로 적용 여부를 지정한다. NAME checksum(target CF의 원래 NAME 8바이트 합의 하위 8비트)으로 SA 변동 가능성을 방어한다.
  • Mode 1: Pending NAME: target CF가 pending NAME 조회 요청에 응답으로 송신. pending NAME을 commanded 필드에 담는다(전 필드 필수). qualifier flag·checksum은 미사용(모두 1). pending NAME이 미설정이거나 유효하지 않으면 이 메시지 대신 Mode 4(NACK)를 보낸다.
  • Mode 2: Current NAME: target CF가 current NAME 조회 요청에 응답으로 송신. current NAME을 commanded 필드에 담는다(전 필드 필수). qualifier flag·checksum은 미사용(모두 1).
  • Mode 3: NAME ACK: target CF가 직전에 받은 "set pending NAME" 명령이 성공적으로 수행됐음을 알린다. pending NAME을 commanded 필드에 담는다(전 필드 필수). qualifier flag·checksum은 미사용(모두 1).
  • Mode 4: NAME NACK: target CF가 직전의 "set pending NAME" 또는 "request pending NAME" 명령이 실패했음을 알린다. 유효 필드는 control mode indicator, error code, qualifier flag뿐이며 나머지는 모두 1.
  • Mode 5: Request pending NAME: commanding CF가 target CF에게 pending NAME 응답을 요청. control mode 파라미터만 유효, 나머지는 모두 1.
  • Mode 6: Request current NAME: commanding CF가 target CF에게 current NAME 응답을 요청. control mode 파라미터만 유효, 나머지는 모두 1.
  • Mode 7: Adopt pending NAME: commanding CF가 보내는 "트리거" 명령. target CF(Global로 보내면 pending NAME을 가진 모든 CF)에게 pending NAME을 current NAME으로 채택하고 그 새 NAME으로 주소 클레임 절차를 다시 시작하도록 지시한다. control mode 파라미터만 유효. 특정 SA 또는 Global 주소로 보낼 수 있다.
  • Mode 8: Request NAME address claim: SA를 모르는 CF에게 address-claimed 메시지를 보내게 하여 요청자가 그 CF의 SA를 알아내는 용도다. qualifier flag로 NAME의 전부 또는 일부만 매칭 조건으로 지정할 수 있으며, 반드시 Global 주소로 송신한다. 지정된 qualifier 필드가 current NAME과 일치하는 CF는 current NAME으로 address claim을 보내고, 일치하지 않는 CF는 address claim도 NACK도 보내지 않는다(침묵).
  • Mode 9~15: ISO 예약.

4.4.3.4 NAME management 절차

NM 메시지 지원 확인

  • commanding CF는 NM 메시지에 대한 Request PGN(59904)을 보내 지원 여부를 확인할 수 있다. NM을 지원하지 않는 CF는 ISO 11783-3에 따라 acknowledgement 메시지(PGN 59392)를 적절한 NACK control byte와 함께 보낸다.
  • NM을 지원하는 CF는 요청 시 NM 메시지로 응답한다. 유효한 pending NAME이 있으면 mode를 "pending NAME"으로, 없으면 "current NAME"으로 설정해 Byte 3~8에 해당 NAME을 담는다. 서비스 툴이나 다중 장치를 구성하려는 ECU가 지원 여부와 현재/pending NAME을 한 번에 조회하는 수단이 된다.

Pending 상태

  • NAME이 성공적으로 수정되면 target CF는 "pending" NAME을 가진다. 이 상태에서도 CF는 current NAME으로 계속 송신할 수 있다.
  • pending NAME은 네트워크 구성 책임 유닛이 "adopt pending NAME"(Mode 7) 메시지를 보내기 전까지는 효력이 없다. Mode 7을 받으면 target CF는 새 NAME으로 address claim을 재발행하고, 그 NAME으로 주소 클레임에 성공한 뒤에야 네트워크 송신을 시작/재개할 수 있다.

Set pending NAME 처리 (4.4.3.4.2)

"set pending NAME" 모드의 NM 메시지를 자기 SA를 목적지로 수신한 target CF는 둘 중 하나로 응답한다.

  • 수락: 명령된 변경을 NAME 필드에 적용한다. 변경분 + 유지분이 pending NAME이 된다. ACK(Mode 3) 메시지에 pending NAME(Byte 3~8)을 담아 commanding CF의 SA로 보낸다. 이때 자신의 current SA(마지막으로 클레임에 성공한 주소)를 발신 주소로 쓴다.
  • 거부: NACK(Mode 4) 메시지를 error code와 함께 보낸다. error code가 "item not allowed"(1) 또는 "item conflict"(2)면 변경 불가 필드의 qualifier flag를 1로, 변경 가능 필드를 0으로 설정한다. 그 외 데이터 바이트는 모두 1.

Adopt pending NAME (4.4.3.4.3)

  • target CF는 명령받은 NAME 변경을 임시 저장해 두었다가, commanding CF가 모든 명령을 마치고 "adopt pending NAME"을 보내면 pending NAME을 채택하고 필요한 "reset"(새 NAME으로의 address claim 송신 포함)을 수행한다.
  • Mode 7은 Global 주소로도 보낼 수 있으므로, commanding CF는 여러 CF를 순차 구성해 두고 한 번에 동시 활성화할 수 있다.

NAME 대상 SA 검증 (4.4.3.4.4)

NM 메시지 송신 전에 변경 대상 CF의 신원과 SA를 검증해야 한다. target CF는 언제든 주소 클레임 과정에서 새 SA를 얻을 수 있고, 이 사건과 commanding CF의 "set pending NAME" 송신 시점은 동기화되어 있지 않다. 새로 그 SA를 획득한 엉뚱한 CF가 NAME을 강제 변경당하는 사고를 막기 위해 "set pending NAME" 모드에 의도한 수신자의 원래 NAME 8바이트 checksum이 포함되어 있는 것이다.

NM 메시지 사용 규칙 (4.4.3.4.5)

  • target CF는 변경 표시된 각 필드를 검사해 그 동작을 실제로 제공할 수 있는지 확인한 뒤에만 수락해야 한다.
  • NM 메시지를 지원한다면 최소한 ECU instance와 function instance의 변경은 허용해야 한다.
  • target CF는 "set pending" 명령을 임의의 CF로부터 수락해도 된다.
  • 단, "adopt NAME" 명령을 보낸 CF가 자신이 수락한 가장 최근의 "set pending NAME"을 보낸 CF와 동일한지 검증해야 한다(다르면 error code 0).

4.4.4 네트워크 오류 관리

  • 네트워크 오류 관리는 특정 주소 지정 오류(예: CF의 주소 확보 실패)의 감지를 말한다. 중복 주소 클레임·중복 NAME 같은 그 밖의 오류는 진단 툴이 request-for-address-claimed 메시지로 탐지할 수 있다.
  • 주소 확보 실패(unable to claim): SA 클레임에 실패한 CF는 cannot-claim-source-address 메시지를 보내고 4.5.5에 따라 동작을 계속한다.
  • 주소 위반(address violation): 두 CF가 같은 SA를 쓰는 상황이다. 자신의 SA를 쓰는 (address-claimed가 아닌) 메시지를 수신한 CF는:
    • Global 주소로 address-claim 메시지를 송신해야 하고,
    • SPN = 2000 + SA, FMI = 31인 진단 트러블 코드(DTC)를 활성화해야 한다(DTC는 ISO 11783-12 참조).
    • 이 요구사항은 2판(2011)에서 추가되었다.

4.5 네트워크 초기화

4.5.1 유일 주소의 획득

전원 인가 후, 다른 어떤 통신도 시작하기 전에 CF는 네트워크에서 유일한 주소를 획득해야 한다. self-configurable CF는 다음 두 시퀀스 중 하나를 사용한다.

a) 주소 테이블 구축 방식

  1. request-for-address-claimed를 Global 주소로 송신
  2. 최소 250 ms + RTxD 대기
  3. 대기 중 수신한 모든 address-claimed 메시지의 SA를 저장
  4. 사용되지 않은 주소를 클레임하는 address-claimed 송신: initial address가 비어 있으면 그것을, 이미 클레임되어 있으면 다른 빈 주소를 클레임

b) 단일 주소 조회 방식

  1. 자신의 initial address를 목적지로 request-for-address-claimed 송신
  2. 최소 250 ms + RTxD 대기: 대기 중 그 주소를 클레임하는 address-claimed를 수신하면 새 initial address를 선택하고 1단계부터 반복
  3. initial address를 클레임하는 address-claimed 송신

대기 시간에 관한 노트

  • 이 획득 시퀀스는 2판(2011)에서 추가되었다.
  • 위 시퀀스는 두 CF가 같은 주소를 클레임할 위험을 최소화할 뿐 완전히 제거하지는 못한다. 유효 주소만 쓰이도록 보장하는 것은 4.5.2·4.5.3의 요구사항이다.
  • 초판(2001)은 250 ms 대신 1,25 s를 규정했다. 부팅 시간이 중요하지 않다면 250 ms보다 긴 대기를 두는 것이 좋은 관행으로 여겨진다.

추가 규칙:

  • 새 initial address 선택 알고리즘은 CF 고유(proprietary)지만, 새 주소는 preferred address 또는 128~247 범위여야 한다.
  • 주소 클레임에 성공하면 그 주소를 이후 모든 전원 인가에 쓸 initial address로 저장한다(preferred address가 할당된 CF도 동일).
  • self-configurable이 아닌 CF는 위 시퀀스에서 request-for-address-claimed를 생략할 수 있으나, 다른 통신을 시작하기 전에 address-claimed는 반드시 보내야 한다.
  • 주소 클레임 전에 항상 request-for-address-claimed를 먼저 보내는 것이 권장된다.

4.5.2 주소 클레임 요구사항

초기화 중 경합 회피와 중복 주소 탐지·제거를 위한 핵심 요구사항:

  1. CF는 초기화 시, 그리고 NAME/주소 변경 명령에 응답할 때(commanded-address 수락 확인 포함) 자기 주소를 클레임해야 한다. 각 CF가 유효 주소 확보에 스스로 책임지고, 자기 클레임을 다른 CF가 아직 못 받았을 경우의 중재까지 수행하게 하기 위함이다.
  2. address-claimed의 목적지 주소는 Global(255)이어야 한다(모든 CF에 알리기 위함, ISO 11783-3 요구사항의 예외).
  3. CF는 다른 CF가 보낸 address-claimed와 자신이 보낸 것을 구분해야 한다.
  4. 주소 클레임 성공 후 250 ms가 지나기 전에는 네트워크 송신을 시작·재개해서는 안 된다. 단, request-for-address-claimed에 대한 응답은 예외다.

4.5.3 그 밖의 초기화 기본 요구사항

  • Global 주소로 온 request-for-address-claimed에는 address-claimed 또는 (클레임 실패 시) cannot-claim-source-address로 응답해야 한다. 단, 아직 클레임을 시도하지 않았다면 응답하지 않는다.
  • 자기 주소를 목적지로 온 request-for-address-claimed에는 응답을 Global(255)로 송신해야 한다.
  • 자기 SA와 같은 SA의 address-claimed를 수신했고 자기 NAME 우선순위가 더 높으면(수치가 낮으면) address claim을 송신해야 한다.
  • 자기 NAME 우선순위가 더 낮으면(수치가 크면) 그 주소 사용을 중단하고, cannot-claim-source-address를 보내거나 다른 주소 클레임을 시도해야 한다.
  • non-configurable·service-configurable·command-configurable CF가 특정 주소를 쓸 수 없게 되면 cannot-claim-source-address를 송신해야 한다.
  • self-configurable CF가 클레임하려는 주소를 쓸 수 없으면 다른 주소를 선택해 클레임을 시도해야 한다.
  • 주소 클레임에 실패한 CF와 이전에 통신하던 CF는, 그 CF의 cannot-claim-source-address와 클레임을 가로챈 상위 우선순위 CF의 address-claimed를 모니터링해 상대가 "disabled" 되었음을 감지할 수 있어야 한다.
  • 서비스 툴(일부 시스템에서는 브리지)이 주소 클레임 실패를 감지·해결할 것으로 기대된다. cannot-claim-source-address를 모니터링해 운용자에게 보고할 수 있다.

4.5.4.2 주소 클레임 우선순위 판정

  • 한 주소를 두 CF가 다투면 NAME 수치가 낮은(우선순위 높은) CF가 주소를 가진다.
  • NAME은 self-configurable address 비트를 최상위로 하는 8바이트 정수 하나로 취급해 비교한다. 경합 CF들의 address-claimed 데이터 필드(8바이트)를 통째로 비교해야 하지만, 이 방식이 주소 클레임 과정의 모호함을 없앤다.
  • 예: 같은 function의 CF A(function instance 0)와 CF B가 같은 주소를 요구하면, A의 NAME 절대값이 더 작으므로 A가 이긴다.

경합 해결 시퀀스는 관련 CF들의 주소 구성 능력에 따라 달라진다.

4.5.4.3 동일 식별자 충돌

request-for-address-claimed·address-claimed·cannot-claim-source-address는 서로 다른 CF가 동일한 CAN 식별자의 메시지를 만들 수 있는 경우다.

  • 두 CF가 동시에 NULL 주소(254)로 보내는 request-for-address-claimed는 데이터 필드까지 같으므로 문제가 없다.
  • 그러나 같은 주소를 다투는 여러 CF가 동시에 address-claimed를 송신하면 데이터 필드(NAME)가 서로 달라 CAN 수준의 네트워크 오류(비트 충돌)가 발생할 수 있다. 여러 CF가 NULL 주소에서 동시에 보내는 cannot-claim-source-address도 같은 이유로 오류를 일으킬 수 있다.
  • 데이터 링크 계층이 이런 오류를 감지·보고할 수 있다면: address claim 송신 후 오류 코드를 모니터링하고, 네트워크 오류가 확인되면 RTxD 후 클레임 재송신을 스케줄한다. (동기화된 충돌이 반복되면 장치들이 Bus OFF까지 갈 수 있는데, 서로 다른 RTxD가 재송신 시점을 흩어 놓아 충돌을 끊는다. Figure 9.)
  • cannot-claim-source-address끼리 충돌한 경우도 같은 절차(RTxD 후 재송신)를 쓴다.

4.5.5 주소를 얻지 못한 CF

주소 클레임에 실패한 CF는 다음 외에는 어떤 메시지도 보내서는 안 된다.

  • request-for-address-claimed에 대한 응답인 cannot-claim-source-address (RTxD 삽입 후 송신)
  • commanded-address 메시지에 대한 응답

전원이 재인가되면 다시 주소 클레임을 시도할 수 있다.

A.4 주소-NAME 연관 테이블

request-for-address-claimed(특정 주소 또는 Global 목적지)로 address-to-NAME 연관 테이블을 구축할 수 있다. 일부 CF는 이 테이블로 핵심 기능의 주소를 확인한다. 예를 들어 powertrain engine이 주소 0에 있음을 확인해, 변속기가 보내는 토크/속도 제어 메시지가 올바른 목적지로 가도록 보장하는 식이다. 필요한 연관이 적으면 특정 주소로, 진단 툴처럼 네트워크 전체를 대상으로 하면 Global 주소로 보낸다.
