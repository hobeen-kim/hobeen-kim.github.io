Task Controller (TC) 기초

학습 목표

  • Task Controller(TC)가 정밀 농업에서 담당하는 역할을 설명할 수 있다.
  • TC-Server와 TC-Client의 차이를 구분하고 각각의 위치를 식별할 수 있다.
  • Section Control과 Rate Control의 목적과 동작 원리를 비교할 수 있다.
  • GPS 위치 데이터가 TC 제어에 어떻게 활용되는지 설명할 수 있다.
  • Version·TC Status·Client Task 메시지 8바이트를 디코딩해 상대의 버전·기능성 옵션·Busy 상태를 판독할 수 있다.
  • 태스크 상태 전이와 200 ms·2 s·6 s 연결 규칙을 묶어 TC 서버·클라이언트의 연결 상태 머신을 설계할 수 있다.
  • TC가 보고한 버전과 붐·섹션·채널 수를 보고 클라이언트가 DDOP와 기능을 어떻게 낮춰야 하는지 진단할 수 있다.

1. TC란 무엇인가

Task Controller(TC)는 ISO 11783-10에 정의된 정밀 농업의 핵심 컴포넌트이다.

ISO 11783 Part 10 — Task Controller and Management Information System Data Interchange

TC는 두 가지 핵심 기능을 수행한다.

  • 자동 제어: 작업 계획(처방 맵, Prescription Map)에 따라 작업기를 자동으로 제어한다. 밭의 위치별로 미리 지정된 살포량·파종량을 GPS 위치와 연동하여 자동으로 적용한다.
  • 작업 기록: 실제 작업 결과(As-Applied Data)를 수집하고 기록한다. 어느 위치에서 얼마나 살포했는지를 나중에 분석할 수 있도록 로그로 남긴다.

TC가 없던 시대에는 농민이 수동으로 살포량을 조절해야 했다. TC는 이 과정을 자동화하여 비료·농약 과용을 줄이고 생산성을 높인다.

TC 기능성 구분

Part 10 Annex F.2는 TC 기능을 네 가지 TC functionality로 구분한다. 제품이 어떤 기능성을 지원하는지에 따라 구현 요구사항이 달라진다.

기능성의미내용

TC-GEOgeo-based위치 기반 로깅과 (선택적으로) 처방 맵 기반 위치 제어

TC 외의 기능(UT, AUX-N, TIM 등)까지 포함한 AEF 기능 단위 전체 구도는 AEF 기능 카테고리에서 다룬다.

현행 2015년판(2nd edition)은 프로토콜 버전 4를 정의하며, 로깅만 수행하는 별도 CF인 Data Logger(DL)와 Peer Control 등이 버전 4에서 추가되었다. DL은 TC 기능의 부분집합으로 같은 연결 메커니즘을 쓰고, 클라이언트는 동시에 TC 1개와 DL 1개에 연결할 수 있다.

TC-BAS·TC-GEO 최소 요건

같은 기능성이라도 TC 서버와 TC 클라이언트가 지는 부담은 다르다. TC 서버는 ISO 11783-11에 해당 기능성 관련으로 정의된 DDI를 전부 지원해야 하지만, TC 클라이언트는 자신이 실제로 다루는 부분집합만 제공하면 된다 — 이 비대칭이 아래 요건 전체를 관통하는 원칙이다(부속서 F.2).

기능성TC 서버 요건TC 클라이언트 요건
TC-BASISO 11783-11에 총계로 정의된 모든 DDI 지원총계의 부분집합만 제공 가능하나 최소 DDI 119(total time)는 필수. DDOP에 rate DDI가 있으면 대응하는 total DDI도 필수
TC-GEOTC-BAS 서버 요건 + ISO 11783-11의 모든 DDI 지원 + Grid type 1·2 처리 필수(최소 350행×350열)TC-BAS 클라이언트 요건 + TC-BAS 자체도 함께 지원 필수
  • TC-BAS: FMIS·TC·TC 클라이언트 모두 파일 세트(ISO11783_TaskData 등)와 Version 메시지에 TC 버전 3을 게시해야 한다. 파일 세트에 미지원 XML 요소(OperationTechnique, CodedCommentGroup 등)가 있어도 파일 세트 자체를 거부하면 안 되고, 해당 요소만 건너뛴 채 나머지 내용은 읽어야 한다.
  • TC-GEO: 폴리곤 기반 처방 처리는 선택 기능이며, 지원할 경우 Control function functionalities 메시지에 명시해야 한다. TC 클라이언트는 TC가 Version 메시지로 보고하는 위치 기반 제어 채널 수 이하로 자신의 device descriptor가 보고하는 제어 채널 수를 제한해야 한다 — 서버가 지원 못 하는 채널을 클라이언트가 먼저 내세우면 안 된다는 뜻이다.

그리드는 서버의 일

Grid type 1·2 처리(350행×350열 이상)는 TC 서버의 요건이지 클라이언트의 요건이 아니다. TC 클라이언트는 자신의 device element·process data 구조와 채널 수 제한만 신경 쓰면 된다.

연결 절차 자체는 §6 클라이언트 초기화와 연결 유지를 참조한다.

기능성별 Version 메시지 옵션 비트·게시 버전 번호와 TC-SC·LOG 요건은 §13에서 이어서 다룬다.

TC 연결 관리

TC와 클라이언트의 연결은 Task Controller Status 메시지로 유지된다.

  • 클라이언트는 address claim 완료 후 6초 대기 → TC의 Status 메시지 수신 확인 → Working Set Master 메시지로 자신을 식별하며 연결 절차를 시작한다.
  • TC는 Status 메시지를 2초 주기로 송신한다(상태 변화 시 즉시 송신해야 하며, 단 메시지 간 최소 200 ms).
  • 타임아웃은 양방향 모두 6초다. 클라이언트가 TC Status를 6초간 못 받으면 TC의 비정상 종료로 간주하고, TC가 클라이언트의 Task 메시지를 6초간 못 받으면 클라이언트의 비정상 종료로 간주한다.
  • 네트워크에는 TC가 여러 대 있을 수 있다. function instance 0인 TC가 primary TC이고, 오퍼레이터에게는 TC number = function instance + 1(1~32)로 표시한다. 클라이언트는 동시에 TC 1개·DL 1개에만 연결할 수 있다.

4. Section Control과 Rate Control

TC의 두 가지 핵심 제어 기능이다.

Section Control

작업기를 여러 구획(Section)으로 나누어 각 구획을 독립적으로 ON/OFF하는 기능이다. 이미 작업한 영역이나 작업이 필요 없는 영역의 구획을 자동으로 끈다.

목적: 중복 살포(Overlap) 방지 → 비료·농약·씨앗 절감

Rate Control

GPS 위치에 따라 살포량(Rate)을 가변적으로 제어하는 기능이다. 처방 맵에 지정된 위치별 목표량을 실시간으로 반영한다.

목적: 토양 조건(양분 상태, 수분 함량)에 맞는 정밀 시비·시약

구분설명제어 단위
Section Control구획별 ON/OFF논리 값(켜짐/꺼짐)
Rate Control살포량 가변 조절연속 수치(L/ha, kg/ha)

두 기능은 함께 사용할 수 있다. 예를 들어, 밭의 경계에서 외부 구획은 OFF(Section Control)하면서 내부 구획의 살포량은 위치별로 조절(Rate Control)할 수 있다.

5. GPS 연동과 위치 기반 제어

TC는 GPS 위치 데이터를 이용해 현재 위치에 해당하는 처방 맵의 값을 조회한다.

처방 맵은 격자(Grid) 또는 폴리곤(Polygon) 형태로 밭을 구획하고, 각 구획에 목표 값을 지정해 놓는다(둘 다 TreatmentZone을 참조한다). TC는 현재 GPS 위치가 어느 구획(TreatmentZone)에 속하는지 계산하고, 해당 구획의 목표 값을 TC-Client에 전달한다.

NMEA와 ISOBUS

GPS 수신기는 NMEA 0183(시리얼) 또는 NMEA 2000(CAN 기반) 프로토콜로 데이터를 제공한다. Part 7이 항법 위치 메시지를 IEC 61162-3(NMEA 2000)에 위임하므로, NMEA 2000 항법 메시지는 ISOBUS 네트워크에서 그대로 사용된다. 이때 여러 데이터 프레임이 필요한 메시지(GNSS Position Data 등)는 ISO 11783-3의 transport protocol이 아니라 NMEA fast packet protocol을 사용해야 한다.

핵심 정리

  • TC(Task Controller)는 ISO 11783-10에 정의된 정밀 농업 컴포넌트로, 처방 맵 기반 자동 제어와 작업 로그 기록을 담당한다. 기능성은 TC-BAS·TC-GEO·TC-SC·LOG로 구분된다(Annex F.2).
  • TC-Server는 트랙터 측에서 처방 맵을 읽고 명령하며, TC-Client는 작업기 ECU로 명령을 실행한다. 연결은 TC Status 메시지(2초 주기)로 유지되고 타임아웃은 양방향 6초다.
  • Section Control은 구획별 ON/OFF로 중복 살포를 방지하고, Rate Control은 위치별 살포량을 가변 조절한다.
  • GPS 위치(NMEA 2000 GNSS Position Data, PGN 129029)를 처방 맵과 대조하여 해당 위치의 Setpoint를 실시간으로 TC-Client에 전달한다.

6. 클라이언트 초기화와 연결 유지

앞 절들이 TC의 역할과 제어 기능을 다뤘다면, 여기서는 TC-Client가 전원이 켜진 순간부터 실제로 명령을 주고받기까지 반드시 거쳐야 하는 절차를 순서대로 짚는다.

흔한 오해 — "DDOP만 올리면 준비 끝"

TC-Client 구현을 "DDOP를 만들어 업로드하는 일"로 요약하는 경우가 많은데, 반만 맞다. DDOP 업로드와 활성화는 클라이언트 초기화 9단계 중 8~9번째일 뿐이다. 그 앞에 주소 확정 → TC 확인 → Working Set Master 선언 → Task 메시지 시작 → 버전 협상까지 7단계가 정해진 순서대로 먼저 끝나야 하고, 순서를 건너뛰면 TC가 DDOP 자체를 받아주지 않는다.

연결 유지

연결이 성립한 뒤에는 §3 TC 연결 관리에서 다룬 값들이 그대로 적용된다 — TC Status는 2초 주기(상태 변화 시 즉시, 단 메시지 간 최소 200 ms), 타임아웃은 양방향 6초. 여기에 클라이언트 쪽 값을 더하면 그림이 완성된다.

항목값
Task Controller Status 주기2초(변화 시 즉시, 최소 200 ms 간격)
Client Task 메시지 주기2초
타임아웃(양방향)6초
  • 클라이언트가 TC Status를 6초간 못 받으면 TC의 비정상 종료로 간주하고 Client Task 송신을 중단한다. 이후 초기화 절차를 처음부터 다시 밟아야 재연결된다.
  • TC가 Client Task를 6초간 못 받으면 클라이언트의 비정상 종료로 간주한다. 클라이언트가 address claim 후 6초를 기다린 뒤에야 Client Task를 보내는 이유가 여기 있다 — 그 지연 자체가 TC 입장에서 "클라이언트가 막 재시작했다"는 신호로 읽힌다.

권고가 아니라 필수값

200 ms·2초·6초는 참고 수치가 아니라 구현이 반드시 지켜야 하는 값이며, 정확도는 AEF(Agricultural Industry Electronics Foundation) 시험 요구사항의 대상이다. 임의로 늘리거나 줄이면 상호운용성 인증을 통과할 수 없다.

재접속

작업 도중 클라이언트가 재시작하면 연결이 끊긴 시점의 상태로 되돌아가지 않는다. TC는 재접속한 클라이언트의 DDOP 업로드·활성화 요청을 다시 수락해야 하고(위 9단계를 처음부터 다시 밟는다), 그 클라이언트에 내리던 measurement 명령도 다시 내려야 한다. 즉 재접속은 "끊긴 지점에서 이어 붙이기"가 아니라 초기화 시퀀스의 재실행이다.

연결 종료

Key Switch가 off로 전환되면(ECU Power는 유지된 채) 정돈된 종료 절차가 시작된다. 클라이언트는 Connection Deactivate 명령을 보내 TC가 이를 비정상 종료로 오인하지 않게 하고, TC는 활성 DDOP를 가진 클라이언트의 마지막 전원 유지 요청 이후 최소 2초간 서비스를 유지해 수집 중이던 데이터가 정상적으로 마무리되게 한다. Key Switch가 다시 켜지면 양쪽 모두 위 초기화 절차를 재실행한다.

7. 태스크 — TC가 다루는 작업 단위

앞 절까지는 TC가 작업기를 어떻게 제어하고 연결을 유지하는지 봤다. 이 절은 TC가 실제로 관리하는 단위인 태스크(task)를 본다. Part 10은 태스크를 "한 고객(customer)의 한 partfield에서 농민이나 계약자가 계획했거나, 실행 중이거나, 이미 끝낸 작업"을 서로 구분하는 단위로 쓴다(ISO 11783-10:2015 5.1). FMIS 쪽에서 보면 태스크는 작업을 무엇을, 어디서, 어떻게, 누가, 언제 할지 정한 계획서다(5.2).

처음 나오는 용어 세 가지를 먼저 정리한다.

  • partfield: 작물 하나만 재배하는 땅 구획이다. 태스크가 할당되는 가장 작은 XML 요소이기도 하다(3.12).
  • MICS(mobile implement control system): 트랙터·작업기 쪽 시스템 전체다. TC는 MICS 안에 있다(5.1).
  • coding data: 기계·약제 데이터처럼 자주 바뀌지 않거나, 태스크를 행정적으로 할당하려고 참조하는 데이터다(3.2).

장치 사전 선택 — NAME과 마스크

FMIS는 계획 단계에서 "어떤 장치로 일할지"를 정할 수 있어야 한다. 그런데 이동 시스템의 클라이언트 장치를 유일하게 가리키는 수단은 CF NAME(Part 5의 8바이트 이름)뿐이다. 그래서 FMIS 관점에서 NAME은 전 세계에서 유일해야 하고, Identity Number와 NAME의 나머지 필드 조합이 유일하도록 보장할 책임은 장치 제조사에 있다(5.3). NAME 필드 구성은 J1939 주소 체계에서 다룬다.

  • DeviceAllocation 요소가 계획된 장치 할당을 담는다. 지정 수준은 특정 장치 하나부터 "이런 종류의 장치"처럼 느슨한 것까지 고를 수 있다(5.3).
  • ClientNAMEValue는 8바이트 NAME이고, ClientNAMEMask는 그중 장치 선택에 쓸 비트를 고르는 마스크다. 마스크 비트 1은 "이 비트가 유효", 0은 "무시"다(D.20). 즉 후보 NAME과 ClientNAMEValue를 각각 마스크와 AND해 결과가 같으면 후보가 조건을 만족한다.
  • 실제로 쓴 장치는 DeviceIdRef 속성에 기록한다. FMIS가 넣은 사전 선택 정보는 MICS가 덮어쓰지 않는다(5.3).

TC 사용자 인터페이스

TC는 VT나 다른 인터페이스로 오퍼레이터와 상호작용할 수 있다. 태스크 하나를 자동으로 돌리는 단순한 TC는 UI가 없어도 되고, 고급 TC는 태스크 목록 선택, start/stop/resume/complete, 태스크 수정·생성, coding data 추가 같은 기능을 제공한다(5.5). 표준이 강제하는 것은 "태스크 실행 메커니즘은 반드시 있어야 한다(shall)"는 것뿐이고, 선택 메커니즘은 있어도 되는(can) 기능이다. 선택·시작·정지 방법 자체는 TC 설계자에게 맡긴다(6.1).

표준은 전이도를 따로 그리지 않는다. 위 그림은 Table 1의 상태 정의, 5.5의 조작 목록(start/stop/resume/complete), 6.2의 "시작·재개할 때 effective Time 요소를 추가한다"는 서술을 엮어 그린 것이다. 특히 Canceled로 들어가는 출발 상태는 표준이 제한하지 않는다. 그림은 가장 흔한 경우인 "아직 실행하지 않은 Planned 태스크의 철회"만 그렸다.

상태 전이는 버스와 파일에 각각 흔적을 남긴다.

  • 버스: TC Status 메시지 Byte 5 bit 1(Task totals active)은 "태스크가 시작되거나 재개돼 total이 누적될 수 있다"는 뜻이다(B.8.1). 이 비트가 0 → 1이 되면 클라이언트는 내부 task total을 0으로 리셋하고 세기 시작하며, 1 → 0이 되면 세기를 멈춘다. 멈춘 값은 TC가 Request Value로 읽어 갈 수 있다(B.8.1). 수거·복원 규칙은 TC 프로세스 데이터에서 다룬다.
  • 파일: Time 요소는 태스크 상태가 바뀔 때, 자원 할당이 바뀔 때, TC가 기동·종료할 때만 Task에 추가하고, 이미 기록한 Time은 고치지 않는다(6.2). MICS가 태스크를 시작했고 네트워크에 시간 정보가 있으면 Time 요소가 적어도 하나는 있어야 한다(D.46).

상태 머신 구현 함정

  • Completed를 "작업기 섹션이 모두 꺼졌다" 같은 조건으로 자동 설정하면 안 된다. 오퍼레이터만 설정할 수 있는 상태다(6.1 Table 1).
  • 새 태스크를 Running으로 올리기 전에 기존 Running 태스크를 내려야 한다. TC 하나에 active 태스크는 하나뿐이다(6.1 Table 1).
  • Template 태스크 자체를 Running으로 바꾸면 안 된다. 복사본을 만들어 그 복사본을 시작한다(6.1 Table 1, D.46).
  • FMIS는 MICS에서 온 Paused 태스크도 처리해야 한다. FMIS 쪽 구현이 Completed만 집계하면 Paused로 끝난 작업 기록이 빠진다(추론, 6.1 Table 1).

    width = stop_bit - start_bit + 1

def zero_based_bit(byte_no, bit_no):
    return (byte_no - 1) * 8 + (bit_no - 1)

정리

  • 태스크는 FMIS와 MICS 사이를 오가는 작업 단위다. 표준이 정한 경계는 XML 파일 세트와 버스 메시지 두 곳뿐이다.
  • 상태 값은 1~6이다. Running은 TC당 하나, Completed는 오퍼레이터만 설정하고, Template·Canceled는 버전 4에서 생겼다.

파이썬으로 검산해 보기 — TC Status 송신 시각

즉시 송신 뒤 2 s 주기를 그 시점부터 다시 세는 방식으로 짠 예다. 주기를 다시 셀지 고정 격자로 둘지는 표준이 정하지 않는다. 어느 쪽이든 "주기 간격 2 s 이하, 송신 간격 200 ms 이상"을 지키면 된다(추론, 6.6.3).

MIN_GAP_MS, PERIOD_MS = 200, 2000


def tc_status_send_times(change_times_ms, until_ms):
    pending, sent, last = sorted(change_times_ms), [], None
    while True:
        if last is not None:
            pending = [t for t in pending if t > last]
        periodic = 0 if last is None else last + PERIOD_MS
        on_change = max(pending[0], last + MIN_GAP_MS) if pending and last is not None else None
        nxt = periodic if on_change is None else min(periodic, on_change)
        if nxt > until_ms:
            return sent
        sent.append(nxt)
        last = nxt


times = tc_status_send_times([2500, 2550, 6100], until_ms=9000)
print(times)
assert times == [0, 2000, 2500, 2700, 4700, 6100, 8100]
gaps = [b - a for a, b in zip(times, times[1:])]
assert min(gaps) >= MIN_GAP_MS and max(gaps) <= PERIOD_MS

[0, 2000, 2500, 2700, 4700, 6100, 8100]

2500 ms와 2550 ms의 변화 두 번은 2500 ms 송신과 2700 ms 송신으로 나뉜다. 2550 ms 변화는 200 ms 간격을 채운 2700 ms에 나간다.

셧다운 — Key Switch Off 이후

§6 "연결 종료"를 원문 6.6.4로 풀면 다음과 같다. 시스템 셧다운은 Key Switch 상태가 Off인데 ECU Power는 아직 켜져 있는 구간이다. Actuator Power는 함께 켜져 있을 수도, 아닐 수도 있다(6.6.4). 아래 절차는 버전 4에서 도입돼 버전 4 구현에는 의무다.

Key Switch 상태는 Wheel-based speed and distance(PGN 65096) Byte 8 bits 4~3에 실린다 — 00 Off, 01 not Off, 10 error, 11 not available(Part 7 A.11). 같은 메시지 Byte 7은 Maximum time of tractor power(남은 전원 시간, 1 min/bit, 0~250)다(Part 7 A.12). TECU의 전원 관리는 ISOBUS 네트워크 아키텍처에서 다룬다.

  • 버전 2는 셧다운 동작을 정의하지 않았고 버전 3은 의무로 정하지 않았다. 그래서 버전 3 이하 TC는 TC Status를 포함한 모든 통신을 그냥 끊을 수 있다(6.6.4.1 NOTE).
  • 버전 3 이하 클라이언트도 경고 없이 통신을 끊을 수 있다. 일부 구버전 클라이언트는 Key Switch를 아예 보지 않고 전원이 끊길 때까지 평소처럼 동작한다(6.6.4.1, 6.6.4.2).

셧다운을 끊김으로 오해하는 구현

키를 끄자마자 클라이언트가 "TC 연결 끊김" 경고를 띄우거나 TC 번호 2로 갈아타면 6.6.4.2 d) 위반이다. 반대로 TC가 키 오프 직후 클라이언트들의 Client Task 끊김마다 경고를 띄우면 6.6.4.1 a) 위반이다. 양쪽 모두 Key Switch Off 이후의 끊김을 정상으로 다뤄야 한다.

전원 사이클 뒤 태스크 재개

전원이 다시 들어오면 TC는 다음 규칙을 따른다(6.6.4.3).

  • TC는 전원 사이클 전의 태스크 상태를 복원해야 한다(shall). 모든 TC 기능을 재개하는 것이 권고다.
  • 전원이 꺼지기 전에 데이터 로깅이나 위치 기반 제어가 켜져 있었다면, 자동으로 다시 켜거나 오퍼레이터에게 계속할지 확인을 받아야 한다.
  • 자동 재개를 못 하는 구현은 "전원이 꺼지기 전에 태스크 기능이 활성이었고 재활성화가 필요하다"고 오퍼레이터에게 알려야 한다.
  • 제어 명령을 실제로 실행할지 말지는 클라이언트 책임이다.

§7의 상태 머신으로 보면, Running이던 태스크는 전원 사이클 뒤에도 Running으로 복원되고, TC Status의 Task totals active와 measurement를 다시 세워야 한다는 뜻이다(추론, 6.6.4.3, 6.6.3).

정리

  • 원문 6.6.2는 a)~j) 10개 항목이다. 버전 질의(f)·응답(g)과 WSM 한정(d)이 버전 4에서 바뀐 부분이다.
  • 활성화 중에도 TC Status는 2 s 주기와 200 ms 간격을 지키며 Busy를 보고한다. 6 s 끊김 처리는 TC와 클라이언트가 대칭이다.
  • Key Switch Off 이후의 끊김은 정상 셧다운이다. 클라이언트는 Maintain Power와 Deactivate를 보내고 다른 TC로 옮기지 않는다.

Version 메시지 디코딩 함정 세 가지

  • 버전 바이트를 먼저 본다. 버전 2 이하 상대는 Byte 3~8을 FF로 보낸다. 옵션 바이트 0xFF를 비트 그대로 읽으면 "TC-BAS·TC-GEO·peer control·TC-SC를 모두 지원하는 TC"가 돼 버린다. 버전이 2 이하면 Byte 3~8을 "정보 없음"으로 다뤄야 한다(추론, B.5.3).
  • 예약 비트는 0이다. Byte 4 bits 6~8과 Byte 5는 "0 = 예약"으로 정의된다. 예약을 1(FF)로 채우는 습관대로 보내면 수신 측이 정의되지 않은 옵션으로 읽을 수 있다(추론).
  • 클라이언트의 붐·섹션·채널 수는 조정 전 값이다. 클라이언트는 TC 능력에 맞춰 DDOP를 줄여야 하지만, Version 메시지에는 줄인 값이 아니라 자기 능력을 그대로 보고한다(B.5.3 각주 a).

11. 다중 TC — TC 번호와 붙을 TC 고르기

TC 번호는 NAME의 function instance에서 나온다

TC 번호(TC number)는 TC의 function instance에서 유도한 식별 번호다(3.18). function instance는 NAME의 5비트 필드(NAME Byte 5 bits 8~4)라 0~31이고(Part 5:2019 Table 1), 오퍼레이터에게는 TC 번호 = function instance + 1, 즉 1~32로 보인다(6.7, B.5.4). 0부터 세는 번호에 익숙하지 않은 오퍼레이터를 위한 오프셋이고, 모든 제조사의 TC가 같은 번호 체계를 보여 주게 하려는 것이다(6.7).

예를 들어 어떤 TC가 보낸 Address Claimed(PGN 60928, 0xEE00) 데이터의 Byte 5가 0x08이면 bits 8~4 = 00001이다. 0x08 >> 3 = 1이 function instance이고(나머지 bits 3~1은 ECU instance 0), TC 번호는 2다.

클라이언트는 어느 TC에 붙나

  • 기본은 function instance 0(TC 번호 1)인 TC다(6.7.1).
  • "Move to another Task Controller" 기능(예: "Next Task Controller" 소프트키)을 가진 클라이언트는 function instance가 0보다 큰 TC에도 붙을 수 있다. 이 기능은 사용 가능한 TC들을 차례로 하나씩 옮겨 가게 해야 한다(6.7.1).

TC Status는 TC도 DL도 보낸다(B.8.1의 상태 바이트 이름이 "Actual TC / DL status"다). 그래서 클라이언트는 TC Status의 SA를 주소 클레임으로 모은 NAME 표에서 찾아 ① function이 TC인지 DL인지(7.1, Part 1), ② function instance가 몇인지(6.7)를 확인한 뒤에야 "내가 선택한 TC"인지 판단할 수 있다(추론). TC와 DL을 구분하는 function 값 자체는 Part 1이 isobus.net 데이터베이스로 넘긴다.

12. Data Logger — TC와 무엇이 같고 무엇이 다른가

DL(data logger)은 TC 클라이언트를 제어하지 않고 태스크와 무관한 로깅을 하려고 네트워크에 두는 CF다(7.1). 텔레매틱스 로거가 대표적이지만 텔레매틱스 환경에 한정되지 않는다(5.6). 확인 필요 — 버전 4 제품이 TC-BAS에 게시할 번호

Annex F 문구대로면 TC-BAS·TC-GEO·TC-SC gen 1 구현은 Version 메시지와 파일 세트에 3을 게시해야 한다. 그런데 6.6.2 f)~g), 6.6.4, B.6.10 같은 버전 4 의무를 모두 구현한 제품이 TC-BAS 적합을 위해 3을 게시해야 하는지, 4를 게시해도 되는지는 Annex F만으로 판단이 서지 않는다. 제품 설계 전에 AEF 적합성 시험 기준을 확인해야 한다.

정리

  • 기능성은 TC-BAS·TC-GEO·TC-SC·LOG 넷이고 모두 generation 1이다. TC-GEO는 TC-BAS를 함께 요구하지만 TC-SC는 독립이다.
  • 붐·섹션·채널 수는 서버가 보고하고 클라이언트가 DDOP를 줄여 맞춘다. 클라이언트의 Version 메시지는 원래 능력을 보고한다.
  • 게시 버전은 BAS·GEO·SC가 3, LOG가 4다. 버전 4 의무는 버전 질의, WSM 한정, 셧다운, Deactivate처럼 연결 계층 곳곳에 흩어져 있다.

Byte 6~8 = 1·5·0은 섹션 제어 붐 1개, 섹션 5개, 위치 기반 제어 채널 0개다. 클라이언트는 물리 섹션 7개를 묶어 DDOP에 섹션 5개 이하로 보고하고(F.2.3), DDOP의 위치 기반 제어 채널 수를 0으로 제한한다(F.2.2). TC가 버전 3이므로 기능도 버전 3 수준으로 낮춰 Deactivate·Identify TC·peer control에 기대지 않고, TC의 Request Version을 기다리며 멈추지 않는다(6.6.2 f·g). 자기 Version Byte 6~8에는 조정 전 능력인 01 07 01을 넣는다(B.5.3 각주 a).
  2. 셧다운은 Wheel-based speed and distance(PGN 65096) Byte 8 bits 4~3이 01(not Off)에서 00(Off)으로 바뀌는 것으로 알아챈다(Part 7 A.11). 클라이언트는 Maintain Power(PGN 65095)를 보내고, Maximum time of tractor power(같은 메시지 Byte 7)를 감시하고, Connection Deactivate(81 00 FF FF FF FF FF FF)를 보내야 했다. 또 TC Status 끊김을 비정상 종료로 보지 말고 다른 TC로 옮기지 말아야 했다(6.6.4.2 d). TC는 예상치 못한 클라이언트 종료 감지 로직을 끄고(6.6.4.1 a), 활성 DDOP를 가진 클라이언트의 마지막 Maintain Power 이후 최소 2 s 동안 서비스를 유지해야 했다(6.6.4.1 b). 키가 다시 Not Off가 되면 양쪽 모두 재초기화한다.
  3. 시작: 주소 클레임과 전역 address claimed 요청을 마치고 6 s 뒤(6.6.1). 형식: PGN 51968, 우선순위 3, DA 255, Byte 1 0xFE, Byte 2~4 FF. 주기: 2 s + 어느 바이트든 바뀌면 즉시, 단 송신 간격 200 ms 이상(바뀐 값을 모아서 보낸다). Byte 5 bit 1은 태스크가 Running(시작·재개)이면 1, Paused·Completed로 가면 0이고, 이 전이가 클라이언트 task total의 리셋·정지 신호다. bit 4는 DDOP 전송·활성화 같은 B.6 명령을 처리하는 동안 1로 두고 Byte 6에 그 클라이언트 SA, Byte 7에 그 명령의 Byte 1을 넣으며, 아니면 Byte 6·7은 0이다. bit 2·3은 비휘발성 메모리 쓰기·읽기 중, bit 8은 메모리 부족이다. 짝이 되는 수신부는 클라이언트별 Client Task를 6 s 감시해 끊기면 (태스크 실행 중일 때) DeviceAllocation을 닫고, Key Switch Off 뒤에는 이 감시를 끈다. 전원 사이클 뒤에는 이전 태스크 상태를 복원한다(6.6.4.3).
