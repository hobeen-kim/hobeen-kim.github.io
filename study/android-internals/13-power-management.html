CH13. 전원 관리

전원 관리는 배터리 단말에서는 수명, 상시 전원 장비에서는 발열과 안정성의 문제다. 안드로이드의 전원 스택은 리눅스 커널의 suspend/resume 위에 wakelock·Doze·thermal이라는 안드로이드 고유 계층을 얹은 구조다. 이 장은 그 양면을 모두 파고들고, 특히 배터리가 없는 농기계 단말에서 "잠들지 않아야 하는" 요구를 어떻게 만족시킬지에 초점을 둔다.

학습 목표

  • 리눅스 suspend/resume·wakeup source·autosleep과 안드로이드 wakelock의 관계를 이해한다.
  • PowerManagerService의 wakelock 관리와 Doze·idle 모드를 파악한다.
  • healthd에서 health HAL로 이어진 배터리 스택과 batterystats를 안다.
  • cpufreq governor·EAS·thermal 관리의 동작을 이해한다.
  • 상시 전원 임베디드 장비에서 suspend/Doze를 다루는 실전 전략을 익힌다.

리눅스 전원 관리 기초

모든 것의 바닥에는 리눅스 커널의 시스템 suspend가 있다. suspend는 CPU와 대부분의 주변장치를 저전력 상태(대개 Suspend-to-RAM, S3)로 내려, RAM만 유지한 채 전력을 거의 쓰지 않는 상태다. 화면을 끄면 곧바로 이 상태로 가는 게 배터리 단말의 기본 동작이다.

문제는 "지금 자면 안 되는 작업"이 있을 때다. 음악 재생이나 파일 다운로드 중에 CPU가 suspend되면 곤란하다. 이를 막는 것이 wakelock이다. wakelock이 하나라도 잡혀 있으면 시스템은 suspend에 들어가지 못한다.

wakelock은 두 층에 걸쳐 있다.

  • 커널 wakelock: 커널이 /sys/power/wake_lock, /sys/power/wake_unlock 인터페이스로 관리하는 wakeup source다. 드라이버가 인터럽트를 처리하는 동안 시스템이 자지 않도록 커널 내부에서 잡는다.
  • 유저스페이스 wakelock: 앱이 PowerManager.WakeLock을 획득하면, 이 요청이 프레임워크를 거쳐 결국 커널의 wakeup source로 내려간다.

여기서 autosleep이 핵심 메커니즘이다. 데스크톱 리눅스는 사용자가 명시적으로 suspend를 요청하지만, 안드로이드는 커널의 autosleep 기능을 켜서 "활성 wakelock이 하나도 없으면 자동으로 suspend"하게 한다. wakeup source는 그 반대로, suspend 상태에서 특정 이벤트(알람, 네트워크 패킷, 버튼)가 시스템을 깨우는 통로다. 커널의 suspend_ops가 실제 suspend/resume 콜백을 실행한다.

# 현재 활성 wakeup source (누가 잠을 막고 있나)
adb shell cat /sys/kernel/debug/wakeup_sources
# 또는
adb shell dumpsys power | grep -A20 'Wake Locks'

# suspend/resume 통계
adb shell cat /sys/power/suspend_stats/success
adb shell cat /sys/power/suspend_stats/fail

PowerManagerService

유저스페이스에서 전원 정책의 중심은 PowerManagerService(PMS)다. 앱들이 잡은 wakelock을 집계하고, 화면 상태·CPU suspend 여부를 결정하며, Doze 같은 절전 모드를 오케스트레이션한다.

앱이 wakelock을 잡는 코드는 이렇다.

PowerManager pm = (PowerManager) getSystemService(POWER_SERVICE);
PowerManager.WakeLock wl = pm.newWakeLock(
        PowerManager.PARTIAL_WAKE_LOCK, "MyApp::CanWorker");
wl.acquire();
try {
    // CPU가 자면 안 되는 작업
} finally {
    wl.release();   // 반드시 해제 — 안 하면 배터리를 계속 갉아먹음
}
  • PARTIAL_WAKE_LOCK: CPU만 깨워 둔다(화면·키보드는 꺼져도 됨). 백그라운드 작업의 표준이다.
  • FULL_WAKE_LOCK(deprecated): 화면까지. 지금은 FLAG_KEEP_SCREEN_ON이나 윈도우 플래그를 쓴다.

PMS가 관리하는 절전 모드가 Doze다. 기기가 화면 꺼진 채 오래 정지해 있으면 Doze에 진입해, 네트워크 접근·wakelock·알람·잡(job)을 배치로 몰아 처리하고 나머지 시간엔 깊이 잠든다. 화면이 꺼진 직후가 아니라 움직임이 없는 채로 일정 시간이 지나야 들어가며, 단계적으로 더 깊어진다. user activity(터치·버튼)는 이 타이머를 리셋해 기기를 활성 상태로 되돌린다.

# Doze 상태 확인·강제 진입 (테스트)
adb shell dumpsys deviceidle
adb shell dumpsys deviceidle force-idle
adb shell dumpsys deviceidle unforce

# 특정 앱을 Doze 예외(allowlist)로
adb shell dumpsys deviceidle whitelist +com.example.app

배터리 — healthd에서 health HAL로

배터리 상태(잔량·전압·온도·충전 여부)는 벤더의 fuel gauge 하드웨어에서 올라온다. 과거에는 healthd라는 네이티브 데몬이 /sys/class/power_supply/*의 sysfs 노드를 폴링해 배터리 정보를 프레임워크에 올렸다.

Treble 이후로는 이 역할이 Health HAL(현재 AIDL 인터페이스, android.hardware.health)로 옮겨갔다. 벤더가 HAL을 구현해 배터리 정보를 표준 인터페이스로 노출하면, 프레임워크의 BatteryService가 이를 받아 Intent.ACTION_BATTERY_CHANGED 브로드캐스트로 앱에 전파한다. healthd의 폴링 루프 로직은 이제 health HAL의 기본 구현(libhealthloop 등)에 흡수됐다.

# 현재 배터리 상태 (sysfs를 프레임워크가 읽은 결과)
adb shell dumpsys battery
#   level: 100
#   AC powered: true
#   temperature: 285   # 0.1°C 단위 → 28.5°C

# raw sysfs 직접 확인
adb shell cat /sys/class/power_supply/battery/capacity
adb shell cat /sys/class/power_supply/battery/temp

소모 통계는 batterystats가 담당한다. 어느 앱·컴포넌트가 얼마나 전력을 썼는지 누적 집계하며, dumpsys batterystats로 뽑아 Battery Historian 같은 도구로 분석한다.

# 통계 리셋 후 일정 시간 사용 → 덤프
adb shell dumpsys batterystats --reset
# ... 사용 ...
adb shell dumpsys batterystats > batterystats.txt
adb bugreport                       # Historian은 bugreport를 입력으로 받음

배터리 없는 장비의 처리

농기계 단말처럼 차량 전원(12V/24V)으로만 동작하는 장비는 물리 배터리가 없다. 이 경우 벤더는 health HAL에서 "항상 AC 전원, 배터리 100%, 정상 온도"를 반환하는 가짜 배터리(pseudo-battery)를 구현하는 게 일반적이다. 그래야 배터리 잔량으로 동작을 분기하는 프레임워크·앱 코드가 오작동하지 않는다. 다만 이렇게 하면 실제 시스템 온도 정보는 별도의 thermal 경로로 다뤄야 한다(다음 절).

CPU 제어

전력의 상당 부분은 CPU가 쓴다. 안드로이드는 리눅스의 cpufreq 서브시스템으로 코어 클럭을 동적으로 조절한다. 정책을 정하는 것이 governor다.

  • schedutil: 현재 표준 governor. 스케줄러가 계산한 CPU 이용률을 직접 받아 클럭을 정하므로, 부하 변화에 빠르게 반응한다. 과거의 interactive governor를 대체했다.
  • cpuidle: 반대로 유휴 시 코어를 얼마나 깊은 절전 상태(C-state)로 보낼지 정한다.
# 현재 governor와 가능한 주파수
adb shell cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
adb shell cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_available_frequencies
adb shell cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq

모바일 SoC는 대개 big.LITTLE 구조다 — 성능 코어(big)와 효율 코어(LITTLE)가 섞여 있다. 초기에는 두 클러스터를 상황에 따라 켜고 끄는 hotplug 방식이었지만, 현재는 HMP(Heterogeneous Multi-Processing)를 거쳐 EAS(Energy Aware Scheduling)로 진화했다. EAS는 스케줄러가 각 코어의 에너지 모델(전력 대비 성능 곡선)을 알고, 작업을 "가장 에너지 효율적인 코어"에 배치한다. CH11에서 본 cpuset·uclamp가 이 위에서 그룹별 배치·부스트를 조정한다.

interrupt affinity도 전력·성능에 영향을 준다. 인터럽트를 어느 코어가 처리할지(/proc/irq/<N>/smp_affinity)를 조정해, 예컨대 고빈도 CAN 인터럽트를 특정 코어에 고정하면 다른 코어를 더 깊이 재울 수 있고 지터도 줄어든다.

Thermal

발열 관리는 상시 고부하로 도는 임베디드 장비에서 특히 중요하다. 안드로이드의 thermal 스택은 커널부터 프레임워크까지 이어진다.

  • 커널 thermal zone: 각 온도 센서(SoC, 배터리, PCB, 모뎀)가 하나의 thermal zone이 된다. zone마다 trip point(임계 온도)와 그에 연결된 쿨링 디바이스(cpufreq, GPU 클럭, 충전 전류 제한)가 정의돼, 커널의 thermal governor가 온도가 trip을 넘으면 자동으로 throttle한다.
  • Thermal HAL(AIDL, android.hardware.thermal): 커널 zone의 온도·throttling 상태를 유저스페이스로 노출한다. 벤더가 구현한다.
  • ThermalService: HAL에서 올라온 상태를 프레임워크 수준의 throttling status(THERMAL_STATUS_NONE~SHUTDOWN)로 정규화하고, PowerManager.addThermalStatusListener로 앱에 통지한다. 앱은 이를 받아 스스로 부하를 줄일 수 있다.
# 커널 thermal zone 상태 직접 확인
adb shell cat /sys/class/thermal/thermal_zone0/type
adb shell cat /sys/class/thermal/thermal_zone0/temp    # 밀리도 단위

# 프레임워크가 본 thermal 상태
adb shell dumpsys thermalservice
adb shell cmd thermalservice override-status 3   # throttling 강제 (테스트)

농기계·고온 환경 장비의 주의점

직사광선 아래 밀폐된 캐빈, 엔진 근처의 고온 환경에서 도는 장비는 항상 thermal 마진이 빠듯하다. (1) 커스텀 보드 bring-up 시 SoC뿐 아니라 케이스·PCB 온도 센서를 별도 thermal zone으로 잡고 보수적인 trip point를 설정한다. (2) SHUTDOWN trip은 반드시 실제 하드웨어 한계보다 낮게 둬 데이터 손상·부품 손상을 막는다. (3) 상시 고부하 데몬(CAN 파싱 등)이 throttling으로 느려져도 안전 동작을 유지하도록, 지연에 강한 설계를 해야 한다. thermal throttle로 CPU가 절반 클럭이 돼도 통신 타임아웃이 안 나게 여유를 둬야 한다.

Power HAL

마지막으로 Power HAL(android.hardware.power, AIDL)은 프레임워크가 SoC에 성능 힌트를 주는 통로다. 두 종류의 인터페이스가 있다.

  • power hint / boost: "지금 사용자가 스크롤을 시작했다", "앱을 실행 중이다" 같은 순간적 상황을 알려, SoC가 잠깐 클럭을 부스트하게 한다.
  • mode: SUSTAINED_PERFORMANCE(장시간 일정 성능), LOW_POWER 같은 지속 모드를 설정한다.

벤더가 SoC 특성에 맞게 이 힌트를 실제 cpufreq·전력 정책으로 변환한다. 커스텀 장비에서 특정 워크로드(예: 지도 렌더링)의 성능이 부족하면, 이 Power HAL에 적절한 힌트를 넣는 것이 튜닝 지점이 된다.

상시 전원 장비 관점 — 무엇을 끄고 무엇을 남길까

배터리 전력 절약을 위해 설계된 안드로이드의 절전 기능들은, 배터리가 없는 상시 전원 임베디드 장비에서는 오히려 방해가 된다. "잠들면 안 되는" 요구를 만족시키려면 다음을 조정한다.

  • suspend 비활성화: 화면을 꺼도 CPU가 계속 돌아야 하면, autosleep을 끄거나(커널 설정) 상주 wakelock을 하나 잡아 시스템이 suspend에 들어가지 못하게 한다. 벤더 init 서비스로 PARTIAL_WAKE_LOCK을 상시 유지하는 방법이 흔하다.
  • Doze 무력화: 백그라운드 작업이 배치로 밀리면 안 되는 텔레메트리·통신 앱은 Doze allowlist에 넣거나, 아예 시스템 앱으로 만들어 Doze 제약에서 제외한다(CH10 sysconfig의 allow-in-power-save).
  • 화면 상시 유지: stay_on_while_plugged_in(CH10 settings) 또는 앱의 FLAG_KEEP_SCREEN_ON으로 화면을 켜둔다. 단 이건 화면만 담당하므로 CPU suspend 방지와는 별개다.
  • 남길 것: thermal은 절대 끄면 안 된다. 배터리가 없어도 SoC 발열은 그대로이고, 오히려 상시 고부하라 throttling·shutdown trip이 안전의 마지막 보루다. cpufreq governor도 그대로 두는 편이 낫다 — 유휴 시 클럭을 낮추는 건 전력이 아니라 발열 관점에서 이득이다.

정리하면, 배터리 절약 목적의 기능(suspend·Doze·배터리 통계)은 걷어내되, 발열 보호 목적의 기능(thermal·cpuidle)은 반드시 남기는 것이 상시 전원 장비 전원 설계의 원칙이다. 이 커스텀 전원 설정은 벤더 파티션의 init .rc·프로퍼티·HAL 구현에 흩어지므로, CH14 AOSP 빌드와 device bring-up에서 보드별 설정과 함께 종합한다.

핵심 정리

  • 리눅스 suspend는 wakelock이 하나라도 있으면 막히고, autosleep이 "활성 wakelock 0이면 자동 suspend"를 구현한다. 안드로이드 wakelock은 커널 wakeup source로 내려가는 유저스페이스 요청이다.
  • PowerManagerService가 wakelock을 집계하고 Doze·idle을 오케스트레이션하며, PARTIAL_WAKE_LOCK이 백그라운드 작업의 표준이다.
  • 배터리 정보는 healthd에서 health HAL(AIDL)로 이관됐고 BatteryService가 프레임워크에 전파한다. 배터리 없는 장비는 가짜 배터리를 HAL에서 반환한다.
  • CPU는 cpufreq(schedutil)·cpuidle로 클럭을 조절하고, big.LITTLE은 EAS로 에너지 효율 코어에 작업을 배치한다.
  • thermal은 커널 zone(trip point·쿨링 디바이스)→Thermal HAL→ThermalService로 이어지며, 고온 환경 장비에서 안전의 최후 보루다.
  • 상시 전원 장비는 suspend·Doze·배터리 통계는 무력화하되, thermal·cpuidle 같은 발열 보호 기능은 반드시 남긴다.
