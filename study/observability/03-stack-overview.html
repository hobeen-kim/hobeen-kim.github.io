Grafana 관측성 스택 개요

학습 목표

  • Grafana LGTM+ 스택을 구성하는 각 컴포넌트(Loki, Grafana, Tempo, Mimir, Pyroscope, Prometheus)의 역할을 안다.
  • 신호별로 어떤 백엔드가 담당하는지, 컴포넌트가 파이프라인에서 어느 위치에 있는지 구분한다.
  • exporter, OpenTelemetry Collector, Alloy 세 가지 수집 전략의 차이와 각각을 선택해야 하는 상황을 판단할 수 있다.
  • 로컬 TSDB 기반 저장과 오브젝트 스토리지 기반 마이크로서비스형 저장의 수평 확장 차이를 이해한다.
  • Grafana 스택을 선택하는 이유와, ELK·Datadog·순수 OpenTelemetry 같은 대안 지형에서의 위치를 안다.

1. Grafana LGTM 스택이란

LGTM은 Loki(로그), Grafana(시각화), Tempo(트레이스), Mimir(메트릭 장기 저장)의 앞글자를 딴 이름이다. 여기에 프로파일을 담당하는 Pyroscope를 더해 LGTM+로 부르기도 한다. Mimir가 나오기 전에는 Prometheus 단독으로 메트릭을 저장했는데, Prometheus는 로컬 디스크 기반이라 단일 노드 용량을 넘어서는 장기 보관·수평 확장이 어렵다. Mimir는 Prometheus의 TSDB 포맷을 그대로 쓰면서 오브젝트 스토리지 기반으로 수평 확장 가능한 저장 계층을 얹은 것이다.

이 네 가지(+Pyroscope) 프로젝트의 공통점은 모두 같은 설계 철학을 공유한다는 점이다. 컴팩트한 인덱스만 유지하고 본문 데이터는 저렴한 오브젝트 스토리지(S3, GCS)에 두며, 읽기·쓰기·압축을 독립적으로 스케일하는 마이크로서비스 아키텍처를 채택한다. Loki가 "로그계의 Prometheus"로 불리는 이유도 라벨 기반 인덱싱이라는 동일한 철학 때문이다.

2. 각 컴포넌트의 위치와 역할

신호마다 전담 백엔드가 있고, Grafana가 이들을 하나의 화면에서 묶는다. Prometheus는 스크레이핑과 룰 평가를 담당하는 "액티브" 컴포넌트이고, 나머지 저장 백엔드는 대부분 수신·저장·질의에 집중하는 "패시브" 컴포넌트라는 차이가 있다.

Prometheus와 Mimir가 분리돼 있다는 점이 자주 헷갈리는 부분이다. Prometheus는 여전히 로컬 TSDB에 단기 데이터를 갖고 있으면서 remote_write로 Mimir에 흘려보내는 2단 구조가 일반적이다 — Prometheus를 걷어내고 Mimir만 쓰는 게 아니라, 스크레이핑은 Prometheus(또는 Alloy)가, 장기 저장·수평 확장은 Mimir가 나눠 맡는다.

3. 수집 전략 전체 지도 — 언제 무엇을 쓰나

이 챕터의 핵심 질문은 "저장 백엔드를 뭘 쓰느냐"가 아니라 "수집은 무엇으로 하느냐"다. 실무에서 선택지는 세 갈래로 갈린다.

Exporter는 대상 시스템(node, PostgreSQL, Redis 등)의 상태를 Prometheus 텍스트 포맷으로 변환해 /metrics 엔드포인트로 노출하는 별도 프로세스다. Prometheus가 이를 pull로 긁어간다. 대상 시스템 자체에 계측을 넣을 수 없을 때(서드파티 소프트웨어, 레거시 시스템) 쓰는 방식이다.

OpenTelemetry Collector는 애플리케이션이 OTLP로 push한 메트릭·로그·트레이스를 받아 가공(배치, 필터, 속성 추가)한 뒤 여러 백엔드로 내보내는 벤더 중립 파이프라인이다. 신호 종류에 무관하게 하나의 프로토콜(OTLP)로 통일하고 싶을 때, 그리고 특정 벤더에 락인되지 않고 싶을 때 표준적인 선택이다.

Alloy는 Grafana Labs가 만든 수집 에이전트로, OpenTelemetry Collector의 기능을 상당 부분 흡수하면서 Prometheus 스크레이핑, Loki 로그 tailing, Pyroscope 프로파일 수집까지 하나의 컴포넌트 그래프로 통합한다(Grafana Agent의 후속으로, 설정 문법이 River에서 Alloy 문법으로 전환됐다). Grafana 스택 전체를 쓸 때 사실상 기본 선택지다.

전략모델강점적합한 상황
ExporterPull (Prometheus가 긁음)설정 단순, 생태계 방대서드파티 시스템, 계측 불가능한 대상
OpenTelemetry CollectorPush (OTLP 수신)벤더 중립, 표준 프로토콜멀티 벤더 환경, 락인 회피가 우선
AlloyPull + Push 혼합Grafana 스택 4대 신호 통합 수집Grafana LGTM+ 스택을 메인으로 쓸 때

세 전략은 배타적이지 않다. 실무 클러스터에서는 node-exporter 같은 exporter를 Alloy나 Prometheus가 그대로 스크레이프하면서, 동시에 애플리케이션은 OTLP로 Alloy에 push하는 혼합 구성이 흔하다. Alloy가 OTLP 리시버 컴포넌트를 내장하고 있어 OpenTelemetry Collector 역할까지 대신할 수 있기 때문이다. Alloy의 컴포넌트 모델과 파이프라인 작성법은 28장~29장에서, Collector와의 세부 비교는 30장에서 다룬다.

4. 저장 계층 — 로컬 TSDB vs 오브젝트 스토리지 마이크로서비스

저장 계층은 두 세대로 나뉜다. 로컬 TSDB(단일 Prometheus 인스턴스)는 설정이 단순하고 지연이 낮지만, 디스크 하나의 용량과 CPU에 갇혀 수평 확장이 안 되고 장기 보관에 취약하다. 오브젝트 스토리지 기반 마이크로서비스형(Mimir, Loki, Tempo가 공유하는 아키텍처)은 ingester·querier·compactor 같은 역할을 독립 프로세스로 분리해 각각 스케일하고, 실제 블록 데이터는 S3/GCS 같은 오브젝트 스토리지에 두어 사실상 무제한으로 저장을 늘릴 수 있다.

대가는 운영 복잡도다. 마이크로서비스형은 컴포넌트 수가 많아지고, 멀티테넌시·컴팩션·캐싱 계층까지 신경 써야 한다. 소규모 환경에서는 단일 바이너리 모드(Mimir/Loki/Tempo 모두 monolithic 모드를 지원한다)로 시작해, 트래픽이 늘면 마이크로서비스 모드로 전환하는 경로가 현실적이다. 장기 저장 아키텍처의 세부 사항은 35장 Mimir 장기 저장에서 다룬다.

5. 왜 Grafana 스택인가

Grafana 스택을 고르는 이유는 크게 네 가지로 요약된다. 첫째, 전 구성 요소가 오픈소스(AGPLv3/Apache 2.0)이며 자체 호스팅이 가능해 벤더 종속 없이 시작할 수 있다. 둘째, Loki·Tempo·Mimir가 동일한 오브젝트 스토리지 기반 아키텍처를 공유해 운영 지식(캐싱, 컴팩션, 멀티테넌시 패턴)을 신호 간에 재사용할 수 있다. 셋째, 라벨 일관성 — 메트릭의 Prometheus 라벨, 로그의 Loki 라벨, 트레이스의 리소스 속성을 같은 값(service_name, namespace 등)으로 맞추면 신호 간 조인이 쉬워진다. 넷째, Grafana가 exemplar·derived field로 상관관계를 1급 기능으로 지원한다(32장).

6. 대안 지형

Grafana 스택이 유일한 선택지는 아니다. ELK/Elastic Stack(Elasticsearch, Logstash, Kibana)은 로그·검색에서 강력하지만 메트릭·트레이스로 확장하려면 별도 스택(APM)이 필요하고 라이선스가 SSPL로 바뀌며 완전한 오픈소스는 아니게 됐다. Datadog·New Relic 같은 SaaS는 운영 부담이 거의 없고 통합 UX가 뛰어나지만, 데이터량에 비례해 비용이 매우 빠르게 늘고 벤더 락인이 생긴다.

이 지형에서 OpenTelemetry는 특정 벤더가 아니라 계측 표준이라는 점이 중요하다. OTel SDK로 계측해두면 백엔드를 Grafana 스택에서 Datadog으로, 혹은 그 반대로 바꿔도 애플리케이션 코드는 그대로 둘 수 있다. Grafana 스택은 OTLP를 네이티브로 수신하므로, "계측은 OTel 표준으로, 백엔드는 Grafana OSS로"라는 조합이 락인을 최소화하는 실전 전략이다. OpenTelemetry 자체는 21장에서 다룬다.

핵심 정리

  • LGTM(+Pyroscope)은 Loki(로그)·Grafana(시각화)·Tempo(트레이스)·Mimir(메트릭 장기 저장)·Pyroscope(프로파일)로 구성되며 동일한 오브젝트 스토리지 아키텍처를 공유한다.
  • Prometheus는 스크레이핑·룰 평가를, Mimir는 장기 저장·수평 확장을 맡는 2단 구조가 표준이다.
  • 수집 전략은 exporter(계측 불가 대상)·OpenTelemetry Collector(벤더 중립)·Alloy(Grafana 스택 통합 수집) 세 갈래로 나뉘고, 실무에서는 혼합해서 쓴다.
  • 로컬 TSDB는 단순하지만 확장에 한계가 있고, 오브젝트 스토리지 기반 마이크로서비스형은 무제한에 가까운 저장을 대가로 운영 복잡도를 요구한다.
  • Grafana 스택의 강점은 OSS·라벨 일관성·상관관계 지원이며, ELK·Datadog 같은 대안과 OpenTelemetry 표준화 흐름 속에서 위치를 이해해야 한다.

다음 챕터

수집 전략을 고를 때 항상 따라오는 두 가지 실무 결정이 있다 — 데이터를 밀어넣을지 끌어올지(pull vs push), 그리고 라벨 설계를 어떻게 해야 시계열이 폭발하지 않을지다. Pull/Push와 카디널리티에서 이 두 축을 다룬다.
